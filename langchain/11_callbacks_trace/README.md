# 11 · 回调系统与本地追踪 / 轻评测

> 回调系统（callbacks）是框架的事件总线：每次 chain / 模型 / 工具调用都发开始与结束事件。挂一个自定义 Handler，就能把一次 Agent 运行记成带父子关系、耗时与 token（模型处理文本的最小单位，按输入/输出分别计数，是成本与上下文长度的基本单位）的 run tree，落盘成 `trace.json`。
> 本篇还搭一个 10 用例的轻评测台：同一数据集跑两版提示词，报通过率与"改善 / 劣化 / 持平"对比——改提示词不再靠感觉。
> 读完你能让 Agent 运行"可复盘、可量化"，并知道 token 成本与准确率该怎么一起看。

## Background

Agent 调试的起点通常是 `print`：把每轮消息打出来看。消息多起来后，输出混成一锅粥——哪条是模型调用、哪条是工具执行、各自花了多久，全靠人眼分拣；线上出问题时，日志里也找不回完整的一次运行。

另一头是提示词迭代：改一句 system prompt，回答"好像好点了"，再改回去"好像又坏了"。缺一个固定数据集上的前后对比，优化方向全靠记忆和感觉，回归（原本对的反而错了）更是无从发现。

框架的补法是两层设施：回调系统把内部事件结构化地吐出来，运行过程可被程序记录；评测则把这套记录能力对准"改动的效果"，用同一卷子前后对拍。两者合起来，让 Agent 开发从"手感驱动"走向"数据驱动"。

## What

回调系统是一组"框架在固定时机调用的钩子函数"，自定义 Handler 继承基类、覆写关心的钩子即可。本篇关心的事件与产物：

| 事件钩子 | 触发时机 | 我们从里面拿什么 |
|:--|:--|:--|
| `on_chain_start/end` | 图与节点进出 | span 的父子关系、节点耗时 |
| `on_llm_start/end` | 模型调用进出 | 耗时 + `usage_metadata` 里的 input/output token |
| `on_tool_start/end` | 工具执行进出 | 工具名、执行耗时 |

把这些事件按 `parent_run_id` 串起来就是 run tree——一个 span 树：Agent 运行是根，模型调用与工具执行是子节点。

可以把 Handler 想象成行车记录仪：不干预驾驶，只按时间戳记录每一段行程。但和行车记录仪不同的是：**记录点由框架声明**，你只能记框架愿意广播的事件，记不到框架没说的事。

评测侧的概念更简单：一个**用例集**（输入 + 期望输出）、一条**判据**（预测是否等于期望）、两版**被测对象**（v1/v2 提示词），跑完输出通过率与逐用例变化。

## When to Use

典型场景：

1. 排障：一次运行的完整时间线（谁慢、谁调了谁）落盘后可反复查。
2. 成本核算：按 span 统计 token，看每次运行花在哪里。
3. 回归评测：提示词/模型/温度（temperature，采样随机性参数；0 表示每次取概率最高的输出）变更前后用同一卷子对拍，防"改一处坏三处"。

何时不用：一次性脚本 `print` 更直接；纯人工对话调试不需要落盘结构。

同类方案对比：

| 方案 | 粒度 | 什么时候选它 |
|:--|:--|:--|
| `print` / 日志 | 自己挑 | 临时调试 |
| 回调 + 本地 trace（本篇） | 框架全事件，零云依赖 | 单机开发、成本核算 |
| 可观测平台（LangSmith 等） | 全事件 + 托管界面 | 团队协作、线上采样（需要云，超出本线约束） |

## How It Works

### run tree：parent_run_id 把 span 串成树

每次回调都带 `run_id`（本 span 的编号）与 `parent_run_id`（父节点编号）。Handler 的职责就是"开始记一条、结束补时间与用量"，最后按开始顺序导出。结构如下图：

![回调追踪：把 Agent 运行的 span 收集成 trace.json](images/trace.architecture.svg)

> 🌐 **交互版**：[在线打开（GitHub Pages）](https://yong-huang.github.io/hands-on-agentic-ai/langchain/11_callbacks_trace/images/trace.architecture.html)
> （或本地打开 [`images/trace.architecture.html`](images/trace.architecture.html)）。

一次"计算 21+21"的运行产出 7 个 span：根 chain（Agent）；先后两个 model 节点 chain，各带一次 llm span；tools 节点 chain 带一个工具 span（1 + 2 + 2 + 1 + 1 = 7）。

断言"每个 span 都有耗时与父子关系"排除了记录断层——trace 树是一张完整的时间线。

### token 从 usage_metadata 里读

`on_llm_end` 的响应对象里，`generations[0][0].message.usage_metadata` 带 `input_tokens` / `output_tokens`（Ollama 原生返回这两个计数）。

`[A]` 段输出里 `in=288 out=31` 就是第一次模型调用的真实账单；评测段用它把两版提示词的 token 成本并排摆出来。

### 轻评测：准确率之外还要看成本

10 条用例分三类（代码/数学/通用），v1 是裸指令、v2 加了判定规则与三条示例。结果：v1 错 1 条（"100 美元换算成人民币"被分到通用——换算类最容易漏），v2 全部答对。改善 1、劣化 0、持平 9，是"改对了且没有回退"的典型曲线。

同时注意成本：v2 的 input token 是 v1 的约 3 倍（1154 vs 394）——规则与示例都要随每次请求发送。**准确率与成本必须一起看**：v2 用三倍输入换来 +10% 准确率，在你的场景里是否合算，取决于错的代价。

## Pitfalls & Q&A

### 踩坑清单

1. **token 字段不是所有模型都有**。现象：换模型/接网关后 `usage_metadata` 为 `None`，统计全零。原因：该字段由各厂商集成填装，有的返回在 `llm_output` 里，有的干脆不返回用量。解法：读 `usage_metadata` 时留兜底与告警，不要假定它存在（脚本里用 `or {}` 防御）。
2. **评测算差异必须固定其他变量**。现象：前后对比噪声大、结论不可信。原因：温度、模型版本、提示词长度任一变动都会影响结果。解法：对拍时 `temperature=0`、同一数据集、同一判据；本机实测三次结果完全一致。
3. **只看通过率会漏掉"劣化"**。现象：总通过率涨了，但某类原本对的题开始错。原因：净增益掩盖局部回退。解法：除总率外必须看逐用例的三分类（改善/劣化/持平），产物里保留每个用例的明细。

### 深入问答

**Q：回调和 04 实验的 Middleware 有什么区别？**

定位不同：回调是**观察者**——只记录发生的事，不能改变运行结果；中间件是**干预者**——能改提示词、拦截工具、终止循环。做追踪用回调，做策略用中间件。两者可以叠加：中间件负责"管"，回调负责"记"。

**Q：这个本地 trace 和生产可观测平台是什么关系？**

同一套事件的两种出口：云平台把回调事件采样上报、给你托管界面与检索；本地方案把事件落成 JSON、零依赖。本线的零云约束下用后者，工程实践里可仅把"出错运行"升级上报，控制成本。

**Q：评测集从哪里来？**

最实用的是"真实失败集"：把线上/使用中答错的 case 收集起来当回归卷子，每修一个问题就加一条。先有 10 条真实问题的卷子，比造 100 条假想的更有价值——本实验的 10 条就是按这个思路手工标注的。
