# 10 · Agentic RAG：检索 + 评分回炉循环

> RAG（Retrieval-Augmented Generation，检索增强生成）让模型"开卷答卷"：先从知识库检索资料，再依据资料回答。Agentic 版比朴素版多三道关卡——用模型给检索结果**评分**、不合格就**改写查询回炉**、重试用尽仍无据则**拒答**。
> 本篇用本仓库 `docs/` 的 5 份文档建向量知识库，跑通"三个可答问题引用正确来源 + 一个库外问题拒答"的完整循环。
> 读完你能给任意私有语料搭一条"宁可拒答、不编答案"的问答管线。

## Background

模型的知识固化在训练数据里：问它企业内网文档、个人笔记、昨天写的清单，要么答不出，要么编一个像模像样的错答案。

把资料"喂进上下文"是最直接的补法——但资料可能几十万字，装不进上下文窗口（模型一次能读入的文字长度上限），而且每次都贴全文既贵又慢。

RAG 的第一步解法是检索：把文档切块、向量化（把每段文字转换成一串数字，语义相近的文字转换出的数字也相近）存库，提问时只取最相关的几块贴给模型。这套"检索 → 拼接 → 生成"的朴素管线很快暴露两类硬伤。

第一，检索可能失灵：相似度检索**永远返回 k 个结果**（k 即取回条数），问"火星矿产"也会塞给你四块最不像的"最近邻"（向量空间里距离最近、即最相似的候选块）；模型拿到不相关材料，要么硬答要么幻觉（编造资料里没有、但看起来合理的内容）。

第二，没有"宁可不答"的出口：管线只会往下走，生成一个必须有的答案。Agentic RAG 的补法是把"资料够不够格"变成流程里的显式判断，不合格先换检索词再试，试完还不行就明确拒答。

## What

Agentic RAG 是一条"检索 → 评分 → 分支"的循环管线，节点各司其职：

| 节点 | 职责 | 实验中的实现 |
|:--|:--|:--|
| `retrieve` | 向量检索 Top-k（取相似度最高的 k 条，本实验 k=4）并记录来源 | Chroma（轻量向量数据库：存储向量并做相似度检索）+ nomic-embed-text（嵌入模型，把文字转成向量） |
| `grade` | 判断资料能否回答问题 | 结构化的模型评分（`relevant` + 理由） |
| `rewrite` | 改写查询再检索（有次数上限） | 保留原意、补关键实体词 |
| `generate` | 依据资料作答并标注来源 | 要求输出 `[来源: 文件名]` |
| `refuse` | 重试用尽仍无据时明确拒答 | 固定文案，不调模型 |

可以把这套管线想象成开卷考试里的判卷员：答题者（生成模型）翻书（检索）之前，先由判卷员确认"翻到的这几页到底切不切题"；不切题就换个关键词再翻（本题只允许换一次），还是找不到就交白卷并说明原因。但和真实判卷不同的是：**判卷员也是模型**，它自己也会犯错——这条误差链要靠拒答策略兜底，而不是假定评分永远正确。

## When to Use

典型场景：

1. 私有知识问答：内部文档、产品手册、个人笔记的问答机器人。
2. 需要引用的回答：答案必须可追溯到来源（合规、审计、论文场景）。
3. 高风险问答：答错的代价大于不答，拒答是特性不是缺陷。

何时不用：资料短到能整段贴进上下文（省掉检索）；纯创作类任务（没有"资料是否相关"可判）。

同类方案对比：

| 方案 | 检索后处理 | 什么时候选它 |
|:--|:--|:--|
| 无 RAG | —— | 通用常识问答 |
| 朴素 RAG | 直接拼接生成 | 语料干净、问题与文档措辞接近 |
| Agentic RAG（本篇） | 评分 + 改写回炉 + 拒答 | 语料杂、要求引用、错误成本高 |

## How It Works

### 索引：切分、嵌入、来源元数据

5 份文档切成 355 个 chunk（文本块；每块约 400 字、相邻块重叠 60 字，避免语义在切口处被切断），每块带 `source` 元数据（文件名）后写入 Chroma。

来源元数据是"可引用"的前提：`generate` 节点拼接资料时把来源名带上，回答才能标注 `[来源: 文件名]`——没有它，引用无从谈起。

### 循环：评分不合格先改写，重试用尽才拒答

`grade` 节点用结构化输出（让模型按约定字段返回结果，而不是自由文本）拿一个 `Relevance`（`relevant` + 理由）。路由规则：相关 → 生成；不相关且还有重试额度 → 改写回炉；额度用尽 → 拒答。本篇把重试额度设为 1 次（可调），结构如下图：

### 拒答为什么独立成节点

`refuse` 不调模型，只返回固定文案。这是有意的：拒答是流程决策，不该交给模型"发挥"。如果把拒答写进生成提示词（"资料不足就说不确定"），模型大概率仍会挤出一个答案；把它做成图上的显式分支，行为才可断言。

## Pitfalls & Q&A

### 踩坑清单

1. **中文短检索上 nomic-embed-text 偏弱**。现象：问"SIGKILL 崩溃恢复实验是第几个项目？"，Top-4 有 3 块来自 qa.md、1 块来自 aitest.md，均与问题无关（实测）。原因：嵌入模型对中文长尾表述的区分度不足。解法：评分 + 改写能兜住一部分；根本手段是换嵌入模型、混合检索（向量 + 关键词）或加 rerank（对检索结果做二次精排，把真正相关的排到前面）——这正是本实验把评分做成显式节点的动机。
2. **相似度检索没有"无结果"概念**。现象：库里没有的问题（火星矿产）照样返回 4 块毫不相关的资料。原因：Top-k 检索永远给 k 个"最近邻"。解法：把"资料够不够格"交给评分节点判断，无据就拒答——绝不能把 top-1 当答案依据。
3. **问题必须落在知识库边界内**。现象：本书开发时最初的题目问的是实验 README 里的细节，知识库只索引了 `docs/` 清单，评分正确判"不相关"并拒答（不是管线坏了，是题目超纲）。解法：验收题先确认为"库里真有答案"的问题；拒答路径专门用库外问题来验证。

### 深入问答

**Q：评分也是模型调用，它判错了怎么办？**

三个防线：提示词里限定"只依据资料、不用自己的知识"；把评分输出做成结构化对象（`relevant` + 理由），理由可审计；给重试设上限并把最终决定权交给拒答分支——单次评分出错不至于让管线失控。高风险场景再加人工复核（07 实验的中断/人工审批机制 interrupt 可以自然挂进来）。

**Q：为什么不把索引好的 355 个块全部贴给模型？**

上下文预算：355 块约 14 万字符，每次问答都这么贴，成本与延迟都不可接受；而且长上下文里模型对"远处"信息的注意力会衰减。检索的价值是"按问题裁剪上下文"——宁可用评分确认裁剪得对不对，而不是全给。

**Q：改写查询和 rerank，该先做哪个？**

先改写、再考虑 rerank：改写解决"查询词与文档用词不匹配"（换个说法就能检索到）；rerank 解决"召回了但排序不对"（候选里有对的，只是 top-k 里排太后）。本实验的拒答场景是前者——库里没有答案，改写多少次也没用，所以上限一到就拒答。
