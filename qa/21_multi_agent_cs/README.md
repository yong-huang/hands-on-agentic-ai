# 21 · 多 Agent 客服系统雏形

> 路由 Agent（意图分类：订单/售后/闲聊/人工）+ 订单/售后专家（各自工具）+ 共享上下文（会话级 Session：身份/订单/历史）+ 人工兜底。10 条请求端到端测试：路由正确率 + 转接后上下文可见（不用重复自我介绍）。真机路由用 LLM 分类，离线用规则。读完你能掌握多 Agent 分工的最小架构，以及"转接不丢上下文"的实现方式。

## Background

最常见的起点是单 Agent（Agent，智能体：能读取用户消息、调用工具并产出回复的程序单元）：把查订单、退款、闲聊、投诉安抚的所有工具和规则，全部塞进一份提示词，让一个模型包办所有对话。

请求类型一多，问题就暴露出来。工具列表越长，提示词越膨胀，模型选错工具的概率越高（本该查物流却去建了工单——这类现象叫工具互扰）；客服规则又常变，每次调整都要在一个巨型提示词里找位置，牵一发动全身。

多 Agent 架构由此而来：像医院那样设一个分诊台——先由一个路由 Agent 判断用户想办什么，再把对话转给对应的专科 Agent。分工后每个 Agent 的提示词短、工具少，职责清晰。

## What

这是一个多 Agent 客服的最小完整架构，四个部件：

- **路由 Agent**：意图分类（判断用户这句话想办哪类事：订单/售后/闲聊/人工），决定谁接；
- **专家 Agent**：各持工具与提示词，互不感知；
- **共享 Session**（Session，一次对话内所有专家共用的存储）：身份/订单/历史，专家只读自己需要的部分；
- **人工兜底**：投诉/要求人工转 human Agent——它是第四个 Agent，不是失败。

心智模型一句话：**共享上下文是转接体验的生命线——用户永远不必重复自我介绍。**

可以把整套架构想象成医院：路由 Agent 是分诊台，专家是各科医生，共享 Session 是病历本——转科时病历跟着走。但和医院病历不同的是，这份"病历"由系统在每个回合自动抽取写入（用户说"我是林晓"就记下姓名），医生（专家）只读自己需要的字段，而不是翻整本病历。

## When to Use

典型场景，共同点是"技能多、领域差异大、需要跨轮记忆"：

- 客服、IT 支持这类多业务线对话：订单查询和售后退款用的工具、口径完全不同，拆开各自维护。
- 对话需要跨轮次记忆：用户第一句说了姓名和订单号，后续任何专家接手都该直接使用。
- 存在必须升级人工的请求：投诉、强烈不满要有确定性的出口，而不是让模型继续勉强应对。

何时不用：任务单一、工具只有一两个、对话三五轮就结束的场景，单 Agent 一个文件就能写完，拆分只会增加路由这个新故障点。

| 方案 | 差异 | 什么时候选它 |
|:--|:--|:--|
| 单 Agent | 一份提示词装所有技能，无转接成本 | 技能少、领域单一 |
| 主 Agent 委托子 Agent | 主 Agent 自己决定何时找谁，灵活但链路长、难测试 | 任务边界模糊、需要动态拆解 |
| 路由 + 专家 + 共享上下文（本篇） | 分类后定点分发，路径确定，好测试好追责 | 业务线清晰、要求转接不丢上下文 |

## Quick Start

前置条件：离线模式（`MOCK=1`）零依赖；真机模式需在同仓库的 `llm.py` 配好 `BASE_URL`/`MODEL`/`API_KEY`（路由由 qwen3.8 完成）。

```bash
cd qa/21_multi_agent_cs
MOCK=1 python3 multi_agent_cs.py    # 离线: 规则路由 + 模板回答
python3 multi_agent_cs.py           # 真实: qwen3.8 做意图路由
```

两种模式都会跑同一个会话的 10 条请求并统计指标。真机实测（qwen3.8 LLM 路由）：

| 指标 | 结果 |
|:--|:--|
| 路由正确 | **10/10**（含 LLM 区分"退款多久到账"vs"什么时候能到"） |
| 上下文可见（转接后回复带称呼） | **10/10** |
| 人工兜底触发 | 投诉/要求人工 → human Agent 2 次 |

会话轨迹：order → order → aftersale → aftersale → order → chitchat ×2 → order → human ×2。用户开场说一次"我是林晓， 订单 A1002"，后续所有专家（含转接的售后/人工）都能带上称呼与订单号作答。

诚实预期：离线模式结果由关键词规则决定，输出固定；真机模式路由依赖 LLM，单次运行可能出现个别误分类，以多次运行的趋势为准。

## How It Works

一条请求进入系统后走四步：**抽取事实 → 路由分类 → 专家处理 → 记录历史**。

**第一步：抽取进 Session。** `extract_facts` 用正则（regular expression，描述文本模式的匹配表达式）从用户消息里抓身份和订单号（"我是林晓"→ `name=林晓`，"A1002"→ `order=A1002`），写入会话级 Session 对象。

Session 是所有专家共享的唯一事实源，每个专家拿到的上下文摘要都由它生成：

```python
    def summary(self):
        """注入每个专家提示的上下文摘要 —— 转接后他人可见。"""
        if not self.facts:
            return "(新会话, 无已知信息)"
        return "; ".join("{}={}".format(k, v) for k, v in self.facts.items())
```

（缩进保持源码原样——该方法位于 `Session` 类内部。）这段在做什么：把 Session 里的事实拼成 `name=林晓; order=A1002` 这样的摘要。你在实测里看到的"转接后回复带称呼 10/10"，就来自售后、人工专家从这个摘要里读到姓名并拼进回复。

**第二步：路由分类。** 离线模式按关键词表匹配（"退款""坏了"→ aftersale）；真机模式把用户消息连同路由提示发给 LLM（大语言模型），要求只输出 `{"agent": "order"}` 这样的 JSON。路由有三档做法：规则（快、可解释）→ LLM 分类（准）→ 混合（规则兜底、低置信上模型）。

**第三、四步：专家处理并记录。** 路由结果查 `EXPERTS` 表拿到对应处理函数：订单专家持 `query_order`/`cancel_order`，售后专家持 `create_ticket`/`query_refund`，互不感知彼此存在；回复完成后调用 `session.add` 记入历史。

扩展性结论：新增一个专家 = 注册一个处理函数 + 路由表加一项，其余部件不动（[22 项目的 Agent Card](../22_agent_card/README.md) 把"路由表加一项"升级成了动态发现）。

## Pitfalls & Q&A

**Q1：人工兜底在架构里算什么？**

第四个 Agent：有自己的处理器与触发条件（投诉/明确要求人工），走同一路由与 Session——兜底是设计出来的一等路径，不是异常分支。

**Q2：怎么新增一个专家？**

注册处理函数、路由表加一项即可，两处改动都在登记处完成（本篇是 `EXPERTS` 字典与路由表）；技能和提示词跟随专家自带，不污染其他专家。

**坑 1：LLM 路由输出了选项外的标签。**

- 现象：路由返回 `{"agent": "logistics"}` 这类架构里不存在的 Agent。
- 原因：LLM 可能生成训练语料里的常见词，而非你定义的枚举值。
- 解法：路由结果做白名单校验，不合法时落到默认 Agent（本实现落到 chitchat），绝不能直接当键去查专家表。
