# 21 · 多 Agent 客服系统雏形

> 路由 Agent（意图分类: 订单/售后/闲聊/人工）+ 订单/售后专家（各自
> 工具）+ 共享上下文（会话级 Session: 身份/订单/历史）+ 人工兜底。
> 10 条请求端到端测试：路由正确率 + 转接后上下文可见（不用重复自我
> 介绍）。真机路由用 LLM 分类，离线用规则。

## What

多 Agent 客服的最小完整架构，四个部件：

- **路由 Agent**：意图分类（订单/售后/闲聊/人工），决定谁接；
- **专家 Agent**：各持工具与提示词，互不感知；
- **共享 Session**：会话级身份/订单/历史，专家只读自己需要的部分；
- **人工兜底**：投诉/要求人工转 human Agent——它是第四个 Agent，
  不是失败。

心智模型一句话：**共享上下文是转接体验的生命线——用户永远不必重复
自我介绍。**

## Why

单 Agent 塞所有技能会提示词膨胀、工具互扰；多 Agent 的代价是转接时
上下文丢失。这套架构的价值要用两个硬指标验证：路由正确率、转接后
上下文可见性。

## How

```bash
cd qa/21_multi_agent_cs
MOCK=1 python3 multi_agent_cs.py    # 离线: 规则路由 + 模板回答
python3 multi_agent_cs.py           # 真实: qwen3.8 做意图路由
```

真机实测（qwen3.8 LLM 路由）：

| 指标 | 结果 |
|:--|:--|
| 路由正确 | **10/10**（含 LLM 区分"退款多久到账"vs"什么时候能到"） |
| 上下文可见（转接后回复带称呼） | **10/10** |
| 人工兜底触发 | 投诉/要求人工 → human Agent 2 次 |

会话轨迹：order → order → aftersale → aftersale → order → chitchat ×2 →
order → human ×2。用户开场说一次"我是林晓, 订单 A1002"，后续所有专家
（含转接的售后/人工）都能带上称呼与订单号作答。

## Deep Dive

**路由层决定架构**：规则（快、可解释）→ LLM 分类（准）→ 混合（规则
兜底、低置信上模型）。扩展性设计：新增专家 = 注册处理器 + 路由加一项
（[22 的 Agent Card](../22_agent_card/README.md) 把这件事变成动态
发现）。

## Q&A

**Q1: 人工兜底在架构里算什么？**

第四个 Agent：有自己的处理器与触发条件（投诉/明确要求人工），走同一
套路由与 Session——兜底是设计出来的一等路径，不是异常分支。
