# 12 · Plan-and-Execute 规划器

> 本项目让"先规划后执行"与 ReAct 逐拍决策在同一组旅行任务上对跑：规划器一次性输出子目标依赖图，执行器按拓扑序调度、工具调用零 LLM 消耗。读完你能判断什么任务值得先规划，以及规划与执行解耦后必须补的参数防御。

## Background

多步任务最早的主流做法是 ReAct（Reason + Act）式逐拍决策：让 LLM（大语言模型）每步先思考再选工具——每执行一步，都把全部历史交给它，问它"下一步做什么"。

这种做法在长任务上暴露出三重代价。每步都烧一次 LLM 调用，调用次数等于步数，上下文随步数滚雪球，费用和延迟同步上涨；前面步骤的错误观察会留在上下文里，污染后续决策；跑完只剩一条事后轨迹，出了错很难说清"哪一步的依赖关系想错了"。

Plan-and-Execute 把决策成本集中为一次规划：LLM 只调用一次，输出全部子目标及它们的依赖关系，之后由普通程序按依赖顺序调度执行，工具调用不再消耗 LLM。本实验用三个旅行任务对跑两种方案，比较成功率、调用次数与 token。

## What

Plan-and-Execute = 一次 LLM 规划（子目标 DAG）+ 程序化调度执行。LLM 调用从 O(步数) 降到 O(1)，步间不再互相污染上下文。

术语解释：DAG（Directed Acyclic Graph，有向无环图）在这里指"子目标为节点、依赖为边"的执行图，比如"预算校验"依赖"订机票"和"订酒店"；拓扑序指按依赖关系排序执行，被依赖的子目标先做；O(步数) 与 O(1) 是复杂度记号，前者表示调用次数随步数线性增长，后者表示恒定不变。

可以把 Plan-and-Execute 想象成装修：设计师（LLM）出一次图纸（水电走线、工序先后），工人（执行器）按图施工，设计师不必盯每个工序。但和装修图纸不同的是，施工中发现承重墙不能砸时必须回去改图——规划时信息不全的方案要靠重规划补救。

心智模型一句话：**规划器出图，执行器施工——LLM 只画一次图。**

## When to Use

- **结构可预知的多步任务**：旅行规划、报表生成、部署流水线——拆成几步、谁依赖谁，开工前就能想清楚；
- **成本敏感的长任务**：LLM 调用按次与 token 计费，逐拍决策每步一次调用，规划式把开销压成常数；
- **需要审计的场景**：显式的执行图打印即可审查，出错时能定位是哪一步的依赖设计错了。

何时不用：后一步怎么走取决于前一步结果的探索型任务——查不到天气就无法按天气调整行程，规划无从下手；这类任务用 ReAct 或"先规划 + 关键结果回来后局部重规划"的混合式（见 13 项目）。

| 方案 | 与本篇方案的差异 | 什么时候选它 |
|:--|:--|:--|
| ReAct 逐拍决策 | 每步一次 LLM 决策 | 探索型任务，下一步取决于上一步结果 |
| Plan-and-Execute（本篇） | 一次规划 + 程序调度 | 结构可预知、步数多的任务 |
| 混合式：规划 + 局部重规划 | 执行中允许改图 | 规划依赖执行结果的任务 |

## Quick Start

前置条件：Python 3；离线模式（`MOCK=1`）用脚本化规划与预置轨迹（工具全部是 mock 数据，即固定假数据，不访问真实服务）；真实模式需要模型服务在线（qwen3.8 做规划与 ReAct 决策）。

```bash
cd qa/12_plan_execute
MOCK=1 python3 plan_execute.py    # 离线: 脚本化规划与轨迹
python3 plan_execute.py           # 真实: qwen3.8 做规划与 ReAct 决策
```

真机实测：

| 指标 | Plan-and-Execute | ReAct |
|:--|:--:|:--:|
| 成功率 | **3/3** | 2/3 |
| LLM 调用 | **1 次/任务** | 4 次/任务（3 任务合计 12 次） |
| token | ≈2004 | ≈4944 |

诚实预期：真机规划器会"自由发挥"——给子目标发明工具不存在的参数（`start_date`、`destination`、`check_in`…）或漏掉必需的 `city`，靠执行器的参数防御才全部跑通（机制见下节）。

ReAct 侧 2/3 是思考模型（先输出推理过程再给答案的模型）在 12 步预算（步数上限）内的诚实结果。

这组数字来自结构清晰的任务；规划时信息不全的场景是本方案的边界（见 Pitfalls & Q&A）。

## How It Works

**规划阶段**只发一次请求，要求 LLM 输出 JSON 数组，每个子目标带 `id`、`desc`、`tool`、`args`、`depends`（前置子目标 id 列表）。`valid_plan` 先做格式校验，不合格就回退到内置的规范规划模板——绝不带着坏结构往下走。

**执行阶段**的核心是 `topological_exec`：按依赖数排序、循环推进，前置未完成的子目标跳过，直到全部完成。工具是普通 Python 函数，执行零 LLM 消耗；最后的 `verify_budget` 从依赖子目标的返回文本里抽取金额求和，与预算比较。

**参数防御**是本实验最关键的一段代码——LLM 规划的 `args` 不可信，执行前按工具签名（函数声明里定义的参数名列表）过滤：

```python
params = inspect.signature(TOOLS[tool]).parameters
dropped = [k for k in s["args"] if k not in params]
if dropped:
    s["args"] = {k: v for k, v in s["args"].items()
                 if k in params}
    trace.append("    [{}] 丢弃规划器发明的参数 {}".format(
        s["id"], dropped))
for pname, p in params.items():
    if pname not in s["args"] and p.default is p.empty \
            and pname in context:
        s["args"][pname] = context[pname]
        trace.append("    [{}] 从任务上下文补全参数 {}={}".format(
            s["id"], pname, context[pname]))
```

两步各管一类事故：丢弃多余参数防 `TypeError`（Python 调用函数时传了它不认识的参数名就报错），补全缺失参数防漏参崩溃。

输出 trace（执行轨迹，逐条记录每个子目标的动作与结果）印证了防御的必要性：真实运行里"丢弃规划器发明的参数 ['start_date', 'end_date']""从任务上下文补全参数 city=成都"这类行反复出现——三任务的规划全部带病，是执行侧防御把它们拉回来的。

## Pitfalls & Q&A

- **现象：执行报 `TypeError: unexpected keyword argument`。** 原因：LLM 规划发明了工具不存在的参数，直接 `**args` 透传必炸。解法：按工具签名过滤与补全（机制见上文 How It Works）——参数防御不是可选优化，是解耦架构的必配部件。
- **现象：规划 JSON 解析失败。** 原因：模型输出夹带解释文字或截断。解法：`extract_json` 先试整段解析再正则截取；仍失败则回退规范模板。
- **现象：执行提前结束、部分子目标没跑。** 原因：`depends` 引用了不存在的 id 或形成环，调度器检测不到进展就退出。解法：规划校验阶段检查依赖的合法性与无环性。

**Q: Plan-and-Execute 的代价是什么？**

规划时信息不全——查不到天气就无法按天气调整行程。生产常见混合式：先规划，关键结果回来后允许局部重规划（见 [13 重规划](../13_replan/README.md)）。
