# 31 · 长任务断点续跑（Checkpoint/Resume）

> 一条 10 步的 LLM（大语言模型）长任务管线，每步完成后原子写检查点（checkpoint，把进度与中间结果落盘的机制）；`--crash-at N` 模拟进程在任意步崩溃，重启后从断点恢复：已完成步骤复用结果、未完成步骤重做。读完本篇，你能说清检查点存什么、为什么落盘必须原子、重做为什么不安全也不重复，并在真机复现"崩溃 → 恢复 → 零重算"三段演示。

## Background

跑一条多步 LLM 长任务管线（每步一次模型调用，整条要几十分钟、有真金白银的成本），最直接的做法是一条命令从头跑到尾。失败了呢？再从头跑一遍。

从头上跑的成本账很难看：任务跑到 70% 崩溃，从头重跑等于多花 100% 的成本，去买已经拥有的 70%。更糟的是，如果不落盘任何中间状态，崩溃之后连"跑到哪一步、前几步的输出是什么"都无从知道，重跑是唯一选择。

检查点机制是批处理与分布式系统领域对这个问题的成熟答案：每完成一步就把进度与结果落盘，崩溃后从最近的落盘点恢复，而不是从零开始。本实验把这套机制落到一条 10 步的 LLM 管线上，并专门验证恢复语义的正确性——复用的不错、重做的安全。

## What

断点续跑（checkpoint/resume）是一种让长任务崩溃后从最近落盘点继续执行的机制。它的四个机制设计：

- **检查点存什么**：已完成步骤 id + 每步输出 + 共享上下文——重启后任务可以一次性恢复到崩溃前的完整状态；
- **原子写**：先写 `.tmp` 再 `os.replace`，任何时刻崩溃都不会留下半截检查点；
- **幂等语义**（幂等：同一操作执行多次与一次效果相同）：at-least-once（至少执行一次）执行 + 结果按步骤 id 去重 = 业务上 exactly-once（恰好一次）——未完成的步骤重做是安全的，因为该步没有检查点记录；
- **LLM 上下文恢复**：重启后把已完成步骤的摘要喂回模型，不"失忆重做"。

心智模型一句话：**检查点的可信度不取决于跑了多少，取决于哪些步骤的结果已经落盘。**

可以把检查点想象成游戏存档：打完一关存一次，失败后从存档继续，而不是重头玩。但和游戏存档不同的是，存档动作本身可能被打断（写到一半崩溃），所以落盘必须原子；而且"某一步到底执行了没有"并不总能确知，需要幂等语义兜底。

## When to Use

断点续跑的收益随任务长度增长，代价是落盘与恢复的复杂度。典型场景：

- 跑多步 LLM 管线（调研、批量生成、多阶段处理）时，每步都有成本，中途崩溃不应推倒重来。
- 批处理或回填任务部署在不稳定环境（部署重启、超时被杀）时，需要"重启后接着跑"的保证。
- 实验型管线需要可重放时，检查点天然提供"已跑部分零重算"的重放能力。

何时不用：任务只有几步、单步便宜时，重跑的代价低于检查点的维护成本；步骤带不可撤回的外部副作用（写外部系统）且无法做成幂等时，先解决副作用问题再谈续跑。

同类方案对比：

| 方案 | 差异 | 什么时候选它 |
|:--|:--|:--|
| 从头重跑 | 零额外代码，崩溃即全损 | 几步以内、单步便宜的短任务 |
| 每步检查点（本实验） | 几十行代码自建，恢复语义自己掌控 | 学习原理、轻量自用管线 |
| LangGraph checkpointer | 框架内建，与图执行深度集成 | 已用 LangGraph 的生产任务 |
| Temporal / Celery 工作流持久化 | 重型基础设施，持久化与调度完备 | 大规模生产工作流 |

## Quick Start

前置条件：Python 3，无第三方依赖。真实模式需要可用的 LLM 服务；加 `--demo` 用 canned（预置好的固定）产出离线演示，机制相同。

```bash
cd qa/31_checkpoint_resume
# 离线演示（无需 LLM 服务）:
python3 checkpoint_resume.py --crash-at 4 --fresh --demo   # 步骤 1-3 完成后崩溃 (exit 137)
python3 checkpoint_resume.py --demo                        # 恢复: 复用 1-3, 续跑 4-10
python3 checkpoint_resume.py --demo                        # 全部复用, 零重算
# 真实 LLM: 去掉 --demo（需要可用的 LLM 服务）
```

离线三连运行输出（节选）：

```text
  💥 步骤 4 执行中模拟进程崩溃 (此步未完成, 无检查点)!
     检查点保留: 步骤 1-3。重新运行本脚本即从断点恢复。
...
本次实际执行 7 步, 复用 3 步。
...
任务此前已完成: 全部步骤幂等复用, 零重算 (重放语义正确)。
```

**实测**：run1 崩溃后检查点保留步骤 1-3；run2 跳过 1-3、执行 4-10（7 步），复用 3 步；run3 全部复用零重算（重放语义正确）。恢复只花 70% 的成本跑完剩余 70% 的任务。每次运行打印 `实际执行/复用` 计数。

诚实预期：真实模式每次运行的 LLM 输出内容不同，但"实际执行/复用"的计数语义一致；`exit 137` 是崩溃模拟的退出码（进程被强制终止），不是脚本故障。新手第一个失败点通常是没加 `--fresh` 就跑 run1——旧检查点存在时不会从头开始。

## How It Works

执行流按固定节奏推进：每完成一步，立即原子写检查点——先把检查点写进 `.tmp` 临时文件，再用 `os.replace` 原子替换正式文件。替换在文件系统层面要么整体发生要么不发生，所以任何时刻崩溃，磁盘上的检查点要么是上一步的完整状态，要么是这一步的完整状态，不会出现半截。

`--crash-at 4` 在第 4 步强制终止进程，制造崩溃现场。

重启后的恢复判定只有一条规则：检查点里有记录的步骤，直接复用落盘结果；没有记录的步骤，重做。Quick Start 里 run2 的"跳过 1-3、执行 4-10、复用 3 步"就是这条规则的输出；run3 重跑时全部步骤都有记录，于是全部复用、零 LLM 调用——重放语义正确。

幂等语义是恢复安全的核心：崩溃可能卡在"步骤执行了但检查点还没写"的间隙，此时重做该步。安全性来自两点——没有检查点记录的步骤重做是预期行为（at-least-once）；结果按步骤 id 去重，业务视角等价 exactly-once。

LLM 上下文恢复则保证重做的步骤不是"失忆重做"：重启后把已完成步骤的摘要喂回模型，续跑的步骤仍然看得到前文。

## Pitfalls & Q&A

踩坑清单：

- 现象：崩溃后重启，程序读检查点直接报错或行为异常。原因：检查点写了一半进程就被杀，磁盘上留下半截文件。解法：先写 `.tmp` 再 `os.replace` 原子替换，保证磁盘上永远只有完整检查点（机制见 How It Works）。
- 现象：恢复后某步重做，外部系统里出现了重复订单/重复写入。原因：该步带外部副作用，重做触发了第二次真实写入。解法：把步骤设计成幂等，或引入业务事务 id——外部系统据 id 识别重复请求，重做才安全。
- 现象：断点续跑后，续跑步骤的输出质量明显下降、前后脱节。原因：只复用了结果，没把已完成步骤的摘要喂回模型，续跑"失忆"。解法：恢复时重建 LLM 上下文——已完成步骤的摘要随检查点一起落盘、一起恢复。

**Q: 检查点写入频率怎么定？**

本篇每步落盘；更细可按 token（模型计量文本的单位）预算或时间窗口。粒度越细，崩溃损失越小，落盘开销越大——按单步成本与崩溃概率权衡即可。
