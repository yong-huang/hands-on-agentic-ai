# 31 · 长任务断点续跑（Checkpoint/Resume）

> 一条 10 步的 LLM 长任务管线，每步完成后原子写检查点；`--crash-at N`
> 模拟进程在任意步崩溃，重启后从断点恢复：已完成步骤复用结果、未完成
> 步骤重做。

## What

断点续跑的四个机制设计：

- **检查点存什么**：已完成步骤 id + 每步输出 + 共享上下文——重启后任务
  可以一次性恢复到崩溃前的完整状态；
- **原子写**：先写 `.tmp` 再 `os.replace`，任何时刻崩溃都不会留下半截
  检查点；
- **幂等语义**：at-least-once 执行 + 结果按步骤 id 去重 = 业务上
  exactly-once（未完成的步骤重做是安全的，因为该步没有检查点记录）；
- **LLM 上下文恢复**：重启后把已完成步骤的摘要喂回模型，不"失忆重做"。

心智模型一句话：**检查点的可信度不取决于跑了多少，取决于哪些步骤的
结果已经落盘。**

## Why

长任务跑到 70% 崩溃，从头重跑等于多花 100% 成本买已拥有的 70%。任务
越长，断点续跑的收益越大——但前提是恢复语义正确：复用不错、重做安全。

## How

```bash
cd qa/31_checkpoint_resume
# 三步演示（真实 LLM）:
python3 checkpoint_resume.py --crash-at 4 --fresh   # 步骤 1-3 完成后崩溃 (exit 137)
python3 checkpoint_resume.py                        # 恢复: 复用 1-3, 续跑 4-10
python3 checkpoint_resume.py                        # 全部复用, 零 LLM 调用
# 离线: 加 --demo（canned 产出，机制相同）
```

**实测**：run1 崩溃后检查点保留步骤 1-3；run2 跳过 1-3、执行 4-10
（7 步），复用 3 步；run3 全部复用零重算（重放语义正确）。恢复只花 70%
的成本跑完剩余 70% 的任务。每次运行打印 `实际执行/复用` 计数。

## Deep Dive

**幂等语义是恢复安全的核心**：崩溃可能卡在"步骤执行了但检查点没写"的
间隙——此时重做该步。安全性来自两点：没有检查点记录的步骤重做是预期
行为（at-least-once）；结果按步骤 id 去重，业务视角等价 exactly-once。

## Q&A

**Q1: 检查点写入频率怎么定？**

本篇每步落盘；更细可按 token 预算/时间窗口——粒度越细，崩溃损失越小，
落盘开销越大。

**Q2: 步骤有外部副作用（写外部系统）怎么办？**

步骤设计为幂等，或引入业务事务 id——外部队据 id 识别重复请求，重做
才安全。

**Q3: 生产对应物？**

LangGraph checkpointer、Temporal/Celery 的工作流持久化——机制同构，
本篇是最小核。
