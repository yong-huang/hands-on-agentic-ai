# 15 · 工具注册表与 Schema 设计

> 让模型稳定调用函数，一半靠参数规范的描述质量，一半靠出错后模型能不能
> 被错误信息拉回来。读完本篇你能获得：一个工具注册表——自动把 Python
> 函数登记成模型可调用的工具（参数规范自动生成、嵌套参数显式校验），
> 以及一套让模型读得懂、改得对的错误格式。

## Background

在 Function Calling（函数调用，指模型按约定格式输出参数、由宿主程序
执行对应函数的机制）普及之前，让模型"调用函数"靠把函数说明写进提示词，
参数由模型自由发挥，程序拿到什么算什么。

问题在出错之后。模型填的参数可能类型不对、缺字段、值不合法，此时程序
抛出的异常是给人看的堆栈字符串：没有指出错在哪个字段、期望什么值。
模型读不懂这种报错，只能凭空猜一个改法重试，同样的错误反复出现。

Function Calling 规范让模型按结构化模式生成参数，参数约束有了统一的
表达位置。

工具注册表（tool registry，集中登记哪些函数可被模型调用的组件）进一步
把模式描述的编写自动化——从函数签名和 docstring（Python 函数首部的
说明字符串）自动生成 JSON Schema（用 JSON 描述参数类型、取值范围与
必填字段的标准格式）。

它还把校验错误格式化成模型可读的结构，使"错误回传 → 模型自纠"的
闭环得以成立。

## What

工具注册表把"函数"变成"模型可调用的工具"，调用质量由三件事决定：

- **Schema 自动生成**：类型 + 枚举（enum，限定取值只能是指定集合之一）
  + 描述缺一不可；docstring 的 `参数名: 说明` 行自动变成字段
  description（即单一事实源——只维护函数定义这一处，别处自动跟随）；
- **嵌套参数**（数组内对象/对象内对象）用 `items.properties` 显式声明，
  jsonschema（Python 的 JSON Schema 校验库）校验；
- **错误友好化**：错误按结构化字段返回（code/message/hint，即错误码/
  人读的说明/修正提示），而不是一段报错堆栈（程序异常时打印的调用
  轨迹文本）。

心智模型一句话：**Schema 是给模型看的 API 文档——模型读得懂错误才能
自行纠正，这是 Agent 稳定性的隐藏关键。**

可以把注册表想象成旅行社的前台登记簿：每个可预订项目（工具）登记了
名称、需要哪些材料（参数类型）、哪些材料必填；材料不合规时，前台
退回的不是"办不了"三个字，而是"第 2 项材料缺签名，请补"（带路径的
结构化错误）。

但和登记簿不同的是，这份登记是从函数定义自动生成的，函数改了登记
就跟着变，不会出现两处维护不一致。

## When to Use

典型场景一：给 agent（能自主调用工具、分步完成任务的程序）接入自定义
工具（下单、查航班、配置告警）时，需要把函数暴露给模型，并保证传进来
的参数合法。

典型场景二：工具参数含嵌套结构（一个订单包含多个商品项，每个商品项
又有数量与规格）时，自由 JSON 无法约束内层字段。

典型场景三：工具数量增多后需要统一管理——注册、枚举、校验、错误
格式全走同一套机制，而不是每个工具各写一套。

何时不用：只有一个工具、参数是一个字符串时，手写一份 schema 更直接；
调用方是人写的普通程序时不需要 schema——那是类型检查与单元测试的
职责。

| 方案 | 差异 | 什么时候选它 |
|:--|:--|:--|
| 手写 JSON Schema | 逐字段手写，控制精细，但易与函数实现脱节 | 工具少、结构特殊时 |
| 装饰器自动生成（本实验） | 从签名 + docstring 生成，函数是单一事实源 | 工具多、经常增改时 |
| 框架内置工具定义 | 框架托管 schema 生成与校验 | 已深度使用该框架时 |
| 不校验的自由 JSON | 模型给什么用什么 | 只读、容错高的演示场景 |

## Quick Start

前置条件：Python 3；离线模式无额外依赖。两种运行方式：

```bash
cd qa/15_tool_registry
MOCK=1 python3 tool_registry.py    # 离线: 预置模型纠错
python3 tool_registry.py           # 真实: qwen3.8 读错误后自行纠正
```

`MOCK=1` 使用预置的纠错响应；真实模式由 qwen3.8 模型读取错误后重试。
诚实预期：实测 5 个含嵌套参数的工具合法调用全通；3 条故意错参（qty
违反 minimum / 缺 to_city / op 不在枚举）均收到带路径的结构化错误，
模型读错误后自行纠正 3/3 ✓：

```
create_order:  参数 items.0.qty 校验失败: 0 is less than the minimum of 1
query_flights: 参数 route 校验失败: 'to_city' is a required property
configure_alert: 参数 rules.0.op 校验失败: '≈' is not one of ['>', '<']
→ 模型修正后 3/3 通过
```

三条错误各代表一类约束：`items.0.qty` 的值 0 低于 schema 规定的
最小值 1；`to_city` 是必填字段却缺失；`≈` 不在允许的枚举 `['>', '<']`
内。每条都带路径与"期望 vs 实际"，模型据此改参数。

## How It Works

整条链路是：注册（装饰器收集函数）→ 生成 schema → 校验模型给的
参数 → 校验失败则格式化错误回传 → 模型修正后重试。

**装饰器自动生成**：装饰器（decorator，Python 中写在函数定义上方的
@ 标记，这里用于把函数登记进注册表）让函数签名里的类型注解变成字段
的类型，docstring 里 `参数名: 说明` 行变成字段的 description，枚举与
范围等约束写在声明处。

类型 + 枚举 + 描述缺一不可——缺类型则校验失效，缺描述则模型不知道
字段含义。

**错误友好化是闭环成立的关键**：校验错误必须带路径（`items[0].qty`）
——没有路径的报错模型修不了，它不知道错误发生在数组第几个元素、
哪个字段。路径 + 期望 vs 实际 + 修正提示三件齐了，"错误回传 → 自纠"
闭环才成立。

与 Quick Start 的输出互相印证：`items.0.qty 校验失败: 0 is less than
the minimum of 1` 正是"路径 + 期望 vs 实际"的格式——路径指出数组
第 0 个元素的 qty 字段，期望是至少 1，实际是 0。

模型把 0 改成合法
数量后重试通过，3/3 的纠正成功率全部来自这个闭环。

## Pitfalls & Q&A

**坑 1：未注解参数默认 string。** 现象：`amount` 不加 `int` 注解，
传 500 也被判类型错误。原因：签名注解是 schema 的源头，源头错全链
错。解法：每个参数都写类型注解，嵌套结构额外用 `items.properties`
显式声明。

**Q: 嵌套参数怎么声明？**

用 `items.properties` 显式声明数组内对象/对象内对象的结构，交给
jsonschema 校验——嵌套结构的错误尤其依赖路径信息（`items.0.qty`），
这也是嵌套参数必须走显式 schema 而不是自由 JSON 的原因。
