# 04 · ReAct 死循环检测与防护

> Agent 死循环不报错、不崩溃，只是烧钱空转。四层防护（defense in depth）：
> L1 步数上限 / L2 重复 Action / L3 Thought 相似度 / L4 预算熔断
> （token+耗时），任何一层触发即输出诊断并**强制"失败总结"**——不空转、
> 不静默截断。读完本篇，你能为无人值守的 Agent 配一套可验证的护栏。

## Background

最简单的做法是只设 max_steps（步数上限）一道闸：循环跑满 N 步就砍断，
多数教程和框架的默认防护止步于此。

单层闸在真实运行中有两个盲区。其一是时机难定：步数设小会误杀合法的
慢任务，设大会在真出事时白白多烧钱。其二是死循环并不总是"重复同一个
动作"——有的循环每一步的决策都不同，但永远不朝答案收敛，只看轮数
根本发现不了。

更麻烦的是，死循环的特征是"不报错、不崩溃，只是烧钱"：每轮输出看
起来都正常，监控无异常，账单在涨；砍断后半成品结果也直接丢失、没有
交代。

单层防护升级成了分层的纵深防御（defense in depth，安全工程思路：每层
只堵一类漏洞，多层互补防漏网），并且要求触发后有意义地收尾而不是静默
截断。本篇构造三种病态场景，逐一验证四层防护各自的拦截能力。

## What

本篇的防护对象是 ReAct Agent 循环（模型每轮输出一个 JSON 决策、调用
工具、观察结果，直到能作答；完整手写实现见 03 项目）。四层防护如下：

| 层 | 信号 | 抓什么循环 | 参数 |
|:--|:--|:--|:--|
| L1 步数上限 | 执行轮数 | 硬兜底，漏网循环最终被它拦 | max_steps=8 |
| L2 重复 Action | (action, input) 签名 | 撞墙式重试（连续 3 次完全相同） | repeat_limit=3 |
| L3 Thought 相似度 | 相邻思考文本编辑相似度 | 换汤不换药的复读（输入微调、思考没变） | ≥0.85 |
| L4 预算熔断 | 累计 token / 耗时 | 每步都不同但永不收敛的资源空转 | 1200 est.tokens / 30s |

表里四个名词先解释：token 是模型生成文本的最小单位，est.tokens 是它的
估算值（按字符数粗估）；编辑相似度指两段思考文本的相似比例，由标准库
difflib.SequenceMatcher 计算，1.00 表示完全相同；熔断指资源超出预算
就立即终止求解。

三层在线信号互为补充——L2 看**行为**、L3 看**语义**、L4 看**资源**，
单一信号都会误报/漏报；L1 不参与判断，只负责兜底。

触发后统一走 `force_summary()`：把防护原因喂回模型，要求基于已有
Observation 产出失败总结。

心智模型一句话：**从外到内观察 Agent 是否在推进——行为、语义、资源
三层互补，兜底另设一层。** 例如"模型反复查天气、思考文本几乎一字
不变"这种复读循环，行为签名各不相同，L2 抓不到，正是 L3 的目标。

## When to Use

在把 Agent 从"人盯着的演示"推向"无人值守的任务"时，需要这层护栏：

- 接上付费模型 API 长时间跑批——预算熔断防账单失控；
- 依赖不稳定的第三方工具（可能持续返回故障）——重复检测防撞墙重试；
- 使用降级模型或自研重试逻辑——这类组合是死循环的高发来源。

何时不用：人在旁边盯着的交互式问答，循环卡住一眼可见；步数天然固定
的流水线任务；原型验证阶段——单层 max_steps 足够，四层是生产要求。

| 方案 | 差异 | 什么时候选它 |
| :--- | :--- | :--- |
| 无防护，人工盯 | 卡住靠人发现并中断 | 交互式问答、演示 |
| 单层 max_steps | 只兜底，慢任务易误杀 | 原型、步数可预估的任务 |
| 四层纵深防护（本篇） | 行为/语义/资源互补 + 强制总结收尾 | 无人值守、付费 API 的生产任务 |

## Quick Start

前置条件：Python 3，仅用标准库（相似度用 difflib，计时用 time）。真实
模式默认连接本机 Ollama（`http://localhost:11434/v1`，模型
`qwen3.8:latest`）。

环境变量 `LLM_BASE_URL` / `LLM_MODEL` / `LLM_API_KEY` 可换目标。

```bash
cd qa/04_loop_guard
MOCK=1 python3 loop_guard.py    # 离线：脚本化病态策略，结果确定
python3 loop_guard.py           # 真实：S1 真模型首轮决策+卡带重放注入
```

实测（离线 mock / 真机各跑一轮，两轮全绿）：

| 场景 | 期望层 | 实际层 | 触发步数 | 结果 |
|:--|:--:|:--:|:--:|:--|
| S1 工具恒失败（航班服务恒 503，即"服务不可用"状态码） | L2 | L2 | 3 | ✓ 拦截 + 失败总结 |
| S2 模型复读（忽略 Observation 反复查天气） | L3 | L3 | 2 | ✓ 拦截，且总结里把已有答案捞了回来 |
| S3 目标矛盾（北京/上海出发反复摇摆） | L4 | L4 | 5 | ✓ token 熔断 |
| S3 消融（关掉 L4，即去掉一个部件看谁接手的对照实验） | L1 | L1 | 9 | ✓ 步数上限兜底 |

真机说明：健康模型不会自己死循环——qwen3.8 对故障工具**一次失败即自行
finish**（还附上替代建议）。所以 S1 采用"真模型首轮决策 + 卡带重放注入"：
第一轮是真实 LLM 对真故障工具的真实决策，之后原样重放模拟卡死的 Agent，
L2 拦截与强制总结（由真模型产出）在真机上确定可复现。

诚实预期：四个场景都按期望层触发、步数与表中一致；若你的模型更强或
更弱，S1/S2 的措辞可能不同，但拦截层与步数应当稳定。

## How It Works

**各层怎么判定。**

- L2：把每轮决策的 action 和 input 拼成一个签名字符串（相同内容得到相同签名，用来判断两次决策是否完全一样），最近 3 个签名完全相同即触发
- L3：取相邻两条 Thought（去掉空白字符）算编辑相似度，达到 0.85 即判复读
- L4：维护累计开销，每轮把上下文文本按 est_tokens 估算（中文约 0.6 token/字符的粗估，生产环境应换 tiktoken 精确计数），连同耗时一起对照 1200 est.tokens / 30 秒双阈值
- L1：只看轮数是否到 8

**触发后统一交接。** 任何一层命中都调用 `force_summary()`：向对话追加
一条"防护已触发、不许再调工具"的用户消息，要求模型基于已有 Observation
输出失败总结；模型不守格式约定时，返回带原因的兜底字符串，保证收尾
永不缺席。

**拦截的价值是交接而非止血。** Quick Start 表里 S2 的答案其实第一步
就拿到了，复读只是把已有 Observation 掩盖掉；强制总结把半成品结果
交接出来，所以"总结里把已有答案捞了回来"。消融行（关掉 L4 后第 9 步
由 L1 拦截）则印证了分工：L4 管资源空转，L1 只兜住漏网的。

## Pitfalls & Q&A

踩坑清单：

- **现象：L3 的相似度 1.00 在第 2 步就抢先触发，L2 的"连续 3 次"永远
  数不满。** 原因：完全相同的决策同时满足 L2 和 L3 的条件，层间语义
  边界没有划清。解法：设 identical-streak——签名完全相同的重复归 L2
  管，L3 检测到连击时让位（实测踩到后用此法修复）。
- **现象：真机上怎么跑都测不出防护，护栏代码像没生效。** 原因：健康
  模型不会自己死循环（一次失败即 finish），防护只对病态策略生效。
  解法：注入病态策略——离线用脚本化策略，真机用重放注入（见 Quick
  Start 的真机说明），才能稳定复现尾部风险。

**Q1: 最大步数怎么设？**

它是兜底不是唯一防护；按任务复杂度分级（简单 3-5 / 研究型 10-20），触发
后必须强制总结、有意义地收尾，而不是静默截断。
