# 18 · 工具优雅降级

> 外部工具必然故障，关键在故障后 agent（能自主调用工具、分步完成任务
> 的程序）的行为是设计出来的还是临场崩溃的。读完本篇你能获得：一条
> 四级降级链（实时价 → 批发价 → 缓存 → 诚实拒答）的完整设计，配套的
> 可降级标记与熔断器（连续失败摘除故障工具）机制，以及实测可用率数据。

## Background

没有降级设计的程序调用外部接口时，通常只有两种结局：异常一路抛给
用户（页面上一堆报错堆栈），或者用一个空的 try/except 把失败吞掉、
返回空数据。

两种结局在 agent 场景里都不合格。前者是"一次故障全盘摆烂"：机票
接口一超时，整个助手什么都答不了，哪怕本地明明有昨天的缓存价。

后者是"无脑兜底"：拿不可靠的数据冒充正常结果用户并不知情，更危险的
是对资金类操作也换通道重试——支付失败找"备用通道"再来一次，可能
造成重复扣款。

优雅降级（graceful degradation，指系统部分故障时主动切换到功能较弱
但可用的路径，而不是整体失败）把"失败时怎么办"变成预先设计好的
固定路径：数据一致性逐级放宽，每一级都告知来源，实在无路可走就带着
原因诚实拒答。

再配上熔断器（circuit breaker，连续失败达到阈值后暂时切断对故障方的
调用，借用电工"跳闸"的概念）把已知故障的通道快速摘除。

## What

本实验的主题是工具优雅降级，核心是一条逐级放宽一致性（consistency，
此处指数据的实时与准确程度）的降级链：**实时价 → 批发价 → 旧缓存 →
拒答**；每降一级都要告知数据来源，拒答必须带原因。配套两个机制：

- **可降级标记**：查询类可降级，资金/删除类不可降级；
- **熔断器**：连续失败 N 次摘除主工具，冷却后半开（half-open，冷却
  结束后放行少量请求试探是否恢复的状态）探测。

心智模型一句话：**降级不是失败，是设计——但降级到"换一个通道做资金
操作"就是事故。**

可以把降级链想象成停电时的大楼供电：市电断了切柴油发电机（备用
工具），发电机没油了用应急灯（缓存），全都失效就广播"本楼暂停
开放"（附原因的拒答），而不是让每层楼各自摸黑乱走。

但和大楼供电不同的是，降级链里"哪些设备允许接应急电源"是注册时就
声明的属性——电梯（资金类操作）宁可停运也不接不稳的电源。

## When to Use

典型场景一：agent 的关键功能依赖第三方接口（机票、天气、汇率），
对方的稳定性不受你控制时，必须有故障下的替代路径。

典型场景二：本地已有次级数据（历史缓存、低精度报价）可以顶上时，
降级比拒答保留更多可用性。

典型场景三：面向真实用户的产品里，"查不到 + 原因"远比报错堆栈
或编造的数据体面。

何时不用：调用内部稳定服务时，降级链增加的复杂度大于收益；数据必须
强一致（下单价格必须与最终结算一致）时不能放宽数据源；资金、删除类
操作不进降级链。

| 方案 | 差异 | 什么时候选它 |
|:--|:--|:--|
| 直接报错 | 无兜底，故障即不可用 | 内部稳定服务、故障率极低 |
| 重试 + 退避 | 同一通道按间隔反复尝试 | 瞬时抖动类故障 |
| 降级链 + 熔断器（本实验） | 逐级放宽数据源，故障通道快速摘除 | 依赖外部接口、本地有次级数据 |
| 无差别兜底 | 任何失败都换通道重试 | 不建议：一致性失守且掩盖故障 |

## Quick Start

前置条件：Python 3，无额外依赖。两种运行方式：

```bash
cd qa/18_graceful_degrade
MOCK=1 python3 graceful_degrade.py    # 离线: 拒答话术用模板
python3 graceful_degrade.py           # 真实: 拒答话术由 qwen3.8 生成
```

`MOCK=1` 的拒答话术来自预置模板；真实模式由 qwen3.8 模型生成话术，
其余行为相同。主工具注入了 100% 超时（故障注入，指测试时人为制造
故障），备用工具只覆盖部分城市。

诚实预期，实测（真机）：主工具全挂情况下**可用率 8/10 (80%) 达标**
（备用接口命中 5 + 缓存命中 3，2 城诚实拒答并附原因）；熔断器在连续
3 次超时后打开，后续查询直接跳过主工具（日志 3 条可见）：

```
· [主工具] 成都 超时 (>0.4s), 熔断状态=closed   ×3 后
⚡ 熔断器 open: 连续失败 3 次, 暂时摘除主工具 1.0s
· [主工具] 熔断打开, 跳过 (拉萨/海口/...)
```

三行日志对应熔断器的三个阶段：成都前 3 次查询放行主工具并超时
（closed）；失败满 3 次触发 open，摘除 1.0 秒；之后拉萨、海口等
城市不再白等主工具超时，直接进降级链。

## How It Works

一次查询的完整路径：进入降级链 → 熔断器按当前状态决定是否放行主
工具 → 主工具失败则依次尝试备用工具（覆盖部分城市）、本地缓存 →
全部未命中则诚实拒答，附原因（真机由大语言模型 LLM 组织话术）。

**熔断器保护的是系统**：没有熔断时，每个请求都要白等一个超时才知道
主工具挂了；连续失败 N 次摘除后，后续查询直接走降级链，冷却期满半开
探测、恢复要及时。

与 Quick Start 的实测互相印证：8/10 的可用率 = 备用接口 5 + 缓存 3，
这正是降级链中间两级各自接住的量；剩余 2 城两级都没命中，落到第四级
拒答——数据来源逐级放宽的顺序在结果分布里清晰可见。

降级链的正确性靠两条纪律：每级降级告知数据来源（用户知道拿到的是
缓存价）、拒答附原因（诚实拒绝好过编一个数）。

## Pitfalls & Q&A

**坑 1：降级了却不告知来源。** 现象：用户把缓存旧价当成实时价，
事后产生纠纷。原因：降级链只切换了数据源，没有把来源传递到回复里。
解法：降级结果必须带来源字段，回复中如实说明。

**坑 2：熔断冷却期设置过短。** 现象：熔断刚进入半开又被连续超时
打断，主工具反复在摘除与恢复间振荡。原因：冷却时间短于故障的实际
恢复时长。解法：冷却期覆盖典型故障恢复时长，半开阶段只放少量探测
请求。

**Q: 什么工具不可降级？**

资金/删除类——支付失败找"替代通道"重试是事故，不是降级。可降级性是
工具的显式属性，注册时声明，降级链只对标记可降级的工具生效。
