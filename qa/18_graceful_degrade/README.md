# 18 · 工具优雅降级

> 机票价格查询的降级链：主工具（注入 100% 超时）→ 备用工具（覆盖部分
> 城市）→ 本地缓存 → 诚实拒答（附原因，真机由 LLM 组织话术）。配套
> 可降级标记（支付类不可降级）与熔断器（连续失败 3 次摘除主工具）。

## What

降级链是逐级放宽的一致性：**实时价 → 批发价 → 旧缓存 → 拒答**；每降
一级都要告知数据来源，拒答必须带原因。配套两个机制：

- **可降级标记**：查询类可降级，资金/删除类不可降级；
- **熔断器**：连续失败 N 次摘除主工具，冷却后半开探测。

心智模型一句话：**降级不是失败，是设计——但降级到"换一个通道做资金
操作"就是事故。**

## Why

外部工具必然故障（超时/挂掉），没有降级链的 Agent 一次故障就全盘摆烂；
但降级也不能无脑兜底——数据一致性逐级放宽、不可降级操作必须挡住，
这些边界要实验数据验证。

## How

```bash
cd qa/18_graceful_degrade
MOCK=1 python3 graceful_degrade.py    # 离线: 拒答话术用模板
python3 graceful_degrade.py           # 真实: 拒答话术由 qwen3.8 生成
```

实测（真机）：主工具全挂情况下**可用率 8/10 (80%) 达标**（备用接口命中
5 + 缓存命中 3，2 城诚实拒答并附原因）；熔断器在连续 3 次超时后打开，
后续查询直接跳过主工具（日志 3 条可见）：

```
· [主工具] 成都 超时 (>0.4s), 熔断状态=closed   ×3 后
⚡ 熔断器 open: 连续失败 3 次, 暂时摘除主工具 1.0s
· [主工具] 熔断打开, 跳过 (拉萨/海口/...)
```

## Deep Dive

**熔断器保护的是系统**：没有熔断时，每个请求都要白等一个超时才知道
主工具挂了；连续失败 N 次摘除后，后续查询直接走降级链，冷却期满半开
探测、恢复要及时。降级链的正确性靠两条纪律：每级降级告知数据来源
（用户知道拿到的是缓存价）、拒答附原因（诚实拒绝好过编一个数）。

## Q&A

**Q1: 什么工具不可降级？**

资金/删除类——支付失败找"替代通道"重试是事故，不是降级。可降级性是
工具的显式属性，注册时声明，降级链只对标记可降级的工具生效。
