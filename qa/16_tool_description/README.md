# 16 · 工具描述优化实验

> 模型挑工具靠读工具描述，描述写多详细才最好，不能凭感觉。读完本篇
> 你能获得：一套对照实验方法——同一批易混工具写 3 版描述、同一指令集
> 跑选对率——以及一个反直觉的实测结论：描述过度工程反而伤害选对率。

## Background

早期给 agent（能自主调用工具、分步完成任务的程序）接工具，描述是
随手的：工具名加一句话，甚至只有函数名。工具少、职责不相干时这样
能跑，模型挑错也怪不到哪里去。

撞墙发生在工具功能相近时。机票、高铁、天气、酒店四类工具接收的输入
长得都差不多（地点、日期、人数），描述含糊时模型会频繁把"查北京
下个月天气"发给酒店工具。

常见直觉是"把描述写详细点就好"，但描述本身占用 token（模型处理文本的
最小单位，约一个词或半个词），过长反而可能干扰选择——这个方向从未被
验证过。

于是描述被当成可实验的变量：同一批工具写多个版本的描述，用同一指令
集分别测"选对率"（模型选中正确工具的比例），用数据决定采用哪一版。
本实验就是这样一个受控对照。

## What

工具描述（tool description）是模型在路由（routing，从多个候选工具中
挑一个的过程）时读到的说明文字。本实验对同一套 4 个易混工具写了
3 版：

| 版本 | 描述内容 |
|:--|:--|
| V1 | 一句话说明工具管什么 |
| V2 | V1 + 参数说明 |
| V3 | V2 + 使用时机 + 边界反例 + 示例 |

心智模型一句话：**描述要"够用且短"——它是路由依据，不是产品文档。**

可以把描述想象成药品盒上的适应症标签：药剂师按标签发药，标签只需
写清"治什么、怎么用、什么时候不能用"。但和药品标签不同的是，标签
越长并不占用药剂师的脑力，而描述的每个 token 都在消耗模型的注意力
预算——这一点后面用数据说明。

## When to Use

典型场景一：agent 挂了多个功能相近的工具（同为出行查询、同为下单）
需要模型准确路由时，描述是唯一区分依据。

典型场景二：上线后发现模型频繁选错工具或传错参数时，先怀疑描述，
再怀疑提示词。

典型场景三：准备扩充工具数量前，先用固定指令集测一版基线选对率，
留一个可比对的参照。

何时不用：只有一个工具时不存在路由问题；工具职责天然无重叠时，
一句话描述已经够用；没有评测手段时不要凭感觉迭代描述——改了也
不知道变好还是变坏。

| 方案 | 差异 | 什么时候选它 |
|:--|:--|:--|
| 一句话描述（V1） | 只说工具管什么 | 工具少、职责清晰、模型较强 |
| 补参数说明（V2） | 加类型/必填/默认值 | 出现传参错误时 |
| 时机+反例+示例（V3） | 加使用时机、边界反例、示例 | 工具易混且基线确实不行时，内容要少而准 |
| 不写描述 | 模型只看工具名 | 仅临时试验，不建议 |

## Quick Start

前置条件：Python 3；离线模式无额外依赖。两种运行方式：

```bash
cd qa/16_tool_description
MOCK=1 python3 tool_description.py    # 离线: 确定性难度模型 (单调递增)
python3 tool_description.py           # 真实: qwen3.8 批量路由
```

指令集共 50 条（易 30/中 12/难 8），每版描述各跑一遍；真机批量评测
按"每调用评 10 条指令"控制 LLM（大语言模型）调用次数。真机实测出现
**反常**：

| 版本 | 易 | 中 | 难 | overall |
|:--|:--:|:--:|:--:|:--:|
| V1-一句话 | 30/30 | 10/12 | 8/8 | 48/50 (96%) |
| V2-补参数 | 30/30 | 11/12 | 8/8 | 49/50 (98%) |
| V3-时机反例 | 30/30 | **2/12** | 8/8 | 40/50 (80%) |

分析与结论：**描述过度工程反而伤害**。qwen3.8 路由能力已接近天花板
（V1 即 96%），而 V3 的长描述（多行"不要用"边界规则）在批量评测中
稀释注意力并破坏输出格式，中等模糊题大面积掉分。

离线难度模型复现了设计预期的单调递增：V1 恒为 30/50（60%）、V3 恒为
50/50（100%）；V2 的中题通过与否由指令文本哈希决定，单次总分在约
32~38/50（64%~76%）间浮动、偶有越出，但始终介于两者之间。两条教训：

1. 先测基线再优化——强模型 + 简单路由场景，描述优化空间很小；
2. 描述要"够用且短"：边界反例对易混淆对有效（难题 8/8），但堆叠
   多条规则会适得其反，需要按 token 预算与错误模式做消融
   （ablation，逐个增删某成分、观察其对结果影响的实验方法）。

## How It Works

实验的执行顺序是：注册 4 个工具 × 3 版描述 → 对每版跑同一 50 条指令
→ 记录选对率 → 对比版本差异。表格里的每个格子是一次评测的命中数。

**反常数据的机制**：长描述不是中性的——多行边界规则在批量路由场景
稀释了模型对工具名与参数的注意力，还破坏了输出格式。描述的每个
token 都在竞争模型的注意力预算，"信息更多"与"路由更准"是两回事。

与 Quick Start 的表格互相印证：V3 掉分集中在"中"难度一列（2/12），
易、难两档满分——简单指令不需要额外信息，最难指令本就该选对；恰好
是"描述里有线索但需要甄别"的中间地带，被长描述干扰得最重。

**离线与真机各回答一个问题**：离线难度模型（确定性规则，难度与正确
率单调挂钩）复现 V1 60%、V3 100%、V2 单次总分在约 64%~76% 间浮动（哈希抽样），
验证实验管线本身能分辨描述好坏；真机 qwen3.8 的反常结果则说明模型
能力才是决定因素——管线正常，结论也要按真实模型修正。

## Pitfalls & Q&A

**坑 1：直接从 V3 开始堆描述。** 现象：描述写得面面俱到，选对率反而
下降且难定位原因。原因：一次改动引入多个变量，长描述的副作用与收益
混在一起。解法：从 V1 基线起步，逐版增加内容并保持同一指令集对照。

**坑 2：用不同指令集比较版本。** 现象：两版描述的选对率不可比。原因：
指令难度分布不同，结果没有可比性。解法：固定同一 50 条指令与难度
配比（30/12/8），只动描述这一个变量。

**Q: 工具描述怎么写？（5 条实践清单）**

1. 名词钉死：工具管什么用【名词】写明，别用动词短语；
2. 参数说明：类型/必填/默认值，缺了模型就开始编；
3. 使用时机：一句话"何时用我"——路由的本质是时机判断；
4. 边界反例：点名最易混的邻居工具划界（少量、精准）；
5. 给示例：一条 输入→调用 示例的收益大于三行形容词。
