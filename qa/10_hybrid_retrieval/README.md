# 10 · 混合检索（向量 + 关键词 + RRF）

> 50 条文档语料，三种检索器对跑 15 条查询（精确词/语义改写/混合 各 5，
> Hit@3 评测）：BM25 简化实现 / 向量检索（真机 nomic，离线 hash 退化）/
> RRF 排名融合。

## What

三种检索路线各有失明区，混合检索用排名融合取长补短：

| 检索器 | 擅长 | 失明区 |
|:--|:--|:--|
| BM25 | 精确词（型号/报错码/专名） | 语义改写（字面零重叠） |
| Vector | 语义改写 | 精确 token 不敏感 |
| RRF 融合 | 两路排名合并 | 依赖两路召回互补 |

RRF 一条公式：score(d) = Σ 1/(60 + rank_i(d))——只看排名不看分数。

心智模型一句话：**RRF 天然规避两路分数量纲不可比的问题，这是它成为
混合检索默认融合方案的原因。**

## Why

精确词命中靠关键词、换说法的问题靠向量——单路检索总有一类查询失明。
但混合检索不是免费午餐：融合效果依赖两路召回互补。值不值、什么语料下
拉开差距，要同语料对跑。

## How

```bash
cd qa/10_hybrid_retrieval
MOCK=1 python3 hybrid_retrieval.py    # 离线: hash 向量 (链路验证)
python3 hybrid_retrieval.py           # 真实: nomic-embed-text
```

实测（nomic-embed-text）：

| 检索器 | 精确词 | 语义改写 | 混合 | overall |
|:--|:--:|:--:|:--:|:--:|
| BM25 | **5/5** | 2/5 | **4/5** | 11/15 |
| Vector | 5/5 | **3/5** | 1/5 | 9/15 |
| RRF | 5/5 | 2/5 | 4/5 | 11/15 |

诚实解读：本语料（短文档 + 中文二元组分词）下 RRF 与 BM25 打平、未拉开
差距——RRF 的收益依赖两路召回互补（向量路要能捞回 BM25 漏掉的语义
改写，本组实测只捞回 1 条）。语料越长、查询改写越激进，向量路与 RRF 的
优势越明显；精确词类两路都全对，RRF 不会拖后腿。

## Deep Dive

**RRF 为什么只看排名不看分数**：BM25 分数与余弦相似度量纲完全不可比，
直接加权融合等于拍系数；排名是两路唯一天然可比的量。代价是丢弃了分数
的置信信息——两路都给高排名时与只给一路时区分度不够。

## Q&A

**Q1: 生产上怎么选？**

默认两路召回 + RRF 融合；评测用 Hit@k/MRR 驱动 chunking 与 k 的调参，
而不是凭感觉。语料短、查询不改写时 BM25 单路可能就够——先测再上。

**Q2: 什么时候向量路收益最大？**

语料长、查询改写激进（用户不按文档原文提问）的场景——本组短语料只
捞回 1 条，说明向量路收益要靠语料与查询形态养。
