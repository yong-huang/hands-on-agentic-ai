# 10 · 混合检索（向量 + 关键词 + RRF）

> 本项目在 50 条文档的小语料上，用 15 条查询对跑三种检索器（BM25 / 向量 / RRF 融合），按查询类别统计命中率。读完你能说清每条检索路线各自的失明区，以及 RRF 为什么用"只看排名"的公式做融合。

## Background

在混合检索出现之前，检索系统通常只跑一条路线：要么关键词检索（按字面词匹配，底座是倒排索引——把每个词映射到包含它的文档列表），要么向量检索（把文本编码成语义向量，按向量相似度找近邻）。选哪条，往往凭经验拍板。

单路方案各有一类必输的查询。用户查"BM25 的 k1 和 b 参数"这类精确词时，关键词路轻松命中，向量路对精确字词却不敏感；用户问"数据库为什么越跑越卡"而文档写的是"索引膨胀与慢查询堆积"时，字面零重叠，关键词路直接失明，向量路反而能配上。

于是出现两路都跑、再合并排名的混合检索：精确词交给关键词路，语义改写交给向量路，用一条统一公式把两份排名合成一份。本实验实现的就是最常用的融合公式 RRF，并同语料对跑三种检索器验证各自的表现。

## What

混合检索是同时运行多路检索器、再把各自排名融合成单一排序的检索方案，用来对冲单路的失明区（各自检索不到的那一类查询）：

| 检索器 | 擅长 | 失明区 |
|:--|:--|:--|
| BM25 | 精确词（型号/报错码/专名） | 语义改写（字面零重叠） |
| Vector | 语义改写 | 精确 token 不敏感 |
| RRF 融合 | 两路排名合并 | 依赖两路召回互补 |

表中术语解释：BM25 是基于词频与逆文档频率的关键词检索算法（词频指词在文档中出现的次数，逆文档频率指越稀有的词权重越高）；token 指最小文本单位，这里泛指型号、报错码一类的精确字词；RRF（Reciprocal Rank Fusion，倒数排名融合）是合并多份排名的公式；召回指检索器返回的候选结果。

RRF 一条公式：score(d) = Σ 1/(60 + rank_i(d))——只看排名不看分数。

可以把 RRF 想象成两位评委各按自己的标准给选手排序，最后只按名次合并、不问各自打了多少分。但融合有效有一个前提：两位评委的盲区要互补——若两路总是给出同一份名单，合并不会带来任何新信息。

心智模型一句话：**RRF 天然规避两路分数量纲不可比的问题，这是它成为混合检索默认融合方案的原因。**

## When to Use

- **文档库含大量精确标识符的检索/RAG 系统**：API 名、报错码、型号必须字面命中，同时用户提问又会换说法——单路必有一类查询失明；
- **查询措辞不可控的客服与搜索入口**：用户不按文档原文提问，语义路是兜底；
- **原型验证阶段**：先用 BM25 单路测基线，确认语义改写类查询确实流失，再上第二路。

何时不用：语料很短、查询基本照抄文档原文的内部工具，BM25 单路可能就够；两路融合多一倍检索开销与一套融合参数，先测再上。

| 方案 | 与本篇方案的差异 | 什么时候选它 |
|:--|:--|:--|
| BM25 单路 | 只按字面匹配 | 查询与文档措辞一致、语料小 |
| 向量单路 | 只按语义匹配 | 查询改写多、无精确词要求 |
| 两路 + RRF（本篇） | 排名融合，兼顾两路 | 生产默认起点，类别混杂的查询 |
| 两路 + RRF + rerank | 融合后再用重排模型精算候选 | 精度要求高、可接受额外延迟 |

表中 rerank 指重排模型（对候选逐对精算相关度的交叉编码器，精度高但慢，只对头部候选打分）。

## Quick Start

前置条件：Python 3；真实模式需要本地模型服务提供 embeddings 接口（embedding 即把文本编码成的一串数字构成的语义向量，模型用 nomic-embed-text）；`MOCK=1` 离线模式向量退化为 hash 词袋（按字面词拼的向量，仅验证链路，不反映检索质量）。

```bash
cd qa/10_hybrid_retrieval
MOCK=1 python3 hybrid_retrieval.py    # 离线: hash 向量 (链路验证)
python3 hybrid_retrieval.py           # 真实: nomic-embed-text
```

实测（nomic-embed-text，指标 Hit@3：目标文档出现在前 3 名即算命中）：

| 检索器 | 精确词 | 语义改写 | 混合 | overall |
|:--|:--:|:--:|:--:|:--:|
| BM25 | **5/5** | 2/5 | **4/5** | 11/15 |
| Vector | 5/5 | **3/5** | 1/5 | 9/15 |
| RRF | 5/5 | 2/5 | 4/5 | 11/15 |

诚实解读：本语料（短文档 + 中文二元组分词）下 RRF 与 BM25 打平、未拉开差距——RRF 的收益依赖两路召回互补（向量路要能捞回 BM25 漏掉的语义改写，本组实测只捞回 1 条）。语料越长、查询改写越激进，向量路与 RRF 的优势越明显；精确词类两路都全对，RRF 不会拖后腿。

## How It Works

三路检索器共用同一份语料与查询，按 Hit@3 评测。

**BM25 路**按字面匹配打分：词越稀有（IDF 高）、在文档里出现越多，得分越高，k1=1.5 控制词频饱和、b=0.75 做长度归一。中文没有空格分词，代码把句子切成二元组（"混合检索"切成"混合""合检""检索"）做匹配单元。

**向量路**把查询和全部文档都编码成 embedding，按余弦相似度（两向量方向的一致程度）排序取前 3。

**RRF 路**拿前两路的前 3 名列表做融合，核心代码只有几行：

```python
def rrf_fuse(rank_lists, k=3):
    """Reciprocal Rank Fusion: score(d) = Σ 1/(RRF_K + rank_i(d))"""
    fused = {}
    for ranks in rank_lists:
        for r, d in enumerate(ranks):
            fused[d] = fused.get(d, 0) + 1 / (RRF_K + r + 1)
    return [d for d, _ in sorted(fused.items(), key=lambda x: -x[1])[:k]]
```

**RRF 为什么只看排名不看分数**：BM25 分数与余弦相似度量纲（计分的单位和尺度）完全不可比，直接加权融合等于拍系数；排名是两路唯一天然可比的量。代价是丢弃了分数的置信信息——两路都给高排名时与只给一路时区分度不够。

输出日志印证了这两点。`RRF✓ (BM25 目标排名 1 / Vec 2)` 这类行：两路都把目标排进前 3，RRF 累加后稳居第一。

而"机器人答不上来用户的怪问题时咋办"一行是 `RRF✗ (BM25 目标排名 - / Vec 2)`：目标只在向量路排第 2，只贡献一次 1/(60+2)；另一个两路都进前 3 的文档分数累加更高，把目标挤出了前 3——这就是丢弃置信信息的代价。

## Pitfalls & Q&A

- **现象：离线模式检索结果与真实模式差异大。** 原因：`MOCK=1` 的 hash 词袋只认字面，语义能力为零，只用于验证链路能跑通。解法：评检索质量必须用真实 embedding。
- **现象：中文查询整句匹配零命中。** 原因：中文无空格分词，整句当词则词频统计全失真。解法：如代码所示切二元组，或引入正式分词器（把句子切成词的工具）。

**Q: 生产上怎么选？**

默认两路召回 + RRF 融合；评测用 Hit@k/MRR（检索评测指标，看目标文档排在第几位）驱动 chunking（长文档切块策略）与 k 的调参，而不是凭感觉。语料短、查询不改写时 BM25 单路可能就够——先测再上。

**Q: 什么时候向量路收益最大？**

语料长、查询改写激进（用户不按文档原文提问）的场景——本组短语料只捞回 1 条，说明向量路收益要靠语料与查询形态养。
