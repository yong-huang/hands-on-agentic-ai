# 11 · Reflection 反思机制

> 本项目在客服场景（9 条事件记忆）上对照"有无 Reflection"的回答质量：每 3 条记忆把近期流水账蒸馏成高层洞察再入库，用同一模糊问题考两个版本。读完你能判断自己的系统该不该上 Reflection——本实验的真机结果是负增益。

## Background

没有 Reflection 时，智能体的记忆库只存原始事件流水账：用户说了什么、客服做了什么，一条一条按时间堆。检索时原样取回若干条，拼进上下文。

流水账条目一多就互相淹没：客服系统跑一个月，关于同一用户的事件可能有几百条，检索只取回几条，剩下的大量上下文里的规律（这位客户吃软不吃硬、优惠券对 TA 无效）散落在没被取回的条目里。而"我现在该怎么办"这类模糊问题需要的恰恰是归纳结论，不是事件罗列。

Generative Agents（斯坦福 2023 年提出的智能体架构，模拟小镇居民的记忆与社会行为）为此引入反思环节：周期性把近期记忆归纳成高层洞察（insight，从多条事件提炼的结论性知识），与原始记忆一起参与检索。本实验把这套机制在客服场景上实现出来，并实测它的适用边界。

## What

Reflection 是一种记忆反思机制：周期性触发，把近期原始记忆蒸馏成高层洞察入库，让洞察与原始记忆同池竞争检索。机制三要素：

- **触发器**：每累计 N 条记忆反思一次，流水账蒸馏为高层洞察；
- **打分**：重要性 × 新近性（指数衰减）决定检索权重；洞察与原始记忆同池竞争——分层而非替换；
- **价值边界**：原始记忆回答"发生过什么"，洞察回答"客户是谁、什么有效"。

两个术语先解释：重要性是给每条记忆打的 1-10 关键度分；新近性按指数衰减计算，半衰期（分数衰减到一半所需的时间）设 72 小时——1 天前的记忆新近分约 0.79，3 天前约 0.5。

可以把 Reflection 想象成记忆的蒸馏器，把流水账原液蒸出精华。但和化学蒸馏不同的是，蒸馏本身要花一次 LLM（大语言模型）调用，还可能蒸出杂质（归纳出跑题的空泛结论）；原液太少时也没东西可蒸。

心智模型一句话：**Reflection 是记忆的蒸馏器——但蒸馏只在原液太多时才有价值。**

## When to Use

- **长期客服/销售助手**：事件流水长，需要回答"这位客户是谁、什么方案对他无效"这类跨事件归纳问题；
- **模糊决策类提问为主的场景**：用户问"我现在该怎么办"，回答质量取决于能否把多条事件收拢成一个行动建议；
- **模型归纳能力弱的系统**：模型较难从原始记忆自发归纳时，预蒸馏的洞察才有检索价值。

何时不用：强模型 + 少量记忆（本实验的反例场景，见 Quick Start 的实测）；一次性事实问答（"订单到哪了"）用不到跨事件归纳。

| 方案 | 与本篇方案的差异 | 什么时候选它 |
|:--|:--|:--|
| 全量塞上下文 | 不检索不蒸馏，全部记忆进 prompt | 记忆极少（十几条以内） |
| 只检索原始记忆 | 无蒸馏环节 | 强模型 + 少量记忆，本实验基线 |
| 原始 + 洞察同池（本篇） | 周期蒸馏，分层竞争 | 记忆量大、弱模型、模糊提问多 |
| 人工维护要点 | 人写客户画像替代自动归纳 | 高价值客户、量小可控 |

## Quick Start

前置条件：Python 3；离线模式（`MOCK=1`）用预置的洞察与模板回答复现同一对照（即诚实结论中的"抽取式基线"），无外部依赖；真实模式需要模型服务在线（qwen3.8 做反思、作答与评分）。

```bash
cd qa/11_reflection
MOCK=1 python3 reflection.py    # 离线: 预置洞察与回答 (引用 0 vs 2, 2.0 vs 4.4)
python3 reflection.py           # 真实: qwen3.8 做反思、作答与评分
```

真机实测出现**反常**：无 Reflection 版 4.0 分（回答主动覆盖电话偏好 + VIP 身份，洞察引用 2/2）；有 Reflection 版 3.0 分（引用 1，且倾向元分析式跑题——先长篇分析"为什么"，迟迟不落到行动）。两轮测量稳定（-4.0 → 修复 Judge 解析后 -1.0）。

诚实结论：**qwen3.8 这类强模型 + 少量记忆的场景下，原始记忆已足够支撑高质量回答，Reflection 无增益甚至负增益**——洞察上下文反而诱发模型"先分析再行动"的跑题。离线模式用抽取式基线（0 引用/2.0 分 vs 2 引用/4.4 分）复现了机制的理想收益。

两个评测指标先说明：Judge 指 LLM-as-Judge（用一个 LLM 按评分标准（rubric）给另一个 LLM 的输出打 1-5 分）；引用计数看回答是否用上了"电话偏好""VIP/优惠券无效"这两条关键洞察，达标线 ≥2。

## How It Works

实验的记忆池是 9 条客服事件（用户来电、查询物流、发优惠券……），每条带重要性分和距现在的小时数。每累计 3 条触发一次反思，由 LLM 归纳一条洞察并自评重要性：

```python
r = extract_json(http_chat([{"role": "user", "content":
    f"以下是客服会话的近期记忆:\n{recent}\n\n"
    "归纳出 1 条高层洞察(客户是谁/核心诉求/什么有效什么无效), "
    '并打重要性分 1-10。只输出 JSON: {"insight": "...", "importance": 8}'}]))
```

打分公式是 `重要性 × 0.5^(小时数/72)`：重要性是 1-10 的整数，新近性按 72 小时半衰期指数衰减。检索时洞察与原始记忆放进同一个池子按这个分排序，取前 4 条拼上下文——不是用洞察替换原始记忆，而是分层共存：

```python
pool = [(m[1] * recency_score(m[2]), f"[原始] {m[0]}") for m in memories]
pool += [(ins["importance"] * recency_score(h), f"[洞察] {ins['insight']}")
         for ins, h in insights]
pool.sort(key=lambda x: -x[0])
```

真机日志印证了同池竞争：模式 B 的最终上下文是 2 条 [原始] + 2 条 [洞察]——高重要性的洞察（imp=8）挤掉了两条较旧的原始事件；模式 A 的 Top4 则全是原始记忆。

两种模式的回答随后交给同一个 Judge 评分，并统计洞察引用数——日志里"洞察引用达标(≥2): ✗   质量提升: -1.0"就是汇总行。

洞察引用计数是刻意设计的行为指标：它数的是回答里有没有真的用到关键洞察（提到"电话""VIP/优惠券"各算一次），比 Judge 的主观分更硬。

## Pitfalls & Q&A

- **现象：有洞察反而答跑题。** 原因：洞察上下文诱发模型"先分析再行动"——真机模式 B 的回答开头是大段动机分析。解法：在指令里限定"直接给可执行动作，不要分析"，或只在弱模型场景启用洞察注入。
- **现象：Judge 打出 0 分或解析失败。** 原因：Judge 模型没按要求输出 JSON。解法：如代码所做，正则兜底提取分数；本实验两轮测量的分差（-4.0 → -1.0）正来自修复 Judge 解析。
- **现象：某次反思产出为空。** 原因：LLM 归纳失败或 JSON 解析失败。解法：降级策略——返回"(反思失败, 保留原始记忆)"并给低重要性分（代码里 imp=3），不让失败反思污染检索。

**Q: 什么时候该上 Reflection？**

两个前提满足其一：记忆量大到原始条目互相淹没，或模型较难自发归纳。都不满足时，洞察上下文反而诱发"先分析再行动"式跑题——先测再上。
