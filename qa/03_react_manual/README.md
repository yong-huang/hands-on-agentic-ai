# 03 · 手写 ReAct 循环

> 纯手写不用框架的 ReAct（Thought-Action-Observation）：calculator + mock
> 天气两工具，JSON 解析失败重试、工具异常转 Observation 喂回。真机下
> 5 个多步任务全部正确，含一条"失败→自愈"轨迹。读完本篇，你能理解
> Agent 循环的每一行控制逻辑，并能自己写出容错版。

## Background

最常见的做法是单次提问：把问题发给模型，直接拿回答案。模型答题只能靠
训练时记住的知识，遇到"北京今天的气温乘以 3"这类问题就会出状况——
今天的气温不在它的知识里，让它心算乘法还容易算错；有的开发者转而写死
固定流水线：先调天气接口，再把结果塞进计算器。

固定流水线在步骤可预知的任务上够用，但开放任务会撞墙。"气温乘以 3"
要先查天气、看到数值后才知道要算什么，而更复杂的任务可能查一次不够、
要不要再查取决于上一步的结果——调用次数事先无法写死。

另外，模型在缺数据时倾向于编造一个看起来合理的数字（即幻觉问题），
固定流水线对此没有任何防御。

2022 年的研究论文给出了一种解法：让模型"想一步、做一步、看一步结果"
地循环，每一步动作和依据都摆在明面上。本篇不用任何框架，把这个循环
完整手写一遍。

## What

ReAct（Reasoning + Acting 的合成词，源自 2022 年的同名论文）是一种
智能体模式。

智能体（Agent，能自主决定"调用哪个工具、何时停止"来完成目标的程序）
每轮输出一个 JSON 决策，包含三部分：Thought（这一步该做什么的推理）、
Action（调用哪个工具）、Observation（工具返回的结果），循环直到模型
主动输出 Answer。

本篇不用任何框架，约 160 行手写完整循环。心智模型一句话：**每个结论
都必须有工具 Observation 支撑——不凭空生成。** 可以把 ReAct 想象成
"做题时翻工具书的学生"：先想清楚要查什么，翻一次书，把查到的数字抄在
草稿纸上，凑齐了才写答案。

但和学生不同的是，模型可能把决策写成不合法的格式、也可能把工具用错，
所以循环必须自带重试与兜底逻辑——这正是本篇手写的部分。

以"北京今天的气温乘以 3 是多少"为例，一轮完整循环是：查天气
（get_weather 返回"晴 28°C"）→ 把 28 交给计算器（calculator 算出 84）
→ 输出 finish。三次决策，每次都有 Observation 撑腰。

## When to Use

在开发需要模型"动手"而不是"动嘴"的功能时，ReAct 适合三类任务：

- 答案依赖实时或私有数据的问答——天气、库存、数据库里的数字；
- 需要精确计算的结果——乘除、单位换算，交给计算器而不是模型心算；
- 步骤数事先未知的开放任务——先查再看，查几次由模型边走边定。

何时不用：静态知识问答（单次提问更省）；步骤完全固定的常规业务
（写死流水线更可控）；对延迟敏感的场景（每一步都是一次模型调用，
多步任务耗时线性增长）。

| 方案 | 差异 | 什么时候选它 |
| :--- | :--- | :--- |
| 单次提问 | 无工具，靠模型内部知识 | 静态知识问答 |
| 固定流水线 | 人工写死调用顺序 | 步骤固定的常规业务 |
| 手写 ReAct（本篇） | 循环、容错逻辑全部自己实现，行为可复现 | 学习原理；需要精细控制每一步 |
| 框架 Agent（LangChain 等） | 现成的循环与工具生态 | 快速搭功能原型 |
| Function Calling（见 05 项目） | 模型 API 原生输出结构化工具调用 | 生产环境且模型支持该接口 |

MOCK 模式（用预置回答替代真实模型调用的离线运行方式）按预置脚本走一遍

答案数值以工具返回为准，逐行 trace（执行轨迹，程序打印的逐步记录）
可核对每个结论的来源。

## How It Works

循环由四段逻辑组成，按一轮的执行顺序展开：

1. **约定输出格式。** 系统提示词要求模型每轮只输出一个 JSON 决策：
   `{"thought": ..., "action": "工具名或 finish", "input": {...}}`，
   能回答时 action 取 `finish`。格式统一后，循环才有稳定的解析对象。
2. **解析与重试。** 用正则（正则表达式，按模式匹配文本的工具）截出
   `{...}` 段再做 `json.loads`（两级回退：先容错模型在 JSON 外多说的
   解释文字，仍失败返回 None）。解析失败不抛异常，而是把原始输出连同
   "请重新输出合法 JSON"追加回对话后重试——真实运行里模型输出不合法
   JSON 时出现的"⚠ JSON 解析失败，回喂重试"就来自这个分支。
3. **执行工具并回喂。** 最核心的一段（节选，缩进保持源码原样）：

```python
        try:
            observation = tool_fn(**tool_input) if tool_fn else f"未知工具: {tool_name}"
        except Exception as e:
            observation = f"工具异常: {e}"
        trace.append(f"  [step {step}] {tool_name}({tool_input}) -> {observation}")
        messages.append({"role": "assistant", "content": json.dumps(decision, ensure_ascii=False)})
        messages.append({"role": "user", "content": f"Observation: {observation}"})
```

   异常不向上抛、也不静默吞掉，而是转成 Observation 字符串喂回模型——
   这就是"失败→自愈"的来源：模型读到"计算错误"后自行换一种输入。
4. **终止与兜底。** action 为 `finish` 时取出 answer 返回；循环最多
   走 `MAX_STEPS = 6` 轮，防止模型反复调工具不停，超限时返回
   "（达到最大步数）"。

## Pitfalls & Q&A

踩坑清单：

- **现象：`json.loads` 报错，循环中断。** 原因：模型常在 JSON 前后
  附带解释文字。解法：先用正则截取大括号段再解析；仍失败就回喂错误
  重试，不要直接崩。
- **现象：计算器收到 `abc*3` 这类输入直接抛异常。** 原因：工具输入
  来自模型，不可信。解法：`try/except` 把异常转成"计算错误: …"回喂，
  让模型自纠（对应输出里的自愈轨迹）。
- **现象：模型反复调用同一个工具，循环不结束。** 原因：没有终止条件
  时模型可能陷入重复决策。解法：`MAX_STEPS` 兜底，超限返回占位答案。

**Q: ReAct 真的解决了幻觉吗？**

每个结论都有工具 Observation 支撑——模型只能基于真实工具输出作答，
而非凭空生成，5 个任务的答案都能在 trace 里指认来源。

但它没有根除幻觉：Observation 只约束"有工具支撑的结论"，工具本身
返回假数据（如本篇的 mock 天气）时，Agent 会照单全收。可靠性等于
循环纪律乘以工具数据的质量。
