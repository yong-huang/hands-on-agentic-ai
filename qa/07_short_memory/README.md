# 07 · 短期记忆管理器（窗口 + 摘要压缩）

> 本项目用 20 轮长对话实证一个问题：对话历史超出模型上下文窗口时，滑动窗口与摘要压缩两种策略各丢什么、丢多少。读完你能按"丢得起哪种"为自己的应用选对策略，并看懂两种丢失在代码里如何发生。

## Background

在专门的记忆管理出现之前，最常见的做法是把对话历史原样全量拼接，每次请求都完整发给模型。对话只有三五轮时，这样做没有任何问题。

痛点出现在对话变长之后。模型一次能读入的文本量有硬上限，即上下文窗口（按 token 计量，token 是模型计算文本长度的基本单位，约对应半个到一个汉字）。20 轮对话就可能触顶。

触顶后只有两条路：请求直接报错，或者先裁掉一部分历史再发。而裁掉的早期消息里，可能就有用户在第 1 轮说过的姓名、预算这类关键约束——模型到第 20 轮还在被问起它们。

于是出现两类"超限怎么办"的策略：一类机械地丢最旧消息，另一类让 LLM（大语言模型）把旧对话归纳成摘要再发。两者丢的信息完全不同，本项目把两种做法各跑一遍，用保留率把差异量化成可复现的数字。

## What

上下文窗口放不下 20 轮对话时的两种超限策略：

- **滑动窗口**：只留最近 N 轮，旧的直接丢——零成本、可预测，但"最近的才存在"，早期事实整段蒸发；
- **摘要压缩**：LLM 把旧对话归纳成摘要——保留语义骨架（对话的大意与结论，而非原文），但细节（数字/日期/专名，即人名、地名等专有名词）最易被抹平，且每次压缩多一次 LLM 调用与延迟。

可以把滑动窗口想象成一块只写得下几行的白板，写满就擦掉最旧的几行；但和真白板不同的是，被擦掉的对话没有任何备份，对模型而言是永久消失。

可以把摘要压缩想象成会议纪要：原文不在了，要点还在。但和人工纪要不同的是，LLM 可能漏掉它自己没意识到重要的细节——数字、日期、人名最危险。

实验用保留率量化两种丢失：对话前几轮（按轮次编号记作 T1、T2……）埋 5 个关键事实（姓名/城市/截止日/预算/咖啡偏好），第 20 轮向模型提问这 5 个事实，统计答对几条。

预算收紧到 350 est.tokens（est 表示估算 token，代码按字符数近似折算），使 20 轮必然多次溢出（窗口截断 5 次 / 摘要压缩 1 次均真实触发）。

心智模型一句话：**窗口确定性丢早期，摘要不可预测地丢细节——选哪种，取决于你丢不起哪种。**

## When to Use

- **客服/陪聊类长会话**：用户聊了几十轮，早期只需要"用户是谁、想要什么"的大意——摘要压缩合适，丢点措辞无所谓；
- **任务执行类会话**：用户在第 1 轮给了预算、截止日，第 20 轮还要按它执行——早期事实丢不起，要么换大窗口全量塞，要么把关键事实写进外部存储按需检索（见 08 项目）；
- **原型阶段或对话很短**：会话长度可控且离窗口上限还远时，加记忆管理是纯开销，全量塞最简单也最不容易出错。

| 方案 | 与本篇策略的差异 | 什么时候选它 |
|:--|:--|:--|
| 全量保留 | 不做任何裁剪 | 对话短、预算充足，最简单可靠 |
| 滑动窗口 | 机械丢最旧，零 LLM 调用 | 只有近期对话有效，早期内容可弃 |
| 摘要压缩 | LLM 归纳旧对话，多一次调用与延迟 | 对话很长，早期只需大意 |
| 三层组合 | 窗口 + 摘要 + 外部记忆库 | 生产长对话，既要近期原文又要远期事实 |

## Quick Start

前置条件：Python 3，目录内已有模型配置 `../llm.py`（真实模式需要模型服务在线）；`MOCK=1` 离线模式无外部依赖。

|:--|:--:|:--:|

| 城市(T1) | ✗ | ✓ |
| 截止日(T2) | ✗ | ✓ |

## How It Works

两种策略挂在同一个钩子上：`add_turn` 每追加一轮对话就累计全缓冲区的 token 量，超预算就调用对应策略修剪，循环直到装得下。

策略 A 的核心是 `sliding_window`。它固定保留 system 消息（设定模型行为的固定指令），对对话消息从最新往回装，装不下就停，剩下的旧消息整段丢弃：

```python
def sliding_window(messages, budget, log):
    """策略 A: 从最旧开始丢, 直到装得下。早期事实整段消失。"""
    sys_msg, rest = messages[0], messages[1:]
    kept, used = [], est_tokens(sys_msg["content"])
    for m in reversed(rest):
        t = est_tokens(m["content"])
        if used + t > budget:
            break
        kept.insert(0, m)
        used += t
    dropped = len(rest) - len(kept)
    if dropped:
        log.append(f"窗口截断: 丢弃最旧 {dropped} 条消息")
    return [sys_msg] + kept
```

"从最新往回装"是关键：`reversed(rest)` 保证最近的对话优先占用预算，最旧的先出局。你在实测表里看到的"姓名/城市/截止日/预算全 ✗"，就是 T1/T2 的消息被 5 次窗口截断丢光、模型根本没见过的结果。

策略 B 的核心是 `summarize_compress`。超限时它把最旧的 60% 对话交给 LLM 压成一条摘要，最近 40% 保留原文（真机分支）：

```python
old = messages[1:1 + int((len(messages) - 1) * 0.6)]
text = "\n".join(f"{m['role']}: {m['content']}" for m in old)
summary = llm([{"role": "user", "content":
                "把以下对话压缩成一条要点摘要, 必须保留用户的姓名/城市/日期/数字等"
                f"关键信息, 100 字以内:\n{text}"}], num_predict=200)
summary = f"[历史摘要] {summary}"
```

提示词里"必须保留数字"不是装饰：LLM 压缩时最先牺牲的是它判定为次要的内容，数字、日期、专名最危险。真机保留 5/5 说明这类强约束能把下限拉高，但代价是每次压缩多一次 LLM 调用与延迟，且失败模式从"确定性丢失"变成"不可预测的漏记"。

这个失败模式的性质差异比保留率数字更重要：窗口的丢失是确定性的——你知道哪些轮次一定没了，可以针对性补救；摘要的丢失是概率性的——哪条细节被抹平不可预测，无法在事前兜底。生产系统必须按"丢得起哪种"来选。

`add_turn` 里还有一道防御：摘要本身也占 token，压完可能仍超限；代码检查修剪后体积若没有变小，就退回 `sliding_window` 硬截断并终止循环。

## Pitfalls & Q&A

- **现象：加了摘要压缩，某条数字还是答不出。** 原因：LLM 摘要是概率性生成，提示词只能拉高下限，保证不了每条细节。解法：不可丢的关键事实在对话当时就抽取进外部存储，不指望摘要兜底。
- **现象：token 计数与模型方报数对不上。** 原因：实验用字符数近似估算（`est_tokens`，中文约 0.6 token/字符）。解法：生产换 tiktoken（常用的精确分词计数库）精确计数。
- **现象：超限修剪后循环不退出。** 原因：摘要自身占 token，压完仍可能超限。解法：保留代码里的防御分支——体积没变小就硬截断。

**Q: 生产上怎么组合？**

组合拳：窗口保近期原文 + 摘要保远期骨架 + 关键事实抽取进长期记忆库（[08 长期记忆](../08_long_memory/README.md)）按需检索——三层各管一段。
