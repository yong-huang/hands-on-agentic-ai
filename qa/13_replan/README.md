# 13 · 规划失败检测与重规划

> 多步任务管线（按固定顺序依次执行的一串步骤）里的失败不是一种东西：服务瞬断
> 重试即可，库存无货要换方案，预算写错得重排计划。读完本篇你能获得：一套
> "先分类失败、再选择响应"的处置框架（RETRY / ALTERNATIVE / REPLAN），
> 以及用两层校验抓住"假成功"的实践方法。

## Background

在失败分类出现之前，自动化脚本遇到错误通常只有两种固定做法：要么直接崩溃
退出，把报错丢给查看日志的人；要么不区分原因，对所有失败统一重试若干次。

在多步任务里，这两种做法都会撞墙。以组织一次团建为例：管线要依次订场地、
订车、订餐厅。"20 座大巴无货"不是瞬时故障，重试一百次依然无货；"餐厅预算
3000 超过剩余额度 2000"是计划本身的错，重试只会把超额订单原样再提交几遍。

于是失败处理从"固定策略"演进为"先诊断、再开方"：每步执行后先校验结果，
把失败按原因分类，再分别选择重试、换路径或重排计划。其中"重排计划"这一步
就是重规划（replanning），它已成为 agent（能自主调用工具、分步完成任务的
程序）工程中执行长任务的标准环节。

## What

本实验的主题是规划失败检测与重规划：agent 在执行多步计划时对每步结果做
校验，把失败按原因分成三类，每类对应一种固定响应；当部分前提失效或计划
本身有错时，只重排受影响的剩余子目标（计划中尚未执行的组成步骤），
而不是从头再来。

三类失败与三种响应的对应关系：

| 失败类型 | 例子 | 响应 |
|:--|:--|:--|
| 工具瞬断 | 查询 504 | RETRY 重试 |
| 前提失效 | 20 座大巴无货 | ALTERNATIVE 改路 |
| 规划错误 | 预算超额 | REPLAN 全局重排 |

心智模型一句话：**一律重试会把错误计划执行三遍——先分类，再响应。**

可以把这套机制想象成机场地勤调度：航班延误时，调度员先看原因——雷雨
过境就等一等再起飞（重试），飞机故障就换一架（换路径），航线被空管否了
就重新排航线（重规划）。

但和地勤调度不同的是，agent 里的判断依据不是经验直觉，而是预先写好的
错误签名（error signature，即报错信息的特征模式，如 `504`、
`无可用车型`）匹配规则。

## When to Use

典型场景一：让 agent 跑多步预订、下单类任务（订会议室、订车、采购）时，
中间步骤依赖外部服务的实时状态，失败不可避免且原因多样。

典型场景二：长链路任务中已完成步骤代价高或不可重复（已付款、已发通知）
时，不能整体重跑，只能定点恢复或重排剩余部分。

典型场景三：批处理或无人值守运行时，失败必须自动处置，不能每个失败都
停下来等人。

何时不用：单步脚本失败后直接报错给人看更省事；失败类型单一（只有网络
超时）时，固定重试加退避就够；结果可以随意丢弃重跑的小任务，一个
"失败就重来"的循环更简单。

| 方案 | 差异 | 什么时候选它 |
|:--|:--|:--|
| 一律重试 | 不区分原因，所有失败重试 N 次 | 失败几乎都是瞬时抖动时 |
| 失败分类 + 定点响应（本实验） | 按错误签名分类到 RETRY / ALTERNATIVE / REPLAN | 多步管线、失败原因多样的长任务 |
| 断点续跑（见 31 项目） | 从上次保存的进度恢复执行 | 进程中断后恢复，而非单步失败 |
| 人工介入 | 失败即暂停，等人决策 | 失败罕见或决策代价极高时 |

## Quick Start

前置条件：Python 3，无额外依赖。运行方式与两种模式：

```bash
cd qa/13_replan
MOCK=1 python3 replan.py    # 离线: 注入故障全规则处置
python3 replan.py           # 真实: 追加 LLM 失败分类对照
```

`MOCK=1` 表示离线模式：管线注入 3 类失败各 1 次，全部由规则处置。不带
`MOCK=1` 直接运行会追加真实 LLM（大语言模型）分类对照。

诚实预期：实测三类失败分别走对 重试/改路/重规划，管线最终完成 ✓；
真机 LLM 分类器对 3 个失败样例与规则判定 3/3 一致（504→RETRY、
无货→ALTERNATIVE、超额→REPLAN）。

决策轨迹（节选）：

```
[step 2] 订场地 -> ERROR: 504  ✗ 分类=RETRY
         ↳ 响应[重试] 第 2 次尝试 -> 湖畔厅预订成功 ¥1200 ✓
[step 3] 订 20 座大巴 -> ERROR: 无可用车型 ✗ 分类=ALTERNATIVE
         ↳ 响应[改路] -> 10 座中巴 ×2 ¥800 ✓
[step 4] 订餐厅 ¥3000 -> WARNING 超剩余额度 ✗ 分类=REPLAN
         ↳ 响应[重规划] 剩余计划改为 餐厅¥1800 -> 预算重算 ✓
```

三条轨迹分别对应三类失败：504（HTTP 状态码，网关超时）在第 2 次尝试后
成功；无货改订 2 辆 10 座中巴；超额则把餐厅预算从 3000 重排为 1800。

## How It Works

这套机制的执行顺序是：执行一步 → 校验结果 → 按错误签名分类 → 分发到
对应响应。下面按这条链展开。

**先校验再行动**：断言式校验器（每步执行后用明确断言检查结果的代码）分
两层。第一层查结果形状——返回的是 ERROR 还是正常数据；第二层查语义——
表面成功但违反任务约束的情况。第三类失败最隐蔽，专抓"假成功"。

与 Quick Start 的输出互相印证：step 2 的 `ERROR: 504` 是形状层抓出的
瞬断，分类为 RETRY 后第 2 次尝试成功；而 step 4 的餐厅预订没有报
ERROR，是语义层对照剩余额度发现的违规，所以标记为 WARNING——同一个
分类入口，两层校验器各自贡献了一类失败。

**分类后的三种响应**：RETRY 原样再试，等瞬时故障过去；ALTERNATIVE 换
一条等效路径，如 20 座大巴 ×1 换成 10 座中巴 ×2；REPLAN 触发全局重排，
如餐厅预算从 3000 改为 1800 并重算预算。

**重规划 ≠ 从头再来**：只重排受影响的剩余子目标，已完成结果复用
（场地 1200、中巴 800 都保留，只动餐厅一项）。这与
[31 断点续跑](../31_checkpoint_resume/README.md)是同一思想。

## Pitfalls & Q&A

**坑 1：只做形状校验，"假成功"漏网。** 现象：餐厅订到了、预算爆了，管线
却以为一切正常继续往下走。原因：工具返回的是正常响应，形状层完全放行。
解法：加语义校验层，对照任务约束（如剩余预算）写断言。

**坑 2：对所有失败一律重试。** 现象：无货类失败重试多次，轮次耗光仍未
解决。原因：前提失效不是瞬时的，重试不改变结果。解法：先按错误签名
分类，只对瞬断类失败重试。

**Q：规则分类器和 LLM 分类器什么关系？**

规则分类器按错误签名确定性分类，是默认路径；LLM 分类器处理规则覆盖不到
的模糊失败。本实验真机对照 3/3 一致，说明在这三类边界场景下两者可互为
校验。
