# 01 · CoT 三态对比实验（Zero / Few / Auto-CoT vs 直接回答）

> 同一题集、同一评分、四种回答模式（direct / Zero-shot CoT / Few-shot CoT /
> Auto-CoT）的正确率对比——并得到一个诚实的负结果：**强模型 + 简单题会让
> 四种模式全部饱和**，CoT 的差异化要在更难的题上才显形（见 MOCK 对照）。

## What

CoT（Chain-of-Thought）让模型把多步推理显式化为中间 token，再给出最终
答案。三种变体的差别只在提示词：

| 模式 | 提示词 | 示例来源 |
| :--- | :--- | :--- |
| direct | "直接给出答案，只输出一个数字" | —— |
| zero_cot | "请一步步思考再回答，最后以'答案: 数字'结尾" | —— |
| few_cot | 3 个人工编写的带推理示例 | 人工 |
| auto_cot | 按固定步长取样 3 道代表题，让模型自产推理链示例 | **数据自产** |

实验自建 20 道数学题（10 单步 + 10 两步），评分从回答中提取最终数值
（优先"答案: X"，否则取最后一个数字）与标准答案精确匹配——CoT 的增益
理论上集中在两步题。

心智模型一句话：**CoT 的增益 = 多步推理任务 × 模型能力不足的乘积；任一
因子变大，另一因子的影响就趋近于零。**

## Why

"CoT 能提升推理能力"人人会说，但拿得出可复现实验数据的不多。本篇把答案
做成实验：同一题集、同一评分、四种模式。实验同时揭示了 CoT 的适用边界
——这比记住"CoT 提升 10 个点"高一个段位。

## How

```bash
cd qa/01_cot_compare
MOCK=1 python3 cot_compare.py    # 离线：预置回答模式，验证评估管线
python3 cot_compare.py           # 真实：qwen3.8（80 次 LLM 调用，约 10 分钟）
```

真实模式：四种模式全部 **20/20（100%）**——包括直接回答。20 道简单数学
题对当前旗舰级模型已无区分度，CoT 没有提升空间。

MOCK 模式（模拟弱推理，验证评估管线的区分度）：

| 模式 | 单步 | 两步 | 总体 |
| :--- | :--- | :--- | :--- |
| direct | 8/10 | **3/10** | 11/20 (55%) |
| zero_cot | 10/10 | 10/10 | 20/20 (100%) |
| few_cot | 10/10 | 10/10 | 20/20 (100%) |
| auto_cot | 10/10 | 10/10 | 20/20 (100%) |

两步题 3/10 → 10/10 的提升集中在 CoT 类模式——**缺失中间步骤正是直接
回答败给 CoT 的原因**。Auto-CoT 实测：取样 3 道代表题自产推理链作为示例，
效果与人工 Few-shot 持平（本例题集简单），省掉了人工编写 3 个示例的成本。

## Deep Dive

**增益来源**：CoT 把多步推理显式化为中间 token，给模型更多计算与自检
空间。代价是输出变长、延迟变高，且简单任务上"逐步思考"属于过度思考——
强模型 + 简单任务时 CoT 无增益甚至有害（适用边界的系统化解剖见
[02 CoT 失效场景](../02_cot_failure/README.md)）。

踩坑清单：

- **负结果归因：题太简单**。想看到提升需要更难的题（多步乘除、干扰
  数字）——02 项目做的就是这件事；
- **MockLLM 的"推理"是关键词规则的预置行为**（诚实标注），只用于离线
  验证评估管线的区分度；
- **few-shot 前缀剥离的正则误加 `re.S`**：`.*` 跨行吞掉了问题行导致
  mock 全错——定位后去掉 flag。评估管线本身也要被测试。

## Q&A

**Q1: 为什么评估要用分层题集（单步/多步）？**

全部同难度时模式差异会被饱和掩盖——本次 20 道简单题全 100% 就是例证；
分层后才能看到"哪类题缺中间步骤"。

**Q2: 数值评分要注意什么？**

要处理"答案: X"提取失败的情况，兜底取最后一个数字；用精确匹配而非相似
度，保证判分确定性。
