# 01 · CoT 三态对比实验（Zero / Few / Auto-CoT vs 直接回答）

> 同一题集、同一评分、四种回答模式（direct / Zero-shot CoT / Few-shot CoT /
> Auto-CoT）的正确率对比——并得到一个诚实的负结果：**强模型 + 简单题会让
> 四种模式全部饱和**，CoT 的差异化要在更难的题上才显形（见 MOCK 对照）。
> 读完本篇，你能说出 CoT 四种用法的差别、它们各自适用的场景，以及
> "CoT 没带来提升"时如何归因。

## Background

不指定任何格式时，人们调用大语言模型（LLM，通过 API 问答的文本生成模型）的
默认做法是"直接回答"：一个问题、一个答案，提示词只要求输出结果。

这种做法在单步任务上够用，但在多步计算题上会撞墙。

例如"商品原价 350 元，先涨价 20% 再打 8 折，现价多少"，模型必须连续
完成两次换算才能作答；被要求一步给出最终数字时，中间换算没有任何输出
可供检查，一旦算错，既看不出错在哪一步，也没有机会在产出答案前自我
纠正。

研究者随后发现：只改提示词、让模型"先把推理过程一步步写出来，再给最终
答案"，同一个模型在同一批题上的正确率就明显上升。围绕"怎么让模型写出
推理过程"，衍生出人工写示例、自动生成示例等多种用法，本实验把它们放在
同一题集下对比。

## What

CoT（Chain-of-Thought，思维链）是一种提示方法：在提示词中要求模型先输出
逐步推理的中间内容，再给出最终答案。中间内容也是 token（模型生成文本的
最小单位，大约相当于一个词或半个词），相当于给模型一张可以演算的草稿纸。

可以把 CoT 想象成让模型"列竖式"而不是心算：把每一步写在纸上，出错更少、
过程可查。但和人类竖式不同的是，模型写出的中间步骤并不保证是它内部真实的
计算过程，它更像一种能引导出正确答案的输出形式。

本实验的心智模型一句话：**CoT 的增益 = 多步推理任务 × 模型能力不足，
两个因子是相乘关系；任一因子趋近于零，增益就趋近于零。** 例如模型本身
很强（因子二为零）或题目一步就能答出（因子一为零）时，CoT 都不会带来提升。

## When to Use

在为"要不要让模型写推理过程"做选型时，典型场景有三类：

- 做多步换算类问答（数学应用题、日程推算、多跳检索问答），直接回答错误率高；
- 使用的模型较小或版本较旧，复杂题一步作答经常出错；
- 答案需要人工抽查，希望中间步骤可核对。

反之，强模型处理简单任务时不要加 CoT：输出变长、延迟变高，却没有正确率
收益。四种模式的选型对比：

| 方案 | 差异 | 什么时候选它 |
| :--- | :--- | :--- |
| direct | "直接给出答案，只输出一个数字" | 简单单步任务；对延迟敏感 |
| Zero-shot CoT | 一句"请一步步思考再回答"指令，不给示例 | 多步任务的第一选择，零额外成本 |
| Few-shot CoT | 3 个人工编写的带推理示例 | 需要控制输出格式、Zero-shot 不稳定时 |
| Auto-CoT | 按固定步长取样 3 道代表题，模型自产推理链示例 | 题量大、人工写示例成本高时 |

## Quick Start

前置条件：Python 3，无第三方依赖。真实模式默认连接本机 Ollama
（一个在本地运行开源模型的工具，地址 `http://localhost:11434/v1`，模型
`qwen3.8:latest`）。

可通过环境变量 `LLM_BASE_URL` / `LLM_MODEL` / `LLM_API_KEY` 指向其他
OpenAI 兼容接口（凡使用与 OpenAI 相同请求格式的模型服务均可）。

题集为自建 20 道多步推理题（GSM8K 风格——GSM8K 是常用的小学数学应用题
数据集，"风格"指题目形态与之类似）。评分规则：从回答中提取最终数值
（优先"答案: X"，否则取最后一个数字），与标准答案精确匹配。

```bash
cd qa/01_cot_compare
MOCK=1 python3 cot_compare.py    # 离线：预置回答模式，验证评估管线
python3 cot_compare.py           # 真实：qwen3.8（80 次 LLM 调用，约 10 分钟）
```

诚实预期：真实模式下四种模式全部 **20/20（100%）**——包括直接回答。
这不是 bug：20 道简单数学题对当前旗舰级模型已无区分度，CoT 没有提升空间。

要看到模式间差异，用 MOCK 模式（模拟弱推理，验证评估管线的区分度——
评估管线指从模型回答到判出对错的自动流程）：

| 模式 | 答对 |
| :--- | :--- |
| direct | 2/20 (10%) |
| zero_cot | 20/20 (100%) |
| few_cot | 20/20 (100%) |
| auto_cot | 20/20 (100%) |

表中 direct 只有 2/20，而三个 CoT 类模式全部 20/20——缺失中间步骤的
差距就是下节机制的可视化证据。

## How It Works

CoT 的增益来源：把多步推理显式化为中间 token，给模型更多计算与自检空间。
模型每多生成一步，就把前文的中间结果固定下来，后续计算建立在已写出的
结果上，而不是一次性装在"心里"。

Quick Start 的 MOCK 表正是这个机制的对照呈现：direct 只有 2/20，缺失
中间步骤正是直接回答败给 CoT 的原因；而真实模式全 20/20，对应增益公式里
"模型能力不足"这一因子为零。

代价同样明确：输出变长、延迟变高；简单任务上"逐步思考"属于过度思考——
强模型 + 简单任务时 CoT 无增益甚至有害（适用边界的系统化解剖见
[02 项目](../02_cot_failure/README.md)）。

Auto-CoT 的实现分两步：先按固定步长从题集取出 3 道代表题（真实 Auto-CoT
用向量聚类选例，本实验用固定步长近似），让模型对这 3 道题各自生成一条
推理链；再把这 3 段"问 + 推理 + 答案"拼成前缀，缀到每道题的提示词前面。

实测效果与人工 Few-shot 持平（本例题集简单），省掉了人工编写 3 个示例的成本。

## Pitfalls & Q&A

踩坑清单：

- **现象：真实模式四种模式全 100%，看不到 CoT 提升。** 原因：题太简单、
  模型太强，增益公式里"能力不足"因子为零。解法：换更难的题（多步乘除、
  干扰数字），02 项目做的就是这件事。
- **现象：MOCK 模式的"推理"看起来像真推理。** 原因：MockLLM 的回答是
  关键词规则的预置行为（测试替身，即用假实现替代真实模型调用的离线测试
  手法），项目里已诚实标注。解法：只用它验证评估管线的区分度，不用它下
  结论。
- **现象：给 few-shot 前缀剥离的正则（正则表达式，按模式匹配文本的
  工具）误加 `re.S` 后，mock 模式全部判错。**
  原因：`.*` 在 `re.S`（让 `.` 也匹配换行符的正则标志）下跨行吞掉了问题行。
  解法：去掉该 flag；评估管线本身也要被测试。

深入问答：

**Q1: 为什么题集全用多步推理题？**

题目太简单时模式差异会被饱和（各模式都拿满分、指标失去区分能力）掩盖
——真机 20 道题四种模式全 100% 就是例证；全多步构成给 CoT 留出显形
空间，MOCK 表里 direct 2/20 的差距即来自缺失的中间步骤。

**Q2: 数值评分要注意什么？**

要处理"答案: X"提取失败的情况，兜底取最后一个数字；用精确匹配而非相似
度，保证判分确定性。
