# 14 · Human-in-the-loop 审批门

> 10 个混合操作先过风险分级器：金额/删除/对外发送/敏感导出 → 强制审批；
> 纯查询/内部写 → 自动放行（零打扰）。审批三态：批准/拒绝/超时默认拒绝
> （fail-safe）。全部决策写审计日志（JSONL）。交互终端真输入；非交互
> 环境走脚本化用户决策并如实标注。

## What

HITL 审批门的分级规则（写入侧）：

- **强制审批四类红线**：**资金操作**（退款/转账>¥1000）、**删除类**、
  **对外发送**（邮件/短信/发布）、**敏感数据出域**（导出/下载）；
- **自动放行**：纯查询、内部低风险写——红线用规则判定，不用模型猜。

审批三态：批准 / 拒绝 / 超时默认拒绝（fail-safe），全部决策落审计日志。

心智模型一句话：**该问的必须问，不该问的一次都别问——分级靠规则，不靠
模型猜。**

## Why

HITL 的两难：危险操作不问会出事故，安全操作次次问是体验灾难。介入时机
的本质是把"哪些操作不可逆、出域、涉资金"从模型判断挪到确定性规则。

## How

```bash
cd qa/14_hitl_gate
MOCK=1 python3 hitl_gate.py    # 离线: 脚本化用户决策 (批准/拒绝/不应答)
python3 hitl_gate.py           # 终端下真实输入; 管道下 fail-safe 全拒
```

实测：

| 指标 | 结果 |
|:--|:--|
| 危险操作全部卡住审批 | ✓ 5/5（退款/转账/删除/群发/导出） |
| 安全操作零打扰 | ✓ 5 个（查询×3 + 内部写×2） |
| 批准/拒绝/超时拒绝 | 2 / 2 / 1 |
| 审计日志条数 | 10（每操作一条, JSONL 落盘） |

## Deep Dive

**fail-safe 原则**：审批超时/通道不可用 = 默认拒绝——宁可不做，不可
做错。与"超时默认放行"相比，前者把故障的代价限制在"事情没办成"，后者
的代价是不可逆的错误操作。

## Q&A

**Q1: 为什么红线用规则判定而不是让模型判断风险？**

红线（资金/删除/出域）是确定性语义，规则判定零误判零漏判；让模型
"觉得危险就问"会把分级变成概率问题——危险操作漏问一次就是事故。

**Q2: 审计日志为什么是生产底线？**

记录谁/何时/批了什么/为什么，事后可追责可复盘——而不是"模型说它
问过用户"。审批行为本身也必须是可验证的事实。
