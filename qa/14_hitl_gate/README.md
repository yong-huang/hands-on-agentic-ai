# 14 · Human-in-the-loop 审批门

> agent 替人执行操作时，危险动作不问人会出事故，安全动作次次问是体验
> 灾难。读完本篇你能获得：一套用确定性规则给操作分级的审批门——哪些
> 强制审批、哪些自动放行，以及 fail-safe（超时默认拒绝）与审计日志两条
> 生产底线。

## Background

在审批门出现之前，agent（能自主调用工具、分步完成任务的程序）任务的
执行粒度只有两个极端：要么全自动——模型决定的事直接执行，不问任何
人；要么每一步都等人确认后再继续。

两个极端各有撞墙的场景。全自动时，退款、删数据、群发邮件这类不可逆操作
一旦模型判断错，事故直接发生且无法撤回；每步都问时，十个操作里九个是
查数据、写内部记录这种安全动作，人被反复打断，要么疲于点确认，要么
养成无脑批准的习惯。

Human-in-the-loop（HITL，人在回路，指人在自动化流程中参与关键决策的
机制）把第三个选项工程化：在执行前加一道审批门（gate，即执行路径上的
检查点），用确定性规则先给操作分级——危险的强制审批，安全的自动放行。
这样"要不要问人"从模型的临场判断变成预先写死的规则。

## What

HITL 审批门是一层位于 agent 与工具调用之间的检查点：写操作先过风险
分级器（按预定义规则给操作判定风险等级的组件），红线操作暂停等人
决策，其余直接放行。分级规则（作用于写入侧）：

- **强制审批四类红线**：**资金操作**（退款/转账>¥1000）、**删除类**、
  **对外发送**（邮件/短信/发布）、**敏感数据出域**（导出/下载）；
- **自动放行**：纯查询、内部低风险写——红线用规则判定，不用模型猜。

人看到审批请求后有三种可能结果（审批三态）：批准 / 拒绝 / 超时默认
拒绝（fail-safe，失效安全——机制本身失效时倒向更安全的一侧）。全部
决策落审计日志（audit log，记录谁在何时批准或拒绝了什么、供事后
追溯的日志）。

心智模型一句话：**该问的必须问，不该问的一次都别问——分级靠规则，不靠
模型猜。**

可以把审批门想象成公司财务的报销流程：小额打车票直接贴票报销（自动
放行），超过一定金额或涉及对外付款的必须领导签字（强制审批），领导
长期不签视作不同意（超时默认拒绝）。但和报销流程不同的是，这里的
"哪些需要签字"是代码里的规则清单，不依赖任何人临场判断轻重。

## When to Use

典型场景一：让 agent 执行混合操作的任务（既要查数据、又要退款、又要
发通知）时，需要把少数危险动作拦下来给人确认，其余不打扰人。

典型场景二：agent 需要接触真实资金、真实用户（对外发送）或生产数据
（删除、导出）时，不可逆操作必须有人的显式批准。

典型场景三：需要向合规或安全团队证明"每个危险操作都经过批准"时，
审批决策要可追溯。

何时不用：任务只有只读查询时，加审批门只是增加延迟；操作全部高危且
量小（人工逐个做更快）时，直接人工执行；风险低但量极大时，事后审计
比逐条拦截更划算。

| 方案 | 差异 | 什么时候选它 |
|:--|:--|:--|
| 全自动执行 | 无人工确认，出错不可逆 | 只读查询、可撤销的内部操作 |
| HITL 审批门（本实验） | 红线强制审批，其余零打扰 | 混合危险与安全操作的 agent 任务 |
| 全人工操作 | 每步由人执行 | 操作量小或全部高危 |
| 事后审计（不阻断） | 只记录不拦截 | 风险低且量大，拦截代价高于损失 |

## Quick Start

前置条件：Python 3，无额外依赖。两种运行方式：

```bash
cd qa/14_hitl_gate
MOCK=1 python3 hitl_gate.py    # 离线: 脚本化用户决策 (批准/拒绝/不应答)
python3 hitl_gate.py           # 终端下真实输入; 管道下 fail-safe 全拒
```

`MOCK=1` 用脚本代替真人做决策，覆盖批准、拒绝、不应答三种情况；在
终端直接运行则是真实键盘输入；通过管道（pipe，前一个命令的输出接
后一个命令的输入，此时没有交互终端）运行时无人应答，全部走 fail-safe
默认拒绝。诚实预期，实测：

| 指标 | 结果 |
|:--|:--|
| 危险操作全部卡住审批 | ✓ 5/5（退款/转账/删除/群发/导出） |
| 安全操作零打扰 | ✓ 5 个（查询×3 + 内部写×2） |
| 批准/拒绝/超时拒绝 | 2 / 2 / 1 |
| 审计日志条数 | 10（每操作一条, JSONL 落盘） |

10 个操作恰好对半分：5 个红线操作全部被拦下进入审批，5 个安全操作
一次都没问；审计日志每操作一条，无论批准与否都落盘，格式为 JSONL
（JSON Lines，每行一个独立 JSON 对象的文本格式，便于逐条追加与解析）。

## How It Works

执行顺序是：操作到达 → 风险分级器按规则清单判定 → 红线操作挂起等
人工决策（三态之一）→ 其余直接放行 → 无论走哪条路，决策都写入审计
日志。

**fail-safe 原则**：审批超时/通道不可用 = 默认拒绝——宁可不做，不可
做错。与"超时默认放行"相比，前者把故障的代价限制在"事情没办成"，后者
的代价是不可逆的错误操作。

与 Quick Start 的表格互相印证：表中"超时拒绝 1"对应脚本模拟的
"不应答"用户——审批等不到答复，fail-safe 生效；而"审计日志条数 10"
说明放行的 5 个安全操作也各留了一条记录，审批门不是只记录被拦的
操作。

分级判定是纯代码：操作携带类型与参数，命中"资金/删除/对外发送/出域"
任一关键字段即进审批队列。这条链上模型只负责执行任务，不参与"要不要
问人"的判断。

## Pitfalls & Q&A

**坑 1：在非交互环境里等输入挂住。** 现象：在定时任务或管道中运行，
进程停在审批处不动。原因：审批门等待人工输入，而这类环境没有终端
应答。解法：为审批设超时并接 fail-safe 默认拒绝；管道场景直接全拒。

**坑 2：把安全操作也设为强制审批。** 现象：查询类操作也要人逐条批准，
任务频繁被打断。原因：红线清单定得过宽。解法：红线只收资金、删除、
对外发送、出域四类不可逆操作，纯查询与内部写自动放行。

**Q1: 为什么红线用规则判定而不是让模型判断风险？**

红线（资金/删除/出域）是确定性语义，规则判定零误判零漏判；让模型
"觉得危险就问"会把分级变成概率问题——危险操作漏问一次就是事故。

**Q2: 审计日志为什么是生产底线？**

记录谁/何时/批了什么/为什么，事后可追责可复盘——而不是"模型说它
问过用户"。审批行为本身也必须是可验证的事实。
