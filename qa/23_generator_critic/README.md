# 23 · Generator-Critic 辩论模式

> 20 道易错题（运算顺序/单位换算/经典脑筋题陷阱）三种模式对跑：direct（1 次调用）/ cot（1 次调用）/ debate（生成器起草 → 评审挑错 → 生成器修订，3 次调用）。答案可程序判定，输出正确率与成本对比。读完你能判断什么任务值得为正确率付 3 倍调用成本。

## Background

最常见的用法是单次作答：把问题发给模型，拿到的第一个答案直接用；稍微讲究一点，加一句"请一步步推理"，让单个 Agent（智能体）独自慢慢推理（这就是 CoT，Chain of Thought，思维链）。

痛点出在易错任务上。运算顺序（`3 + 3 / 3`）、单位换算（30 分钟走多远）、脑筋急转弯（10 斤棉花和 10 斤铁哪个重）这类题，模型一次作答就可能栽在粗心上；而某些场景错误的代价很高——自动下单、自动发邮件，错了没有"撤回"。单 Agent 独自作答，没有人兜底。

Generator-Critic（生成器-评审者）模式因此出现：让一个生成器起草答案，另一个评审角色专门挑错，生成器再修订一次。代价是每题从 1 次模型调用（即一次大语言模型 API 请求）变成 3 次——它到底值不值，要用实验说话。

## What

Generator-Critic 是一种多 Agent 协作模式：生成器与评审角色对同一道题各司其职。本实验用三种模式对跑同一批题，成本结构如下：

| 模式 | 流程 | 每题调用 |
|:--|:--|:--:|
| direct | 直接作答 | 1.0 |
| cot | 单模型逐步推理 | 1.0 |
| debate | 生成器起草 → 评审挑错 → 生成器修订 | 3.0 |

心智模型一句话：**辩论的收益 = 可验证的易错任务 × 错误的高代价——两个因子都不满足时，3 倍成本白花。**

可以把 debate 想象成论文的同行评审：作者写初稿，审稿人挑毛病，作者修改后再交。但和期刊评审不同的是，这里的评审通常拿不到金标准（预先确定的标准答案），它只能按"运算顺序、单位、陷阱表述"这些检查点挑过程错误，不能对答案本身背书。

## When to Use

典型场景，按"是否易错、可验证、代价高"三问筛选：

- 数值与事实型任务：数学运算、单位换算，答案能用程序判定，评审意见有据可依。
- 高代价自动化动作前：自动下单、自动发邮件，宁可用 3 次调用换一次正确。
- 有经典陷阱表述的问答：脑筋急转弯类题目，第一反应经常是错的。

何时不用：开放式创作（写文案、起名字）没有对错判据，评审只能输出主观偏好；低延迟实时对话承受不了 3 倍调用；任务本身简单到直接作答就全对时，多 Agent 没有提升空间。

| 方案 | 什么时候选它 | 什么时候别选 |
|:--|:--|:--|
| direct | 任务简单、延迟敏感 | 题目有陷阱、错误代价高 |
| cot | 需要推理但预算只有 1 次调用 | 单模型反复栽同一类坑 |
| debate | 易错 + 可验证 + 错误代价高，三者同时满足 | 创作类任务、简单任务 |

## Quick Start

前置条件：离线模式（`MOCK=1`）零依赖，用确定性模型（输出不随机的模拟模型，用于得到可复现的统计）跑 20 题全量；真机模式需在同仓库 `llm.py` 配好 `BASE_URL`/`MODEL`/`API_KEY`（qwen3.8），为控制调用成本只跑 6 道代表题。

```bash
cd qa/23_generator_critic
MOCK=1 python3 generator_critic.py    # 离线: 确定性模型, 20 题全量
python3 generator_critic.py           # 真实: qwen3.8, 6 道代表题
```

真机实测（6 道代表题）：三种模式 6/6 全对（代表题上 qwen3.8 已是天花板，正确率拉不开）；成本差异如实呈现。

离线 20 题全量（哈希抽样难度模型）：direct 平均约 10/20、cot 平均约 12/20（单次各在约 ±4 题内浮动，多次运行保持 cot 不低于 direct）→ debate 恒为 20/20；三档目标通过率为 50%/60%/100%，辩论成本 3 倍。

诚实预期：真机样本只有 6 题，且这 6 题对 qwen3.8 过于简单，看不出三模式差距——正确率结论以离线 20 题全量为准；真机部分主要看成本数字的对比。

## How It Works

debate 模式的三次调用是一条固定的流水线，对应源码里的 `debate_answer`：

**第 1 次调用（起草）**：生成器拿到题目直接作答，提示词与 direct 模式相同——保证对比公平，起点一致。

**第 2 次调用（挑错）**：评审角色拿到题目和候选答案，提示词是（节选）：

```python
"你是苛刻的评审。题目: {}\n候选答案: {}\n"
"检查: 运算顺序/单位换算/陷阱表述。"
"指出错误或说'无错'。80 字内。"
```

这段在做什么：给评审三个明确的检查点，并限定 80 字——它的职责是挑过程错误，不是重新解题。注意评审拿不到金标准答案，独立视角来自"不看标准答案、只查过程"。

**第 3 次调用（修订）**：生成器拿到"题目 + 自己的初答 + 评审意见"，复核后给出最终答案。

**判分是程序化的**：`grade` 函数从答案文本里抽出数字（或匹配关键词）与金标准比较，正确与否不含主观判断。你在离线实测里看到的"direct/cot 通过数随哈希抽样浮动、debate 恒为 20/20"就来自这套统一判分。

而真机 6/6 全对说明代表题对 qwen3.8 没有提升空间——强基线（baseline，用作对比基准的最强单模型配置）已经打满时，辩论加不了分，这正是"打不过基线就不该上多 Agent"的实例。

## Pitfalls & Q&A

**Q1：什么时候该上多 Agent 协作？**

同时满足两个条件：任务易错但可验证（评审的意见有判据），且错误代价高（值得付 3 倍调用）。先跑单 Agent + CoT 基线——多 Agent 打不过它就别上。

**坑 1：评审"客气化"，修订形同虚设。**
现象：评审对错误答案也回"无错"，debate 退化成 3 倍成本的 direct。
原因：评审提示词没有约束时，模型倾向附和已有答案。
解法：像本实现一样在提示词里明写"苛刻的评审"并给出检查清单，限定"指出错误或说'无错'"两种输出。

**坑 2：拿 6 题的真机结果下正确率结论。**
现象：真机跑一次三模式全对，就断言"debate 没用"。
原因：真机为控制成本只跑 6 道代表题，样本小且偏简单。
解法：正确率结论以离线 20 题全量和多次运行的趋势为准，真机结果用于核对成本与流程。
