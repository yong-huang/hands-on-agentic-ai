# 08 · 长期记忆库（写入 + 检索注入）

> SQLite 持久化 + 向量检索 + TopK 注入 system prompt。写入路径 = 显式
> "记住" + 自动抽取（LLM/规则归一化事实）；读取路径 = query 向量化 →
> 余弦 TopK → 注入。跨会话测试：关库重开（模拟新进程）后提问 4 个事实。

## What

长期记忆库 = 短期记忆（[07](../07_short_memory/README.md)，管本会话上下文
预算）之外，跨会话持久化事实的存储与检索层：

```
用户输入 ──► 短期记忆 (窗口/摘要, 本会话上下文) ──► LLM
                │ 会话结束/关键事实
                ▼
            写入路径: 显式"记住" + 自动抽取(归一化)
                ▼
            长期记忆库 (SQLite + 向量, 跨会话)
                │ 检索 TopK 注入
                ▼
            下一次会话的 system prompt ◄── 读取路径
```

心智模型一句话：**写入要过滤、读取要检索——这对读写路径就是"设计记忆
系统"的骨架。**

## Why

短期记忆只活在一个会话里；"用户叫什么、项目代号是什么"这类事实要跨会话
生效，必须持久化 + 语义检索。这对读写路径是记忆系统设计题的通用骨架。

## How

```bash
cd qa/08_long_memory
MOCK=1 python3 long_memory.py    # 离线: hash 词袋退化向量 + 模板回答
python3 long_memory.py           # 真实: nomic-embed-text + qwen3.8
```

实测（真实模式 4/4 全对）：

| 查询 | Top1 命中 | 相似度 | 结果 |
|:--|:--|:--:|:--:|
| 我的项目代号是什么？ | 用户的项目代号叫夜莺 | 0.92 | ✓ |
| 我叫什么名字？ | 用户名叫林晓 | 0.75 | ✓ |
| 我在哪个城市？ | 用户常驻杭州 | 0.65 | ✓ |
| 我咖啡喝什么？ | 用户咖啡只喝燕麦拿铁 | 0.74 | ✓ |

nomic 语义检索把表面形式完全不同的查询（"我在哪个城市" vs "用户常驻
杭州"）正确配对——这是 hash 退化向量做不到的（离线模式 3/4，"城市"查询
零字面重叠导致漏检，恰说明语义 embedding 是这一层不可省的投入）。
记忆写入前先做归一化（"我叫林晓" → "用户的名字是林晓"）显著提升检索
稳定性。

## Deep Dive

**读写路径各自的关键设计**：写入侧做归一化——口语形式（"我叫林晓"）
转成规范陈述（"用户的名字是林晓"），查询与事实的字面形式才能对齐检索；
读取侧用语义 embedding 而非字面匹配——查询是问句、事实是陈述句，字面
零重叠是常态而非例外。

## Q&A

**Q1: 记忆互相冲突怎么办？**

需要来源置信度与冲突检测，见 [09 记忆污染攻防](../09_memory_poison/README.md)。

**Q2: 记忆怎么过期？**

TTL/时间戳标记，过期记忆检索时排除（09 的三层防御之一）。

**Q3: 为什么不用全文检索？**

语义改写场景字面零重叠——"我在哪个城市"与"用户常驻杭州"没有一个共同
关键词，BM25/全文检索直接失明。
