# 08 · 长期记忆库（写入 + 检索注入）

> 本项目实证：助手如何跨会话记住用户事实——写入路径负责存，读取路径在下次会话按需取回。读完你能说清一个记忆系统的读写骨架，以及为什么这一层必须用语义检索而不是关键词匹配。

## Background

没有长期记忆层时，助手的记忆只活在单个会话里：对话结束，进程退出，模型对用户的了解清零。用户第二天回来，得重新自我介绍一遍。

要绕开失忆，常见有两种土办法。一是把全部历史对话原样堆进每次请求：历史越长费用越高，迟早撑爆上下文窗口，而且从一堆闲聊里翻出"用户咖啡喝什么"全靠模型碰运气。二是靠用户每次自己重说，体验最差。

借鉴数据库的思路就出现了专门的记忆层：把值得记的事实写进持久化存储，新会话开始时按当前问题取回最相关的几条，注入模型。本项目按这个思路实现最小可用的读写路径，并用"关库重开"验证跨会话生效。

## What

长期记忆库是一个跨会话持久化用户事实、并在后续会话中按相关性取回的存储与检索层，补的是短期记忆（管本会话上下文预算，见 07 项目）管不到的那部分。

| 部件 | 职责 | 本实验的实现 |
|:--|:--|:--|
| 写入路径 | 把值得记的事实存进库 | 显式"记住" + 自动抽取（LLM/规则，先归一化） |
| 存储层 | 跨会话持久化，存文本与向量 | SQLite（单文件嵌入式数据库） |
| 读取路径 | 新会话按当前问题取回相关事实 | query 向量化 → 余弦相似度 TopK → 注入 system prompt |

表里出现的术语先解释：LLM 指大语言模型；embedding 指把一段文本映射成一串数字（向量），语义越接近的文本对应的向量越相似；余弦相似度衡量两个向量方向是否一致，1 表示完全同向；TopK 指只取得分最高的 K 条；system prompt 指发给模型的系统级指令；归一化指把口语原句改写成统一的规范陈述。

可以把长期记忆库想象成助理的客户档案柜：见客户前抽出相关档案页（读取），谈完把新信息归档（写入）。但和纸质档案不同的是，抽哪一页由语义相似度自动决定——归档时写得规范不规范，直接决定以后抽得对不对。

心智模型一句话：**写入要过滤、读取要检索——这对读写路径就是"设计记忆系统"的骨架。**

## When to Use

- **个人助理类产品**：用户隔几天回来继续聊，不想每次重新说自己的名字、城市、偏好；
- **长期项目协作**：项目代号、截止日这类事实要贯穿数周的多次会话，不能靠单次上下文；
- **个性化服务**：需要按历史偏好持续调整行为（推荐、措辞、默认选项）。

何时不用：一次性的任务型会话（翻译、改写、单轮问答）没有"跨会话"可言，加这层是纯开销；事实高频变化且旧值必须立即失效的场景，还要叠加冲突处理（见 09 项目）。

| 方案 | 与本篇方案的差异 | 什么时候选它 |
|:--|:--|:--|
| 全量塞历史 | 不删不拣，所有历史进 prompt | 历史很短；长了超窗且费用随轮数上涨 |
| BM25/全文检索 | 关键词字面匹配，不需要 embedding | 查询与文档措辞基本一致的场合 |
| 向量记忆库（本篇） | 语义检索，措辞不同也能配上 | 跨会话、查询措辞多变的场景 |

## Quick Start

前置条件：Python 3；真实模式需要本地模型服务同时提供 embeddings（nomic-embed-text，一个本地文本 embedding 模型）与对话（qwen3.8）；`MOCK=1` 离线模式用 hash 词袋向量（按字面词拼出来的退化向量，只认字面不认语义）加模板回答。

```bash
cd qa/08_long_memory
MOCK=1 python3 long_memory.py    # 离线: hash 词袋退化向量 + 模板回答
python3 long_memory.py           # 真实: nomic-embed-text + qwen3.8
```

实测（真实模式 4/4 全对）：

| 查询 | Top1 命中 | 相似度 | 结果 |
|:--|:--|:--:|:--:|
| 我的项目代号是什么？ | 用户的项目代号叫夜莺 | 0.92 | ✓ |
| 我叫什么名字？ | 用户名叫林晓 | 0.75 | ✓ |
| 我在哪个城市？ | 用户常驻杭州 | 0.65 | ✓ |
| 我咖啡喝什么？ | 用户咖啡只喝燕麦拿铁 | 0.74 | ✓ |

诚实预期：4/4 依赖语义 embedding。离线 hash 词袋同样 4/4——归一化后的记忆与查询共享"城市"等字面词；"零字面重叠漏检"需用未归一化语料才能复现。

## How It Works

**写入路径**分两种来源。显式写入直接存规范化事实：

```python
store.add("用户的项目代号叫夜莺", kind="fact", source="explicit")
```

自动抽取从对话里提炼持久事实（真机让 LLM 输出 JSON，离线用正则规则），关键动作是归一化，例如"我叫林晓"存成"用户的名字是林晓"。查询与事实的字面形式因此才能对齐。

**读取路径**的核心是 `search`：把查询向量化，对库中每条记忆算余弦相似度，排序取 TopK：

```python
def search(self, query, k=3):
    qv = embed(query)
    rows = self.db.execute("SELECT text, kind, source, vec FROM memories").fetchall()
    scored = [(cosine(qv, json.loads(v)), t, kind, src) for t, kind, src, v in rows]
    scored.sort(reverse=True)
    return scored[:k]
```

`answer_with_memory` 再把命中条目拼进 system prompt，让模型"回答时优先使用"这些记忆。

实测表的现象可以逐条对上机制："我在哪个城市"配到"用户常驻杭州"（Top1，相似度 0.65），是因为两句话在 embedding 的语义空间里方向接近——尽管没有一个共同关键词。

离线 hash 词袋也能命中城市：归一化后的记忆"用户的城市是杭州"与查询共享"城市"字面词——是字面匹配，不是语义匹配。

**跨会话验证**靠 SQLite 的文件持久性：会话 1 结束时 `close()` 关闭连接（模拟进程退出），会话 2 重新打开同一个数据库文件，5 条记忆仍在，4 个提问全部命中——日志里的"库中共 5 条记忆，关闭连接"（真机模式；离线为 4 条）之后紧跟"新进程重开数据库"。

## Pitfalls & Q&A

- **现象：明明存了，却检索不到。** 原因：入库的是口语原句，与查询字面、语义都对不齐。解法：写入前归一化（机制见上文 How It Works），这是记忆库的标准实践。
- **现象：没有相关记忆时，模型仍一本正经地回答。** 原因：TopK 检索总会返回 K 条，不相关的低分记忆注入后会被模型硬用。解法：对相似度过低的命中做阈值过滤（代码里 `s > 0.05` 才注入），过滤后为空就明确走"没有相关记忆"分支。

**Q: 记忆互相冲突怎么办？**

需要来源置信度与冲突检测，见 [09 记忆污染攻防](../09_memory_poison/README.md)。

**Q: 记忆怎么过期？**

TTL（time-to-live，按时间戳让数据到期失效的机制）/时间戳标记，过期记忆检索时排除（09 的三层防御之一）。

**Q: 为什么不用全文检索？**

语义改写场景字面零重叠——"我在哪个城市"与"用户常驻杭州"没有一个共同关键词，BM25（经典的关键词全文检索算法）/全文检索直接失明。
