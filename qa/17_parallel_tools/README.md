# 17 · 并行工具调用（依赖分析 DAG）

> 模型一轮吐 4 个工具调用，calc_cost 的参数用 $1/$2 占位符引用前两个
> 调用的结果。三种调度器对跑：串行 / 分析后并行（$引用建 DAG，无依赖层
> asyncio.gather）/ 盲并行（不分析直接全量并发）。工具以 0.3s sleep
> 模拟耗时，计时完全可复现。

## What

| 调度器 | 策略 |
|:--|:--|
| 串行 | 逐个执行 |
| 分析后并行 | 扫描参数里的 $N 引用建 DAG，无依赖同波 gather，有依赖等回填 |
| 盲并行 | 不分析依赖，全量并发 |

心智模型一句话：**并行提速的前提是依赖分析——错序的结果必须拦截，
错得快不等于对。**

## Why

多工具调用串行执行白白浪费等待时间；但调用间有数据依赖（后一个的参数
引用前一个的结果），盲并行会拿到未回填的占位符。并行的正确姿势是
DAG：先分析依赖，再决定谁能同波。

## How

```bash
cd qa/17_parallel_tools
MOCK=1 python3 parallel_tools.py    # 离线: 预置调用批次
python3 parallel_tools.py           # 真实: qwen3.8 生成调用批次, 计时同
```

实测（两种模式一致）：

| 调度器 | 耗时 | 结果 |
|:--|:--:|:--|
| 串行 | 1.21s | 4/4 成功 |
| 分析后并行 | **0.60s（50%）** | 4/4 成功，2.0x 加速 ✓ |
| 盲并行 | 0.30s | **calc_cost 失败**：读到未解析占位符 "$1" ✓ 可复现 |

## Deep Dive

**依赖检测是关键**：扫描参数里的 $N 引用建 DAG，无依赖的进同一波
gather；有依赖的等前序结果回填后再发。**结果按调用 id 归位**（不是完成
顺序），保持与模型的 tool_call_id 对应，下一轮对话才不会串线。

踩坑清单：

- **盲并行的失败模式**：占位符没回填就开跑，拿到 "$1" 字符串——调度
  器必须校验参数已全部解析，依赖错序的结果宁可不发。

## Q&A

**Q1: 一轮多工具调用的能力从哪来？**

FC 传输层自带：`message.tool_calls` 是数组（见
[05 的实测](../05_fc_vs_react/README.md)，qwen3.8 一轮并行返回两个
查询）。本篇解决的是执行侧"怎么安全地并发跑完这一批"。
