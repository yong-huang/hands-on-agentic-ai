# 17 · 并行工具调用（依赖分析 DAG）

> 模型一轮吐出 4 个工具调用时，怎么并发执行才既快又对？读完本篇你能
> 获得：用 $N 占位符（先用记号占位、等前序调用返回后替换成真实值）
> 表达调用间依赖的方法，三种调度器（串行 / 分析后并行 / 盲并行）的
> 同题对比结果，以及"2.0x 加速"背后的 DAG（有向无环图）调度机制。

## Background

Function Calling（函数调用，指模型按约定格式请求宿主程序执行函数的
机制）早期一轮只发一个调用：程序执行完、把结果发回，模型再发下一个，
整条链严格串行（逐个执行）。

串行在多调用任务里浪费明显：4 个各耗 0.3 秒的查询排队执行要 1.2 秒，
其中大量时间只是干等。

想并发时会撞上另一个问题——调用之间有数据依赖，后一个调用的参数引用
前一个的结果（如"算总价"要用"查单价"的返回值）；不看依赖直接全量
并发，后一个调用会拿到未替换的占位符 "$1"，当成真实参数跑出错误。

解决方案分两层。传输层上，Function Calling 的 `message.tool_calls`
本就是数组，模型一轮可以返回多个调用。

执行层上，先扫描参数里的引用关系建出 DAG（有向无环图，用箭头表示
"谁依赖谁"的图结构，无环即不存在循环等待），再决定哪些调用可以同一波
并发、哪些必须等前序结果回填（把占位符替换为实际结果）。

## What

并行工具调用指宿主程序（host program，承载模型、替它执行函数调用的
应用程序）在一轮内并发执行模型返回的多个工具调用。核心是调度策略，
本实验对跑三种调度器：

| 调度器 | 策略 |
|:--|:--|
| 串行 | 逐个执行 |
| 分析后并行 | 扫描参数里的 $N 引用建 DAG，无依赖同波 gather，有依赖等回填 |
| 盲并行 | 不分析依赖，全量并发 |

表中 gather 是 Python asyncio 的并发原语（同时发起多个任务并等它们
全部完成），具体机制在 How It Works 展开。

心智模型一句话：**并行提速的前提是依赖分析——错序的结果必须拦截，
错得快不等于对。**

可以把 DAG 调度想象成做一桌菜：凉菜互不相干可以同时开做（无依赖同
波），热汤必须等高汤吊好（依赖回填）才能下锅；安排顺序的人看着菜谱
上的"先做 X 才能做 Y"排班。

但和做菜不同的是，这里的依赖关系不是人排的，而是从参数里的 $N 引用
自动扫描出来的——菜谱写错一眼能看出，引用漏扫只有运行时才暴露。

## When to Use

典型场景一：一轮里要跑多个互不依赖的查询（同时查 3 个城市的天气、
同时查 3 家航司报价）时，并行能把总耗时压到最慢一个调用的水平。

典型场景二：调用链有数据依赖（先查单价、再算总价、最后下单）时，
需要 DAG 调度既保住顺序又把无依赖部分并行掉。

典型场景三：工具以网络请求为主（等待远端响应占大头）时并行收益
最大；纯本地毫秒级计算收益有限。

何时不用：调用数少、总耗时可接受时，串行逻辑最简单、不易出错；工具
有速率限制（rate limit，单位时间允许的调用次数上限）或多个调用写
同一份共享状态时，不能盲目并发。

| 方案 | 差异 | 什么时候选它 |
|:--|:--|:--|
| 串行 | 逐个执行，实现最简单 | 调用少，或有限流、共享状态约束 |
| 分析后并行（本实验） | $引用建 DAG，无依赖同波、有依赖回填 | 一轮多调用且存在数据依赖 |
| 盲并行 | 不分析依赖，全量并发 | 所有调用彼此独立且参数已知 |

## Quick Start

前置条件：Python 3，无额外依赖。两种运行方式：

```bash
cd qa/17_parallel_tools
MOCK=1 python3 parallel_tools.py    # 离线: 预置调用批次
python3 parallel_tools.py           # 真实: qwen3.8 生成调用批次, 计时同
```

`MOCK=1` 使用预置的调用批次；真实模式由 qwen3.8 模型生成调用批次，
计时口径相同。工具内部以 0.3s sleep（程序主动暂停，模拟远端耗时）
保证计时完全可复现。诚实预期，实测（两种模式一致）：

| 调度器 | 耗时 | 结果 |
|:--|:--:|:--|
| 串行 | 1.21s | 4/4 成功 |
| 分析后并行 | **0.60s（50%）** | 4/4 成功，2.0x 加速 ✓ |
| 盲并行 | 0.30s | **calc_cost 失败**：读到未解析占位符 "$1" ✓ 可复现 |

三个数字各说明一件事：串行 1.21s 是排队等待的代价；分析后并行
0.60s 用一半时间拿全对的结果；盲并行 0.30s 最快，但 calc_cost 的
参数是字符串 "$1" 而不是数值——速度没有意义。

## How It Works

分析后并行的执行顺序：收集一轮的全部调用 → 扫描每个调用的参数找
$N 引用 → 建出依赖图 → 分层：无依赖的进同一波 gather（asyncio 的
并发原语，同时挂起多个协程、等它们全部完成；协程是单线程内并发等待
I/O 的机制）→ 有依赖的等前序结果回填后进入下一波。

**依赖检测是关键**：扫描参数里的 $N 引用建 DAG，无依赖的进同一波
gather；有依赖的等前序结果回填后再发。

以本实验为例：4 个调用中 3 个参数齐全，进第一波并发（0.3s）；
calc_cost 用 $1/$2 引用前两个结果，等回填后进第二波（0.3s）——两波
合计 0.60s，正是表格里的数字；串行则是 4 个 0.3s 排队，约 1.21s。

**结果按调用 id 归位**（不是完成顺序），保持与模型的 tool_call_id
（每次调用的唯一标识）对应，下一轮对话才不会串线——模型发出的调用
和收到结果的配对靠 id，不靠先后次序。

## Pitfalls & Q&A

**坑 1：盲并行把占位符当参数。** 现象：calc_cost 失败，参数里是
字符串 "$1"。原因：占位符没回填就开跑，调度器没做解析校验。解法：
调度器在发出前校验参数已全部解析，依赖错序的结果宁可不发。

**坑 2：按完成顺序回填结果。** 现象：模型把 A 调用的结果当成 B 的。
原因：并发下完成顺序与发起顺序不一致，结果却按次序排了队。解法：
见 How It Works 的"结果按调用 id 归位"。

**Q: 一轮多工具调用的能力从哪来？**

FC 传输层自带：`message.tool_calls` 是数组（见
[05 的实测](../05_fc_vs_react/README.md)，qwen3.8 一轮并行返回两个
查询）。本篇解决的是执行侧"怎么安全地并发跑完这一批"。
