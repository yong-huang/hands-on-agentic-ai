# 22 · Agent Card 与 A2A 风格互操作

> 每个 Agent 发布 Agent Card（JSON：描述/技能/输入输出 schema/端点）；客户端闭环 = 发现(拉卡片) → 匹配(真机 LLM 选 Agent) → 调用(统一 invoke)。零改动验证：运行时注册一张 promo 促销卡片，路由端不改一行代码即可发现并调用新 Agent。读完你能理解 Agent 间互操作的发现-匹配-调用机制，以及卡片该怎么写。

## Background

在 [21 的多 Agent 客服](../21_multi_agent_cs/README.md)里，新增一个专家要改路由代码：路由表加一项、分发逻辑对一次号。这在单个系统内部可行，因为所有专家都在同一个代码库里。

痛点出现在 Agent（智能体，能读取输入、调用工具并产出回复的程序单元）之间要跨系统协作时。不同团队的 Agent 分散在各处代码库，调用方既看不到对方源码，也不可能每接入一个新 Agent 就改一遍自己的分发逻辑——按这种方式组网，每加一个节点，全网都要跟着改。

A2A（Agent-to-Agent，Agent 间协作协议，Google 于 2025 年 4 月发布）给出的是互操作思路：把"接入"变成"发一张卡片"。Agent 对外发布一张自描述的名片，任何客户端都能拉到名片、判断要不要找它、怎么调它。

## What

Agent Card 是 Agent 的能力自描述文件，四个字段：描述、技能清单、输入输出 schema（结构定义，声明参数名与类型）、端点（endpoint，服务的网络地址，本实验用 `a2a://` 形式的标识串）。对方据此决定"要不要找你、怎么调你"，无需读对方源码。

它和 MCP 的分工一句话：MCP 是垂直协议，管 Agent ↔ 工具/资源；A2A 是水平协议，管 Agent ↔ Agent 协作——互补而非竞争。

心智模型一句话：**生态从静态组合变成动态发现——新 Agent 只发布卡片即可被网络找到。**

可以把 Agent Card 想象成招聘网站上的简历：用人方按简历上的技能栏筛人，不必把所有候选人都约来面谈。但和简历不同的是，卡片是机器可读的结构化数据，"筛选"由程序或模型按字段完成，不靠人眼。

## When to Use

典型场景，共同点是"接入方与被接入方互不见源码，或成员经常变动"：

- 跨团队、跨组织的 Agent 网络：各方只约定卡片格式，各自独立演进实现。
- 能力池经常增减的系统：营销活动的临时 Agent、节假日客服 Agent，用时注册、过时下线。
- 客户端要做成通用外壳：代码里不写死任何 Agent 名单，全部靠运行时发现。

何时不用：单一封闭系统、Agent 集合固定且只有四五个，一张静态路由表（21 的做法）更简单；只接工具不接其他 Agent，那是 MCP 的领域。

| 方案 | 差异 | 什么时候选它 |
|:--|:--|:--|
| 静态路由表 | 写死在代码里，加 Agent 必须改调用方 | 同仓库内、成员固定的系统 |
| 注册中心 + 手写适配 | 有独立注册服务，但每个调用方仍要写各自的对接代码 | 调用方少且愿意各自维护适配 |
| Agent Card 动态发现 | 发现、匹配、调用走统一协议，新 Agent 零改动接入 | 开放生态、成员频繁变动 |

## Quick Start

前置条件：离线模式（`MOCK=1`）零依赖；真机模式需在同仓库 `llm.py` 配好 `BASE_URL`/`MODEL`/`API_KEY`（技能匹配由 qwen3.8 完成）。

```bash
cd qa/22_agent_card
MOCK=1 python3 agent_card.py    # 离线: 关键词技能匹配
python3 agent_card.py           # 真实: qwen3.8 技能匹配
```

真机实测输出：

```
帮我查下订单 A1002 -> order-agent    :: 订单 A1002 状态: 运输中
我要退款           -> aftersale-agent :: 已创建退款单, 3 个工作日到账
我要投诉           -> human-agent    :: 已升级人工专席
── 运行时注册 promo-agent 卡片, 路由端零改动 ──
有什么优惠活动?     -> promo-agent    :: 本周大促: 满 199 减 30...
```

发现→匹配→调用闭环全程走通；新 Agent 零改动接入 ✓。

诚实预期：前三行验证初始四个 Agent 的闭环；第四行之后验证运行时注册——`promo-agent` 不在初始名单里，注册后立刻可被发现与调用。离线模式输出固定；真机模式匹配依赖 LLM，措辞模糊的请求可能选偏 Agent。

## How It Works

闭环三步对应三个函数：`discover()` 拉全部卡片 → `match_agent()` 按技能选卡 → `invoke()` 统一调用。

**卡片即数据。** 卡片由一个工厂函数生成，四个字段与 What 节的定义一一对应：

```python
def make_card(name, description, skills, endpoint):
    return {"name": name, "description": description,
            "skills": skills, "endpoint": endpoint}
```

每个技能还带 `input`/`output` 的 schema——调用方靠它知道传什么参数、拿什么结果，这就是"无需读源码"的落点。

**匹配只看卡片字段。** 真机模式下，客户端把所有卡片的"名字 + 描述 + 技能 id"拼成清单发给 LLM（大语言模型），要求只输出 `{"name": ..., "skill": ...}`；你在输出里看到的每个 `-> xxx-agent`，都是模型基于卡片文本做出的选择。

**零改动接入靠运行时注册。** 演示的关键只有一行：`CARD_BOOK.append(PROMO_CARD)`——把促销卡片加进登记处，下一轮 `discover()` 自然拉到它。

输出块第四段"运行时注册 promo-agent 卡片"后紧跟的那次调用，证明发现与调用完全解耦于具体 Agent 名单：路由端没有任何 `if promo` 这样的分支。

## Pitfalls & Q&A

**Q1：A2A 和 MCP 什么关系？**

互补：MCP 解决 Agent 接工具（垂直，Agent↔工具/资源），A2A 解决 Agent 之间协作（水平，Agent↔Agent）。一个完整的系统通常两者并用——工具接入用 MCP，Agent 网络用 A2A 风格的卡片发现。

**坑 1：卡片描述含糊，匹配频频选错。**

- 现象：模型把"我要投诉"路由给了 chitchat-agent。
- 原因：匹配阶段模型只看卡片字段做选择，description 写成"处理各类事务"时没有任何区分度（与 16 项目验证的工具描述规律同源：要写清"何时找我"）。
- 解法：description 写触发场景（"人工专席升级兜底"），技能清单用动词短语（"对指定订单发起退款"）。

**坑 2：匹配失败被静默吞掉。**

- 现象：明显该给售后的请求被 order-agent 接了，且全程无报错。
- 原因：真机匹配在 LLM 返回的名称对不上任何卡片时，回退到列表第一张卡，失败被掩盖。
- 解法：回退目标改为专职兜底 Agent（chitchat/human），并记录一次"匹配失败"日志，让失败可观测。
