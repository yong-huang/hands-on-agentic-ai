# 29 · Agent 可观测性（Tracing + 回放）

> 给一次确定性 Agent（自主多步执行任务的程序）执行（规划 → 3 个工具调用，含一次异常重试）埋点（在执行路径的关键位置插入记录代码）：JSONL 事件流落盘 → trace 树命令行渲染 → 成本/延迟统计面板 → 时间旅行回放（读回事件，不调任何模型逐步重放），全流程离线可跑。读完本篇，你能用最小代码搭出"记录一次、三种视图复用"的可观测性内核，并理解它为什么与生产平台同构。

## Background

程序出问题时，最常见的排查手段是加 print 日志、看函数最终返回值。单步脚本这样够用；Agent 的执行是多步的：一次规划、多次工具调用、可能还有重试，print 出来的信息散落在时间线上，拼不出完整的调用过程。

三个具体场景会撞墙。出错时，要定位"谁调了谁、哪一步炸了"，日志里找不到调用层级；优化时，要知道"贵不贵、慢不慢"，却没有按步骤拆开的耗时与 token（模型计量的文本单位）计量；复盘时，想离线重现当时现场，但语言模型重新跑一遍输出就变了，回放无从谈起。

分布式系统领域对这类问题已有成熟答案：埋点把执行过程记成结构化事件流，事后所有分析都从事件派生。Agent 领域沿用了这套思路，LangSmith、Langfuse、OpenTelemetry 等平台都是它的工业化实现。本实验不依赖任何平台，用最小代码实现同一个内核。

## What

可观测性（observability）指从系统对外输出的记录中还原其内部执行过程的能力。

本实验的内核是 span 事件模型：span 是一次有起止时间的工作单元（如 LLM 调用、工具调用），每个 span 记录类型/父子关系/输入输出/token/耗时/异常，以 JSONL（每行一个 JSON 对象的文本格式）落盘。事后一切分析——trace（由父子关系组成的调用树）、统计、回放——都从事件流派生。

心智模型一句话：**一切皆事件——渲染、统计、回放都只是同一份事件流的不同视图。**

可以把 span 事件流想象成飞机的黑匣子：飞行中只管如实记录，事后靠它还原全程。但和黑匣子不同的是，这份记录来自主动埋点——埋点没覆盖的环节就真的没有记录，事后补不回来，所以埋点要在执行路径设计时一并考虑。

## When to Use

是否需要事件流，看执行是否多步、事后是否需要分析。典型场景：

- 调试多步 Agent 时，异常藏在第几层工具调用里，需要按调用树逐层下钻定位。
- 控制成本与延迟时，需要知道每一步各花了多少 token、多少毫秒，找出最贵最慢的一环。
- 做回归测试或故障复盘时，需要不调模型、逐事件重放当时的执行路径。

何时不用：单次 LLM 调用的简单脚本，一条 print 足够；一次性的探针脚本，埋点的维护成本高于收益。

同类方案对比：

| 方案 | 差异 | 什么时候选它 |
|:--|:--|:--|
| print 日志 | 零成本，但无结构、无层级、难聚合 | 单步脚本、临时调试 |
| 自建 span 事件流（本实验） | 几十行代码，完全可控，无外部依赖 | 学习原理、内网不能出流的场景 |
| LangSmith / Langfuse 托管平台 | 现成 UI 与告警，数据要出内网 | 团队产品化后的默认选择 |
| OpenTelemetry（OTel） | 行业标准协议，需接入生态 | 已有统一可观测性基础设施的公司 |

## Quick Start

前置条件：Python 3，无第三方依赖，全流程离线确定。

```bash
cd qa/29_observability
python3 observability.py    # 生成事件 -> 渲染 -> 统计 -> 回放
```

实测（全离线；事件与结构逐字可复现，耗时见下方诚实预期）：5 个 span 落盘并一致回放（5=5 ✓）。trace 树一眼看清调用结构与异常：

```
[agent] root (0ms)
  [llm] planner (25ms, 180 tok)
  [tool] 查库存 (24ms, 40 tok)
  [tool] 查价格 (42ms, 40 tok) ⚠ 第一次尝试失败: 价格服务 503
  [tool] 下单 (23ms, 40 tok)
```

统计面板：spans=5，总 token=300，估算成本 ¥0.0006，P99 延迟（99% 的请求快于该值的尾部指标）39ms，工具调用 {查库存:1, 查价格:1, 下单:1}，异常 span 1（重试后成功）。

诚实预期：事件内容、树结构与统计口径确定可复现；耗时与 P99 是真实计时，每次运行略有不同，token 数与估算成本不变。树里的缩进层级、耗时数字都来自落盘事件，改埋点或改流程后再跑，数字会随流程变化。

## How It Works

整套系统只做一件事：把执行过程写成 span 事件，再用三种视图消费同一份 JSONL。三类视图各答一个问题：

- **trace 树**回答"谁调了谁"——缩进层级由 span 的父子关系字段渲染，你在树里看到的 `⚠ 第一次尝试失败: 价格服务 503` 就来自 span 上的异常字段；排障时先找异常 span，再下钻它的输入输出。
- **统计面板**回答"贵不贵、慢不慢"——面板上的总 token=300、估算成本 ¥0.0006 由各 span 的 token 字段累加，P99 延迟由各 span 耗时派生。
- **时间旅行回放**回答"当时发生了什么"——读回落盘事件逐步重放，不调任何模型。Quick Start 里"5 个 span 落盘并一致回放（5=5 ✓）"验证的正是这一点：语言模型重新执行输出会变，读事件重放则与当时逐字一致，调试、回归测试、故障复盘都靠它。

生产同构：LangSmith/Langfuse/OTel 的 span 模型与本篇实现一致——本篇实现的是最小核，理解它再用平台，配置项不再是黑盒。

## Pitfalls & Q&A

踩坑清单：

- 现象：任务最终成功，但中途一次调用失败在记录里毫无痕迹，复盘无从谈起。原因：只记最终结果，没把异常与重试记成事件。解法：埋点时把每次尝试都记成 span，异常写进 span 字段（本实验 trace 树中的 ⚠ 行即由此而来）。
- 现象：平均延迟看着很低，用户却偶发感到很慢。原因：均值掩盖长尾，个别慢调用被平均掉。解法：看 P99 这类尾部指标——统计面板直接给出，用它而不是均值定位慢环节。
- 现象：故障复盘时重跑一遍任务，行为和当时对不上，无法复现。原因：语言模型输出非确定，重新执行不等于当时执行。解法：用时间旅行回放——读回当时落盘的事件重放，不调模型（见上文时间旅行部分）。

**Q: 为什么坚持 JSONL 事件流，而不是直接存渲染结果？**

事件是原始事实，树/面板/回放是派生视图——存了事件，随时能补出新视图；只存渲染结果，则每个新的分析需求都要重新跑一遍 Agent。
