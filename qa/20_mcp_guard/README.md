# 20 · MCP Server 安全加固

> 给书店库存 MCP Server（原型见[项目 19](../19_mcp_server/README.md)）包一层服务端安全网关：①参数白名单（字段/类型/范围）②只读/读写权限分离 ③调用审计留痕 ④每 client（调用方）限速 ⑤参数注入特征扫描（提示词注入 / SQL 注入，SQL 即操作数据库的语言）。5 条恶意调用 + 3 条正常回归验证。读完你能掌握 server 侧防护的分层设计与执行顺序。

## Background

在加这类防护之前，一个常见的做法是"裸跑"：把工具直接注册给模型，约束写在客户端代码或系统提示词里，比如加一句"请勿调用下单工具超过限额"。

痛点出现在把 Server 开放给多客户端之后。工具参数是模型生成的自由文本，没有人保证里面装的是什么：有人在下单参数里塞 `admin=true` 之类不该存在的字段试探权限，有人在查询参数里藏 SQL 或"忽略之前所有指令"这类指令，也有脚本高频刷调用。客户端侧的约束全都可以被绕过——提示词只是建议，不是强制。

服务端安全网关因此成为标准做法：把校验收拢到 server 侧，在调用进入业务逻辑之前统一拦截，防护从"文档里的建议"变成代码里的强制声明与统一检查层。

## What

MCP Server 安全网关是一种部署在工具调用链入口的统一拦截层：所有调用先过安全检查，通过后才进入业务逻辑。本实验的网关有五层，全部在 server 侧强制执行：

| 层 | 挡什么 |
|:--|:--|
| 限速 | 滥用/打爆 |
| 权限分离 | 只读会话调写操作 |
| 参数白名单 | 白名单外字段、超范围值 |
| 注入扫描 | 参数里藏指令/SQL |
| 审计 | 兜底留痕（谁/何时/哪层/为什么） |

心智模型一句话：**服务端是唯一可信边界——客户端/模型侧的约束都能被注入绕过。**

可以把网关想象成机场安检：无论你是谁、票在哪买的，登机前都要统一过检，任何"我保证没带违禁品"的口头承诺不算数。但和机场安检不同的是，这个网关还按调用者身份区别放行（只读会话不能写），并且每一件"行李"的检查结果都记入台账（审计日志）。

## When to Use

典型场景，共同点是"有不可信的调用方，或调用会产生真实后果"：

- 把下单、改配置这类写操作暴露给模型调用时——写操作必须有权限分离与参数校验兜底。
- 同一个 Server 面向多个外部客户端开放时——限速与审计按 client 区分，才能追责和限流。
- 有合规或复盘需求时——审计日志回答"谁在何时调了什么、在哪层被拦"。

何时不用：纯本地、单用户、只读的工具（个人笔记查询），裸跑基础版 Server 即可，五层网关是不必要的复杂度。

| 方案 | 差异 | 什么时候选它 |
|:--|:--|:--|
| 提示词约束 | 零代码，但只是建议，注入即可绕过 | 无真实后果的演示 |
| 客户端侧校验 | 离调用方近，但每个客户端各写一份且可被跳过 | 客户端完全可信的内部场景 |
| server 侧安全网关 | 强制执行、集中审计，客户端无需配合 | 多客户端、含写操作、要留痕 |

## Quick Start

前置条件：已安装 `mcp` 库（同 19 项目，mcp 2.x）。在 `qa/20_mcp_guard` 目录下运行：

```bash
cd qa/20_mcp_guard
MOCK=1 python3 mcp_guard.py    # 打安全网关 (拦截矩阵)
python3 mcp_guard.py serve     # 亦可作为加固版 MCP Server 被 stdio 拉起
```

`MOCK=1` 这条会依次发出 5 条恶意调用与 3 条正常调用，把每条的拦截情况打印成矩阵。实测结果：

| 攻击 | 拦截层 | 结果 |
|:--|:--|:--|
| 白名单外字段 admin=true | whitelist | ✓ 拒绝 |
| qty=1000000 超范围 | whitelist | ✓ 拒绝 |
| sku 藏 `drop table users;--` | injection | ✓ 拦截 |
| sku 藏"忽略之前所有指令…" | injection | ✓ 拦截 |
| 只读会话调 place_order | permission | ✓ 拒绝 |

**拦截 5/5，正常调用 3/3 不受影响，审计日志 8 条**（每条含 client/tool/verdict/layer/args）。

诚实预期：5 条攻击全部被拦、正常调用无感知；拦截结果同时写入 `audit.jsonl`（每次运行会先清空重建，想留存请自行备份）。

## How It Works

核心是网关函数 `guarded_call`，五层检查有严格顺序：**限速 → 权限 → 白名单 → 注入扫描 → 业务逻辑 → 审计**。你在拦截矩阵里看到的 `layer=whitelist`、`layer=injection`，就是调用在对应检查分支被拦时记下的层名。

**白名单层**以一份声明式 schema（结构定义，声明"允许哪些字段、什么类型、什么范围"）为执行依据：

```python
SCHEMA = {'query_stock': {'sku': str},
          'place_order': {'sku': str, 'qty': (int, 1, 99)},
          'sales_stats': {'days': (int, 1, 365)}}
```

这段在做什么：`place_order` 只接受 `sku`（字符串）和 `qty`（整数，1~99）两个参数；调用里多出来的字段（如 `admin=true`）直接拒，`qty=1000000` 因超出 `[1, 99]` 被拒——拦截矩阵第 1、2 行分别对应这两个分支。

**注入扫描层**对参数值做特征匹配。SQL（Structured Query Language，操作数据库的语言）片段和提示词注入（prompt injection，用文本诱导模型忽略原有指令）各有一组特征：

```python
INJECTION_PATTERNS = re.compile(
    r'(ignore (all )?previous|system\s*:|你现在是|忽略(上面|之前|所有)指令|'
    r'drop\s+table|--\s|\bexec\b)', re.I)
```

这段在做什么：只要任一字符串参数命中这些正则（regular expression，描述文本模式的匹配表达式），如 `drop table`、"忽略之前所有指令"，立即拦截并回显命中片段——对应矩阵第 3、4 行。

**审计层**每条调用（无论放行还是拦截）都追加写入 JSONL（JSON Lines，每行一个独立 JSON 对象的日志格式），字段含 `client`/`tool`/`verdict`（判定结果）/`layer`（命中层）/`args`。

事后复盘"哪类攻击最多"全靠 `layer` 这一字段，所以每层拒绝时必须如实记录自己。

**纵深防御（defense in depth，多层防线逐层消耗攻击）是有顺序的**：限速挡滥用 → 权限挡越权 → 白名单挡畸形 → 注入扫描挡劫持 → 才轮到业务逻辑。便宜的检查放前面，让绝大多数恶意流量在早期就被终止。

## Pitfalls & Q&A

**Q1：注入检测为什么盯参数？**

工具参数是模型可控的自由文本输入，藏在里面的指令（"忽略之前所有指令…"）与 SQL（`drop table users;--`）和网页注入同源同罪——参数在进入业务逻辑前必须过特征扫描。

**Q2：白名单外字段为什么要直接拒绝而不是忽略？**

`admin=true` 这类字段被忽略时，攻击者可以慢慢试探哪些字段生效；直接拒绝让探测立刻暴露，也让 schema 成为最小权限的执行载体。

**坑 1：把注入扫描当成唯一防线。**
现象：换一种措辞（英文变体、谐音、拆字）的恶意参数可能漏拦。
原因：特征正则只覆盖已知模式，无法枚举所有表达方式。
解法：把它当作 How It Works 所述纵深防御中的一层，配合白名单、权限与审计使用——单层被绕过时其余层仍在。
