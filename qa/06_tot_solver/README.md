# 06 · ToT 求解器（BFS vs DFS）

> 思维树引擎双任务域共用：24 点（状态=剩余数字）+ 迷宫（状态=坐标）。
> LLM 只生成候选（每次扩展 1 次调用），评估打分用规则神谕；BFS/DFS 可
> 切换，剪枝=分数阈值丢弃；统计每配置 LLM 调用数与成功率。读完本篇，
> 你能判断自己的任务适不适合上树式搜索，以及怎么配组件。

## Background

让模型解需要推理的题，常规做法是思维链（Chain-of-Thought，简称 CoT，
即 01 项目对比过的单链推理）式的一次生成：顺着一条思路一步步写下去，
直到给出答案。

单链的问题是没有回头路。以 24 点（经典数字游戏：给 4 个数，用加减乘
除算出 24）为例，先试 12-4=8 走不通，就得推翻前两步换一条路——但
自回归生成（模型顺着前文逐字续写、不能回头修改）只能在前文基础上
继续，错一步就错到底。

靠调高随机性多次重跑，又没有依据决定保留哪次。

2023 年的 Tree of Thoughts 论文把推理组织成树：每一步生成多个候选，
给候选打分，按搜索策略决定展开谁、何时回头。但生成、评估、搜索三个
组件各有成本与适配条件——值不值、怎么配，要靠双任务域的对跑数据说话。

## What

ToT（Tree of Thoughts，思维树）是一种推理框架：把推理过程组织成一棵
树，每个节点是一个中间状态（如 24 点的剩余数字、迷宫所在坐标），模型
为每个节点生成多个候选下一步，评估器打分后由搜索策略决定展开与回溯。

与 CoT 的本质区别：**CoT 是链，ToT 是树**——支持分叉、评估、回溯；
设计上是把"生成"交给模型，把"验证与调度"交给程序。

可以把 ToT 想象成下棋时的"想了几个走法再挑最好的"：草稿上并列几个
方案，划掉明显差的，顺着最有希望的再想几步。但和下棋不同的是，这里的
候选与打分都由程序调度和记录，生成质量完全取决于模型本身。

| 配置 | 信号 | 语义 |
|:--|:--|:--|
| CoT | 单链自回归 | 错一步错到底 |
| ToT-BFS | 层层展开 beam=2 | 找浅解稳，调用多 |
| ToT-DFS | 高分优先深潜 | 首解快，回溯代价大 |
| ToT-BFS+剪枝 | 神谕阈值砍死分支 | 评估器越强省得越多 |

表里四个名词先解释：BFS（广度优先搜索）指先横向铺开同层所有分支再
深入；DFS（深度优先搜索）指沿一条高分分支走到底、失败再回头；beam
是每层保留的分支数；神谕（oracle）指用确定性规则实现的完美评估器；
剪枝指按分数阈值提前丢弃低分分支。

## When to Use

在决定"这道题值不值得上树"时，看三个条件是否同时成立：

- 任务需要试错与回溯——24 点、谜题、多步规划，单链一错到底的场景；
- 存在可靠的中间状态评价信号——剩余数字能否凑出目标、当前坐标离出口
  的可达性，评分有依据搜索才有效；
- 愿意用调用次数换成功率——ToT 一次求解动辄几十次 LLM（Large
  Language Model，大语言模型）调用。

何时不用：强模型加常规难度的题，单链 CoT 已经够用（真机实测 CoT 9/10，
见下表）；没有可靠评估信号时，搜索会朝错误的分数走；延迟与成本敏感的
线上任务。

| 方案 | 差异 | 什么时候选它 |
| :--- | :--- | :--- |
| CoT | 单链自回归，一次生成 | 强模型 + 常规难度；成本敏感 |
| ToT-BFS | 层层展开 beam=2 | 解的深度未知、求稳 |
| ToT-DFS | 高分优先深潜 | 解较浅、单链命中率高；接受回溯代价 |
| ToT-BFS+剪枝 | 神谕阈值砍死分支，评估器越强省得越多 | 评估信号可靠且要控成本 |

## Quick Start

前置条件：Python 3，无第三方依赖。真实模式默认连接本机 Ollama
（`http://localhost:11434/v1`，模型 `qwen3.8:latest`），环境变量
`LLM_BASE_URL` / `LLM_MODEL` / `LLM_API_KEY` 可换目标。

思考型模型（推理前先输出长思考的模型）单次调用约 100 秒，故真机只
裁剪跑 2 个配置，全量对比在 MOCK 模式完成。

```bash
cd qa/06_tot_solver
MOCK=1 python3 tot_solver.py    # 离线全量: 20 题 + 迷宫, 结果确定
python3 tot_solver.py           # 真实: CoT + ToT-BFS+剪枝 (10 题 24 点)
```

实测：

| 配置 | mock 24点(10题) | mock 调用 | mock 迷宫 | 真机 24点 |
|:--|:--:|:--:|:--:|:--:|
| CoT | 4/10 | 10 | ✗ | **9/10** |
| ToT-BFS | 10/10 | 55 | ✓ (17 次) | — |
| ToT-DFS | 10/10 | 55 | ✓ (13 次) | — |
| ToT-BFS+剪枝 | 10/10 | 30 (**省 46%**) | ✓ (17 次) | **2/10** |

真机反常结果（最有价值的发现）：**CoT 9/10 反超 ToT 2/10**——机制分析
见 How It Works。离线全量表补齐 BFS/DFS 策略对比与剪枝节省
（46% ≥ 30% 验收线）。

诚实预期：mock 结果确定、可复现；真机结果取决于所用模型的生成与推理
能力，弱于或强于 qwen3.8 的模型数字会不同，"mock 全对"不保证真机全对。

## How It Works

引擎由三个组件加一项优化构成，与任务域解耦：

- **生成器**：LLM 本体，每次树扩展调用 1 次产出候选下一步；
- **评估器**：本实验用规则神谕（oracle，指确定性规则的完美评估器），
  例如 24 点域判断剩余数字能否凑出 24；
- **搜索策略**：BFS 或 DFS 两种树搜索策略（语义见 What 节表后说明），
  引擎可切换；
- **剪枝**：评分低于阈值的分支直接丢弃，不再展开。

每个配置跑完统计两项指标：成功率与 LLM 调用数——就是实测表的
"mock 调用"列。同一引擎换状态定义（剩余数字 vs 坐标）即可服务两个
任务域。

**死锁分析：为什么真机 ToT 反而输给 CoT。** 真机评估器是完美神谕，
而 qwen3.8 的候选生成偏保守——难解需要 3/4、8/3 这类分数除法，模型
不产出这类深候选，浅候选被神谕全部剪掉，树在根上枯死；同时 qwen3.8
的思考型 CoT 一步推理已很强。

结论：**ToT 要求生成器与评估器能力匹配——评估器过强 + 生成器过弱 =
组合死锁**。这正是 ToT 论文用 GPT-4 同时做生成与评估的原因。

Quick Start 表里的两个数字都能在这里对上号：迷宫"DFS 13 次 < BFS
17 次"来自 DFS 不展开同层、直奔高分分支；"省 46%"来自剪枝把注定
无解的分支提前砍掉。

## Pitfalls & Q&A

踩坑清单：

- **现象：真机跑一轮实验要等数分钟，全量配置跑不完。** 原因：思考型
  模型单次约 100 秒，ToT 一次求解又要几十次调用。解法：真机裁剪配置
  （只跑关键对比），全量对比放 MOCK 模式。
- **现象：mock 全对的配置，真机只有 2/10。** 原因：mock 候选是脚本化的，
  掩盖了真实生成器的短板（见死锁分析）。解法：涉及模型能力的结论必须
  真机复核，mock 只用于验证引擎逻辑。

**Q1: BFS 和 DFS 怎么选？**

解浅（24 点固定 3 步）用 DFS 省调用；解深或浅解不明用 BFS——迷宫实测
DFS 13 次 < BFS 17 次，但 DFS 首解失败时要付回溯代价。

**Q2: 计算成本怎么控？**

三板斧：beam 宽度、评估器剪枝（评估器越强省得越多）、max_calls 预算
熔断（调用数超限即终止）。本次剪枝省 46% 调用。

**Q3: ToT 什么时候反而更差？**

组件能力错配时——神谕评估 + 弱生成会组合死锁（见真机 2/10 vs CoT 9/10）。
上 ToT 前先评估自己的生成器能不能产出评估器想要的候选。
