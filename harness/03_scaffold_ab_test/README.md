# 03 · 固定模型变 Harness：亲手复现"换 harness 比换模型影响大"

> 01 实验证明了"有 vs 无"执行的差别；这一篇做受控实验：**模型不动、任务
> 不动、判分器不动，只变 harness 的契约治理配置**——A 配置裸奔（无 schema
> 校验、原始错误直传、输出不截断、JSON 解析失败即判负），B 配置契约治理
> （jsonschema 校验 + 友好错误回传自纠 + 8KB 截断 + 一次结构修复机会）。
> 这正是 alphaXiv 论文"固定模型、只变支架"方法论的迷你复现。

## 1. 为什么需要它

"Harness 比模型重要"在 2026 年已有大量实证（同模型换 scaffold 42% vs 78%、
Vercel 删 80% 工具成功率反升），但别人的数据是别人的。本实验用 10 个可自动
判分的文件操作任务，在自己的 Ollama 上把这句话变成一张自己的对比表——
它同时也是项目 16 评测台的雏形：先会对比两个配置，才能回归两个版本。

## 2. 总览：核心机制一图看懂

![契约治理差异](images/scaffold_ab.workflow.svg)

**怎么看这张图**：上下泳道是同一模型的两种待遇。A 组的工具调用参数直传、
错误原样甩回；B 组多三道工序——参数校验、错误翻译、输出截断，外加一次
"输出不是合法 JSON"的结构修复机会。差异全部集中在 `exec_tool()` 一个函数。

心智模型一句话：**契约治理 = 让模型每次失败都拿到"下一步该怎么改"的确定性信息。**

## 3. 快速开始

```bash
cd harness/03_scaffold_ab_test
MOCK=1 python3 scaffold_ab_test.py --selftest   # 离线自检
python3 scaffold_ab_test.py --tasks 3           # 冒烟（3 任务 × 2 配置）
python3 scaffold_ab_test.py                     # 验收口径：10 任务 × 2 配置
```

跑批断点续跑：`results/trial_*.json` 已存在的任务自动跳过。产物
`results/COMPARE.md` 是自动生成的对比表（解决率 / 平均轮次）。

<!-- 真机跑批 2026-09-18, qwen3.8:latest, temperature=0, 10 任务 × 2 配置 -->

```text
[A0-A9] 全部 ✅，平均 3.3 轮
[B0-B9] 全部 ✅，平均 3.2 轮
配置 B 修复机会使用次数: 0 次
A/B 逐任务轨迹 diff: 完全一致
```

| 配置 | 解决率 | 平均轮次 | 轨迹 diff |
|:--|:--:|:--:|:--|
| A 裸奔 | 10/10 | 3.3 | 与 B 完全一致 |
| B 契约治理 | 10/10 | 3.2 | — |

**零差异——这是本次实验最重要的发现，不是失败。** 逐字相同的轨迹说明：
20 次跑批里 40 个工具调用全部一次成功，A 组的三道"裸奔惩罚"（无校验、
原始错误、无截断）**一次都没被触发**。qwen3.8（27B）在这种简单任务域里
根本不犯错，契约治理自然无从体现。这与 alphaXiv 论文的发现同构：固定模型
只变支架版本，解决率围绕均值停滞——**支架差异要在故障域才显形**。

三个推论写进后续实验的设计约束：

1. **契约治理的价值在故障域**——05 工具契约实验必须注入扰动（错参数、
   坏路径）才能测出 A/B 分野；强模型 + 顺任务测不出 harness 差异；
2. **修复预算 0 次使用**说明强提示词下模型一次就对，预算体系（项目 09）
   要按弱模型/难任务校准；
3. **temperature=0 的可复现性**再次应验：想看分布差异，需要采样温度 > 0
   或任务难度梯度——评测台（项目 16）的任务集必须分难度档。

引用文献里的"42% vs 78%"发生在 SWE-bench 级难度的故障密集域；本实验
用 10 个顺任务复现了它的对照命题：**顺任务域里 harness 不可区分**。
两半合起来才是完整结论。

## 4. 核心概念

### 4.1 受控变量：只许变一处

| 要素 | A 配置（裸奔） | B 配置（契约治理） |
|:--|:--|:--|
| 模型 / 任务 / 判分器 | 相同 | 相同 |
| 参数校验 | 无，args 直传 | 缺必填参数即拒绝并说明 |
| 错误回传 | 原始 `repr(e)` | 归纳为"哪里错、怎么改" |
| 输出截断 | 无 | 8KB |
| JSON 解析失败 | 直接判负 | 给一次结构修复机会 |

### 4.2 错误回传是工具契约的灵魂

A 组拿到 `KeyError('path')` 只知道"出错了"；B 组拿到
"参数校验失败: 工具 write_file 缺少必填参数 ['path']，请重新输出完整
JSON"——**错误信息的质量决定自纠的成功率**。这是 05 工具契约实验的主题预演。

### 4.3 修复预算是 harness 的显式资源

B 组的"一次结构修复机会"是有意设计的稀缺资源（不限次会变成死循环津贴）。
09 预算实验会把它推广成完整的 token/轮次/修复次数三维预算体系。

## 5. 代码关键点

```python
exec_tool(cfg, name, args, sandbox)  # A/B 全部差异集中在这一个函数
feed(cfg, text)                      # B: 8KB 截断；A: 原样
write_compare(recs)                  # 自动生成 COMPARE.md 对比表
```

坑（与 01 共通的不再重复）：**mock 序列是跨任务共享的迭代器**，冒烟时
各任务会"抢剧本"，只适合验证管道不适合验证行为；真机数据请看真模型。

## 7. 深入要点

- **为什么不用更强模型"顺便"提分？** 受控实验的效力来自只变一个变量；
  混入模型升级就无法归因。项目 18 会做反方向（固定 harness 变模型）补全 2×2。
- **B 组修复机会用掉几次？** 真机答案是 **0 次**——40 个调用全部一次成功。
  这提示修复预算要按故障域校准，也说明本任务集还没踩到模型的能力边界。
- **解决率之外为什么记录轮次？** 论文的教训：支架演进可能"功能不变、成本
  翻倍"。轮次是 token 成本的代理指标，回归评测必须看两个维度。

## 8. 总结

真机给出的是零差异：强模型 + 顺任务域里，harness 契约治理完全隐形——
结合引用文献的故障域数据，完整结论是**"harness 的价值与任务故障密度成正比"**。
学会用受控实验并诚实报告反常数据，比拿到一张好看的表更重要。
