# 02 · 拆解工业 Harness：Claude Code 分层地图与四层对照

> 本篇不写代码，先解剖工业级 harness（模型外围负责执行与约束的设施层）的分层结构，产出两张地图：**九模块职责表**与 **Model/Harness/Framework/Platform 四层对照**。读完你能回答"每一层为什么存在、失效了会怎样"，并掌握"Harness AI 与 Agentic AI 差在哪"的论述框架。

## Background

从零造 agent（能自主决策并调用工具完成任务的程序），最常见的起点是"对话循环 + 一把工具函数"：接上模型 API，把可调用的函数列给模型，模型点名哪个就执行哪个。带工具的 chat 循环（模型对话加工具调用的最简循环）由此成为多数自研项目的第一版。

这个形态做 demo 够用，进真实任务就暴露缺口：误操作没有拦截、token（模型计费与限长的最小文本单位）花超没人管、多轮之后上下文（模型当轮能看到的全部对话内容）失守。这些能力"不出事看不见"，动笔前最容易整个漏掉；功能堆完，也难回答"自研的和成熟产品差在哪"。

工业界的成熟实现把这些答案写进了源码。与其靠试错补课，不如先解剖一个工业级实现，把它隐性的工程决策画成显式的地图——这就是本实验的方法：拆解 Claude Code，产出两张自己画的地图。

## What

harness（模型外围负责执行、约束与反馈的工程设施层）是把"模型可能的智能"翻译成"被允许的可靠工作"的确定性工程层。工业级代表 Claude Code（Anthropic 的命令行编程 agent）据源码拆解转述，内部有五层结构、约 51 万行工程代码——模型只占其中几乎为零的推理调用。

先辨析一组概念：**Harness AI 与 Agentic AI 差在哪**——范式 vs 工程层；what/why vs how/where；概率性推理 vs 确定性规则。六字版：**范式定上限，harness 定下限。**

两条支撑论断：同一模型换 scaffold（模型外围的提示与结构支撑）得分 42% vs 78%；生产故障大多来自 harness 而非模型。完整论述见 [REPORT.md §4](REPORT.md)。

九个模块按职能分三条线记：

- **主干道**：启动链路（从命令行启动到可对话的准备过程）→ Prompt 装配（把系统提示、工具说明、历史对话拼成模型输入）→ 主循环（反复执行"要决策→执行→回喂"的循环体）；
- **执行面**：工具契约（向模型声明工具名、参数与返回格式）→ 权限门（执行前按策略放行或拦截）→ 沙箱（限制文件与网络副作用的隔离执行环境）；
- **续航面**：上下文管理（决定哪些信息进入模型有限的输入窗口）→ 会话/记忆（跨轮保存与恢复状态），扩展机制（外挂技能与插件的挂载点）挂载一切。

心智模型一句话：**模型在区域外，harness 在区域内——边界画在哪，权力就在哪。**也可以把 harness 想象成跨国公司的本地执行团队：总部（模型）出意图，本地团队决定哪些能落地、怎么落地，并把结果汇报回去。但与人类团队不同的是，harness 是确定性代码，同样的输入必然触发同样的动作，没有自由裁量。

## When to Use

什么时候需要画这张分层地图：凡是要为模型补执行与治理能力的事，先看工业实现的答案，能少走整段弯路。

典型场景：

1. 准备动手自研 harness 或 agent 运行时之前：先列出工业实现的分层清单，逐层确认"我的设计里这层在哪"。
2. 评估各家 agent 产品（Claude Code、Cursor、Gemini CLI 等）做技术选型时：功能清单已趋同，用四层对照比**假设**而不是比功能。
3. 向团队解释"接个模型 API 不等于能交付"时：四层对照是最省力的沟通框架。

何时不用：只做单轮文本任务、不涉及工具执行与权限治理时，五层九模块的地图是过度设计。

四层对照（一句话测试）：

| 层 | 回答的问题 | 换掉它要重写什么 | 代表 | 什么时候关注它 |
|:--|:--|:--|:--|:--|
| Model | 会不会 | 不用改任何东西 | qwen3.8 | 选型、评估能力上限 |
| Harness | 做不做得到、被允许做什么 | 不用改模型 | Claude Code、本系列 mh/ | 落地执行、权限与治理 |
| Framework | 多 agent 怎么组合 | 改 harness 交互 | LangGraph、CrewAI | 多 agent 协作编排 |
| Platform | 组织怎么治理一群 harness | 改组织接入 | Databricks Agent Bricks | 组织级批量治理 |

**"Frameworks compose agents. Harnesses run them."**（Winder.AI）

## How It Works

### 一次工具调用的旅程

九个模块不是并列清单，而是一条流水线：主循环向模型要决策 → 工具调用先过权限门 → 放行后在沙箱执行 → 结果经上下文治理回喂主循环；记忆与扩展机制分别从下方/上方挂载。九个模块全部是确定性工程代码，区域外只有两个东西：终端用户和 LLM（大语言模型）。

对照 Quick Start 里的职责表读这条流水线：主干道三模块决定"这次调用怎么开始、怎么循环"，执行面三模块决定"这次调用能不能发生、在哪发生"，续航面模块决定"模型每轮能看到什么、记住什么"。

### 权限门为什么在工具系统和沙箱之间

位置不是随意的：拦截点必须放在"意图"与"副作用"之间。模型输出的只是意图（"我想执行这条命令"），真正的文件删除、网络请求发生在工具执行时，所以门装在工具系统之后、沙箱执行之前，而不是模型和工具之间。

这句话浓缩了第三代设计哲学——**"The model decides what to do. The harness decides what's allowed."**：不定义行为，只定义约束边界（07 权限门实验实现的就是这个位置）。

失效反例也在这里：把门装到模型与工具之间，等于相信模型的自我汇报，01 实验已经演示过自我汇报的不可靠。

## Pitfalls & Q&A

### 踩坑清单

1. **把 UI 当 harness**。现象：以为终端界面就是 harness 的主体。原因：界面最显眼，最先被看到。解法：终端界面只是启动链路的外壳（suedbroecker 列的三个"≠"之一）；同理执行环境（沙箱）也不必然是 harness 的一部分——但治理它的策略代码是。
2. **拿功能清单比 harness**。现象：对比各家产品得不出结论，功能表几乎一样。原因：2026 年各家功能已趋同（三家支持 ACP（Agent Client Protocol，agent 互相驱动的开放协议）互相驱动）。解法：改比**假设**——模型锁不锁定、部署在哪、谁能改行为。

### 深入问答

**Q：Claude Code 五层和九模块是什么关系？**

五层是源码包结构，九模块是职能切分；一一对应关系见 [REPORT.md §2](REPORT.md) 表格备注。

**Q：为什么说护城河在 harness 不在模型？**

模型商品化后可随换；沙箱、权限、预算、审计编码的是组织政策与机构知识，模型升级不会废除它们（Winder.AI）。

**Q：Agent QA 是什么？**

alphaXiv 论文实证：支架演进不必然提升解决率，却让 token 翻倍——所以 harness 需要回归评测（固定模型、固定任务集），见 16 评测台。
