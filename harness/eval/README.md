# 16 · Harness 评测台：Agent QA 回归管线

> alphaXiv 论文的核心警示：支架（harness，包在模型外面的执行框架）演进
> 不必然提升解决率（任务通过比例），却让 token（模型计量文本长度的
> 单位）消耗 391K→668K——"功能正常"的测试抓不住效率型退化。
> `harness/eval/` 是本系列的质检环节：固定 10 任务集、固定判分器、
> 只变配置的对比。读完本篇你能说清评测台为何固定任务集、只留一个
> 变量，以及回退如何被自动拦下。

## Background

没有评测台时，harness 的改动靠手点几个例子：任务解出来了就合入。这类
检查只回答"能不能用"。痛点是效率与成本的退化它看不见：alphaXiv 论文
测量到，支架一路演进，解决率不升，token 消耗却从 391K 涨到 668K——
每次改动都可能"功能照常、账单翻倍"。

来龙去脉：03 实验证明了"测 harness 要受控对照（只留一个变量、其余
固定，才能把差异归因到它）"，本篇把这条原则产品化——任务集入库存、
配置一行切换、结果自动出表。

此后 mh/ 的任何改动（新模块、参数调整、模型切换）都可以一键回归
（改动后重跑既有检查，确认没有弄坏原有行为），这正是支架工程的刚需
（Agent QA，针对代理的质检学科），也是 17 终极总装与 18 收尾对照要
用到的基础设施。

## What

评测台机制：左半边固定不变——10 个任务（含串行依赖：后一个任务要用到
前一个任务的产出，09 的教训）与文件系统判分（自动检查任务产出文件的
判分函数，01 的哲学）；右半边是唯一变量——两套配置。

baseline（基线配置）v0.1 是 04 水平的裸 loop（无防护的模型-工具循环）
加无防护 run_bash；full v1.0 是契约（每个工具调用前按声明的参数格式
做校验，05 实验的主题）、沙箱（限制时长与输出大小的受限执行环境）、
预算齐备的完整形态。

产出三维对比表，任一指标向坏方向变化即标 🔴 回退并 exit 1（shell 的
失败退出码，非 0 即失败）。

心智模型一句话：**评测台回答的不是"能不能用"，是"比昨天强了多少、
代价是什么"。**

| | baseline v0.1 | full v1.0 |
|:--|:--:|:--:|
| 工具 | 裸 subprocess(15s 兜底) | `@tool` 契约校验 + 沙箱(3 秒超时/8KB 输出上限/危险命令守卫) |
| 预算 | 无 | max_turns=10 + token 止损 |
| 崩溃处理 | 单任务炸死全批 | 评测台捕获, 记 ❌ 继续 |

## When to Use

典型场景：

- 给 mh/ 加新模块、调参数、换模型的前后各跑一遍，用同一张表回答
  "值不值"。
- 支架类改动合入前挂门禁（不合标准即阻止合入的自动检查），回退即
  拦下。
- 怀疑某个防护"是不是把代理拖慢了"时，用受控对照拆出它的代价。

何时不用：改动只碰 demo 脚本、不影响 harness 行为时，无需回归；
10 任务集是回归哨兵，不能代替面向真实分布的大规模评测。

同类做法对比：

| 方案 | 差异 | 什么时候选它 |
|:--|:--|:--|
| 手点几个例子 | 快，但只看"能不能用" | 一次性 demo |
| 功能正确性测试 | 抓行为对错，不抓效率退化 | 纯逻辑模块 |
| 本评测台（本篇） | 固定任务集 + 受控配置 + 三维指标 | harness 行为改动 |
| 线上监控 | 真实流量、事后发现 | 已部署系统 |

## Quick Start

前置条件：Python 3 与 bash 环境；`MOCK=1` 走离线管道，不需要模型
服务；真机全量需要一个可用的模型接入，2 配置 × 10 任务约 1 小时；
冒烟命令同样走真机模型，仅规模缩小（1 配置 × 3 任务）。

```bash
cd harness/eval
MOCK=1 bash run.sh            # 离线: 管道自检(两配置打平, 无回退; 🔴 标红逻辑见 compare())
bash run.sh                   # 真机全量: 2 配置 × 10 任务(约 1 小时)
python3 eval_run.py --profile full --tasks 3   # 快速冒烟
```

冒烟（smoke test，用最小规模验证管线通不通）建议先跑第三条命令
（`--profile` 即选择哪套配置），确认环境正常再上全量。

真机实测（10 任务 × 2 配置，`results/` + `COMPARE.md` 为产物）：

```text
| 指标 | baseline v0.1 | full v1.0 | 变化 |
|:--|:--:|:--:|:--:|
| pass | 9/10 | 9/10 | +0 |
| avg_turns | 5.0 | 5.0 | +0% |
| avg_tokens | 100 | 100 | +0% |
```

诚实预期：真机数值随模型波动；本例串行任务集下两配置完全打平
（+0%，无回退），唯一失败的 task 9 在两个配置下同样失败——是任务/
模型能力边界，不是配置回退，门禁放行。

实现入口速览：

```python
TASKS            # 10 任务: (指令, 文件系统判分函数)
build_tools(p)   # 唯一变量: profile → 工具表
compare(res)     # 对比表生成 + 回退标红 + exit 1
run.sh           # 两配置跑批 + 自动对比
```

## How It Works

三维指标各有方向：**解决率**（有效性，越高越好）、**平均轮次**（收敛
速度，越低越好）、**est token**（成本，越低越好）。你在输出里看到的
三行各对应一维；任一格向坏方向变化，`compare(res)` 把该格标 🔴 并
exit 1。阈值放宽与否是策略决策，"发现即报告"是评测台的本分。

**回退就该 exit 1——这是门禁语义**：评测不过，改动不合入。生产里对应
"支架的 PR（合并请求）也要跑支架回归"——alphaXiv 论文呼吁的 Agent QA
学科的最小实现。回归评测的"门禁"语义可直挂 CI（持续集成：代码合入前
自动跑检查的机制）。

评测台自身的健壮性有三条：单任务崩溃被捕获记 ❌ 而非中止全批；任务集
含串行依赖（可批量任务测不出配置差异，09 的教训）；token 用字符估算
（准确性与取舍见下方 Q2）。

## Pitfalls & Q&A

踩坑清单：

- **双重包装 bug（评测台首跑抓到的真 bug）**
  - 现象：第一版 full 配置 10 任务全灭，全部顶满轮次、0 产出。
  - 原因：run_bash 解包了外层包装函数的**字符串**，而非 sandbox_run
    的元组（双重包装 bug）。
  - 解法：修正解包，让 run_bash 拿到沙箱返回的元组。门禁 exit 1 的
    语义第一天就兑现了价值。

Q&A：

**Q1: 为什么对比配置而不是对比 git 版本？**

语义等价：git 快照之间的差异最终都体现在行为配置上。等 mh/ 有正式
版本后，`--profile` 换成 `--ref v0.1 v1.0` 即可（接口已留）。

**Q2: est token 够准吗？**

方向正确、粒度够回归用；精确计量（eval_count）是后续优化，不能阻塞
门禁上线。
