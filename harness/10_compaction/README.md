# 10 · 上下文压缩：让 agent 跑得久

> 控制面（07-09）管"敢跑"；本篇开始管"跑得久"。context rot——长任务里
> 上下文被工具结果和重复历史撑爆、模型逐渐遗忘早期关键事实——是 Databricks
> 失败模式清单的头号常客。`mh/compaction.py`：估算 token 超阈值就把中段
> 历史压缩为模型自生成的结构化摘要（硬性要求保留文件名/数字/路径），
> 头尾保留、原地替换，loop 依旧零改动。

## 1. 为什么需要它

40 轮串行任务的历史轻松破万 token：本地 32K 窗口被吃掉大半，模型开始
"忘记"第 5 轮的约定。Databricks 的公式是**压缩 + 按需注入**——本篇做
前者：中段历史 → ≤250 字摘要 + 头尾保留。Salesforce 说这是防"context
rot"的核心手段，02 解剖图里它属于"续航面"（会话/记忆是它的邻居）。

## 2. 总览：核心机制一图看懂

![上下文压缩流程](images/compaction.workflow.svg)

**怎么看这张图**：每轮请求前检查估算 token；超阈值就"头 2 条 + 尾 6 条
保留、中段送摘要器"，摘要以 `[历史摘要]` 消息拼接回历史——
`messages[:] = compacted` 原地替换，loop 持有的同一列表同步瘦身。
摘要全文进事件表留档（暗桩检查的依据）。

心智模型一句话：**压缩不是删历史，是把历史换成一张"必带关键事实"的便签。**

## 3. 快速开始

```bash
cd harness/10_compaction
MOCK=1 python3 demo.py                  # 离线管道自检
python3 demo.py                         # 真机串行长任务（约 30-60 分钟）
python3 demo.py --threshold 3000        # 放宽阈值对照
```

真机实测（2026-09-20，qwen3.8，20 目录串行任务约 60 轮，阈值 900）：

```text
① 压缩 ≥2 次: ✅ (实际 14 次)
② 任务级暗桩存活: f07.txt ✅ | 数字42 ✅ | deep/dir03 ✅ | 单次摘要最高 2/3
③ 触发前峰值有界(≤阈值×1.3): ✅ | 峰值 [942 … 922]，全部 ≤ 阈值×1.12
目录建成: 20+ | deep/dir03 嵌套: ✅
```

14 次压缩之后，三个暗桩事实**全部活在磁盘上**——模型对"dir07 要叫
f07.txt、dir03 要嵌套、dir15 写 42"的记忆穿越了 14 轮历史瘦身没有丢，
这就是压缩防御 context rot 的直接证据。调试路上还修了一个比压缩本身
更重要的坑：qwen3.8 在复杂长任务上会**过度思考**，1200 token 全进
`thinking` 字段导致 `content` 与 `tool_calls` 双双为空、`/no_think`
提示词拦不住——最终用 Ollama 服务端 `think: false` 参数解决（已固化进
`mh/llm.py`），并记入踩坑：提示词级软开关挡不住推理癖，关键行为要服务端硬开关。

## 4. 核心概念

### 4.1 摘要器也是模型：硬性要求 + 暗桩兜底

摘要由模型自己生成（省一套摘要模型），prompt 里"必须原样保留文件名/
数字/路径"是**硬性要求**；但模型摘要不可全信——所以事件表里存摘要全文，
验收用 3 枚暗桩（f07.txt / 42 / deep/dir03）做存活检查。**不可信输出 +
确定性断言**是本系列一贯的判分哲学。

### 4.2 头尾保留的份额

头 2 条（system + 任务描述）是身份与目标，永不压缩；尾 6 条是模型当前的
工作记忆，压缩它等于失忆。中间段才是摘要的对象——这与人开会只记结论、
盯住当前议题是一个道理。

### 4.3 与 09 预算的分工

预算是"不许再花"，压缩是"花得更省"。两者叠加才是长任务的正解：压缩
延寿，预算兜底。09 结论（任务须不可批量）在本篇再次生效——20 目录串行
构建，模型无法一条命令做完，压缩才有触发机会。

## 5. 代码关键点

```python
compact_chat_fn(chat_fn, threshold=1500, keep_recent=6)
# → _chat(messages, tools): 估算→超阈→摘要→messages[:] 原地替换
_compactor.events  # [{call, before, after, summary}] — 验收与调试全靠它
```

`messages[:] = compacted` 是全篇最关键的一行：chat_fn 收到的列表与
loop 持有的是同一个对象，原地替换让主循环**无感**瘦身——对比 06 的
cwd 教训，这次是刻意利用别名而非被它坑。

## 7. 深入要点

- **为什么阈值用估算而不是精确 token？** 估算（字符/3）零成本、方向正确；
  精确计量要解析 Ollama 的 eval_count 且每轮不同。压缩触发不需要精确性，
  需要稳定性——16 评测台再上精确计量。
- **摘要丢了事实怎么办？** 三层兜底：prompt 硬性要求、暗桩验收、关键
  工具结果保留在尾部未压缩区。12 记忆系统会把"永不许丢"的事实再升一级。
- **为什么不用占位符就够了？** 只截断不留摘要，模型知道"发生过 20 件事"
  却不知道内容——[历史摘要] 消息正是 Salesforce 说的 compression+injection
  里的 injection 部分。
- **压缩本身也花 token？** 是——每次摘要一次 LLM 调用。论文的教训（支架
  通胀）提醒我们：压缩频率是成本项，阈值过低反而更贵。
