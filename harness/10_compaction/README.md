# 10 · 上下文压缩：让 agent 跑得久

> 上下文压缩在对话历史超长时，把中段历史替换为模型自己生成的结构化摘要：头尾保留、原地替换，让 agent（能自主决策并调用工具完成任务的程序）跑得久。读完本篇，你能跑通 20 目录串行长任务的压缩演示，学会用暗桩（预先埋好的已知事实）验证关键事实没有在压缩中丢失。

## Background

长任务的历史处理历来有两种老办法：一是任由历史原样滚动，二是最旧的消息直接截断。前者窗口迟早用尽，后者模型只知道"发生过很多事"，不知道内容。

痛点场景：40 轮串行任务的历史突破一万 token，本地模型 32K 的上下文窗口（模型一次能读入的最大文本量）被吃掉大半，模型开始"忘记"第 5 轮立下的约定。这个现象有专门名字：context rot（上下文腐化，模型随历史膨胀逐渐遗忘早期关键事实）——Salesforce 称之为长跑 agent 的核心风险。

Databricks 给出的公式是"压缩 + 按需注入"，本实验实现前半：在历史超阈值时把中段换成摘要。02 实验的架构解剖图里，它属于"续航面"（会话、记忆是它的邻居）。

## What

上下文压缩是一种在历史超过阈值时、把中段历史替换为结构化摘要的机制。`mh/compaction.py` 在每轮请求前检查估算 token（计量模型输入输出文本长度的单位，本实验按字符数除以 3 估算），超阈值就执行"头 2 条 + 尾 6 条保留，中段送摘要器"。

摘要器由同一个模型兼任。摘要以一条 `[历史摘要]` 消息拼接回历史，再用 `messages[:] = compacted` 原地替换——主循环持有的同一个列表同步瘦身，主循环零改动。摘要全文进事件表（记录每次压缩调用的明细列表）留档。

保留份额的分工：头 2 条（system，即系统设定消息 + 任务描述）是身份与目标，永不压缩；尾 6 条是模型当前的工作记忆，压缩它等于失忆；中间段才是摘要对象。

心智模型一句话：压缩不是删历史，是把历史换成一张"必带关键事实"的便签。

可以把压缩想象成开长会后整理纪要——只记结论、盯住当前议题。但和人不同的是，纪要由与会者自己写，可能漏记，所以本实验用暗桩（预先埋好的已知事实，如"dir15 要写 42"）做事后验收。

## When to Use

三个信号：任务轮次多（几十轮起）、模型上下文窗口小、早期事实会在后期被反复引用。

典型场景：

- 数十轮的串行构建任务（例如依次建 20 个目录并写文件）；
- 本地 32K 窗口模型跑长会话，历史逼近上限；
- 工具输出巨大（长日志、长表格）持续涌入历史。

何时不用：任务三五轮就结束；使用 128K 以上大窗口模型且历史远未到阈值；单轮问答没有"历史"可言。

同类方案对比：

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| 历史滚雪球（不处理） | 信息零损失，窗口迟早耗尽 | 几轮内结束的短任务 |
| 截断最旧消息 | 省窗口，早期事实直接消失 | 早期事实后文不再引用 |
| 滑动窗口（只留最近 N 条） | 实现最简，丢失无补偿 | 内存有硬上界、事实集中在近期 |
| 摘要压缩（本篇） | 早期事实以摘要形式存活 | 长任务且早期事实仍被引用 |
| 外部记忆库 | "永不许丢"的事实落盘、按需取回 | 关键约定需要跨会话存活（12 实验的主题） |

## Quick Start

前置条件：进入 `harness/10_compaction` 目录，Python 3 与 Ollama 本地模型；`MOCK=1` 走离线假模型，秒级完成；真机串行长任务约 30-60 分钟。

```bash
cd harness/10_compaction
MOCK=1 python3 demo.py                  # 离线管道自检
python3 demo.py                         # 真机串行长任务（约 30-60 分钟）
python3 demo.py --threshold 3000        # 放宽阈值对照
```

真机实测（20 目录串行任务约 60 轮，阈值 900）：

```text
① 压缩 ≥2 次: ✅ (实际 14 次)
② 任务级暗桩存活: f07.txt ✅ | 数字42 ✅ | deep/dir03 ✅ | 单次摘要最高 2/3
③ 触发前峰值有界(≤阈值×1.3): ✅ | 峰值 [942 … 922]，全部 ≤ 阈值×1.12
目录建成: 20+ | deep/dir03 嵌套: ✅
```

诚实预期：离线模式能跑通管道并给出压缩统计（实测压缩 5 次，① ③ 两项 ✅），但暗桩存活（②）显示 ❌ 属预期——假模型写不出真摘要，不代表失败；三行验收全绿以真机为准。阈值放宽到 3000 时，压缩触发次数会明显减少，可用于对照观察。

实现代码：

```python
compact_chat_fn(chat_fn, threshold=1500, keep_recent=6)
# → _chat(messages, tools): 估算→超阈→摘要→messages[:] 原地替换
_compactor.events  # [{call, before, after, summary}] — 验收与调试全靠它
```

这两行在做什么：`compact_chat_fn` 把压缩逻辑包在 `chat_fn`（与模型对话的函数）外面——每轮先估算 token，超阈值就生成摘要并原地替换历史；`_compactor.events` 记录每次压缩的调用参数、压缩前后 token 数与摘要全文，验收与调试都从这里读。

## How It Works

最核心的一行是 `messages[:] = compacted`：`chat_fn` 收到的列表与主循环持有的是同一个对象（别名，即两个变量指向同一份内存数据），切片赋值让它原地变短，主循环无感瘦身。对比 06 实验的 cwd 教训（别名意外共享导致串目录），这次是刻意利用别名而非被它坑。

摘要器也是模型：硬性要求 + 暗桩兜底。摘要 prompt 里写明"必须原样保留文件名/数字/路径"；但模型摘要不可全信，所以事件表存摘要全文，验收用 3 枚暗桩（f07.txt / 42 / deep/dir03）做存活检查。"不可信输出 + 确定性断言"是本系列一贯的判分哲学。

Quick Start 输出的三行验收与机制一一对应：① 的 14 次来自每轮的超阈检查；③ 的峰值 [942 … 922] 全部 ≤ 阈值×1.12，说明触发前历史确实有界。

② 的三个暗桩全部存活——模型对"dir07 要叫 f07.txt、dir03 要嵌套、dir15 写 42"的记忆穿越 14 轮历史瘦身没有丢，这是压缩防御 context rot 的直接证据。

## Pitfalls & Q&A

踩坑清单：

- **qwen3.8 在复杂长任务上会过度思考**
  - 现象：1200 token 全进 `thinking` 字段，`content` 与 `tool_calls` 双双为空，`/no_think` 提示词拦不住。
  - 原因：提示词级的软开关挡不住模型的推理癖。
  - 解法：用 Ollama 服务端 `think: false` 参数解决。关键行为要服务端硬开关。

**Q1：阈值为什么用估算而不是精确 token？**

估算（字符数除以 3）零成本、方向正确；精确计量要解析 Ollama 的 `eval_count` 且每轮不同。压缩触发不需要精确性，需要稳定性——16 实验（评测台）再上精确计量。

**Q2：摘要丢了事实怎么办？**

三层兜底：prompt 硬性要求、暗桩验收、关键工具结果保留在尾部未压缩区。12 实验（记忆）会把"永不许丢"的事实再升一级。

**Q3：为什么只截断不够，还要注入摘要？**

只截断不留摘要，模型知道"发生过 20 件事"却不知道内容。`[历史摘要]` 消息正是 Salesforce 所说 compression+injection（先压缩历史、再把要点注回对话）里的 injection 部分。

**Q4：压缩本身也花 token？**

是——每次摘要是一次 LLM 调用。支架通胀（scaffold bloat，支架自身的开销反噬任务收益）的教训在此适用：压缩频率是成本项，阈值过低反而更贵。

**Q5：与 09 实验的预算怎么分工？**

预算是"不许再花"，压缩是"花得更省"，两者叠加才是长任务的正解：压缩延寿，预算兜底。09 的结论（任务须不可批量）在本篇再次生效——20 目录串行构建，模型无法一条命令做完，压缩才有触发机会。
