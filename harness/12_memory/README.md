# 12 · 跨会话记忆：A 学到 · B 遵循 · C 遗忘

> 跨会话记忆把"值得长期记住的事实"存进人类可读的文件：会话收尾自动沉淀（提取值得记住的事实）、新会话自动带回、随时可删除。读完本篇，你能跑通"学到→遵循→遗忘→验证无残留"四会话闭环演示，理解记忆系统为什么必须做错能改。

## Background

没有记忆机制时，每个新会话都要重新交代一遍：用哪个测试框架、路径怎么约定、我是谁。会话一结束，这些信息全部归零，下一次从头再来。

痛点场景有两层：一层是重复劳动——每次会话都是复读机式的自我介绍；另一层更危险，叫记忆污染（旧事实留在上下文里误导新任务）。所以解药不是"多记"，而是记下的东西看得见、可追溯、可删除。

跨会话记忆因此出现：把事实存进文件而不是模型的"脑子"。Databricks 的 agent（能自主决策并调用工具完成任务的程序）组件清单里，"文件系统与持久存储"和"记忆与上下文管理"是并列的两项，本实验把它们接通。

## What

跨会话记忆是一种把事实存进文件、并在新会话自动带回给模型的机制，三个入口：

- **沉淀**：会话收尾时 `consolidate()` 让模型从对话提取不超过 3 条值得长期记住的事实，带时间戳写入 MEMORY.md（一个人类可读的 Markdown 文件，一行一条）；
- **回带**：新会话启动时把记忆块拼进 system（系统提示词，会话开头给模型的设定消息）——模型在从未见过任务描述的情况下自觉遵守；
- **遗忘**：`forget(关键词)` 删除含该关键词的条目，下次回带的记忆随之清空。

三层记忆至此集齐：

| 层 | 模块 | 粒度 | 载体 |
|:--|:--|:--|:--|
| 工作记忆 | 10 实验（压缩） | 本任务内 | 上下文窗口 |
| 任务记忆 | 11 实验（会话） | 本任务进度 | checkpoint.json |
| 长期记忆 | 本篇 | 跨任务世界观 | MEMORY.md |

心智模型一句话：记忆的可靠性不靠模型记性好，靠"看得见、可追溯、可删除"。

## When to Use

需要同一套偏好、约定或事实跨会话复用时使用：信息由会话中产生、又要在会话之外存活。

典型场景：

- 新会话自动带上项目约定（代码风格、目录结构、工具链），不必每次重申；
- 个人助手记住用户偏好（输出语言、命名习惯），换会话依然生效；
- 长期协作的 agent 逐步沉淀项目事实（"部署脚本在 scripts/ 下"）。

何时不用：一次性任务没有沉淀价值；事实变化太快，记下即过期；知识量大到需要按需检索，该用检索系统而非全量注入。

同类方案对比：

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| 每次在提示词里重申 | 零机制，重复劳动 | 一次性会话 |
| 开发者在 system 里写死约定 | 改约定要改代码 | 稳定不变的团队规范 |
| MEMORY.md 记忆（本篇） | 模型沉淀，人类可读、可手改、可删 | 偏好与事实会逐步累积的场景 |
| 向量库检索 | 记忆条目上万时按需取回 | 全量注入放不下的规模 |
| RAG（检索增强生成） | 从大文档集检索后注入 | 知识来自文档而非会话沉淀 |

## Quick Start

前置条件：进入 `harness/12_memory` 目录，Python 3 与 Ollama 本地模型；`MOCK=1` 走离线管道自检，不加则跑真机四会话。

```bash
cd harness/12_memory
MOCK=1 python3 demo.py    # 离线管道自检
python3 demo.py           # 真机四会话（A/B/C 验收 + D 观察项）
```

真机实测：

```text
[A 学偏好] 声明"所有 Python 文件头部必须加 # PROJECT: mh-demo"
  沉淀: 1 条 → MEMORY.md
[B 遵循] 全新会话仅下发"创建 calc.py" → 头部带标记 ✅（无提示）
[C 遗忘] forget("mh-demo") → 移除 1 条, recall 清空 ✅
[D 遗忘后] 模型自发不写标记 ✅（无习惯残留——对照很有说服力）
```

诚实预期：四个会话各验一件事——A 学到（沉淀 1 条）、B 在全新会话且无任何提示的情况下遵循、C 遗忘后回带清空、D 观察模型无习惯残留。D 是观察项而非硬断言：遗忘后的模型行为不可控，能证明的是"没有反例"。

实现代码：

```python
Memory(path)                     # MEMORY.md 读写, 条目即行
consolidate(chat_fn, transcript, memory)  # 收尾提取 ≤3 条
system_with_memory(base, memory) # 新会话 system 拼接(空记忆原样)
memory.forget(keyword)           # 删含关键词条目, 返回条数
```

四行各管一件事：`Memory` 封装 MEMORY.md 的读写（条目即一行）；`consolidate` 在收尾时提取事实；`system_with_memory` 把记忆拼进新会话的 system（空记忆时原样返回）；`forget` 删除条目并返回条数。

注入走的是 11 实验加的 `messages=` 参数——主循环依旧零改动。

## How It Works

沉淀是模型的判断，删除是用户的权力。`consolidate()` 让模型自己判断"什么值得记"——它可能记错、记多、记偏。所以每条带时间戳、每条可被 `forget(关键词)` 单独删除、整个文件人类可读可手改。

记忆系统的健壮性不来自记得准，来自错了能改。（Claude Code 的 auto-memory 是同一哲学：markdown + 人工可编辑。）

Quick Start 输出的四幕正是三个入口的接力：A 会话的"沉淀: 1 条"来自 `consolidate()`；B 会话头部带标记来自 `system_with_memory` 的注入——模型没见过任务描述里的这条要求，遵守只能来自记忆。

C 会话的"移除 1 条, recall 清空"来自 `forget()`；D 会话观察无残留，确认遗忘是干净的。

## Pitfalls & Q&A

踩坑清单：

- **consolidate 会把闲聊也存进去**
  - 现象：模型把与任务无关的对话内容也提炼成记忆条目。
  - 原因：沉淀本身是模型判断，没有硬性边界。
  - 解法：三道防线——prompt 限定"偏好/事实"、条数上限、时间戳可删；遗忘入口是解药不是补丁。

**Q1：为什么不向量库？**

几十条偏好用不上检索；MEMORY.md 全量注入成本可忽略。向量检索（把文本转成向量、按相似度检索的存储方案）是"记忆条目上万"之后的优化，不是前提——先让记忆可见可删，再谈规模（alphaXiv 的教训：支架复杂度不等于能力）。

**Q2：注入放 system 还是首条 user？**

本篇放 system 尾部——09 实验的踩坑结论是会话中途插入的 system 消息不可靠，会话开头的 system 可靠。若记忆很长，应转为按需检索注入（RAG 化，15 实验的主题）。

**Q3：D 会话为什么单独做观察项？**

遗忘后模型的自发行为不可控（可能凭习惯写标记）。硬断言会把模型的巧合当成系统的功劳——观察并如实报告即可。

**Q4：演示偏好为什么选"文件头注释"而不是"用 pytest"？**

后者模型可能凭训练习惯直接押中，B 会话通过也不能证明记忆生效。测记忆要用模型不会自发做的事——与 03 实验"顺任务测不出 harness"是同一条方法论。
