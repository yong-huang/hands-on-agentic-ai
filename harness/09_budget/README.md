# 09 · 预算与止损：给 07 的 7 轮空转装上硬天花板

> 预算闸给 Agent（能自主决策并调用工具完成任务的程序）的连续空转装上硬性天花板：预算将尽时注入提醒，超限时撤走工具并强制输出三行交接摘要。读完本篇，你能跑通轮次与 token（文本用量计量单位）两种预算的演示，理解止损为什么设计成"不抛异常的降级"而不是"报错打断"。

## Background

没有预算闸时，Agent 任务的时长与花费没有上限，唯一的约束是提示词里请求模型"尽快完成"。模型自觉时两三轮收工，不自觉时就一直试下去。

痛点场景：07 实验实测，模型被权限拒绝后连续改道 7 轮。Databricks 的 agent 失败模式清单里，"延迟""上下文腐化""无限循环"指向同一件事——agent 不知道自己该停。

alphaXiv 论文的数据更直接：失败任务的 token 消耗是成功任务的 2.7 倍，支架（scaffold，包裹模型的主循环程序）常让模型陷入无效推理循环。

预算闸因此出现：它不是性能优化，而是故障止损——把钱和轮次的上限从"依赖模型自觉"变成"由 harness（包裹模型的执行支架）强制执行"，在主循环每轮开始前做一次检查。

## What

预算闸是一种挂在 Agent 主循环每轮之前的用量检查器，支持轮次与 token（计量模型输入输出的文本单位，本实验按字符估算）两个维度。检查结果分两档：

- **warn**：预算将尽（用量到 80%，或轮次只剩最后一轮）时触发，只在消息尾部附加一条"请尽快收敛"的提醒；工具还在，模型可收尾可继续；
- **force**：预算耗尽时触发，撤走整个工具表，再要一次最终回答。

心智模型：可以把预算闸想象成手机电量剩 10% 时的低电量模式——先提醒你省着用，再自动关掉最耗电的功能。但和手机不同的是，它最后不会直接关机，而是强制产出一份 HANDOFF（交接摘要，固定三行：已完成/未完成/关键文件），让人或下一个 Agent 能接着干。

一句话：止损不是打断 agent，而是换一种它无法拒绝的方式让它收尾。

## When to Use

三个信号任一成立就值得接：任务无人值守、按 token 计费、任务结束后需要明确的"干到哪了"。

典型场景：

- 夜里批量跑一批 agent 任务：轮次预算兜住死循环，早上看到的全是可交接结果；
- 给单次任务的模型服务调用花费封顶：token 预算到线即止损；
- 长任务中途要求交棒：force 档产出的 HANDOFF 就是给下一棒的任务说明。

何时不用：交互式使用、人就在旁边随时能打断时，预算闸是多余的保险；任务只有一两次工具调用、用量可预估时也不必接。

同类方案对比：

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| 提示词求收敛 | 零成本，靠模型自觉，无保证 | 一次性交互任务 |
| 外层计时强杀 | 到点杀进程，成果全部丢弃 | 只想兜底防挂死 |
| 预算闸 | warn 先提醒，force 保住已完成成果并交接 | 需要止损且成果可复用的批任务 |
| 平台用量告警 | 事后通知人工处理 | 大团队成本治理，配合预算闸用 |

## Quick Start

前置条件：进入 `harness/09_budget` 目录，Python 3；`MOCK=1` 走离线假模型，不加该变量则调用真机模型。

```bash
cd harness/09_budget
MOCK=1 python3 demo.py    # 离线三组对照
python3 demo.py           # 真机: 无预算对照 / 步数预算 / token 预算
```

真机实测：

```text
① 对照组: 自然 3 轮完成 5/5（模型两条批量 bash 干完全部活）
② 步数预算 max_turns=2: 预算事件 [(warn,1),(force,2)] → HANDOFF 三行摘要 ✅
③ token 预算 ~100: 事件 [(force,3)] → HANDOFF ✅
   已完成: 创建 d1~d5 五个目录并统计确认均为 1 行
   未完成: 无
   关键文件: d1/f.txt … d5/f.txt
```

诚实预期：不加预算时，模型自然 3 轮完成，预算事件一次都不触发。强模型会把"5 个目录 × 建目录+写文件+统计"合并成两条批量 bash，预算很难自然触发——所以演示口径选"预算低于自然轮次"（`max_turns=2`），才逼出 `[(warn,1),(force,2)]` 的事件序列与 HANDOFF。

这条设计约束写进了 16 实验（评测台）：任务集必须有"不可批量"的串行依赖，预算指标才有区分度。

实现代码：

```python
Budget(max_turns=…, max_tokens=…)      # 双维度, warn 在 80%/max-1 触发
budget_chat_fn(chat_fn, budget)        # 包一层 chat_fn, loop 零改动
# force 轮: chat_fn(finalize, tools=None) —— 撤走工具表
```

这三行在做什么：`Budget` 声明两个维度的上限与 warn 触发点；`budget_chat_fn` 把预算检查包在 `chat_fn`（与模型对话的函数）外面，主循环零改动；force 轮的关键是 `tools=None`——对话请求里不再携带任何工具。

## How It Works

优雅降级（graceful degradation，出故障时退到功能受限但可控的状态，而不是崩溃）三原则：

1. **不抛异常**：预算超限走正常返回路径，`result["final"]` 就是 HANDOFF；
2. **force 轮撤走 tools**：`tools=None` 后，对话请求里已不含任何工具，模型无从调用；
3. **HANDOFF 固定三行**：已完成/未完成/关键文件——止损输出必须可交接。

force 是物理禁止而非口头禁止，这是本篇最重要的设计决策：口头禁止（"别再调工具了"）在 07 实验已被证明会被绕过；`tools=None` 之后模型根本拿不到工具。warn 档不撤工具，是给模型留体面收尾的机会——多数任务在 warn 档就能自然收敛，省下一轮 force。

你在 Quick Start 输出里看到的 `[(warn,1),(force,2)]` 就是两档的先后接力：第 1 轮触发 warn，第 2 轮触发 force 并产出 HANDOFF 三行摘要；token 预算组（③）只出现 `[(force,3)]`，同样以 HANDOFF 收束。

token 计量用字符估算（约 3 字符/token，中英混合），精度足够预算判断；精确计量（Ollama 响应里的 `eval_count` 字段）归 16 实验（评测台）。

## Pitfalls & Q&A

踩坑清单：

- **中途 system 消息会被无视**
  - 现象：第一版 force 用 `role: "system"` 注入收尾指令，qwen3.8 完全无视，照常输出任务汇报。
  - 原因：会话中途插入的 system 消息（系统级指令角色）在本地模型上权重不可靠。
  - 解法：改成对话尾部的 user 消息后立刻遵守。关键指令要用 user 角色 + 固定格式要求。

**Q1：HANDOFF 为什么不自动存盘？**

它是模型输出，可信度未经验证；11 实验（会话持久化）落盘的是工具副作用（权威事实），HANDOFF 只是给人看的摘要。

**Q2：轮次和 token 两个维度都要吗？**

要。轮次限"死循环"，token 限"单轮爆炸"（超长命令、超长输出）——07 实验的 7 轮空转是前者，yes 刷屏是后者。

**Q3：止损后的任务算成功还是失败？**

都不是。HANDOFF 引入第三种终态："预算内未竟，可交接"。16 实验（评测台）会给它单独计分。
