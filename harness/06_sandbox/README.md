# 06 · 执行安全沙箱：让 `while True` 也拖不垮宿主

> `mh/sandbox.py` 用三层防御对付"参数对但命令危险"的执行：词法守卫（`../`、fork 炸弹在执行前拒绝）、进程组限时（`killpg` 处决整组不留孤儿）、输出截断（8KB 并告知模型）。三场景确定性验收全绿，真机 agent 循环一并过关——过程中还揪出一个真 bug：**cwd 静默丢失，沙箱隔离整条链路失效**。读完你能搭起同款三层沙箱，并知道每一层挡得住什么、挡不住什么。

## Background

04/05 的工具层解决了"参数合不合法"，但对"参数对、命令危险"毫无防御：命令被原样交给 shell（命令行解释器）执行，模型一句 `while true; do :; done` 就能把宿主挂死，一条 `yes | head -c 100M` 就能用 100MB 输出撑爆上下文（模型单次能读入的输入总量）。

痛点场景：agent 拿到写文件任务，顺带执行了一条死循环命令——宿主卡死，人工只能登机杀进程；或者命令正常返回，但 100KB 的输出直接挤占掉后续所有对话空间。错误没有代价上限，一次就拖垮整个进程甚至整台机器。

工业界的共识是把执行环境列为 agent（能自主决策并调用工具完成任务的程序）设施的核心组件：Databricks 把"沙箱与执行环境"列为 harness（模型外围负责执行与约束的设施层）八大组件之一。

执行层的职责不是阻止错误，而是**让错误付不起代价**——本实验的三层设计（3 秒处决、8KB 封顶、越界拒绝）就是这个原则的落地。

## What

执行安全沙箱：一条命令从进入到回喂要过三道关卡——词法守卫（执行前对命令文本做模式匹配检查的守门代码）在执行前拒绝危险模式；进程组执行带 3 秒限时，超时 `killpg` 全组处决；输出过 8KB 截断器。

所有出口都汇成"可回喂的文本"，`sandbox.run` 与 05 的 `Tool.call` 一样**永不抛异常**。

心智模型一句话：**沙箱不阻止错误，只让每个错误的代价有上限。**可以把沙箱想象成电路里的保险丝：短路不因保险丝而不发生，但损失被封顶在保险丝烧断的那一刻。但和保险丝不同的是，沙箱还要把"我为什么被熔断"写成文本回喂给模型，让下一轮换条路走。

| 层 | 手段 | 挡得住 | 挡不住（诚实边界） |
|:--|:--|:--|:--|
| 词法守卫 | 模式匹配拒绝 | `../` 爬升、fork 炸弹（不断自我复制进程直到耗尽系统资源的命令）、`rm -rf /` | 绝对路径写 `/tmp`、编码混淆 |
| 进程组限时 | `setsid` + `killpg` | 死循环、挂起 | 已写盘的副作用（要靠快照/事务） |
| 输出截断 | 字节上限 + 告知 | 上下文爆炸 | 语义空洞的长输出 |

词法守卫是**启发式**（基于经验规则、不保证完备）不是隔离：绝对路径治理归 07 权限门，容器级隔离（Docker/nsjail 这类操作系统级隔离方案）超出本实验范围——诚实标注，不假装。

## When to Use

什么时候需要给执行层上沙箱：模型触发的命令一旦可能失控，防御就要在执行前就位。

典型场景：

1. 让模型执行任意 shell 命令做文件操作或批处理时：死循环和超长输出必须有时限与封顶。
2. agent 跑在开发机或共享环境、不能接受宿主被挂死时：进程组限时保证 3 秒内了断。
3. 上下文窗口紧张、工具输出可能巨大（读日志、生成类命令）时：截断加告知保住对话空间。

何时不用：命令集合固定且经人工审计、无模型参与时，沙箱是多余的；需要强隔离（多租户、运行不可信代码）时，三层防御不够，应直接上容器级隔离。

同类方案对比：

| 方案 | 与本实验的差异 | 什么时候选它 |
|:--|:--|:--|
| 无防御直执行（04/05 形态） | 无限时、无封顶、无拒绝 | 极受控的本机试验 |
| 三层沙箱（本实验，`mh/sandbox.py`） | 单机轻量，进程级防御 | 模型驱动的本机 agent |
| 容器级隔离（Docker/nsjail） | 文件系统与网络级强隔离，更重 | 多租户、不可信代码 |

## Quick Start

前置条件：Python 3；三场景确定性验收不需要模型服务；`--agent` 追加真机 agent 循环，需要本机装有 Ollama（在本地运行大语言模型 LLM 的工具）与 `qwen3.8:latest`。

```bash
cd harness/06_sandbox
python3 demo.py            # 三场景确定性验收（无需 LLM）
python3 demo.py --agent    # 追加真机 agent 循环（截断任务）
```

真机实测：

```text
场景1 死循环: 耗时 3.0s | [错误: 超时 3s, 进程组已杀死] | 孤儿进程 0
场景2 输出截断: 100KB 输出 → 返回 4590 字符 | 含截断提示 ✅
场景3 越界探测: echo hacked > ../treasure.txt 被拒 | 沙箱外文件零改动 ✅
agent 循环: 3 轮 2 次调用, big.txt 50000 字节生成并汇报 ✅
```

诚实预期：场景 1 应在约 3.0 秒返回超时错误且孤儿进程为 0；场景 2 应看到 100KB 输出被压到约 4590 字符并带截断提示；场景 3 应拒绝越界写入且沙箱外目录零改动；`--agent` 应 3 轮 2 次调用完成 50000 字节文件生成并汇报。四行全绿即验收通过。

## How It Works

### 为什么杀进程组而不只是子进程

`bash -c "while true"` 的直接子进程死了，bash 自己 spawn 的孙进程还活着——只杀子进程等于没杀。`start_new_session=True` 让命令独立成组，超时后 `os.killpg` 一锅端。

输出里场景 1 的"孤儿进程 0"（孤儿进程：父进程结束后仍在运行的进程）就是这条设计的实测证据。

### 截断必须"告知"

只截断不告知，模型不知道自己看到的是残本，会基于残本继续推理——截断就从保护变成幻觉放大器。截断器在尾部追加"[输出已截断: 原始输出超过 8192 字节…]"，把元信息一并喂回。**元信息也是上下文工程的一部分**（10 压缩的雏形）；场景 2 输出里的"含截断提示 ✅"就是这条的验收。

### 守卫的粒度与判分的铁证

词法守卫只做文本模式匹配，粗粒度是已知代价，细粒度放行策略归 07。场景 3 的"零改动"证明沿用 01 的判分铁证哲学：执行前后对沙箱外目录做内容 hash 快照（对目录内容计算摘要值，前后对比可证明未被改动）对比，不信任任何声称。

## Pitfalls & Q&A

### 踩坑清单

1. **cwd 静默丢失（潜伏两个实验的真 bug）**
- 现象：`--agent` 验收时 `big.txt` 没出现在沙箱里。
- 原因：`as_loop_entry` 的包装函数签名是 `def _fn(**args)`，而 loop 按 `'cwd' in signature(fn)` 决定是否注入任务目录——`**args` 吞掉了形参签名，cwd 静默丢失，agent 的写入全部落在**当前目录**。
- 解法：改成 `def _fn(cwd=None, **args)`。
- 教训：它最可怕之处是**之前的实验全部照常通过**——05 的故障注入走的是 `Tool.call` 直调路径，没经过 loop 的 cwd 注入。**包装器与调用方之间的隐式协议（签名约定）必须有测试钉死**，否则重构时它第一个坏、最后被发现。

### 深入问答

**Q：`sandbox.run` 为什么永不抛异常？**

与 05 的 `Tool.call` 同哲学：执行层的所有失败都要变成模型可读的文本回喂。补充一条边界：异常只允许出现在 harness 自己的 bug 里，不允许出现在被治理的对象上。

**Q：3 秒默认值怎么定的？**

本系列任务（文件操作/文本处理）正常执行都在亚秒级，3s 是 3 个数量级冗余；编译/下载类任务应显式放宽，并配合 09 预算。

**Q：`../` 守卫会不会误伤？**

会——`cd .. && ls` 这类合法操作也被拒。这是粗粒度词法防御的已知代价；细粒度要等 07 的 allow/ask/deny 规则引擎。

**Q：场景 3 的"零改动"怎么证明？**

执行前后对沙箱外目录做内容 hash 快照对比——判分铁证哲学（01）在安全场景的复用。
