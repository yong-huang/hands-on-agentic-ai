# 14 · Skills 按需注入：菜单常驻，正文按需付费

> `mh/skills.py` 实现 Claude Code 式的渐进式披露：启动时上下文里只有
> 145 字符的技能菜单（名称+描述+触发词），命中场景才通过 `load_skill`
> 工具加载 1536 字符正文。真机计量：**加载前正文 0 字符在上下文，加载后
> 一次性付费 ≈512 est token**。token 只为用到的知识支付。

## What

渐进式披露机制：启动阶段扫描 `skills/*/SKILL.md`，把 frontmatter 摘成
菜单注入 system——这是唯一常驻成本。任务命中触发场景时，模型调用
`load_skill` 工具把正文拉进上下文，一次性付费。不命中？正文永远不出现
（实测加载前 0 字符）。

心智模型一句话：**菜单是订阅费，正文是点单——模型自己看菜单点菜。**

| 阶段 | 上下文成本 | 内容 |
|:--|:--|:--|
| 启动 | 每技能 ~30-50 token | 名称 + 描述 + 触发词 |
| 命中 | 正文一次性 ~500+ token | SKILL.md 正文 |
| 常驻 | 0 | 未命中的技能（0 字符实测） |

## Why

把所有操作规范塞进 system 是最直白的做法，也是最贵的：3 个 skill ×
1500 字符 = 常驻 1500+ token，而单次任务通常只命中一个。Skills 的经济学
与 10 压缩互补：压缩管"历史瘦身"，Skills 管"知识分期"。alphaXiv 论文
发现系统提示膨胀直接推高 token 通胀——菜单化是结构性解法。

## Deep Dive

**加载为什么走工具调用而不是正则匹配？**触发词写在 frontmatter 里供
模型**选择**，但真正加载走 `load_skill` 工具调用——把"要不要读规范"的
决定权交给模型推理，而不是字符串匹配。正则会漏（用户说"要发版了"没说
"发布"）、会误（闲聊里提到"发布"也注入）。而且两个错误方向的代价都
温和：漏触发的代价是"模型没用上规范"（可观测），误触发的代价是"白付
500 token"（便宜）。这是 07 权限门哲学的镜像：**模型负责判断，机制负责
执行。**

## Q&A

**Q1: skill 正文里能写操作指引（如"跑测试"）吗？**

能，且应该——正文是知识不是说明文，模型读完会按其中的步骤行动。本篇
任务刻意要求"只依据规范作答"，是为了让验收不依赖命令执行。

**Q2: menu:body 比例多少才值得 Skill 化？**

菜单:正文 ≈ 1:10 时懒加载划算；若正文只有 200 字符，加载流程的开销
（一轮工具调用）反超收益。**机制要配故障密度**（03/09 教训第三次出现）：
知识短就直接写 system，长才值得 Skill 化。

**Q3: frontmatter 还能放什么？**

version/owner 便于治理；两个 skill 触发词冲突时以 description 更具体者
优先并在加载头部注明——这些是本篇示例正文里写下的扩展约定。

**Q4: 与 12 记忆什么关系？**

记忆是"用户教给我的"（动态、可遗忘），Skills 是"工程预先写好的"（静态、
受版本管理）。两者都进 system，来源不同。
