# 14 · Skills 按需注入：菜单常驻，正文按需付费

> 技能（Skill，预先写好、按场景取用的操作规范）若全部塞进系统提示
> （给模型的常驻指令文本），模型每一轮都在为用不到的知识付费。
> `mh/skills.py` 只让 145 字符的技能菜单常驻，命中场景才加载 1536
> 字符正文。读完本篇你能算清这笔成本账，并说清加载为什么要走模型
> 自己的工具调用。

## Background

最直白的做法是把所有操作规范塞进 system 提示（会话开始前注入、整个
会话常驻的指令文本）。代价按轮重复：3 个 skill × 1500 字符，就是常驻
1500+ token（模型计量文本长度的单位），而单次任务通常只命中一个规范
——另外两份的钱白花。

痛点场景很具体：用户问"准备发布"，模型只需要发布检查清单，却背着
数据库迁移规范在跑。alphaXiv 论文进一步发现，系统提示膨胀会直接推高
token 通胀（上下文里冗余内容越滚越多，有效信息密度被稀释）。

思路于是转向"知识分期"：目录常驻、正文按需。Claude Code 把这套做法
称为渐进式披露，14 实验把它做成 `mh/skills.py`。它与 10 压缩互补：
压缩管"历史瘦身"，Skills 管"知识分期"。

## What

渐进式披露（先给目录、命中再给全文的加载策略）：启动阶段扫描
`skills/*/SKILL.md`，把 frontmatter（文件开头一段 YAML 格式的元数据，
YAML 即缩进式键值文本）摘成菜单注入 system——菜单含名称、描述、触发词
（标明什么场景该用这个技能的关键词），这是唯一常驻成本。

任务命中触发场景时，模型调用 `load_skill` 工具把正文拉进上下文，
一次性付费；不命中，正文永远不出现（实测加载前 0 字符）。

可以把 Skills 想象成餐厅经营：菜单常驻桌上，菜按单下锅——模型自己看
菜单点菜。但和点单不同的是：没人点菜时菜单钱照付（菜单是常驻成本），
而上了一道菜可以反复夹（正文加载后整个会话可反复引用）。

| 阶段 | 上下文成本 | 内容 |
|:--|:--|:--|
| 启动 | 每技能 ~30-50 token | 名称 + 描述 + 触发词 |
| 命中 | 正文一次性 ~500+ token | SKILL.md 正文 |
| 常驻 | 0 | 未命中的技能（0 字符实测） |

## When to Use

典型场景：

- 维护多份互斥的长规范：发布检查清单、数据库迁移规范各自上千字符，
  单次任务通常只命中一份。
- 规范低频但关键：不常用的操作知识，常驻不值、用时必须有。
- 给同一个代理扩领域：加一个技能目录即扩一个领域，菜单自动更新。

何时不用：正文太短就不值得。菜单:正文 ≈ 1:10 时懒加载（用时才加载）
才划算；若正文只有 200 字符，加载流程的开销（一轮工具调用）反超收益，
直接写进 system 即可——机制要配故障密度（03/09 的同一教训：值不值得
上机制，看它挡住的问题发生得多频繁）。

同类做法对比：

| 方案 | 差异 | 什么时候选它 |
|:--|:--|:--|
| 全写进 system | 常驻、零流程 | 知识只有一两百字符 |
| Skills（本篇） | 菜单常驻，正文按需一次付费 | 长规范、命中互斥 |
| 记忆（12 的主题） | 动态、用户教出来的、可遗忘 | 个性化偏好类知识 |
| 检索增强（RAG，按当前提问的相似度取文档片段） | 每轮按查询检索 | 知识库大到菜单放不下 |

## Quick Start

前置条件：Python 3 环境；`skills/` 目录下已有示例技能；`MOCK=1` 走
离线管道，不需要模型服务；真机运行需要一个可用的模型接入。

```bash
cd harness/14_skills
MOCK=1 python3 demo.py    # 离线管道自检
python3 demo.py           # 真机: "准备发布 v1.0" 命中 release 技能
```

真机实测：

```text
② frontmatter 解析单测: ✅（name/description/triggers）
① 菜单 145 字符常驻; 加载前正文 0 字符在上下文 ✅
   加载后会话总估算 3683-838 token（含 1536 字符正文 ≈512）
③ 最终回答: 已加载 release-checklist 规范…逐项检查结论
```

诚实预期：真机的总估算数值随模型与对话内容浮动，但三条结构不变——
菜单常驻、加载前正文 0 字符、回答引用已加载规范。

实现入口速览：

```python
SkillBook(skills_dir)             # 扫描 */SKILL.md, YAML frontmatter 解析
book.index()                      # 菜单文本(注入 system)
skill_tools(book)                 # load_skill 工具表条目
system_with_skills(base, book)    # 菜单拼接(空库原样返回)
```

两个示例 skill：`release-checklist`（发布检查 12 项 + 失败处置）与
`db-migration`（迁移规范），正文均为真实可用的运维知识。

## How It Works

一次会话按顺序发生四步：

1. 启动时 `SkillBook` 扫描技能目录，解析各 frontmatter；
2. `system_with_skills` 把菜单文本拼进 system，正文不动——你在输出里
   看到的 `菜单 145 字符常驻` 就来自这一步；
3. 模型判断当前任务命中某技能，主动调用 `load_skill`；
4. 正文整段进入上下文，输出里 `总估算 3683-838 token（含 ≈512）`
   的差额就包含这笔一次性付费，此后引用免费。

**加载为什么走工具调用而不是正则匹配（按固定字符串模式做匹配）？**
触发词写在 frontmatter 里供模型**选择**，但真正加载走 `load_skill`
工具调用——把"要不要读规范"的决定权交给模型推理，而不是字符串匹配。

字符串匹配两个方向都会出错：会漏（用户说"要发版了"没说"发布"）、
会误（闲聊里提到"发布"也注入）。两个方向的代价都温和：漏触发是
"模型没用上规范"（可观测），误触发是"白付 500 token"（便宜）。

这是 07 权限门（给工具调用设审批关卡）哲学的镜像：**模型负责判断，
机制负责执行。**

## Pitfalls & Q&A

**Q1: skill 正文里能写操作指引（如"跑测试"）吗？**

能，且应该——正文是知识不是说明文，模型读完会按其中的步骤行动。本篇
任务刻意要求"只依据规范作答"，是为了让验收不依赖命令执行。

**Q2: frontmatter 还能放什么？**

version/owner 便于治理；两个 skill 触发词冲突时以 description 更具体者
优先并在加载头部注明——这些是本篇示例正文里写下的扩展约定。
