# 01 · 无 Harness 基线：裸 LLM 的多步任务失败实录

> 本实验把"没有执行层的裸 LLM"与"只多 15 行执行逻辑的最小 harness（模型外围负责执行与反馈的工程设施）"放在同一道多步文件任务上对照，用文件系统当唯一裁判。读完你能看到工具幻觉、虚假成功、上下文漂移三类失败的现场与 0/10 对 10/10 的判分数据，并得到 harness 的最小定义：替模型执行 + 把现实喂回去。

## Background

把大语言模型（LLM，通过对话接口生成文本的程序）接进应用，最直接的做法是调用其 API（程序间调用接口），把回复里的 shell 命令（在终端执行的指令）打印出来，由人复制执行，或仅当作建议展示。早期的"AI 助手"demo 多是这个形态。

多步任务里这套做法会撞墙。场景：让模型在磁盘上创建三个内容固定的文件。模型每轮都输出"正确的"命令，但程序不执行它，磁盘始终零变化；模型得不到任何执行结果，只能重复输出命令并宣称"任务完成"。命令正确、进度为零、报告成功，三者同时成立。

业界的应对思路，是把"替模型执行操作、把执行结果作为新输入喂回去"从对话逻辑里剥离，做成一层确定性的工程设施。实证结果很一致：同一模型配上不同执行设施，任务解决率能差一倍（42% 对 78%）；而固定设施只升级模型，解决率几乎不动。本实验把这层设施的有与无，做成可复现的对照现场。

## What

harness 是包裹模型的程序设施层，负责替模型执行操作、回喂真实结果、施加约束。行业用公式 **Agent = Model + Harness** 概括分工：模型是大脑，harness 是身体——执行工具、管理记忆、强制权限。harness 不是模型的装饰，而是模型智能变成可靠工作的必要条件。

本实验给出它的最小定义：**替模型执行 + 把现实喂回去。**

实验设计：同一道多步文件任务，A 组（裸 LLM）与 B 组（最小 harness）对照解题。提示词完全相同，唯一差别是 B 组多约 15 行"真执行 + 输出回喂"逻辑：

| | A 组（裸 LLM） | B 组（最小 harness） |
|:--|:--|:--|
| 提示词 | 完全相同 | 完全相同 |
| 模型输出 bash 代码块 | 提取、记录 | 提取、**执行** |
| 执行结果 | 不存在 | 回喂为下一轮 user 消息（对话中扮演用户角色的输入） |
| 判分 | 文件系统（相同） | 文件系统（相同） |

判分不看模型的自我汇报，只看磁盘：三个文件都存在且行数精确等于 3/2/1 才算成功。这样设计的原因见 How It Works。

可以把 harness 想象成模型的手：大脑想得再对，没有手就改变不了现实。但和手不同的是，这层设施还必须把"手摸到了什么"翻译回给大脑（回喂）——只执行不回喂的纯执行器，不构成完整的 harness。

## When to Use

这一节回答：什么时候需要为模型任务补执行层，什么时候适合跑本实验这样的对照实验。

典型场景：

1. 评估要不要为某个模型任务投入工程设施：先跑"裸模型 vs 最小执行层"的对照，用成功率差异决定投入。
2. 争取团队资源：需要可复现的失败证据（本实验的 `FAILURES.md` 即此类证据）说明痛点真实存在。
3. 诊断线上 agent（能自主决策并调用工具完成任务的程序）事故：先区分失败来自模型能力还是执行层缺失，再决定优化方向。

何时不用：任务是单轮纯文本生成（无副作用、不调用工具）时，执行层帮不上忙；已选定成熟框架时，不必从零复现本实验。

同类方案对比：

| 方案 | 与本实验的关系 | 什么时候选它 |
|:--|:--|:--|
| 裸 API 直调（A 组形态） | 无执行层，模型输出仅作展示 | 问答、文本生成等无真实副作用的任务 |
| 自研最小 harness（B 组形态，本系列路线） | 15 行起步，每行职责可见 | 要理解原理、要求行为完全可控 |
| 成熟 agent 框架（LangGraph、OpenAI Agents SDK 等） | 内置执行、重试、权限等成套能力 | 直接交付生产功能 |

## Quick Start

前置条件：Python 3。离线自检（`MOCK=1`，一个环境变量开关，置 1 时用假模型离线运行）不需要模型服务；真机运行需要本机装有 Ollama（在本地运行 LLM 的工具），默认模型 `qwen3.8:latest`，免 API Key。

```bash
cd harness/01_no_harness_baseline
MOCK=1 python3 no_harness_baseline.py --selftest   # 离线自检（不需要 Ollama）
python3 no_harness_baseline.py --trials 10         # 真机跑 A/B 各 10 次（验收口径）
python3 no_harness_baseline.py --groups B          # 只跑对照组
```

想提速可换 `LLM_MODEL=qwen3:4b`，但注意 qwen3 小模型是混合推理架构（回复中会先生成思考段），思考会吃掉 token（模型限长与计费的最小文本单位）配额，导致空回复，处理方式见踩坑清单第 2 条。

每次试验落一份 `results/trial_<组><n>.json`（完整对话 + 判分 + 失败标签），最后汇总生成 `results/FAILURES.md`。真机 A/B 各 10 次的结果：

```text
[A0] 4 轮 4 条命令 → ❌ 虚假成功: 宣称任务完成, 但文件系统零变化
[A1] 4 轮 4 条命令 → ❌ 虚假成功 …（含死循环证据）
……（A2-A9 同）
[B0] 2 轮 1 条命令 → ✅
[B1] 2 轮 1 条命令 → ✅
……（B2-B9 同）
A 组(裸 LLM)成功 0, B 组(最小 harness)成功 10
```

| 组 | 成功率 | 平均轮次 | 结论 |
|:--|:--:|:--:|:--|
| A 裸 LLM | **0/10** | 4.0 | 每轮都输出"正确"命令，但磁盘零变化，直到上限轮仍宣称完成 |
| B 最小 harness | **10/10** | 2.0 | 第 1 轮执行、第 2 轮据实收尾，全程无人工干预 |

诚实预期：`--trials 10` 跑完应复现 0/10 对 10/10；20 份 trial 文件被 git 忽略，重跑命令即可再生。换模型型号后，轮次与失败标签可能不同。

## How It Works

### 同一道题的两种命运

输出里 A 组"4 轮 4 条命令"、B 组"2 轮 1 条命令"的差异来自唯一分支：B 组提取命令后多执行一步，并把程序打印的标准输出（程序运行产生的文本结果）回喂成下一轮输入。主脚本约 200 行，四个关键函数：

```python
run_bash(cmd, cwd, timeout=3)   # B 组唯一的 harness 能力：真执行
grade(sandbox)                  # 铁证判分：行数精确匹配
classify(turns, executed_ok)    # 失败模式归类（纯函数）
run_trial(group, n, llm, keep)  # 单次试验：对话循环 + 落盘
```

`run_bash()` 用 `subprocess.run` 执行命令，并施加三项约束：`cwd` 锁定工作目录、3 秒超时、输出截断。A 组没有这约 15 行，命令永远停留在字符串状态——这就是输出里 A 组"文件系统零变化"的直接来源。

### 判分为什么只看磁盘

`grade()` 只认一件事：三个文件都存在，且行数精确等于 3/2/1。模型的自我汇报是概率性的，文件系统状态是确定性的；用后者判分，"正确命令 + 没有执行 = 零进度"才成为可复现的实验事实。A 组 0/10 全灭，正是这条判据的必然结果。

`classify()` 从对话记录里自动抓三种经典失败模式，证据摘录写进 `FAILURES.md`：

- **虚假成功**：末轮含"任务完成"，但执行层缺失（A 组必中）
- **死循环**：同一命令重复输出 ≥3 次仍不收敛
- **上下文漂移**：8 轮里始终没出现任务第 3 步 gamma.txt

A 组 10 份失败证据一字不差（`temperature=0`，采样温度参数设为 0，输出完全确定），失败完全可复现。这是评测台（批量跑用例并量化得分的设施）需要的性质，16 评测台的雏形就在这里。

B 组"2 轮 1 条命令"则说明：拿到真实执行反馈后，模型第一轮就完成了任务。执行反馈不只是纠错，还缩短了收敛路径——它既兜底，也提速。

## Pitfalls & Q&A

### 踩坑清单

1. **同轮漏执行**。现象：B 组最后一批命令没被执行，任务假性失败。原因：模型习惯在同一轮里既给命令又宣布"任务完成"，最初的循环见到"完成"就 break。解法：先执行再收尾——harness 的动作顺序必须先于模型的结论，这是运行时视角和对话视角的典型差异。
2. **thinking 吃掉配额**。现象：换 `qwen3:4b` 后回复为空、`finish_reason=length`。原因：混合推理模型把 1200 个 token 配额全花在思考段上。解法：脚本用 `/no_think` 软开关兜底；配额管理本身是 harness 的职责（09 的主题）。
3. **本地请求被代理劫持**。现象：跑批静默卡死。原因：系统代理把 `localhost:11434` 的请求转发到 `127.0.0.1:7890`。解法：脚本顶部设置 `NO_PROXY=localhost,127.0.0.1` 豁免本地地址；网络出口管理同样是 harness 工程的一部分。

### 深入问答

**Q：判分为什么不信任模型的自我汇报？**

模型的自我评估是概率性的，harness 的判分必须是确定性的；生产里对应"测试通过才算完成"，而不是"模型说改完了"。

**Q：A 组是不是太不公平？**

公平，且必须公平：A 组模拟的是"只接了 API、没有任何工程设施"的真实团队。它的失败模式（工具幻觉：声称执行过实际未发生的操作；上下文漂移：多轮后遗忘任务的早先要求）与生产事故类型一一对应。

**Q：对照组的循环为什么不抽象成 agent loop（提取→执行→回喂的循环结构）？**

该循环已经藏在 `run_trial()` 里，它就是 [04 实验（最小循环）](../04_min_loop/README.md) 的雏形。本实验刻意不提前抽象——先记录失败现场，再谈结构。

**Q：换更强模型能救 A 组吗？**

不能。执行层不存在时，模型再智能也只能"说出"命令，无法在磁盘上留下任何结果。结论可概括为：范式决定上限，harness 决定下限。
