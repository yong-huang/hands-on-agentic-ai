# 11 · 会话持久化与崩溃恢复：kill -9 之后的断点续跑

> 会话持久化让 agent（能自主决策并调用工具完成任务的程序）长任务在进程被强杀后从精确断点续跑：运行中持续快照，恢复时依据副作用清单（记下哪些命令已执行过）跳过重放。读完本篇，你能跑通 kill -9 崩溃恢复演示，理解快照、裁剪、跳过重放三件套如何协作。

## Background

不持久化时，长任务的中断等于清零：40 分钟的任务第 39 分钟断电，一切从零再来。已有的改进是只保存问答文字（qa/31 实验的主题）——对话记录能恢复，但"任务干到哪了"没有依据。

痛点场景：就算把消息历史原样恢复，也没人知道哪些命令已经执行过。恢复等于把 `mkdir`、写文件全部重放一遍——建好的目录再建一次，写好的文件再写一次，mtime（文件最后修改时间戳）全变了，之前的成果无法证明还在。

Salesforce 把这叫"AI 失忆"问题，解法是生命周期管理：运行中持续快照，失败时从精确断点恢复。本实验的关键升级是副作用感知——把"哪些命令已成功执行"也存进快照，恢复安全才成立。

## What

会话持久化是"运行中持续快照、失败时从精确断点恢复"的机制，分两个阶段：

- **Phase A（运行中）**：每轮做一次原子快照（写临时文件再原子改名，任何时刻被杀，磁盘上都是完整版本），内容为消息历史 + manifest（已成功命令清单）；
- **Phase B（恢复时）**：三步——裁掉悬空尾部（已发出但没等到结果的工具调用）、按 manifest 跳过已执行的命令、注入历史继续跑。

kill -9（强制杀死进程的信号）只杀进程，checkpoint（磁盘上的快照存档）完好无损。

心智模型一句话：恢复的可信度不取决于消息历史，取决于副作用清单。

可以把整个机制想象成游戏存档：随时写档、读档续玩。但和游戏存档不同的是，决定能否放心读档的不是画面进度（消息历史），而是"哪些关卡已通关"的清单（manifest）。

## When to Use

三个信号：任务跑得久（分钟级以上）、执行带昂贵或不可逆的副作用、事后需要证明"哪些命令执行过"。

典型场景：

- 无人值守的批量构建（夜里生成数据集、编译多个目标），进程被杀后从断点续跑；
- 副作用昂贵的任务（下载、训练、付费 API 调用），重放一遍就是真金白银的损失；
- 需要执行审计的任务：manifest 本身就是一份"本会话执行过什么"的记录。

何时不用：秒级短任务，崩了重跑更快；副作用天然幂等（idempotent，同一操作执行多次与一次效果相同）且重跑成本低的任务。

同类方案对比：

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| 不持久化 | 零成本，崩了从零开始 | 秒级任务 |
| 只存消息历史 | 对话能续，但副作用状态未知 | 纯问答会话（qa/31 的主题） |
| 消息 + manifest（本篇） | 副作用感知，恢复时跳过重放 | 带工具副作用的 agent 任务 |
| 工作流引擎重试 | 平台级，每个步骤需显式声明幂等 | 步骤天然幂等的生产编排 |

## Quick Start

前置条件：进入 `harness/11_session` 目录，Python 3 与 Ollama 本地模型；一条命令完成"启动 worker → 13 秒后 kill -9 → resume → 五项断言"全流程。

```bash
cd harness/11_session
python3 demo.py    # 完整流程: 启动 worker → 13s 后 kill -9 → resume → 五断言
```

诚实预期：运行中会看到进程在 13 秒时被杀一次，这是演示的一部分，不是故障；随后自动恢复并打印五项验收。真机实测：

```text
Phase A: 崩溃前 13 条消息, 6 条已成功命令, 已建 6/8 个目录
Phase B: 跳过重放直调探针 ✅ | resume 循环继续 6 轮
验收 ①②③④⑤ 全绿:
  ② 崩溃前 6 个 f.txt 的 mtime 全部未变 ✅
  ③ 8 个目录最终全部建成 ✅
  ④ 恢复事件留档 {turns_restored:13, commands_restored:6} ✅
最终回答: 任务完成：已串行创建 d1 到 d8 共 8 个目录……
```

实现代码：

```python
SessionStore(path)            # load 时自动记录 recovery 事件(审计线)
record_chat_fn(chat_fn, store)     # 每轮 LLM 调用后快照
snapshotting_tools(tools, store)   # 成功命令即时入 manifest
skip_redo_tools(tools, store)      # 恢复态: manifest 内命令拒绝重放
store.resume_messages()            # 裁悬空尾部
```

五行各管一件事：`SessionStore` 载入快照并自动记录 recovery 事件；`record_chat_fn` 在每轮模型调用后快照；`snapshotting_tools` 让成功命令即时写入 manifest。

`skip_redo_tools` 在恢复态拒绝重放 manifest 内已有的命令；`resume_messages` 裁掉悬空尾部。

主循环侧唯一改动：`run_agent(..., messages=None)` 新增一个可选参数——传入历史即为恢复会话。这是加法扩展，04 以来的所有 demo 全部照常（本篇跑批前回归过）。

## How It Works

**manifest：副作用清单是恢复的安全带。**每个成功命令即时落盘（`flush()`），恢复时两处用处：其一，包装层直接拒绝重放（提示"已恢复·跳过重放"），验收 ② 里 6 个文件的 mtime 分毫未动就是铁证；其二，模型侧即使想重做也会被拦。

诚实边界：跳过判定基于命令文本相同——生产要用效果哈希（目标文件内容的指纹）判定，本篇是演示级。

**原子写：kill -9 打不断一致性。**快照用 `write(tmp)` + `os.replace()`——任何时刻被杀，磁盘上要么是旧完整版本，要么是新完整版本，永远不会是半截 JSON。这是单文件事务的标准做法。

Quick Start 输出与机制的对应：Phase A 行的"13 条消息"来自消息快照，"6 条已成功命令"来自 manifest；④ 的 `{turns_restored:13, commands_restored:6}` 来自 `SessionStore` 的 recovery 事件留档。

验收 ② 的 mtime 未变，来自拒绝重放。

## Pitfalls & Q&A

踩坑清单：

- **悬空尾部：崩溃留下的隐蔽问题**
  - 现象：第一版恢复后模型输出全空。
  - 原因：崩溃卡在 `assistant(带 tool_calls)` 与 `tool(结果)` 之间——恢复后模型看到一条悬空的工具调用，协议错乱。
  - 解法：`resume_messages()` 裁掉所有尾部带 tool_calls 的 assistant 消息。

**Q1：跳过重放为什么不基于"文件已存在"？**

`f.txt 存在`可能是别的进程建的，内容也可能是错的。manifest 记录的是"本会话确实执行过这条命令且成功"，因果明确。效果哈希（内容指纹）是生产级加强。

**Q2：快照为什么在 chat_fn 出口，而不是每条消息？**

快照点选在完整轮次边界，此处一轮消息刚好收齐，不会出现半截调用；在 assistant/tool 之间快照正是悬空尾部的来源。但崩溃仍可能卡在任何位置，所以裁剪仍是必需的双重保险。

**Q3：HANDOFF（09 的主题）和 checkpoint（本篇）什么关系？**

HANDOFF 是"时间不够"时给人的交接摘要；checkpoint 是"电没了"时给程序的完整状态。一个有损，一个无损。

**Q4：与 12 记忆的分界？**

本篇恢复的是"这个任务的进度"；12 恢复的是"跨任务的世界观"。粒度不同，载体不同（checkpoint.json 对 MEMORY.md）。
