# 17 · 对话记忆与长期记忆：滑动窗口 + 向量检索 + MEMORY.md

> 给 Agent 装上真正的两层记忆：**短期记忆**用滑动窗口在上下文预算内保留
> 最近对话；**长期记忆**把值得记的事实 embedding 入库，新对话按相似度
> 检索 top-k 注入。真实模式跑两段会话：第二段用全新的 ShortTermMemory，
> 答对"我叫什么"全靠跨会话记忆召回。

## Background

最朴素的 Agent 只带着当前对话的 messages（消息列表）工作：窗口一满就
硬截断丢历史，或者全量重发让成本随对话长度直线上升。会话一关，Agent
对用户的所有认识清零——昨天说过的事，今天问起只能答"我不知道"。

痛点来自两头：上下文窗口按 token（模型计费与计长的最小文本单位）计价，
对话越长、成本越高、注意力越稀释；而用户恰恰期待 Agent 记住偏好和
约定（"我说过不能吃辣"）。

理想的记忆系统应该"近事详记、远事摘要、要事永久保留"——这正是人类
记忆的分层结构。

本篇用约 300 行纯 Python 实现最小完整版：不加 chromadb、不加 LangChain
Memory（两者都是现成的向量库/记忆框架）。

向量库自己写（JSON 落盘 + 余弦相似度，即按向量方向的相近程度检索），
embedding（把文本映射成语义向量的技术）用本地 nomic-embed-text
（768 维，零 API Key）。

理解了这套最小实现，任何记忆框架都不再是黑盒。

## What

Agent 记忆系统是一种在有限的上下文预算内，尽量保留"该记住的信息"的
机制。本实验分两层，分工如下：

| | 短期（滑动窗口） | 长期（向量库 + MEMORY.md） |
| :--- | :--- | :--- |
| 形态 | 逐字 messages | 压缩成一句话事实 |
| 生命周期 | 预算外自动淘汰 | 永久沉淀 |
| 入库条件 | 不需要判断 | LLM 判定"值得记" |
| 生效时机 | 本回合 | 下次对话检索注入 |
| 本篇预算 | 300 token | top-2、相似度阈值 0.5 |

top-2 指每次检索只注入相似度最高的 2 条记忆；表中 LLM（大语言模型）
负责判定哪些事实"值得记"。

类比：可以把短期记忆想象成人的工作记忆（眼前这几句话），长期记忆想象
成一本笔记本。但和笔记本不同的是，长期记忆的写入由 LLM 自动判定、
检索按语义匹配而不是按页码翻找。

心智模型一句话：**短期逐字保真但会淘汰，长期压缩成事实但跨会话。**

## When to Use

判断标准：对话是否超出"一次全塞进去"的预算，或是否需要跨会话记住
信息。

典型场景：

- 多轮长对话逼近上下文预算时：滑动窗口保证最近语境在场、成本有上界；
- 助理类应用要记住用户偏好与身份时（"张三、不能吃辣"）：长期记忆
  跨会话召回；
- 知识库问答：按语义而非关键词召回相关片段。

何时不用：

- 单轮无状态调用：没有"上一次"，两层记忆都无处着力；
- 对话很短、全量历史装得下且成本可接受：直接全量重发（05 实验的
  方式）更简单。

同类方案对比：

| 方案 | 差异 | 什么时候选它 |
| :--- | :--- | :--- |
| 全量重发全部历史 | 逐字保真，但 token 成本无上界 | 对话短、预算充足 |
| 滑动窗口（本实验短期层） | 成本有上界，早期对话被淘汰 | 长对话的近期语境 |
| 向量库记忆（本实验长期层） | 事实压缩 + 语义召回，跨会话 | 记偏好、记约定、记知识 |
| chromadb / LangChain Memory | 生产级功能全（索引、持久化、去重） | 不想自己维护向量层时 |

## Quick Start

前置条件：`--demo` 离线，不需要 Ollama（本地大模型运行环境）；真实模式
需要 Ollama 提供 nomic-embed-text（embedding 模型）与对话模型。

```bash
cd agents/17_memory
python memory.py --demo   # 离线：伪向量演示两层机制（无需 Ollama）
python memory.py          # 真实：两段会话验证跨会话记忆召回
```

`--demo` 演示写入/检索/窗口淘汰三件事（用确定性伪向量，仅验证管线，
即流程链路本身）。

真实模式跑两段会话：会话 1 告诉 Agent"我叫张三、喜欢吃火锅不能吃辣、
正在学记忆系统"；会话 2 用**全新的 ShortTermMemory**（模拟重启）问
"我叫什么？学到哪了？"。

**预期输出**：会话 2 检索到记忆（相似度
0.67/0.57）并正确回答——没有任何短期历史，答对只能靠长期记忆。每轮
结束 LLM 提取值得记的事实入库。

## How It Works

记忆分三层流转：**对话层**——用户输入经滑动窗口放行、与检索到的相关
记忆一起进入 `build_context`，组装后交给模型。

**记忆层**——用户输入先被 nomic-embed-text 变成 768 维向量，在
memory_store.json 里做余弦相似度检索。

**沉淀层**——对话结束后 LLM 判定值得记的事实，向量入库并写入
MEMORY.md。

**滑动窗口**：`build_window()` 从最新消息向前收集，预算（300 token）
用尽即停，system 消息永远保留。与全量重发（05 实验）相比 token 成本有
上界，代价是早期对话被淘汰——被淘汰的内容若有长期价值，就该在对话时
沉淀进长期记忆（两层配合的逻辑）。

**向量检索：语义而非关键词**。"我喜欢吃什么？"与"用户喜欢吃火锅"没有
共同关键词，但 embedding 空间里意思越近的文本向量越接近——这两句话
的余弦相似度达 0.67（值越接近 1 越相似）——**语义检索让记忆按意思被
找到，而不是按字面**。

检索带相似度阈值（0.5）过滤不相关记忆：宁可
少注入，不注入噪音。

组装与召回的核心：

```python
def build_messages(user_msg, hits):
    """短期窗口 + 长期检索结果 -> 完整请求"""
    stm = ShortTermMemory(SYSTEM_PROMPT)
    stm.add("user", user_msg)
    if hits:
        lines = "\n".join(f"- {t} (相似度 {s:.2f})" for s, t in hits)
        stm.system_prompt += f"\n\n【相关记忆】\n{lines}"
    window, dropped = stm.build_window()
    return window, dropped

def recall(user_msg, store):
    return store.search(embed(user_msg), top_k=TOP_K, threshold=SIM_THRESHOLD)
```

与会话 2 的输出互相印证：你看到的"相似度 0.67/0.57"两行来自 `recall()`
的 `store.search(...)` 返回的 top-k（相似度最高的 k 条）；prompt 里的
"【相关记忆】"块就是 `build_messages` 拼的 `lines`。

**沉淀：LLM 判定"值得记"**。每轮对话结束后，用 LLM 从对话中提取值得
长期记住的事实（一句话），embedding 入库并追加 MEMORY.md。MEMORY.md
是人可读的沉淀层——可以直接打开看 Agent 记了什么、手动删掉不该记的。

## Pitfalls & Q&A

踩坑清单（现象 + 原因 + 解法）：

- **同一事实被反复提取入库（本篇真实发生）**。现象："喜欢吃火锅"沉淀
  了两次。原因：提取环节没有去重与融合。解法：去重与融合是 19 实验
  的主题。
- **重复运行后记忆越滚越多**。现象：跑几次实验，召回结果越来越杂。
  原因：`memory_store.json` 与 `MEMORY.md` 是运行时产物，每次运行
  追加。解法：想从零开始就删掉这两个文件。
- **阈值设错导致失忆或噪音**。现象：阈值过高时召回为空（"失忆"），
  过低时注入不相关记忆。原因：阈值没按库的规模调。解法：按库规模
  调整（本篇用 0.5）。
- **更换 embedding 模型后检索全错**。现象：维度对不上或召回结果不
  相关。原因：新旧模型向量维度与语义空间都不同，旧向量作废。解法：
  全量重建索引。

**Q1: 滑动窗口的预算怎么定？淘汰时要注意什么？**

按模型上下文与成本预算定；system 消息永不淘汰，尽量成对淘汰，被淘汰
内容若值得保留应先沉淀长期记忆。

**Q2: 向量检索相比关键词匹配的优势？**

语义级匹配（机制见 How It Works 的检索段），代价是每次查询多一次
embedding 计算与一份向量存储。

**Q3: 什么事实值得写入长期记忆？谁来判定？**

偏好、身份、约定等稳定事实；由 LLM 判定（本篇），更精细的重要性分级、
去重融合与遗忘策略见 19 实验。
