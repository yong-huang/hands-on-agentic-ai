# 03 · Prompt 结构设计：CoT + Few-shot 引导结构化输出

> 用一套分层的 System Prompt（系统提示词）——角色设定 + CoT 思维链 +
> Few-shot（少样本）示例 + 输出标签约定——让模型"先想后说"，稳定输出
> 可解析的 JSON（结构化数据格式）；并用三种不同角色实测同一问题的回答
> 差异。读完你能写出一份让模型稳定输出结构化数据的提示词模板。

## Background

在没有结构化约定之前，让模型输出数据的最常见做法是直接加一句"请返回
JSON"。模型通常配合，但偶尔会在 JSON 前后添一句"好的，以下是您要的
内容"，或者临时加字段、换行带注释。

程序侧的 `json.loads`（Python 标准库的 JSON 解析函数）碰到这些字符
就直接抛异常。

这件事在 Agent 场景是硬约束：Agent（在循环中自主调用模型并执行动作的
程序）的每个决策都来自模型输出，而程序的每个动作都要求输出可解析。
输出格式不稳，程序就无法可靠地往下走。

问题不在模型"不配合"，而在于调用方没有同时说清两件事：想的过程放在
哪、结果的格式长什么样。把这两件事写进一份分层的系统提示词，再用示例
钉死格式，就是本篇的方案。

它也是 ReAct（推理与行动交替的 Agent 提示格式，见 06 实验）的直系
祖先——ReAct 的 `Thought/Action/Answer` 格式就是同一套思路。

## What

System Prompt 结构化设计，指用一份分层的提示词（Prompt，发给模型的
文字输入）同时约束模型的推理过程与输出格式，使回复既可读、又可被程序
解析。

四层结构：

| 层 | 作用 | 本项目的实现 |
| :--- | :--- | :--- |
| 角色（Identity） | 限定语气与专业域 | "你是一个专业的数据分析助手" |
| 任务 + 格式约定 | 说明做什么、输出长什么样 | 情感分析 + `<thinking>`/`<output>` 双标签 |
| CoT 指令 | 要求先推理再下结论 | "先在 `<thinking>` 中逐步分析" |
| Few-shot 示例 | 用 3 个样例钉死格式 | 正面/负面/中性各一条 |

CoT（Chain of Thought，思维链）指要求模型把推理步骤写出来再下结论；
Few-shot（少样本提示）指在提示词里放几个输入/输出示例供模型模仿；
`<thinking>`/`<output>` 是一对 XML 风格的标签（成对出现的标记文本），
分别圈住推理与结论。

心智模型：**可以把写这份 Prompt 想象成"用自然语言编程"——Prompt 是
编程，示例是类型声明，双标签是返回值的信封。** 但和真代码不同的是：
模型不保证完全遵守约定，解析侧永远要留兜底（见 How It Works 的两级
回退）。

## When to Use

核心判断：输出要给程序消费，就该约定格式；纯属给人看的聊天，不必上
模板。

典型场景：

- **给 Agent 或流水线喂模型输出**：后续代码要读取字段做判断，输出必须
  可解析；
- **接口不支持服务端格式约束**：本地模型或旧版接口没有 Function
  Calling（函数调用——由服务端强制模型按预定义函数的参数格式输出的
  机制）或 JSON mode（服务端保证只输出合法 JSON 的开关），只能靠提示词
  自救；
- **要控制回答的视角**：让同一个问题从不同专业视角作答，如本篇实测的
  工程师/产品经理/安全审计三种角色。

何时不用：接口支持 Function Calling 或 JSON mode 时优先用服务端保证，
比提示词约定更稳。

| 方案 | 差异 | 什么时候选它 |
| :--- | :--- | :--- |
| Prompt + 标签约定（本篇） | 纯提示词层实现，任何接口可用 | 无服务端约束的接口、本地模型 |
| Function Calling | 服务端强制 JSON Schema（描述字段与类型的规范），连解析都省了 | 接口支持时的首选（见 11 实验） |
| JSON mode | 服务端保证合法 JSON，不保证字段 | 只要求"是 JSON"，字段自行校验 |

## Quick Start

前置条件与 01 实验相同：Ollama 已启动、已执行 `ollama pull
qwen3.8:latest`、Python 环境装有 `requests` 库。

```bash
cd agents/03_call_llm_cot
python call_llm_cot.py
# 🧑 请输入需要分析的文本: （回车用默认："这个产品很好用，质量也很棒！"）
```

脚本依次做四件事：

1. 读入待分析文本；
2. 以 `temperature=0.3`（采样温度——控制输出随机性的参数，结构化任务
   要低温）调用 API；
3. 打印模型完整响应——你能亲眼看到 `<thinking>` 里的推理过程；
4. `extract_json()` 提取并解析，美观打印五字段结果。

预期输出：`📊 结构化输出结果`，含 `category / sentiment / confidence /
keywords / summary`。

Prompt 模板骨架（实际文件里是完整版，含三条示例）：

```python
SYSTEM_PROMPT = """你是一个专业的数据分析助手...
## 输出格式要求
1. 先在 <thinking> 标签中逐步分析（CoT）
2. 再在 <output> 标签中给出纯 JSON，字段:
   category, sentiment, confidence, keywords, summary
## 示例
输入: 这家店服务太差了...     ← Few-shot 第 1/3 条
<output>{"sentiment": "负面", ...}</output>
"""
```

## How It Works

本节回答两个问题：这份模板为什么能稳定出 JSON，以及解析侧怎么接住
偶尔的不合规输出。

### 为什么稳定：每一层都在缩小输出空间

角色层限定语气与专业域。它不是玄学，是对采样分布（模型输出逐词按概率
挑选，角色设定改变这些概率）的条件约束：把 System Prompt 换成"工程师/
产品经理/安全审计"三种角色问同一个问题，回答侧重点立刻分化——工程师
谈实现、产品谈用户价值、安全审计谈风险。

格式层由 Few-shot 与双标签配合：模型对"照着例子输出"的服从度远高于
"按 JSON Schema 输出"，三个示例覆盖正/负/中性三类，等于告诉模型——
**输出就长这样，字段一个都不能少**；双标签则给解析器一个精准的锚点。

### CoT：先想后说

`<thinking>` 圈住推理、`<output>` 圈住结论，推理过程可读、结论可解析，
两者兼得。

可以把 `<thinking>` 想象成发给模型的草稿纸：把推理显式写出来，后面的
内容就能参考前面的分析（为什么这能提升准确率，见文末 Q1）。但和草稿纸
不同的是：草稿内容留在上下文里、会持续影响后续输出，且可能包含自我矛盾
的内容。

因此只把 `<output>` 的 JSON 交给程序，`<thinking>` 不进入下游。

CoT 家族速览（文件头注释里有 10 种形态的完整表格）：Zero-Shot（零
样本，指令里只说"一步步想"，不给示例）、Few-Shot（少样本，带推理
示例）、Self-Consistency（自洽性，同一问题多次采样投票取多数）、
ReAct（推理与行动交替进行，见 06 实验）。

### 解析的两级回退

```python
pattern_tag  = r"<output>\s*(\{.*?\})\s*</output>"   # 第一级: 标签内提取
pattern_json = r"\{[^{}]*\}"                          # 第二级: 全文第一个 {...}
```

正则表达式（用模式字符串在文本中定位内容的工具）分两级：第一级精准，
第二级兜底——模型偶尔忘写标签时仍能救回。第二级只匹配无嵌套的扁平
JSON，所以字段设计时要避免嵌套对象。

一个必须注意的细节：正则必须带 `re.S`（DOTALL，让 `.` 也能匹配换行符
的标志），否则跨行 JSON 匹配失败。完整的自救链不止这两级，见文末 Q3。

## Pitfalls & Q&A

踩坑清单（每条 = 现象 + 原因 + 解法）：

- **解析出的 JSON 多字段、换行带注释**：现象是解析出的对象和约定格式
  不符。原因：`temperature` 偏高，模型在格式上"发挥"。解法：结构化
  任务把温度控制在 0-0.3。
- **`confidence` 很高但答案是错的**：原因：`confidence` 是模型自估的
  置信度，**不是真实概率**。解法：只拿它做相对比较，不做绝对判断。
- **`keywords` 里混着标点**：现象是中文场景下关键词带逗号、句号。原因：
  模型按示例风格输出，不保证自行清洗。解法：下游解析后做一次标点清洗。

**Q1: CoT 为什么能提升准确率？**

把中间推理显式化，相当于给模型草稿纸——后续 token 可以"参考"前面的
推理，降低一步到位的出错率；代价是输出变长、延迟变高。

**Q2: Few-shot 示例数量越多越好吗？**

不是。示例占上下文窗口（模型单次能读入的最大文本长度）且边际收益递减，
2-5 个覆盖典型 case 通常最优；示例的**格式一致性**远比数量重要。

**Q3: 模型输出的 JSON 解析失败有哪些自救手段？**

①正则提取标签/花括号；②重试并在消息里附上解析错误；③温度调 0；
④终极方案 Function Calling / JSON mode 由服务端保证格式。

**Q4: temperature=0.3 而不是 0，为什么？**

留一点随机性避免措辞僵化，同时足够低保证格式稳定；纯分类任务可以到 0
（温度对照实验见 04 实验）。
