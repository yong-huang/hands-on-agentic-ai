# 19 · 记忆更新策略：重要性判定、查重与融合

> 项目 17 暴露了一个真实问题：Agent 的长期记忆"只进不出"——同一句"喜欢吃
> 火锅"被沉淀两次，天气寒暄和核心画像混在一库。本篇给长期记忆装上管理器：
> 每条新事实经过**三重决策**（LLM 重要性判定 → 向量查重 → LLM 融合），并用
> 对照实验证明：同一组陈述，裸入库攒下 5 条带重复带琐碎的记忆，托管入库
> 只剩 2 条干净且自我更新的记忆。

## 1. 为什么需要它

没有更新策略的记忆库会得三种病：**重复**（同一事实换种说法再存一遍）、
**过时**（"更喜欢日料了"和"最喜欢吃火锅"并存，模型不知道哪个新）、**噪音**
（天气寒暄与核心画像同权）。病根都是"只进不出"。本篇的三重决策让记忆库
像数据库一样有约束（查重）、像文档一样有更新（融合）、像人一样有判断
（重要性）——检索质量随之提升，因为注入的每条记忆都是干净且当前有效的。

## 2. 总览：核心机制一图看懂

![记忆更新的三重决策](images/memory_update.workflow.svg)

**怎么看这张图**：一条用户新陈述先过**重要性判定**（LLM 打分 0-10，低于 4
直接丢弃）；存活者进入**向量查重**——与最相似旧记忆的余弦相似度决定去向：
≥0.85 判为重复跳过，0.70-0.85 交给 LLM **融合**（新信息更新旧事实），
<0.70 作为新记忆入库。真机实测：日料偏好更新（0.82）、重复跳过（0.93）、
天气丢弃（0 分）各命中一路。

心智模型一句话：**先问值不值得记，再问是不是记过了，最后问要不要改写旧记忆。**

真实模式把同一组 5 条陈述分别跑 17 式裸入库和本篇托管入库。**真机实测**：

- 「更爱吃日料了」→ **merged**：与旧记忆融合成"我叫张三，现在更爱吃日料，
  火锅吃得少"（相似度 0.82）——偏好变化被更新而不是并存；
- 重复的"喜欢吃火锅"→ **skip_duplicate**（相似度 0.93）；
- "今天天气真不错"→ **skip_trivial**（重要性 0 分）；
- 最终：裸入库 5 条（含重复 + 琐碎）vs 托管入库 2 条（干净、带重要性分）。

## 4. 核心概念

### 4.1 三重决策

| 决策 | 手段 | 阈值 | 拦截的问题 |
| :--- | :--- | :--- | :--- |
| 重要性判定 | LLM 打分 0-10 | < 4 丢弃 | 琐碎噪音入库存 |
| 向量查重 | 余弦最相似旧记忆 | ≥ 0.85 跳过 | 同一事实重复占用 |
| LLM 融合 | 更新旧事实并重嵌入 | 0.70-0.85 触发 | 新旧偏好并存、模型不知哪个新 |

未命中的（< 0.70）作为全新记忆入库。三个阈值都是可配置的策略参数。

### 4.2 融合是"更新"而非"追加"

偏好变化是最典型的融合场景："最喜欢吃火锅"之后来了"更爱吃日料了"——两者
语义相关（0.82）但内容冲突。`llm_merge` 把新信息合并进旧记忆并重嵌入，
库里永远只有一条当前有效的偏好。**没有融合的记忆库无法表达"变化"**。

### 4.3 决策审计

`ManagedMemory.log` 记录每次决策（陈述、决策类型、依据）——生产系统的
记忆治理同样需要审计：为什么这条被丢？那条和谁合并了？出了错能回放。
`--demo` 里的离线版（difflib 查重 + 规则判定）与真实版决策逻辑一致，
验证的就是这条可测试的决策流。

### 4.4 已知边界

- 阈值是经验值：语料变了（中文/英文、长短句）0.85/0.70 需要重新标定；
- LLM 打分有噪声，同一条陈述多次打分可能差 1-2 分——边界附近建议重试或
  取多次均值；
- 仍然没有"遗忘"：过时记忆只是被融合覆盖，按时间衰减的主动遗忘策略是
  记忆系统的下一步。

## 5. 代码关键部分

```python
def remember(self, statement):
    imp = judge_importance(statement)                    # 决策 1: 重要性
    if imp < IMPORTANCE_FLOOR:
        return "skip_trivial", f"重要性 {imp}"
    vec = embed(statement)
    best_sim, best = max(((cosine(vec, it["vec"]), it) for it in self.items),
                         default=(0.0, None))
    if best_sim >= DUP_THRESHOLD:                        # 决策 2: 查重
        return "skip_duplicate", best["text"]
    if best_sim >= MERGE_THRESHOLD:                      # 决策 3: 融合
        merged = llm_merge(best["text"], statement)
        best.update(text=merged, vec=embed(merged),
                    importance=max(best["importance"], imp))
        return "merged", merged
    self.items.append({"text": statement, "vec": vec, "importance": imp})
    return "added", statement
```

坑清单：

- 判定失败（网络/解析）时保守放行（重要性记 5），不要静默丢弃用户信息；
- 融合后必须重嵌入——文本变了向量不变会让后续查重失真；
- 决策日志是治理的基础设施，与功能代码同等重要。

## 7. 面试要点

- **Q: Agent 长期记忆为什么需要更新策略？**
  A: 只进不出会导致重复、过时与噪音三类污染，检索注入的上下文质量随之劣化；
  更新策略让记忆库保持"干净且当前有效"。
- **Q: 如何判断一条新记忆与旧记忆是重复还是需要融合？**
  A: 用向量相似度分档：极高（≥0.85）为重复跳过；中度（0.70-0.85）交 LLM
  融合——新信息更新旧事实；低（<0.70）为新记忆。阈值靠语料标定。
- **Q: 为什么融合后要重新计算 embedding？**
  A: 文本已变，旧向量不再代表新内容；不重嵌入会让下一次查重给出错误的
  相似度。
- **Q: 重要性判定失败时应该丢弃还是保留？**
  A: 保守保留（记中等分）——判定失败是基础设施问题，静默丢弃会丢失用户
  数据；配合重试与审计。
- **Q: 记忆治理还缺什么？**
  A: 主动遗忘（时间衰减/容量驱逐）、访问统计（长期不被召回的记忆降权）、
  用户可见可编辑的记忆面板。

## 8. 总结

重要性判定挡住噪音，查重挡住重复，融合让记忆能表达"变化"——加上决策审计，
长期记忆从"只进不出的日志"变成"有治理的数据资产"。至此第四阶段（16-19）
收官：上下文组装、两层记忆、压缩策略、更新策略——Agent 已经具备了完整的
记忆与上下文工程能力。下一篇进入第五阶段 RAG：先从文档加载与切分开始。
