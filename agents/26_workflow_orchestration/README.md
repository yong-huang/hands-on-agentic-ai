# 26 · 工作流编排：扇出评审 + 反思修订循环

> 扇出/扇入——同一份稿件并行送给 3 个不同视角的评审员（准确性/结构/风格），意见与评分扇入汇总；反思循环——均分不达标就带着全部意见回炉修订，再评，直到达标或用尽轮数。读完本篇你能跑通一个"三路评审 + 回炉修订"的编排实验，并掌握 Reflection 模式的适用边界。真机实测：三路评审并行 9.7s，均分 8.0 一次过。

## Background

在没有这套编排的做法里，产物写完只有两条路：直接发布，或者交给一个评审员逐项过目。直接发布意味着结构与风格问题无人把关；单评审员只有单一视角，容易漏掉自己不关注的维度；想多几个视角，就只能串行排队评，一个评完再评下一个。

痛点在两个方向同时出现：单视角评审漏检，多视角串行评审又慢，而且评完之后"怎么改"没有机制保证——模型重新生成一版，未必针对上次的批评。

"生成 → 批评 → 修订 → 再批评"的闭环做法因此被系统化为 Reflection 模式，配合并行评审编排落地：多个异构视角同时审视同一份产物，意见合并后作为修订输入。批评比生成容易，这让多角色批评能实质提升产物质量。

## What

工作流编排是一种把多个步骤（并行、汇总、条件分支、循环）组织成固定流程的技术。

本篇的编排流程：写作层的初稿扇出（Fan-out，把一份产物同时分发给多个并行处理者）给三个并行评审，意见与评分扇入（Fan-in，把多个并行结果汇合到一处）到反思修订节点。修订稿回炉重新评审，条件边（按条件决定流程走向哪个分支的路由机制）在"均分 ≥8 或轮数用尽"时走向定稿。

| 阶段 | 机制 | 收益 |
| :--- | :--- | :--- |
| Fan-out | 3 个评审视角并行（ThreadPoolExecutor，Python 标准库线程池） | 墙钟时间（真实流逝的时间）≈ 最慢评审，而非之和 |
| Fan-in | 意见与评分汇总为一个反馈块 | 多维反馈一次到位 |

评审视角是异构的（各视角关注点互不相同：准确性/结构/风格各有评审提示词）——同构的多份评审只会互相重复，异构才产生增量信息。

心智模型一句话：**一个作者、三个批评家、一个循环——改到能过审为止。**

## When to Use

适合在三类时候选它：

- 产物需要多维质检时：文档、报告、规范在发布前要过准确性、结构、风格几道关，缺一不可。
- 单次生成质量不稳时：需要"批评驱动修订"的闭环，而不是碰运气式地重新生成。
- 反馈可以并行收集时：各评审维度互不依赖，能同时给出意见。

不要用的两种情况：

- 评审之间需要看到彼此意见再下结论：应改为串行辩论（27 的主题）。
- 只有单一质量维度、一次生成即达标：直接生成即可，编排只增加成本与延迟。

与相邻编排的对照（24 实验：LangGraph，用状态图组织流程的编排框架；25 实验：Manager-Worker）：

| | 24 LangGraph | 25 Manager-Worker | 26 本篇 |
| :--- | :--- | :--- | :--- |
| 编排原语 | 状态图 + 条件边 | 分解 + 并行 + 合并 | 扇出评审 + 反思循环 |
| 循环 | 有（修订回炉） | 无 | 有 |
| 并行 | 无 | 有（Worker 产出独立） | 有（同一产物的多维评审） |
| 适用 | 需要检查点（可保存与恢复的中间状态）的复杂流程 | 任务可独立拆分 | 产物需要多维质检 |

## Quick Start

前置条件：Python 3 环境；`--demo` 模式离线可跑，真实模式需要已配置可用的模型访问（真机实测用的是 qwen3.8）。

```bash
cd agents/26_workflow_orchestration
python workflow_orchestration.py --demo   # 离线：预置评审，走完两轮编排
python workflow_orchestration.py          # 真实：qwen3.8 三路并行评审 + 修订
```

真实模式的诚实预期（默认任务：撰写《如何为团队编写高质量的 Agent 开发规范》）：初稿 254 字 → 三路评审并行（9.7s，均分 8.0：准确性 8/结构 8/风格 8，意见集中在"缺 Agent 特有技术细节"）→ 均分达标一次过定稿。

demo 模式则完整演示了修订分支：第一轮 6/7/7 分 → 带意见回炉 → 第二轮 8/8/9 定稿。跑 `--demo` 能在几秒内看到"不达标 → 回炉 → 达标"的完整路径。

## How It Works

流程分两段：扇出评审负责打分与汇意见，反思循环负责不达标时回炉。扇出评审的实现是本篇最核心的一处代码：

```python
def review_once(reviewers, draft, round_no):
    """Fan-out: 三路并行评审; 返回 (均分, 汇总反馈)"""
    t0 = time.time()
    with ThreadPoolExecutor(max_workers=len(reviewers)) as pool:
        reviews = list(pool.map(one, reviewers))
    avg = round(sum(r["score"] for r in reviews) / len(reviews), 1)
    feedback = "\n".join(f"- {r['reviewer']}({r['score']}分): {r['comment']}"
                         for r in reviews)
    return avg, feedback
```

`pool.map` 把三位评审员同时提交进线程池，等全部返回后计算均分、把意见拼成一个反馈块——你在 Quick Start 看到的 9.7s（≈ 最慢一路评审而非三路之和）就来自这里；那个"均分 8.0"就是函数返回的 `avg`，条件边拿它决定定稿还是回炉。

反思循环的关键在修订提示词：**携带全部评审意见**。修订不是重新生成，而是带着批评做针对性改进。真机首轮三位评审员的意见高度一致（"缺 Agent 特有细节"），这种共识意见正是修订的最佳输入——demo 里 6/7/7 回炉后变 8/8/9，靠的就是这一机制。

Reflection（反思模式：生成 → 批评 → 修订的闭环）之所以有效：批评比生成容易——模型判断"哪里不好"的准确率高于"一次写好"。多维批评意见作为修订输入，等效于把评估信号注入生成过程。

## Pitfalls & Q&A

踩坑清单（现象 / 原因 / 解法）：

- 某一路评审打分缺失。现象：一轮评审少一个分数，均分算不出。原因：评审 JSON（键值对形式的文本数据格式）解析失败，格式抖动。解法：解析失败时给中位分兜底，不让一个评审员的格式抖动拖垮整轮。
- 修订后老问题仍在。现象：修订稿没改正被批评的点。原因：修订提示词只带了低分项意见，漏掉共识意见。解法：修订提示词必须包含全部意见——共识意见最有指导性。
- 想核对某路评审的意见。现象：结果顺序对不上评审员。解法：`ThreadPoolExecutor.map` 本身保持结果顺序与评审列表对应，直接按下标对照即可。

已知边界：评审员与作者是同一个模型，存在"自己偏好自己风格"的相关性偏差，生产可混用不同模型当评审员；轮数用尽时以当前版本定稿并如实标注均分，不假装达标。

**Q1: 扇出并行的前提是什么？**

子任务相互独立。评审恰好独立（同一输入、不同视角）；若评审之间需要看到彼此意见，则应改为串行辩论（见 27 实验）。它与 25 实验的并行差异（拆分子任务分头处理 vs 多视角质检）见 When to Use 的对照表。
