# 22 · Agentic RAG：检索成为 Agent 的工具

> 检索不再是无脑执行的固定管线，而变成 Agent（能自主调用工具、按目标行动
> 的 LLM 应用）手里的**工具**——模型先看问题，自主决定"要不要查、查什么"，
> 查完基于结果作答；知识库没有的内容明确拒答，绝不编造。读完你能把"检索
> 决策权"交给模型，并守住拒答底线。

## Background

前面实验搭好的检索管线是固定的：拿到问题，先检索，再把资料拼进提示词，
最后生成回答——每个问题都走同一条路，一步不跳。

固定流程在两类问题上撞墙。闲聊寒暄（"你好""讲个笑话"）明明不需要资料，
也要白白过一遍检索；而用户说"切分文档有什么讲究"，资料里写的却是"递归
字符切分"，拿原句直接当检索词，召回质量很差。更糟的是知识库根本没覆盖
的问题——流程里没有"不答"这个出口，模型只能硬编。

解法是把"查不查、查什么"从代码里拿出来，交给模型自己判断：检索被封装
成模型可以调用的工具，模型看问题决定用不用、怎么用。能力做成工具、决策
交还给模型——这就是 Agent 与管线的分界线。

## What

**Agentic RAG（代理式检索增强生成）是一种把检索交给模型自主决策的 RAG
（Retrieval-Augmented Generation，先从资料库检索相关内容再生成回答的技术）
形态：检索不再是每个问题必经的固定步骤，而是模型可以选用或不选的工具。**

它运行在一个决策循环里：用户问题进入循环，LLM 每轮输出一个 JSON 决策
（JSON 是一种键值成对的文本格式）——`search`（带上改写后的检索词）就走
检索工具、结果回喂给模型；`answer` 则输出最终回答结束循环。

检索工具背后是 21 实验的向量索引（把文本转成向量——一组能表达语义的
数字——再按距离查找的索引）。max_rounds=3 兜底防死循环：

```json
{"action": "search", "query": "文档切分 chunking 策略"}
{"action": "answer", "answer": "最终回答"}
```

可以把这个循环想象成一位查档案的研究员：收到问题先判断"需要查资料吗"，
需要就先拟好检索词翻档案，翻到足够材料再下结论；档案里没有就明说"没有"。
但和研究员不同的是，这里的每一步都是 LLM 输出的一行 JSON 决策，模型不会
主动反思策略，轮数超过 max_rounds=3 就兜底退出。

心智模型一句话：**把 search 做成工具，"查不查、查什么"由模型自主决策。**

## When to Use

在问题类型不可预知、且检索有成本的时候用：面向真实用户的助手（一半输入
是寒暄，不该每次都查库）；用户表述与资料措辞差距大的知识库问答（模型会
把"切分文档有什么讲究"改写成向量空间更认的检索词）；对编造零容忍的场景
（检索无果时明确拒答）。

不用的情况：每个问题都必然需要检索（固定管线更简单、延迟更低）；只有
一种固定问法的小系统；对响应速度极敏感的线上接口——决策循环每轮都要
调用一次 LLM。

| 方案 | 差异 | 什么时候选它 |
| :--- | :--- | :--- |
| 固定管线 RAG | 每问必检索，无决策 | 问题全部需要查库、模式固定 |
| Agentic RAG（本篇） | LLM 自主决定查不查、查什么 | 问题混杂、需要改写检索词与拒答 |
| Function Calling 多工具 | 协议级工具调用，工具可并存 | 工具多（search/read_more/compare 等）、参数复杂 |

## Quick Start

前置条件：本地 Ollama（localhost:11434，本地运行大模型的工具）已拉取
`qwen3.8:latest` 与 `nomic-embed-text`，并 `pip install chromadb`；
索引数据复用 20/21 实验的 docs 与代码。

```bash
cd agents/22_agentic_rag
python agentic_rag.py --demo   # 离线：预置决策脚本走完整循环
python agentic_rag.py          # 真实：qwen3.8 自主决策 + 项目 21 的向量索引
```

`--demo` 用脚本里预置的决策序列和伪向量（由内容 hash 算出的替代向量，
只为验证循环结构、不携带语义）跑完整循环，不调用任何在线服务，适合先
看循环结构。真实模式测两个问题，实测输出：

- "切分文档有什么讲究？"→ round 1 自主检索（查询被改写成"文档切分
  chunking 策略 讲究 注意事项"），round 2 基于检索给出 4 点结构化回答
  （切分大小 / 递归策略 / overlap / 元数据）；
- "量子力学的波函数坍缩？"（知识库外）→ 检索无果后明确回答"知识库中没有
  相关信息"，零编造。

诚实预期：真实模式每个问题至少要跑两轮 LLM 决策，回答明显慢于固定管线
的单次调用；换模型或改系统提示词后，决策轮数与回答内容会有变化，但
"库外问题拒答"的行为由提示词强制保证。

## How It Works

决策循环的实现只有十几行——模型出决策，代码只负责执行与回填：

```python
def agentic_answer(collection, question, llm, max_rounds=3):
    messages = [{"role": "system", "content": SYSTEM_PROMPT},
                {"role": "user", "content": question}]
    for round_no in range(1, max_rounds + 1):
        decision = extract_json(llm(messages))
        if decision["action"] == "answer":
            return decision["answer"]
        print(f"  [round {round_no}] search: {decision['query']}")
        messages.append({"role": "assistant",
                         "content": json.dumps(decision, ensure_ascii=False)})
        messages.append({"role": "user",
                         "content": f"[search 结果]\n{search_tool(decision['query'])}"})
    return "（达到最大轮数仍未给出答案）"
```

每轮做三件事：把全部对话历史交给 LLM，`extract_json` 从回复中解析出决策
JSON；`action` 为 `answer` 就直接返回；否则执行检索，把决策和
`[search 结果]` 作为两条新消息追加回历史，进入下一轮。

你在实测输出里看到的 `[round 1] search: 文档切分 chunking 策略 讲究
注意事项` 这一行，就是 `print` 语句打印的模型改写后的检索词。

**检索词改写是 Agent 的隐性增值**：用户问"切分文档有什么讲究"，模型检索
用的是"文档切分 chunking 策略 讲究 注意事项"——**检索词比原句更适合
向量空间（资料被表示成向量后所在的数字空间）**。

这是 Agentic RAG 相对固定管线最实在的收益：把"提问"和"查询"两个任务
解耦给最擅长的角色。

**拒答靠三道防线**：系统提示词明确要求"知识库中没有的信息必须拒答"；
检索无果时模型拿不到可依据的材料；答案被要求引用 chunk（文本块）出处，
即元数据（记录来源与属性的数据）。

**RAG 的信任来自"知之为知之"**——一次编造毁掉的可信度，十次正确回答
也换不回来。实测里"量子力学"问题的回答就来自第一道防线。

三条终止路径都要如实报告而不是硬答：模型显式输出 answer、达到 max_rounds
（返回"（达到最大轮数仍未给出答案）"）、决策解析失败。

## Pitfalls & Q&A

踩坑清单（每条：现象 → 原因 → 解法）：

- **循环崩在 JSON 解析**。现象：模型输出夹带说明文字，`extract_json`
  抛异常，整个回答中断。原因：LLM 不保证每轮都输出合法 JSON。解法：
  解析失败要有兜底（提示重试或直接报告失败），不能让循环崩掉。
- **答案无法溯源**。现象：回答正确但不知道出自哪个文件。原因：检索结果
  注入时没带出处。解法：检索结果注入时带上 `[文件#块号]` 出处标注。
- **该拒答的不拒答**。现象：库外问题模型开始凭参数知识编造。原因：模型
  不知道知识库的边界。解法：知识库主题要在 system prompt（系统提示词）
  里声明，模型才能判断"什么该拒答"。
- **Agent 救不了垃圾索引**。现象：改写检索词后仍然召回不准。原因：检索
  质量的上游仍是切分（20 实验）与索引（21 实验）。解法：先治理上游，
  再谈决策层。

**Q1: 如何避免 RAG 编造（幻觉，指模型输出看似合理但无依据内容的现象）？**

How It Works 的三道防线：系统提示词强制"知识库外必须拒答" + 检索无果时
不给答案 + 让答案引用 chunk 出处（元数据），缺一不可。

**Q2: 决策用 JSON 还是 Function Calling？**

单工具 JSON 足够且好调试；多工具/参数复杂时升级 Function Calling（11
实验的协议，模型按协议描述直接"调用"函数），决策空间变大后的选型见
When to Use 的对比表。
