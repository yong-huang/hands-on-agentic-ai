# 08 · Plan-and-Execute：先规划，后执行

> 主流架构 Plan-and-Execute（先规划、后执行）：先让大模型一次性把任务分解
> 成 JSON 计划（机器可读的步骤清单），再按计划逐步执行本地工具，最后汇总
> 所有结果作答——规划 1 次、汇总 1 次，中间零模型调用。读完本篇，你能用
> 纯 Python 实现这套三段式架构，并知道什么任务该用它而不是逐步对话式循环。

## Background

在本篇之前，主流做法是 ReAct 式循环（Reason + Act，"走一步看一步"的范式）：每一步都把当前对话交给大模型（LLM，Large Language Model，能理解并生成文本的超大规模语言模型），让它看着最新结果决定下一步调用什么工具，循环往复直到它给出答案。

这个做法在任务变长时会撞上两堵墙。其一，模型调用次数随步数线性增长——一个 6 步的任务要调用 6 次模型，慢且按次计费；其二，模型没有全局视图，走一步看一步，经常做完三步才发现路线不对，前面几步全部白费。步骤之间的数据也只能靠对话历史隐式传递，多一步就多一分被模型记错的可能。

Plan-and-Execute 的思路是把"想"和"做"彻底分开：模型只在开头一次性生成完整计划，之后每步执行的是确定性的本地代码（确定性：同样输入永远得到同样输出，不经过模型采样），最后再让模型汇总。

LangGraph（主流的智能体编排框架）生态的 plan-and-execute 模式、Claude Code（Anthropic 的编程智能体工具）里维护任务清单的 TodoWrite 功能，都是这个架构。

## What

Plan-and-Execute（计划-执行架构）是一种先把任务一次性分解成显式计划、再逐步执行计划的三段式智能体架构。三层各司其职：

- **规划层**：调用一次大模型，把用户任务变成 JSON 计划——形如
  `{"steps": [{"tool", "input", "why"}]}` 的步骤清单，每个步骤写明用哪个
  工具、入参是什么、为什么要这一步；
- **执行层**：按计划逐步调用本地工具，用 `{{N}}` 引用替换解决步骤间的
  数据依赖（"第 3 步要用第 1 步的输出"这类关系）；
- **汇总层**：把全部步骤结果交给大模型，生成最终答案。

心智模型一句话：**规划 1 次看清全局，执行阶段零模型调用，汇总收口——想、做、说三段分离。**

"计划形状跟着任务变"是这套架构的关键性质：任务要求求三个城市的人口，计划就是三次查询加一次求和；换成汇率换算，计划就变成查询加乘法。计划由模型按任务动态生成，而不是写死的流程。

## When to Use

这节回答：什么任务该先规划后执行，什么任务不该。

典型场景：

- **任务能一次性拆成固定几步时**（多城市数据汇总、多步单位换算）：规划
  一次、执行零模型调用，成本和时延都显著低于逐步循环；
- **计划需要给人看或审时**（危险操作先审后跑、流程需要存档审计）：计划
  是 JSON 数据，可以打印、存档、人工修改后再执行；
- **步骤间有明确数据依赖时**：`{{N}}` 显式引用比"指望模型从对话历史里
  记住上一步结果"可靠得多。

何时不用：信息不全、需要边探索边调整的任务——那种场景里每一步的观察都会推翻既有计划，应使用 ReAct，或给本架构加重规划（replan，发现计划与现实不符时让模型重新生成计划）机制。

与 ReAct 的逐维度对照：

| 维度 | ReAct（见 06/07 实验） | Plan-and-Execute（本篇） |
| :--- | :--- | :--- |
| LLM 调用次数 | 每步 1 次（N 步 = N 次） | 规划 1 次 + 汇总 1 次 |
| 全局视图 | 无，走一步看一步 | 有，计划可审计、可修改 |
| 步骤间数据传递 | 靠对话历史 | `{{N}}` 显式引用 |
| 适合任务 | 探索型、信息不全 | 结构明确的多步计算/查询 |
| 失败恢复 | 下一步自然调整 | 需要重规划（replan）机制 |

生产系统常两者混合：先规划，执行中偏差过大时触发重规划。

## Quick Start

前置条件：本地装有 Python 3；`--demo` 为离线模式，使用预置计划加真实本地工具；另外两条命令需要本地 Ollama 已启动且已执行 ollama pull qwen3.8:latest。

```bash
cd agents/08_plan_execute
python plan_execute.py --demo                    # 离线：预置计划 + 真实本地工具
python plan_execute.py                           # 真实：默认任务（两城市人口求和）
python plan_execute.py "成都、深圳、广州三个城市的人口总和是多少？"
```

真机实测的诚实预期：模型输出 4 步计划——三次 `get_population` 加一步
`calculator({{1}} + {{2}} + {{3}})`；执行阶段自动替换引用，得到
`calculator(2126 + 1768 + 1881) -> 5775`；汇总器给出"三城人口总和
5775 万"。

换任何人口/计算类任务，计划形状都会跟着变——这就是"动态规划"的含义。

首次运行最常见的失败点是计划提取失败（模型在 JSON 外附加了说明文字），
程序会走两级回退重试，机制见 How It Works。

## How It Works

这节按数据流顺序讲三层内部的两个关键机制：JSON 计划怎么被可靠提取，
`{{N}}` 引用怎么被安全替换。

**机制一：计划即数据。** 规划器的输出是结构化数据而不是一段对话文本——
可以打印、存档、人工修改后再执行，这是文本协议（让模型按约定格式输出
纯文本、代码再解析的做法，见 06 实验）做不到的。

提取计划用两级回退：优先从代码围栏（` ```json ... ``` ` 包裹的代码块）里
取，失败则在全文里找最外层花括号兜底。为什么要回退：模型偶尔会在 JSON
前后加一句"好的，计划如下"，直接解析全文会失败。

**机制二：`{{N}}` 引用的工具感知替换。** 规划器在入参里写 `{{N}}` 引用
第 N 步的输出，执行器在调用工具前完成替换。替换规则因工具而异：calculator
只接受纯数字，所以引用替换时从步骤输出里提取数值部分（"2487万人" →
"2487"）；文本类工具则原样替换。

你在 Quick Start 看到的
`calculator(2126 + 1768 + 1881)`，就是三次 `get_population` 的原始输出
（"2126万人"等）经过这条规则提取后的结果。

```python
def substitute(arg, results, tool):
    """把入参里的 {{N}} 引用替换成第 N 步的输出。
    calculator 只接受纯数字: 引用替换时从步骤输出里提取数值部分。"""
    def fill(m):
        n = int(m.group(1))
        out = next((r["output"] for r in results if r["step"] == n), m.group(0))
        if tool == "calculator":
            num = re.search(r"-?\d+(?:\.\d+)?", str(out))
            return num.group(0) if num else str(out)
        return str(out)
    return re.sub(r"\{\{(\d+)\}\}", fill, str(arg))
```

这段代码里最值得注意的是 `tool == "calculator"` 分支：它对**每个引用独立**
提取数值，保证 `{{1}} + {{2}}` 里的两个占位符各自得到一个数，算式完整。
跳过这个分支会发生什么，见下一节的第一个坑。

## Pitfalls & Q&A

踩坑清单，每条按"现象 → 原因 → 解法"：

- **现象：计算结果碰巧正确，但算式本身是错的。** 原因：替换若不做工具
  感知，`calculator("2487万人 + 2189万人")` 会被工具白名单（只允许列出
  的工具与格式被调用）拒绝；而初版兜底逻辑只提取了第一个数，`{{1}} +
  {{2}}` 被替换成 `"2487"`——第二个数静默丢失，靠汇总器的大模型碰巧算
  对。静默的数据丢失比报错更危险。

  解法：calculator 的每个引用独立提取数值，拿到完整算式 `2487 + 2189 -> 4676`。
- **现象：规划器输出解析失败。** 原因：模型偶尔在 JSON 前后加说明文字，
  或不按围栏格式输出。解法：两级回退提取（代码围栏优先 → 全文花括号
  兜底）。
- **现象：某一步执行失败导致整体作答缺失。** 解法：汇总器兼任安全网——
  某步失败时，大模型仍可基于其余结果作答并明确说明缺失了什么。
- **现象：计划空泛、无法执行。** 原因：规划提示词没有约束步数与工具。
  解法：把步数上限（2-4 步）和工具白名单写进规划提示词。

深入问答：

**Q: 计划生成的可靠性怎么保证？**

结构化输出（JSON，复用 03 实验的方法）+ 两级回退提取 + 步数/工具白名单
约束 + 解析失败时的降级路径（重试或提示用户）。

**Q: 生产系统里这份计划还有什么用？**

人工审批的对象（危险计划先审后跑）、并行执行的依据（无依赖步骤可并发）、
进度展示与审计追溯的数据源。什么任务适合本架构、什么任务适合 ReAct，
见 When to Use 一节的对照表。
