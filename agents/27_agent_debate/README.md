# 27 · 多智能体辩论与投票：用立场对立逼出真实权衡

> 单个 LLM 对争议问题的回答是"一碗水端平的综述"——两个方案各说一句好话就
> 结束。辩论式多 Agent 换一种问法：三个立场对立的专家（架构师/兼容性工程师/
> 求实审计师）就"Function Calling vs 文本协议 ReAct"正面对辩两轮、互相反驳，
> 最后投票产生 2:1 的结论。辩题就是本系列 06 与 11 的真实架构分歧。

## 1. 为什么需要它

 Du et al. (2023) 的研究表明：多 Agent 辩论能显著提升事实性与推理质量——
本质是**用角色对立制造认知压力**。中立综述的毛病是回避取舍；而让一个天然
倾向标准化的架构师和一个天然关注兼容性的工程师正面对抗，双方必须给出证据
并回应对方的最强反驳，权衡分析才会真实发生。投票（而非主持人裁决）让结论
带完整的辩论上下文，可追溯。

## 2. 总览：核心机制一图看懂

心智模型一句话：**立场对立的角色 + 互相可见的发言 + 匿名于立场的投票 =
结论的公信力。**

**真机实测**：round 1 三方立论（FC 的结构化可靠性 vs ReAct 的零依赖兼容性，
审计师意外先行选了 FC）；round 2 的反驳质量显著提升——兼容性工程师指出
"FC 依赖厂商私有实现"，审计师反驳"FC 是 OpenAI 发起的行业标准而非私有黑盒"。
投票：FC 2 票（架构师 + 审计师"长期解析成本更低"）、ReAct 1 票（现状兼容
优先）——**FC 以 2:1 获胜**。

## 4. 核心概念

### 4.1 角色 bias：立场是设计出来的

| Agent | bias 提示词 | 效果 |
| :--- | :--- | :--- |
| 架构师 | "天然倾向标准化与协议化方案" | 先验偏向 FC |
| 兼容性工程师 | "关注模型兼容性与实现成本" | 先验偏向 ReAct |
| 求实审计师 | "中立，只看成本与证据" | 摇摆票，决定结论 |

**摇摆票的存在是辩论有意义的前提**——没有中立者，投票只是形式。bias 写在
system 级提示词里，让角色立场贯穿两轮发言。

### 4.2 辩论轮次：transcript 的累积

Round 2 的每个 Agent 都能看到**全部** round 1 发言（transcript 累积传入），
所以反驳是针对性的（"兼容性工程师混淆了通用与可靠"）。轮数不是越多越好：
2-3 轮后发言开始重复，边际收益归零。

### 4.3 投票：结论的共识机制

投票用 `temperature=0` 的 JSON 输出（`{"vote", "reason"}`），允许投给任何
一方（含自己）但必须给理由。多数派获胜；平票时以审计师（中立者）为准。
**票型本身就是信息**：2:1 说明结论有争议，落地时应配灰度验证。

### 4.4 已知边界

- 角色 bias 会让"辩论"退化为"立场表演"——审计师的中立设定与"允许改票"
  是对冲手段；
- 三个 Agent 是同一模型的不同人格，相关性偏差仍在（生产可混用不同模型）；
- 辩论成本 = 人数 × 轮数 × 调用，9 次调用是本篇的预算。

## 5. 代码关键部分

```python
def vote(agent, transcript):
    raw = chat([{"role": "user", "content": VOTE_PROMPT.format(
        topic=DEBATE_TOPIC, name=agent["name"], bias=agent["bias"],
        transcript=transcript)}], temperature=0.0)
    m = re.search(r"\{.*\}", raw, re.S)
    return json.loads(m.group(0)) if m else {"vote": "无效", "reason": raw[:60]}
```

坑清单：

- 提示词里的 JSON 示例花括号必须转义（`{{}}`），否则 `.format` 直接 KeyError
  （本篇真机踩到）；
- transcript 累积全部发言传给反驳与投票轮——上下文是辩论质量的燃料；
- 投票解析失败时记"无效票"而不是中断，保证流程走完。

## 7. 面试要点

- **Q: 多 Agent 辩论为什么能提升结论质量？**
  A: 角色对立制造认知压力，逼出真实的权衡分析；研究（Du et al. 2023）显示
  辩论能提升事实性与推理质量，代价是调用次数成倍增长。
- **Q: 辩论和项目 26 的评审有什么区别？**
  A: 评审是多视角**质检同一产物**（意见汇聚后修订）；辩论是多个**立场就同一
  问题对抗**（结论由投票产生）——前者改产物，后者选方案。
- **Q: 如何避免辩论变成立场表演？**
  A: 设置中立摇摆票、允许改票、限制轮数防重复、要求反驳针对对方最强论点。
- **Q: 平票怎么处理？**
  A: 以中立者票为准、引入额外证据轮、或上报人工——策略要预先声明而非
  事后决定。
- **Q: 辩论的成本如何估算？**
  A: 人数 ×（轮数 + 1）次调用（含投票），每次的上下文包含完整 transcript，
  token 成本随轮次平方增长——控制在 2-3 轮。

## 8. 总结

三个立场对立的专家、两轮正面对辩、一次带理由的投票——FC 以 2:1 胜出，且
结论带着完整的辩论上下文可追溯。辩论式多 Agent 把"争议决策"从黑盒直觉变成
了可审计的过程。下一篇开始第七阶段：把 Agent 从脚本变成 HTTP 服务。
