# 27 · 多智能体辩论与投票：用立场对立逼出真实权衡

> 三个立场对立的专家（架构师/兼容性工程师/求实审计师）就"Function Calling vs 文本协议 ReAct"正面对辩两轮、互相反驳，最后投票产生 2:1 的结论。读完本篇你能理解"角色对立 + 投票"这套编排为什么能逼出真实权衡，并跑通这个 9 次调用的辩论实验。辩题就是 06 与 11 实验的真实架构分歧。

## Background

在没有辩论编排的做法里，技术选型靠向模型提一个问题，或者让它写一份中立综述。得到的答案往往面面俱到却回避取舍——中立综述的毛病正在于此：不站在任何一边，也就不为任何一边负举证责任。

痛点场景：问"该用 Function Calling（FC，让模型按预定义函数签名发起工具调用的机制）还是 ReAct（让模型以思考、行动、观察循环使用工具的文本协议）"。

单次提问的答案倾向顺从提问者的措辞，权衡分析不会真实发生；换个问法可能得到相反结论，且无法追溯是哪些论据支撑了它。

Du et al. (2023) 的研究表明多 Agent 辩论能显著提升事实性与推理质量，做法被引入编排：给每个参与者写入对立的立场，让双方必须给出证据并回应对方的最强反驳；结论改由投票产生，票与理由全程可追溯。

## What

多智能体辩论是一种让多个立场对立的 Agent（能自主调用大模型完成任务的程序）就同一辩题轮流立论、互相反驳、最后投票定结论的编排模式。流程：三个专家 Agent 并行立论（round 1）→ 各自阅读全部立场后反驳（round 2）→ 每人投票（可投给任何一方，含理由）→ 主持人计票宣布多数派结论。

可以把这场辩论想象成一场技术评审会：三方先各自陈述方案，再交叉质询，最后举手表决。但和真实评审会不同的是：这里的发言顺序固定为"全体立论 → 全体反驳"两轮，没有自由讨论，结论也不由主席裁决而由票数决定。

角色的立场是设计出来的——每个 Agent 的提示词里刻意写入 bias（先验倾向）：

| Agent | bias 提示词 | 效果 |
| :--- | :--- | :--- |
| 架构师 | "天然倾向标准化与协议化方案" | 先验偏向 FC |
| 兼容性工程师 | "关注模型兼容性与实现成本" | 先验偏向 ReAct |
| 求实审计师 | "中立，只看成本与证据" | 摇摆票，决定结论 |

摇摆票的存在是辩论有意义的前提——没有中立者，投票只是形式。

投票机制：`temperature=0`（控制输出随机性的采样参数，0 表示基本总选概率最高的词）的 JSON（键值对形式的文本数据格式）输出（`{"vote", "reason"}`），允许投给任何一方（含自己）但必须给理由；多数派获胜；平票时以审计师（中立者）为准。

心智模型一句话：**立场对立的角色 + 互相可见的发言 + 匿名于立场的投票 = 结论的公信力。**

## When to Use

适合在三类时候选它：

- 技术选型存在真实分歧时：两个方案各有代价（如 FC 的结构化可靠 vs ReAct 的零依赖兼容），需要把权衡摆到台面上。
- 结论需要可追溯的论证时：投票附理由、辩论实录全程累积，决策依据可以回查。
- 单次询问的答案可疑地顺滑时：用对立立场制造认知压力，逼出对方最强反驳的回应。

不要用的三种情况：

- 要改进的是同一份产物而不是方案选择：用多视角评审加修订循环（见 26 实验）。
- 问题有客观正确答案：直接写测试或查证，辩论只会增加成本。
- 预算紧张：辩论成本 = 人数 × 轮数 × 调用，token（模型计费与计长的最小文本单位）成本随轮次平方增长。

| 方案 | 差异 | 什么时候选它 |
| :--- | :--- | :--- |
| 单次询问 | 一个答案，无对抗、无追溯 | 事实性问题、无取舍争议 |
| 中立综述 | 一份平衡但不表态的报告 | 需要背景梳理，不需要决策 |
| 评审 + 修订循环（26 实验） | 多视角质检同一产物并修订 | 目标是改产物质量 |
| 辩论 + 投票（本篇） | 立场对抗，投票选方案 | 方案选型有真实分歧 |

## Quick Start

前置条件：Python 3 环境；`--demo` 模式离线可跑，真实模式需要已配置可用的模型访问。

```bash
cd agents/27_agent_debate
python agent_debate.py --demo   # 离线：预置发言与投票
python agent_debate.py          # 真实：三专家两轮辩论 + 投票（9 次 LLM 调用）
```

真实模式的诚实预期：round 1 三方立论（FC 的结构化可靠性 vs ReAct 的零依赖兼容性，审计师意外先行选了 FC）；round 2 的反驳质量显著提升——兼容性工程师指出"FC 依赖厂商私有实现"，审计师反驳"FC 是 OpenAI 发起的行业标准而非私有黑盒"。

投票：FC 2 票（架构师 + 审计师"长期解析成本更低"）、ReAct 1 票（现状兼容优先）——**FC 以 2:1 获胜**。

demo 模式用预置发言与投票走完全流程，几秒内可看到两轮发言与计票结构。

## How It Works

流程有两处机制值得展开：transcript（辩论实录，全部发言按顺序累积的文本）的累积，以及投票函数本身。

Round 2 的每个 Agent 都能看到全部 round 1 发言（transcript 累积传入），所以反驳是针对性的——你在真实输出里看到的"兼容性工程师混淆了通用与可靠"这类点名反驳，就是因为反驳模型读到了对方的原文。上下文是辩论质量的燃料：轮数不是越多越好，2-3 轮后发言开始重复，边际收益归零。

投票函数是本篇最核心的一处代码：

```python
def vote(agent, transcript):
    raw = chat([{"role": "user", "content": VOTE_PROMPT.format(
        topic=DEBATE_TOPIC, name=agent["name"], bias=agent["bias"],
        transcript=transcript)}], temperature=0.0)
    m = re.search(r"\{.*\}", raw, re.S)
    return json.loads(m.group(0)) if m else {"vote": "无效", "reason": raw[:60]}
```

`vote` 把辩题、本人 bias 和完整 transcript 填进投票提示词，用 `temperature=0.0` 让输出稳定；再用正则从回复中抠出 JSON 解析——解析失败不中断，记"无效票"放行。你在输出里看到的"FC 2:1 获胜"就是三份投票 JSON 按多数派计票的结果。

票型本身就是信息：2:1 说明结论有争议，落地时应配灰度验证（先小流量上线验证再全量放开的发布策略），而不是当作全票通过来执行。

## Pitfalls & Q&A

踩坑清单（现象 / 原因 / 解法）：

- 程序启动即 KeyError。现象：`.format` 抛出 KeyError。原因：提示词里的 JSON 示例花括号没有转义成 `{{}}`，被当成格式化占位符（本篇真机踩到）。解法：所有字面花括号写成 `{{}}`。
- 投票环节中断。现象：某个 Agent 的回复不含合法 JSON，流程崩溃。解法：解析失败记"无效票"而不是抛异常，保证计票走完（对应上文 `vote` 的回退分支）。

已知边界：角色 bias 会让辩论退化为"立场表演"——对冲手段见下问 Q2；三个 Agent 是同一模型的不同人格，相关性偏差仍在，生产可混用不同模型；本篇预算是 9 次调用，轮数控制在 2-3 轮。

**Q1: 辩论和 26 实验的评审有什么区别？**

评审是多视角**质检同一产物**（意见汇聚后修订）；辩论是多个**立场就同一问题对抗**（结论由投票产生）——前者改产物，后者选方案。

**Q2: 如何避免辩论变成立场表演？**

四个手段：设置中立摇摆票、允许改票、限制轮数防重复、要求反驳针对对方最强论点。

**Q3: 平票怎么处理？**

以中立者票为准、引入额外证据轮、或上报人工——策略要预先声明而非事后决定。
