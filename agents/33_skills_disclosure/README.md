# 33 · Agent Skills 与渐进式披露：分层加载技能信息

> 10 个技能全量塞上下文 = 5000 token，且大部分用不上。**渐进式披露**
> （Claude Code 的 SKILL.md 同款机制）：索引层（名称 + 一句话，约 200
> token）常驻上下文，模型按需点名后才加载技能正文。对照实验：token 消耗
> 与回答质量双指标。

## What

- **两层结构**：索引层（name + description，总是可见）+ 内容层（SKILL.md
  正文，按需加载）——目录页与正文的关系。
- **披露的代价模型**：索引 token 是固定开销（技能越多越划算），按需加载
  是变动开销（只付用到的部分）。
- **与上下文工程的关系**：渐进式披露 = 上下文工程的 Skills 版，同思想见
  项目 18（上下文压缩）与 qa/11（Reflection 的分层记忆）。

心智模型一句话：**索引常驻、内容按需——给上下文做一张"目录页"。**

## Why

Agent 能力越多，描述能力的上下文开销越大——而单次对话往往只用到其中一
两个技能。全量塞有两个代价：token 膨胀（钱与延迟）+ 注意力稀释（无关
描述干扰模型）。

## How

```bash
cd agents/33_skills_disclosure
python skills_disclosure.py --demo   # 离线: 规则路由模拟
python skills_disclosure.py          # 真实: qwen3.8 选技能
```

实测输出：v1 全量塞 **558 token** vs v2 索引+按需 **172 token**（省
69%）；三个测试问题均正确加载对应技能正文。诚实标注：真实模式的技能路由
目前是关键词级匹配，语义模糊的问法可能选错技能（输出里可见）——生产应换
embedding 相似度或 LLM 选择。

## Deep Dive

**与 RAG 的对比**：RAG 检索的是**知识**，Skills 披露检索的是**能力说明**
——机制同源，对象不同。

踩坑清单：

- 索引描述写得含糊会直接选错技能（与 qa/16 工具描述优化同一条规律——
  描述质量决定路由质量）；
- 技能路由的关键词匹配是演示级，语义模糊场景必须升级 embedding/LLM
  路由。

## Q&A

**Q1: "Agent 技能多了上下文怎么办"？**

渐进式披露是标准做法：索引常驻、正文按需，再配 LLM/embedding 做技能
路由——token 只为用到的知识支付。
