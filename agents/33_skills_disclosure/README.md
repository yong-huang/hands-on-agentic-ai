# 33 · Agent Skills 与渐进式披露：分层加载技能信息

> 渐进式披露（progressive disclosure，先展示摘要、按需加载正文的分层信息
> 策略）解决 Agent（能自主完成任务的语言模型程序）技能描述撑爆上下文的
> 问题：索引层（名称 + 一句话，实测 172 token）常驻上下文，模型按需点名后才
> 加载技能正文。读完本篇你能理解分层的代价模型，并跑通一个 token 消耗与
> 回答质量的双指标对照实验。

## Background

没有分层加载之前，给 Agent 配技能的通行做法是全量注入：把所有可用技能的
完整说明一次性塞进上下文（context，模型单次推理能看到的全部文本）。

本实验的 v1 版本采用同一做法——真实场景下单个技能正文数百 token，10 个
技能全量塞入就是 5000 token 量级；demo 为离线可复现改用精简技能库
（实测 558 token，见 Quick Start）。

痛点有两个，且同时发生。其一，token（模型计算长度的最小文本单位）膨胀，
直接换算成钱和延迟，而单次对话往往只用得上其中一两个技能；其二，注意力
稀释——大量无关的技能描述占据模型的注意力，反而干扰它把手头的事做好。

渐进式披露为此而生：Claude Code 的 SKILL.md（描述单个技能的 Markdown 文件）
机制采用同款思路——只让"名称 + 一句话描述"组成的索引常驻上下文，模型判断
需要哪个技能时，再把该技能的正文加载进来。

## What

渐进式披露是一种把技能信息分层加载进上下文的机制：完整说明不预先进入
上下文，而是按模型的实际需要分批进入。它把技能信息拆成两层：

- **索引层**：每个技能的 name + description，总是可见，供模型判断"该用
  哪个技能"；
- **内容层**：SKILL.md 正文（操作步骤、细节参数），模型点名后才加载。

可以把索引层想象成书的目录页：目录常在手边，正文按章节去翻。但和书的目录
不同的是，索引常驻在模型每次推理都可见的窗口里，而且每个条目必须独立足以
让模型判断"要不要翻这一章"——目录写得含糊，翻错章节的概率就高。

代价模型一句话：**索引 token 是固定开销**（技能越多，摊到每个技能上的
常驻成本越划算），**按需加载是变动开销**（只为实际用到的技能付费）。

## When to Use

典型场景（在做什么事的时候）：

- Agent 技能数量多（十几个以上流程说明、操作手册），而单次对话只会用到
  其中一两个；
- 上下文预算紧张：对话已经很长，或任务要跑很多轮，每轮都背着全量技能
  说明不划算；
- 技能正文本身很长（每个几百上千 token），全量注入的浪费被正文长度放大。

何时不用：技能只有两三个、每条描述很短时，全量注入更简单——加载与路由
环节本身就是成本，技能少时省下的 token 抵不上引入的复杂度。两种做法对比：

| 方案 | 差异 | 什么时候选它 |
| :--- | :--- | :--- |
| 全量注入 | 所有技能说明一次性进上下文，无路由环节 | 技能少、描述短、上下文宽裕 |
| 渐进式披露 | 索引常驻 + 按需加载正文，需要技能路由 | 技能多、正文长、单次只用一两个 |

## Quick Start

前置条件：Python 3 环境，无第三方依赖，脚本完全离线运行。

```bash
cd agents/33_skills_disclosure
python skills_disclosure.py --demo   # 离线: 规则路由模拟
python skills_disclosure.py          # 同一套规则路由，仅输出标题换成"真实模式"
```

`--demo` 与不带参数运行执行的是同一套离线规则路由（按预先写死的匹配规则做
选择，不调用模型），后者仅把输出标题换成"真实模式"。

诚实预期（实测输出）：v1 全量塞 **558 token**，v2 常驻索引仅 **172 token**
（省 69%），被点名的正文按需另加、每次 +44 token。

demo 的规则路由按技能名做字面匹配，三个测试问题未命中、一律兜底加载
rag_pipeline——这一局限在输出里直接可见（对应 Pitfalls 第 1 条）。

## How It Works

v2 的一次运行分三步：启动时只把索引层（全部技能的 name + description）放进
上下文；模型读到用户问题后，按索引点名一个技能；程序把该技能的 SKILL.md
正文追加进上下文，模型基于正文作答。

对照 Quick Start 的数字看分层的作用：v1 的 558 token 里，绝大部分是十个技能
中没被用到的正文；v2 常驻上下文只有 172 token 的索引，被点名的正文按需追加
（demo 里每次 +44 token）。"+44 token 只在被点名后才追加"，验证的正是
"每次只付变动开销"。

路由质量取决于索引质量：模型是在"只看目录"的条件下做选择的，description
就是它唯一的依据。这就是为什么诚实预期里提醒——描述含糊或问法模糊时，
关键词匹配会选错技能，错误会直接体现在加载了不相关的正文上。

## Pitfalls & Q&A

踩坑清单（现象 + 原因 + 解法）：

- **模型选错技能，加载了不相关的正文**。原因一：索引描述写得含糊，模型
  无从判断（与 qa/16 的工具描述优化是同一条规律——描述质量决定路由质量）；
  原因二：演示用的关键词匹配只看字面，问法稍一变就失配。解法：description
  写明触发场景与关键词；生产环境把路由升级为 embedding（把文本映射成向量、
  用向量距离衡量语义相似度的技术）相似度或 LLM 选择。

**Q1: 技能多了上下文怎么办？**

渐进式披露是标准做法：索引常驻、正文按需，再配 embedding/LLM 做技能
路由——token 只为用到的知识支付。

**Q2: 它和 RAG、上下文压缩是什么关系？**

与 RAG（检索增强生成：先从知识库检索资料再作答的机制）机制同源、对象不同：
RAG 检索的是**知识**，Skills 披露检索的是**能力说明**。渐进式披露也可以看
成上下文工程思想在 Skills 上的应用，同一思想的另外两处落地见 18 实验（上下文
压缩）与 qa/11（Reflection 的分层记忆）。
