# 20 · 文档加载与切分：RAG 的第一步

> 把 docs/ 下的 md / txt / pdf 三种文件统一加载进程序，再自动切成大小
> 合适、能查到出处的文本小块。全程离线，不依赖任何模型。读完你能为文档
> 检索管线搭好最前端的准备环节。

## Background

让模型回答私有资料的问题，最早的做法是把整份文档直接贴进提示词。文档只有
几段时可行；文档一多，上下文窗口（模型单次能读入的文本长度上限）装不下，
调用成本也随长度线性上涨。

换一种思路：不把整个文档给模型，只把与问题最相关的几段找出来。但"找几段"
引出两个新问题。其一，资料格式不统一——Markdown、纯文本、PDF 各写各的，
程序没法用同一套逻辑处理；其二，找到的东西粒度不对——整篇太大带噪音，
碎成单句又缺上下文，答非所问。

于是检索管线的最前端出现了一个专门的准备环节：先把各格式统一成同一种内存
结构，再沿着语义边界（段落、句子）把长文切成大小合适的块。这一环节的
质量决定后面"找"的准确度上限，是整条管线的第一步。

## What

**文档加载与切分是 RAG（Retrieval-Augmented Generation，检索增强生成——
先从资料库检索相关片段、再交给模型生成的技术）管线的第一环：检索的对象
不是文档本身，而是切分后的块（chunk，被当作独立检索单位的小段文本）。**

三种原始文件（md / txt / pdf）按扩展名分派给对应加载器，统一成
`Document`（source + type + text，PDF 文本经过 NFKC 归一化——一种把外观
不同、编码不同的字符统一成标准形式的处理，详见 Pitfalls）。

然后 `recursive_split` 按"段落 → 句子 → 字符"的优先级降级切分，小片
合并成块并在相邻块间回填 overlap（相邻块重复携带的上一块尾部内容），
每个块带来源与序号。

统一文档结构：

| 字段 | 内容 | 用途 |
| :--- | :--- | :--- |
| source | 来源文件名 | 答案溯源 |
| type | txt / md / pdf | 调试与过滤 |
| text | 归一化后的全文 | 切分输入 |

心智模型一句话：**切分 = 沿语义边界把文档撕成整齐的小条，撕口互相咬合。**
可以把切分想象成撕一张印满段落的长纸：优先沿段落间的空白撕，撕下的每张
纸条头部重复上一条的一小截。但和撕纸不同的是，撕的位置由分隔符优先级
决定而不是随手，且"纸条"还带着记录出处的元数据。

## When to Use

在为问答系统准备私有资料库的时候用：公司 wiki、产品手册要接入"提问—回答"
机器人；批量抓取的网页正文要整理进检索库；本地文档要做语义搜索（按意思
而非关键词匹配）。这三种情况都需要先加载、再切分成块。

不用的情况：文档本身很短（几百字以内，整篇作为一块即可）；需求只是精确
关键词查找（grep——命令行文本搜索工具——或数据库全文索引更直接）；资料
是扫描图片型 PDF（需要先 OCR，即光学字符识别，本管线不覆盖）。

| 方案 | 差异 | 什么时候选它 |
| :--- | :--- | :--- |
| 固定长度切分 | 每 N 字符切一刀，实现最简 | 格式规整、不要求语义完整 |
| 递归字符切分（本篇） | 优先段落/句子边界，超限才降级 | 通用文本，要求块内语义完整 |
| 按结构切分 | 沿 Markdown 标题/代码块边界 | 结构清晰的 md 文档 |
| 语义切分 | 用向量相似度找主题断点 | 长文且预算充足、追求检索精度 |

## Quick Start

前置条件：Python 3，纯离线、无需任何模型或 API；读取 PDF 需要 pypdf
（一个提取 PDF 文本的 Python 库，安装：`pip install pypdf`）。

```bash
cd agents/20_doc_splitting
python doc_splitting.py --demo   # 内联文本演示切分算法
python doc_splitting.py          # 加载 docs/ 目录（md + txt + pdf）
```

`--demo` 用脚本内置的示例文本跑切分算法，适合先看算法行为。目录模式会
加载 docs/ 下三个样例文件并打印加载与切分两份报告。

实测结果：3 个文件共 735 字符 → 9 个 chunk，块长 78/89/100（min/avg/max），
0 个超限；chunk #0 尾部"…重新打"与 chunk #1 开头"测试用例上重新打分"
就是 overlap 衔接。

诚实预期：目录模式没有联网请求，运行是瞬时的；看到"加载报告 + 切分报告"
两段输出、且切分报告中所有块长度不超过 120（脚本里的 CHUNK_SIZE），即
运行成功。

## How It Works

切分的核心是递归降级：分隔符按语义优先级排队——`\n\n`（段落）→ `\n`
（换行）→ `。！？；`（句子）→ 空格 → 逐字符。算法对超出块上限的片段
**降级**到下一级分隔符继续切：段落放得下就不拆句子，句子放得下就不拆词。

这就是 LangChain `RecursiveCharacterTextSplitter`（该领域最常用的切分器）
的核心思想，本篇用 40 行手写：

```python
def recursive_split(text, separators=SEPARATORS, chunk_size=CHUNK_SIZE):
    if estimate_len(text) <= chunk_size:
        return [text]
    sep, rest = separators[0], separators[1:]
    pieces = _split_by_sep(text, sep) if sep in text else (
        [text] if sep == "" else recursive_split(text, rest, chunk_size))
    chunks = []
    for piece in pieces:
        if estimate_len(piece) <= chunk_size:
            chunks.append(piece)
        elif rest:
            chunks.extend(recursive_split(piece, rest, chunk_size))   # 降级
        else:
            chunks.extend(piece[i:i+chunk_size]
                          for i in range(0, len(piece), chunk_size))  # 硬切兜底
    return chunks
```

读这段代码抓三处：第一行先判断整段文本放不放得下，放得下就直接返回；
`elif rest` 分支是"降级"——当前分隔符切出的片仍超限，就换下一级分隔符
递归再切；最后的 `range(...)` 是硬切兜底，所有分隔符用尽后按固定长度切，
保证函数总能返回。

overlap 解决切断问题：相邻块回填约 30 字符的尾部重叠。没有 overlap 时，
"每次修改提示词都需要在同一组用例上重新打**分**"这句话可能被切成两半，
两半都答不全"怎么评估"。

Quick Start 里 chunk #0 尾部与 chunk #1 开头的重复文字，就是这 30 字符
重叠的直观呈现；9 个块的长度落在 78 到 100 之间，说明降级逻辑把所有片段
都控制在了 120 的上限内。overlap 的代价是存储与索引的少量冗余，属于用
空间换完整性。

## Pitfalls & Q&A

踩坑清单（每条：现象 → 原因 → 解法）：

- **PDF 中文检索永远匹配不上**。现象：肉眼相同的两个字，程序比对不相等。
  原因：Chrome 生成的 PDF 用 CID 字体（PDF 内嵌的字体引用机制），pypdf
  （PDF 文本提取库）取出的汉字常是**兼容形式**（"⼿" U+2F8B 而非
  "手" U+624B）。解法：加载器统一做 `unicodedata.normalize("NFKC", text)`，
  归一化必须发生在切分之前。
- **中文块长度虚高或虚低**。现象：按纯字符数算长度，中文块信息量被低估。
  原因：一个汉字承载的信息多于半个英文字符。解法：长度口径用"CJK（中日韩
  字符）记 1、其余记 0.5"的近似。
- **切块后发现内容重复或关键句断裂**。现象：块间大量重复，或答案被切成
  两半。原因：overlap 设得太大等于变相放大块，太小防不住切断。解法：本
  实验的折中值是块上限 120 / overlap 30，换语料需重调。

**Q1: 块大小的权衡是什么？**

检索与注入都以 chunk 为单位。太大：一块多主题，检索带噪音；太小：上下文
不完整。折中值靠评估实验定，不是拍脑袋。

**Q2: chunk 的元数据有什么用？**

溯源（答案引用出处）、过滤（按文件/章节限定检索范围）、去重与更新。
字段定义见 What 节的表格。
