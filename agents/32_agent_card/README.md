# 32 · A2A / Agent Card：Agent 能力卡片、发现与互操作

> A2A（Agent-to-Agent，Agent 之间互相发现与调用的协议）用一个 JSON 卡片
> 描述每个 Agent（能自主完成任务的语言模型程序）的能力（skills/schema/端点），
> 路由端只看卡片做发现与调度，新增 Agent 零代码改动。读完本篇你能理解卡片
> 即接口的机制，并跑通一个离线的注册-发现-调用实验。

## Background

没有能力卡片之前，多 Agent 系统的协调靠路由端（把任务分派给合适 Agent 的
中间层）硬编码：一张写死的路由表列明"系统里有哪些 Agent、地址是什么、怎么
调"（21 实验的硬编码路由表就是这种做法）。

痛点在系统增长时出现：每新增一个 Agent，都要改一次路由端代码并重新部署——
所有 Agent 的知识堆在同一处，组合随数量爆炸。调用方还得读对方源码才知道
参数怎么传，接一个新 Agent 的成本是"改代码"而不是"加数据"。

Google 提出的 A2A 协议把能力声明从代码里抽出来：每个 Agent 用一张 JSON
（通用的键值文本格式）卡片描述自己，路由端按需检索卡片目录来做发现与调度，
路由端逻辑从此与 Agent 数量无关。

## What

Agent Card 是一张自我描述的 JSON 卡片，声明"我是谁、我能做什么、怎么调我"；
A2A 则是 Agent 之间基于这类卡片互相发现与调用的水平协议。本实验用到的卡片
字段：

| 字段 | 含义 |
| :--- | :--- |
| `name` | Agent 名字 |
| `description` | 一句话描述，供关键词检索 |
| `skills[{id, input_schema, output_schema}]` | 技能列表：技能 id 与输入/输出 schema（描述参数名与类型的数据契约） |
| `endpoint` | 端点（Agent 接收调用请求的网络地址） |

可以把 Agent Card 想象成挂在招聘网站上的简历：姓名、技能清单、联系方式
（endpoint）写清楚，猎头（路由端）按技能关键词搜人、按联系方式派活。但和
简历不同的是，卡片面向机器而非人——schema 是精确的数据契约，调用方据此直接
构造合法请求，不需要读懂文字描述。

心智模型一句话：**卡片即接口——路由端逻辑与 Agent 数量无关。**

## When to Use

典型场景（在做什么事的时候）：

- 多个 Agent 由不同团队开发、互不共享代码，需要互相调用；
- Agent 池频繁增减（今天加一个翻译 Agent、明天加一个天气 Agent），不想每次
  都改路由端代码并重新部署；
- 搭建开放平台，允许第三方 Agent 随时接入，接入方只需提交一张卡片。

何时不用：系统里只有固定一两个 Agent、调用关系稳定时，直接函数调用或写死的
配置更简单，引入卡片目录属于过度设计。与同类协议的对比：

| 方案 | 差异 | 什么时候选它 |
| :--- | :--- | :--- |
| MCP | Agent↔工具的垂直协议（见 14 实验） | Agent 接数据库、搜索等外部工具 |
| A2A / Agent Card | Agent↔Agent 的水平协议 | Agent 之间互发现、互调用 |
| 两者结合 | 对下接工具、对上暴露能力 | 一个 Agent 同时用 MCP 接工具、用 A2A 暴露自身 |

## Quick Start

前置条件：Python 3 环境，无第三方依赖，实验全离线运行。

```bash
cd agents/32_agent_card
python agent_card.py    # 全离线: 模拟卡片 + 确定性路由
```

诚实预期（实测输出，节选）：三个 Agent（translator / weather / math）先注册
卡片，随后按关键词发现、路由调用；其中 [翻译] 一行会显示"无匹配"——查询词
"翻译"与技能 id（translate）、描述（中英互译）字面不重合，这正是 Pitfalls
第 1 条的现场演示。

接着脚本在运行时执行 `AGENT_CARDS.append(new_agent)` 模拟新 Agent 接入——
**注册后即刻被发现，路由端零改动**。

所谓确定性路由，指同样的输入必得到同样的分发结果，便于离线复现。

## How It Works

一次 A2A 调用分三步：**发现**（按技能 id 或描述关键词过滤卡片目录）→
**匹配**（选定目标 Agent 与技能）→ **调用**（向统一 endpoint 发送
skill_input，即按该技能 input_schema 构造的参数）。

路由端每一步都只依赖卡片内容，不持有任何具体 Agent 的知识。这就是 Quick
Start 里"注册后即刻被发现"的原因：`AGENT_CARDS.append(new_agent)` 只是往
卡片目录追加一条数据，而路由端本来就是在目录里现查现用，目录一变、下一次
发现的结果就变。

生产环境里，"卡片目录"对应 A2A 规范的 registry（卡片目录服务）或
well-known URI（按约定固定地址发布卡片，例如 `/.well-known/` 路径），
机制与实验中的目录列表等价。

卡片的最小集是"能力描述 + 输入输出 schema + 端点"：schema 让调用方无需
读源码即可构造合法请求，这是"卡片即接口"的物质基础。

## Pitfalls & Q&A

踩坑清单（现象 + 原因 + 解法）：

- **按关键词搜不到目标 Agent**。原因：发现阶段是对 `description` 与技能
  描述做关键词匹配，描述含糊或用了同义词就匹配不上。解法：技能 `id` 用稳定
  命名，`description` 写明调用方会用的词。
- **调用时参数报错**。原因：调用方没有严格按 `input_schema` 构造请求字段。
  解法：卡片里把必填字段与类型写全——schema 越精确，"无需读源码"的承诺才
  越成立。

**Q: 零改动接入为什么是开放生态的前提？**

对比 21 实验的硬编码路由表可以看到差异：新 Agent 只发一张卡片即可被网络
发现，接入成本从"改路由代码"降到"注册数据"。接入不改别人的代码，第三方
才可能持续加入，这正是开放生态的成立条件。
