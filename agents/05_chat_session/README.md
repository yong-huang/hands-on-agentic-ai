# 05 · 消息历史与多轮对话：模型的"记忆"就是 messages 数组

> 只做一件事：**把累积的 messages 列表（对话消息列表）整体重发**——这
> 一个动作就让模型"记住"了你说过的话。本篇把它封装成 `ChatSession` 类，
> 配一个可交互的命令行程序，并守住历史一致性：失败的回复不会留在历史里。
> 读完你能实现一个自己维护"记忆"的多轮对话程序。

## Background

最初的调用都是单轮的：发一条消息，拿一条回复，程序就结束了。模型对
之前说过的话一无所知——想接着上一句追问，只能手动把之前的问答复制进
下一条消息里再发一次。

手动拼历史的做法在真实对话里很快失控：追问两三轮后没人记得哪些话已经
带过、哪些漏了；更隐蔽的是误解——很多人以为模型"记住"了会话，基于
这个错觉做出的产品会出现对话莫名其妙的断裂或串场。

聊天 API 为此定下的设计契约是：**服务端无状态，"记忆"由调用方维护**。
客户端把 system 消息（设定角色与规则的顶层消息）、历轮问答与本轮输入
组装成一个 messages 数组整体重发，模型就能接上前面的话。本篇实现的
就是这个契约的最小完整版。

## What

多轮对话，指在一次会话里连续问答：客户端维护一个 messages 数组（发给
API 的消息列表，每个元素带 `role` 和 `content`），每轮把**全部历史**
加上新输入重发一遍——API 本身无状态（stateless，服务端不保存任何请求
之间的信息）。

心智模型一句话：**会话状态 = messages 数组的长度；"记忆" = 每轮全量
重发。** 可以把模型想象成一位每次见面都失忆的顾问：你每次都要把之前
的谈话记录带过去，它才接得上话。但和真人不同的是：它不是"想起"历史，
而是逐字读你带来的记录——记录里的错误它也会照单全收。

这个机制直接推出一条代价：messages 越长，每次请求携带的 token（模型
处理文本的最小单位）越多，费用与时延越高。

## When to Use

核心判断：只要对话需要引用前文（追问、改写、先给信息后引用），就需要
会话管理；历史变长后，管理策略本身成为一个独立课题（18 实验的主题）。

典型场景：

- **做需要追问的对话产品**：客服机器人、多轮改写，用户第二句话依赖
  第一句话；
- **会话内先给信息、后续引用**：用户先说"我叫张三"，之后问"我叫
  什么"；
- **排查"模型忘了"类问题**：先确认历史是否真的随请求发出去了。

何时不用：单轮任务（翻译一句、总结一篇）不需要会话类；会话特别长时，
全量重发成本高，按下表选策略。

| 策略 | 做法 | 优点 | 代价 |
| :--- | :--- | :--- | :--- |
| 全量保留（本项目） | 原样重发全部历史 | 实现最简、信息无损 | token 随轮次线性增长 |
| 滑动窗口 | 只保留最近 N 轮 | 成本可控 | 早期信息丢失 |
| 摘要压缩 | 旧历史用大模型摘成一段 | 省 token 且保留要点 | 摘要有损、需额外调用 |

选择准则：会话短、实现优先选全量；会话长且只关心近期内容选滑动窗口；
会话长且早期信息仍要保留选摘要压缩。

## Quick Start

前置条件与 01 实验相同：Ollama 已启动、已执行 `ollama pull
qwen3.8:latest`、Python 环境装有 `requests` 库。

```bash
cd agents/05_chat_session
python chat_session.py
# 🧑 你: 我叫张三，最喜欢吃火锅
# 🤖 助手: ...
# 🧑 你: 我刚才说我叫什么？最喜欢吃什么？
# 🤖 助手: 你叫张三，最喜欢吃火锅……     ← "记忆"生效
```

交互命令：`/hist` 看历史摘要与最近消息、`/clear` 清空重建会话、`/exit`
或 Ctrl+C/Ctrl+D 退出。脚本每轮结束打印 `📊 历史摘要`（总消息/用户/
助手/轮次），**你能亲眼看到 messages 数组每轮 +2**。

诚实预期：回复的具体措辞每次运行可能不同；只要第二问能答出"张三"和
"火锅"，就说明记忆链路正常。若第二问答不上来，用 `/hist` 检查历史里
是否真的带着第一条消息。

## How It Works

本节沿一轮对话的执行顺序展开：组装、发送、记录、以及出错时的回滚。

### 与单轮调用的唯一区别

```python
payload["messages"] = session.get_messages()   # 完整历史列表
```

模型没有任何服务端状态——Quick Start 示范里它"记得"张三和火锅，就是
因为那次请求的 messages 里本来就写着张三和火锅。除此之外的调用方式与
单轮完全相同。

### ChatSession 类

```python
class ChatSession:
    def __init__(self, system_prompt=None):
        self.messages = [{"role": "system", "content": system_prompt}] if system_prompt else []
        self.conversation_count = 0

    def add_user_message(self, content):
        self.messages.append({"role": "user", "content": content})
        self.conversation_count += 1

    def add_assistant_message(self, content):
        self.messages.append({"role": "assistant", "content": content})
```

这个类就是"记忆"的载体：两个 `add_*` 方法各追加一条消息，主循环把
整个列表重发。

REPL（Read-Eval-Print Loop，读取-求值-打印循环，命令行交互环境）主
循环是一个状态机（按固定状态顺序流转的程序结构）：等待输入 → 把
system + 全部历史 + 新输入组装成 messages → 等待 API 响应 → 回复有效
则记录（历史 +2）→ 回到等待。

### 历史一致性：失败回滚

流程是先 `add_user_message` 再调用 API；如果回复为空或太短（长度
不超过 5），必须 `session.messages.pop()` 把刚加的 user 消息弹掉——
这就是回滚（撤销刚才的追加），否则历史里会留下一条"没有回答的问题"，
下轮模型会困惑甚至开始自问自答。

**历史数组只允许成对的 user/assistant 追加**——这是会话管理的不变量
（代码在任何时刻都必须成立的约束）。主循环的两个分支就守着它：回复
有效才 `add_assistant_message`；否则打印失败提示并回滚。

### 推理模型回复的清洗

qwen3.8 是推理模型（会把思考过程单独输出的模型），回复可能带思考痕迹、
列表符号。`extract_response()` 做了三层兜底：`content` → 从 `thinking`
里按"Final Answer/所以/最终"等线索抽答案 → 退化为过滤编号后取最后
两句。

再用正则（用模式字符串匹配文本的工具）剥掉行首的 `*`/`-`/`•`。
**解析推理模型的输出是脏活，兜底链比单点解析可靠得多。**

## Pitfalls & Q&A

踩坑清单（每条 = 现象 + 原因 + 解法）：

- **外部改动污染会话内部状态**：现象是改一下 `get_messages()` 返回的
  列表，会话历史跟着变了。原因：该方法返回浅拷贝（只复制列表外壳，
  里面的元素仍与原列表共享），代码注释里有自评。解法：外部只读不改，
  或改返回深拷贝。
- **管道输入时程序死循环**：现象是用管道喂输入，输入结束后循环不停。
  原因：`EOFError`（输入流结束（如 Ctrl+D）时抛出的 Python 异常）未被
  处理。解法：Ctrl+C/Ctrl+D（EOFError）统一捕获、优雅退出。
- **长对话后模型"忘记"开头的名字**：原因：未超限时注意力（模型处理
  每个词时对上下文各部分的关注度分配）也会被长上下文稀释，且历史里的
  错误信息会持续影响后续回答。解法：这不是模型故障，是上下文工程问题
  ——控制历史长度、及时清理错误信息。

**Q1: 滑动窗口截断要注意什么？**

永远保留 system 消息；最好成对截断（user+assistant 一起丢）；被截断
的信息如有长期价值应写入外部记忆（见 17 实验）。

**Q2: 会话状态应该放在哪里？**

短命会话在内存即可；跨进程/重启需要持久化（把数据写进磁盘等长期存储，
程序重启后仍在）——见 10 实验。
