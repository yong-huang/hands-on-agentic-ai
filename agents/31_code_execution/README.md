# 31 · Code Execution / Code Mode：让 Agent 写代码调工具

> Code Mode 是 Anthropic 在 2025 年 11 月提出的工具调用范式：把工具函数预载到
> 沙箱（资源受限的隔离执行环境）里，让 Agent（能自主决策并调用工具完成任务的
> LLM 程序）写一段 Python 代码直接调用，中间结果留在沙箱、不过模型上下文，实测
> LLM（大语言模型）调用从 8 次降到 2 次。读完本篇你能判断什么场景该用它，并跑通
> 一个离线可复现的两版对比实验。

## Background

没有 Code Mode 之前，Agent 调工具走的是 Function Calling（函数调用：模型按预
定义的数据契约输出一次调用请求，宿主程序执行后把结果写回对话）。每调一个工具
就是一轮完整的 LLM 往返，工具几个就得往返几轮。

痛点出在工具多、链条长的时候。比如"查上月销量、算营收、汇总结论"要用 3 个
工具，标准做法是 3 轮往返：每一轮的中间结果都全量塞进上下文（context，模型
单次推理能看到的全部文本），token（模型计算长度的最小文本单位）随步骤数膨胀；
模型还要在多轮之间"记住"中间值，容易遗忘或抄错数字。

Code Mode 的来路：Anthropic 在 2025 年 11 月的文章里把方向反过来——不让模型
逐个发请求，而是把工具函数预载进隔离执行环境，让模型写一段 Python 代码一次
完成所有调用，只有最终结果回到对话。Anthropic 实测 token 省 98.7%，工具越多
差距越大。

## What

Code Mode 是一种"让模型写代码来调用工具"的范式：模型不再逐个发出调用请求，
而是生成一段程序，在沙箱里运行；代码内部的变量传递、条件逻辑、循环都由执行
环境消化，中间结果不出沙箱。

它的核心洞察：与其给模型 N 个工具的 N 份 schema（描述工具名与参数类型的数据
契约），不如给模型一个代码编辑器和 N 个函数签名——模型天然擅长写 Python，
比自己拼 JSON 参数更不容易出错。

可以把标准调用想象成逐个点菜：每道菜都要服务员跑一趟后厨。Code Mode 则是把
模型请进厨房，按菜谱（代码）自己做完一整桌菜。但和真实厨房不同的是，这个
厨房只预装了指定的炊具（预载的工具函数），模型不能自由发挥，越界操作会被
拒绝或报错。

## When to Use

典型场景（在做什么事的时候）：

- Agent 要串联多个工具做多步数据处理，例如"查销量 → 算营收 → 生成结论"，
  中间值只想算一遍，不想反复经过模型；
- 工具返回的数据量大（整张表、整段日志），全量写进上下文既贵又挤占别的内容，
  只想把最终摘要送回模型；
- 流程含条件分支或循环（比如"对每个门店循环计算"），用代码表达比多轮对话
  编排更直接。

何时不用：工具只有一两个且单次结果极小时，标准调用反而更简单——为一次调用
引入沙箱和代码解析得不偿失。本实验两种版本的完整对比：

| 维度 | v1 标准调用 | v2 Code Mode |
| :--- | :--- | :--- |
| LLM 调用次数 | N 工具 × N 步 = 8 | 1 写代码 + 1 汇总 = 2 |
| 中间结果 | 全过上下文（token 膨胀） | 留在沙箱，只回传 result |
| 多工具协作 | 需多轮编排 | 代码内顺序/循环/条件自然表达 |
| 安全 | schema 层约束 | 需沙箱隔离 |
| 适用规模 | 工具少、结果小 | 工具多、数据大、需组合逻辑 |

## Quick Start

前置条件：Python 3 环境，`pip install requests`（仅真实模式调用模型用到，但脚本启动即导入，离线 `--demo` 也需要）。两条命令分别对应离线与真实模式。

```bash
cd agents/31_code_execution
python code_execution.py --demo   # 离线：MockLLM 走完两版流程
python code_execution.py          # 真实：qwen3.8 + 沙箱代码执行
```

`--demo` 用 MockLLM（以预置响应替代真实模型的假客户端）离线复现两版流程，
不需要模型服务；不带参数运行则调用真实的 qwen3.8 模型，需要模型接入已配置。

诚实预期（真机实测）：v1 标准调用用了 **8 次 LLM 调用**（每个工具一次往返），
v2 Code Mode 仅 **2 次**（写代码 + 汇总回答）——调用次数省 75%；上下文累计
字符 v1 为 1140、v2 为 1244，基本持平：Code Mode 省的是往返次数与中间
结果进上下文，不是总字符。

## How It Works

v2 主流程的核心是三步：让模型写代码、从回复中抽出代码块、放进沙箱执行并取回
result。对照下面的实现看（这是全部机制里最核心的一处代码）：

```python
SANDBOX_PRELUDE = {"__builtins__": __builtins__,
                   "query_sales": query_sales,
                   "compute_revenue": compute_revenue}

def run_v2(task):
    raw = _chat([{"role": "system", "content": CODE_MODE_PROMPT},
                 {"role": "user", "content": task}])
    code_text = re.search(r"```(?:python)?\s*(.*?)```", raw, re.S).group(1)
    sandbox = dict(SANDBOX_PRELUDE)
    exec(code_text, sandbox)                    # 沙箱执行
    result = sandbox.get("result")              # 取回最终结果
```

- `SANDBOX_PRELUDE` 是沙箱预载命名空间：只有两个工具函数和内建对象，不暴露
  os/sys 等系统模块。`exec(code_text, sandbox)`（Python 内置函数，把字符串
  当作代码在给定命名空间里执行）就在这份命名空间中运行模型写的代码。
- 正则那一行从模型回复里抽出 ` ```python ` 代码块；模型输出的其余文字不进
  上下文，第 2 次调用只拿 `result` 做汇总。

你在 Quick Start 看到"v2 只有 2 次 LLM 调用"，就来自这里的分工：第 1 次调用
产出代码，`exec` 在本地执行，第 2 次调用只负责写汇总回答。`query_sales` 的
返回值从头到尾没有进过模型上下文。

**工具感知的代码生成**：模型看到的不是 JSON Schema，而是函数签名本身——
代码即接口文档，函数签名写什么、模型就能调什么。

**与 Function Calling 的关系**：互补不冲突——Function Calling 定义工具的
能力边界（schema 层），Code Mode 改变工具的调用方式（执行层）。

Anthropic 的做法是把 MCP（Model Context Protocol，一种工具接入协议）工具
转为 TypeScript API 文件供代码引用。

## Pitfalls & Q&A

踩坑清单（现象 + 原因 + 解法）：

- **运行中抛异常，v2 流程整体中断**。原因：模型写的代码可能调用不存在的
  函数、传错参数。解法：用 `try/except` 包住 `exec`，把报错信息回传给模型
  自纠（错误回传模式见 13 实验）；多次失败则降级为标准工具调用。
- **一处语法错误导致整段代码作废**。原因：`exec` 按整段编译执行，一处出错
  全段不跑。解法：先用 `ast.parse`（Python 的语法解析模块，只检查语法、
  不运行代码）预检，通过后再执行。
- **沙箱内的代码可访问文件、网络等敏感资源**。原因：示例预载了完整的
  `__builtins__`（Python 内建名称空间，含 `open`、`input` 等），危险能力
  都可达。
- 解法：收窄 `__builtins__`（禁 `open`/`os`）；生产环境必须容器级隔离
  （Docker / gVisor / Firecracker microVM 这类强隔离方案）、网络白名单、
  CPU/内存限额——代码来自 LLM 输出，永不可信。
