# 18 · 上下文压缩策略：截断、摘要与不压缩的对照实验

> 同一段"前重后轻"的长对话（前 5 轮埋 5 个事实，后 12 轮灌水），分别用
> **不压缩 / 滑动窗口截断 / LLM 摘要**三种策略压缩后考模型同样的问题，
> 量化上下文大小与信息保留率的差异。

## Background

长对话塞不进预算时，最常见的做法是二选一：要么全量重发全部历史，要么
按条数硬截断只留最近几轮。选哪个通常凭感觉，很少有人真的测过。

凭感觉会两头吃亏：全量保留 token（模型计费与计长的文本单位）随对话
线性增长、没有上界；硬截断最省钱，但早期交代过的事实确定性丢失——
模型不是答错，是压根看不到。LLM（大语言模型）摘要看似两全，但摘要
本身有损、还要多花一次调用，"值不值"同样没人说得清。

上下文压缩（context compression）的系统化做法因此出现：把"压缩 +
评估"当成实验来做，用数据找折中点。生产系统的 Compaction（上下文
压缩机制，如 Claude Code 的实现）就是这个框架的完整版，本实验是它的
微缩版。

## What

上下文压缩是一种在有限上下文预算内决定"保留什么、丢弃什么"的策略。
三种候选策略的取舍：

| 策略 | 做法 | 优点 | 代价 |
| :--- | :--- | :--- | :--- |
| full | 全量重发 | 零信息损失 | token 随对话线性增长，无上界 |
| window | 预算内放行最近消息 | 实现最简、成本有上界 | 早期事实确定性丢失 |
| summary | 旧对话 LLM 摘要 + 近 N 条逐字 | 折中：省 token 且保事实 | 摘要有损、多一次 LLM 调用 |

评估用双指标：压缩后 token 大小（成本）+ 信息保留率（用只出现在早期
对话里的事实设计 5 道探针题——只考被压缩内容的问题，关键词命中计分）。

心智模型一句话：**压缩策略没有绝对优劣，只有"token 成本 × 信息保留"的
折中点——而折中点必须用实验找。**

## When to Use

判断标准：对话历史是否已经大到需要做取舍。

典型场景：

- 多轮对话逼近上下文预算时：要决定保最近语境还是保早期事实；
- 接入长文档、长工具输出时：塞进上下文前先压缩；
- 为团队选型时：用本实验的对照方法拿到量化证据，替代拍脑袋。

何时不用：

- 对话短、远小于窗口预算：直接全量重发，压缩是白费功夫；
- 单轮任务：没有历史，无可压缩。

同类方案对比：

| 方案 | 差异 | 什么时候选它 |
| :--- | :--- | :--- |
| full（不压缩） | 零损失，token 无上界 | 对话短、预算充足 |
| window（截断） | 成本有上界，丢早期事实 | 只需要近期语境的任务 |
| summary（摘要 + 近景） | 省 token 且保早期事实，有损 + 额外调用 | 长对话且早期事实仍会被问到 |

## Quick Start

前置条件：`--demo` 离线（预置摘要，演示评估管线，即打分流程链路）；
真实模式需要 Ollama（本地大模型运行环境）与 qwen3.8 模型在线。

```bash
cd agents/18_context_compression
python context_compression.py --demo   # 离线：预置摘要演示评估管线
python context_compression.py          # 真实：三策略对照 + qwen3.8 答题评分
```

真实模式流程：构建 22 条长对话 → 三种策略各生成压缩产物 → 各做 5 道
"早期事实"测验（qwen3.8 答题、关键词评分）→ 打印对照表。

**真机实测结果**：

| 策略 | tokens | 保留率 |
| :--- | ---: | :--- |
| full（不压缩） | 254 | 5/5 |
| window（预算 160） | 191 | **0/5** |
| summary（摘要 + 近 4 条） | 188 | **5/5** |

window 只保住了最后两轮，5 个早期事实全军覆没；summary 用 74% 的 token
保住全部事实——压缩的价值一次实验就说清。

## How It Works

**LLM 摘要的关键：提示词强制保留事实**。摘要不是越短越好——是"在
预算内保留最多任务相关信息"：

```
将以下对话压缩成要点摘要（不超过 120 字），
必须保留所有事实（名字、地点、数字、日期、偏好）
```

摘要函数——"摘要远景 + 逐字近景"是标准折中：

```python
def compress_summary(messages, system_prompt, keep_recent=KEEP_RECENT):
    """旧对话 -> LLM 摘要, 最近 KEEP_RECENT 条逐字保留"""
    old, recent = messages[1:-keep_recent], messages[-keep_recent:]
    summary = summarize("\n".join(f"{m['role']}: {m['content']}" for m in old))
    compaction = {"role": "user",
                  "content": f"[以下是更早对话的摘要]\n{summary}\n[摘要结束]"}
    return [system_prompt, compaction] + recent
```

代码把消息切成两段：`old`（旧对话）送 `summarize` 压成一段摘要文本，
`recent`（最近几条）逐字保留，最后按 `system_prompt → 摘要 → 近景` 的
顺序拼回完整请求。

实测结果与机制互相印证：window 5 题全部"不知道"——不是模型笨，是
事实真的不在上下文里，这反过来验证了评估的有效性；summary 的 188
tokens 略低于 window 的 191——摘要把 14 条旧消息压成一句话，比"多
保留两条灌水对话"还省。

生产系统的 Compaction 就是"摘要 + 保留最近"的结构，外加触发阈值与
压缩时机管理。

## Pitfalls & Q&A

踩坑清单（现象 + 原因 + 解法）：

- **评估的题目本身有缺陷**。现象：初版问"项目叫什么名字"，full 策略
  也答不出。原因：模型把"电商推荐系统"当成描述而非名称。解法：改成
  "用户在做什么项目？"后 full 恢复 5/5——题目本身也要被评估。
- **token 数字与计费对不上**。现象：估算值偏差明显。原因：教学启发式
  （CJK 即中日韩字符按 1 字 1 token）。解法：只用于相对比较，不当
  计费依据。
- **摘要自由发挥、丢事实**。现象：摘要里出现原文没有的发挥，或漏掉
  数字与偏好。原因：默认采样温度让模型有创造性。解法：摘要调用设
  `temperature=0`（温度越高输出越随机）——摘要要的是保真不是创造。
- **答对了却判错分**。现象：保留率评分失真。原因：关键词没覆盖同义
  写法。解法：关键词覆盖同义写法（"电商推荐"/"推荐系统"）。

**Q1: 为什么 LLM 摘要压缩必须保留最近几条原文？**

摘要是有损压缩，最近对话是当前任务的直接上下文，细节（代词指代、
半成品方案）丢不得。

**Q2: 如何量化一个压缩策略的好坏？**

双指标（见 What 节）：压缩后 token 大小 + 信息保留率。只有单指标会
系统性偏向某一端。

**Q3: 生产系统的 Compaction 和本实验的差距在哪？**

增加触发时机（阈值/轮数）、摘要缓存与增量摘要、工具调用结果的特殊
处理、以及可配置的策略层级——骨架与本实验相同。
