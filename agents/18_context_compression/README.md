# 18 · 上下文压缩策略：截断、摘要与不压缩的对照实验

> 项目 17 的滑动窗口管住了预算，但代价是"淘汰即失忆"——早期对话里的事实
> 全部丢失。本篇做一次严格的对照实验：同一段"前重后轻"的长对话（前 5 轮埋
> 5 个事实，后 12 轮灌水），分别用 **不压缩 / 滑动窗口截断 / LLM 摘要** 三种
> 策略压缩后考模型同样的问题，量化上下文大小与信息保留率的差异。

## 1. 为什么需要它

长对话的上下文管理是个不可回避的权衡：全量保留最忠实但 token 无上界；截断
最省钱但失忆；LLM 摘要看似两全，但摘要本身有损、还要花一次额外调用。"值不值"
不该靠感觉，该靠数据。本篇把压缩做成可测量的实验：固定实验材料、固定测验题目，
三种策略各跑一遍——**结论从数据里长出来，而不是从文档里抄来**。这个"压缩 +
评估"的框架也是生产系统 Compaction（如 Claude Code 的上下文压缩）的微缩版。

## 3. 快速开始

```bash
cd agents/18_context_compression
python context_compression.py --demo   # 离线：预置摘要演示评估管线
python context_compression.py          # 真实：三策略对照 + qwen3.8 答题评分
```

真实模式流程：构建 22 条长对话 → 三种策略各生成压缩产物 → 各做 5 道"早期
事实"测验（qwen3.8 答题、关键词评分）→ 打印对照表。

**真机实测结果（qwen3.8:latest）**：

| 策略 | tokens | 保留率 |
| :--- | ---: | :--- |
| full（不压缩） | 254 | 5/5 |
| window（预算 160） | 191 | **0/5** |
| summary（摘要 + 近 4 条） | 188 | **5/5** |

window 只保住了最后两轮，5 个早期事实全军覆没；summary 用 74% 的 token
保住全部事实——压缩的价值一次实验就说清。

## 4. 核心概念

### 4.1 三种策略的取舍

| 策略 | 做法 | 优点 | 代价 |
| :--- | :--- | :--- | :--- |
| full | 全量重发 | 零信息损失 | token 随对话线性增长，无上界 |
| window | 预算内放行最近消息 | 实现最简、成本有上界 | 早期事实确定性丢失 |
| summary | 旧对话 LLM 摘要 + 近 N 条逐字 | 折中：省 token 且保事实 | 摘要有损、多一次 LLM 调用 |

本实验 window 只保留最近两轮——因为预算（160）故意设小。**预算大小本身就是
一个实验变量**：调大预算，保留率上升、成本上升，你可以自己跑出一条曲线。

### 4.2 LLM 摘要的关键：提示词强制保留事实

```
将以下对话压缩成要点摘要（不超过 120 字），
必须保留所有事实（名字、地点、数字、日期、偏好）
```

摘要不是越短越好——是"在预算内保留最多任务相关信息"。明确列出必须保留的
类别（名字/数字/日期/偏好），摘要才不会把截止日期之类悄悄丢掉。

### 4.3 保留率评估：探针问题 + 关键词评分

与项目 16 的"注入验证"同源：用**只出现在早期对话里**的事实设计 5 道题，
答对（关键词命中）计 1 分。两个设计细节：

- 测验题目用关键词评分而非 LLM 评分——确定性强、零成本，教学场景足够；
- 问法要避免歧义：初版问"项目叫什么名字"，模型把"电商推荐系统"当成描述
  而非名称答了"不知道"——改成"用户在做什么项目？"后 full 策略恢复 5/5。
  **评估的题目本身也要被评估。**

### 4.4 实验里的真实发现

- window 策略 5 题全部"不知道"——不是模型笨，是事实真的不在上下文里；
  这反过来验证了评估的有效性。
- summary 的 188 tokens 略低于 window 的 191：摘要把 14 条旧消息压成了
  一句话，比"多保留两条灌水对话"还省。
- 生产系统的 Compaction（如 Claude Code 的上下文压缩）就是这个"摘要 +
  保留最近"的结构，外加触发阈值与压缩时机管理。

## 5. 代码关键部分

```python
def compress_summary(messages, system_prompt, keep_recent=KEEP_RECENT):
    """旧对话 -> LLM 摘要, 最近 KEEP_RECENT 条逐字保留"""
    old, recent = messages[1:-keep_recent], messages[-keep_recent:]
    summary = summarize("\n".join(f"{m['role']}: {m['content']}" for m in old))
    compaction = {"role": "user",
                  "content": f"[以下是更早对话的摘要]\n{summary}\n[摘要结束]"}
    return [system_prompt, compaction] + recent
```

坑清单：

- token 估算是教学启发式（CJK 1 字 1 token），只用于相对比较，别当计费依据；
- 摘要调用要 `temperature=0`——摘要要的是保真不是创造；
- 保留率测验的关键词要覆盖同义写法（"电商推荐"/"推荐系统"），否则评分失真。

## 7. 面试要点

- **Q: 长对话的上下文压缩有哪些策略？如何选择？**
  A: 不压缩（保真/无上界）、滑动窗口（省/失忆）、LLM 摘要（折中/有损+额外
  调用）。选择依据是任务的"早期信息依赖度"——用保留率实验量化后决策。
- **Q: LLM 摘要压缩为什么必须保留最近几条原文？**
  A: 摘要是有损压缩，最近对话是当前任务的直接上下文，细节（代词指代、半成品
  方案）丢不得；"摘要远景 + 逐字近景"是标准折中。
- **Q: 如何量化一个压缩策略的好坏？**
  A: 双指标：压缩后 token 大小（成本）+ 信息保留率（用早期事实的探针问题
  测验评分）。只有单指标会系统性偏向某一端。
- **Q: 摘要提示词的关键是什么？**
  A: 强制保留任务相关的事实类别（名字/数字/日期/偏好）、限制长度、低温采样；
  摘要质量要用保留率测验验证而不是目测。
- **Q: 生产系统的 Compaction 和本实验的差距在哪？**
  A: 增加触发时机（阈值/轮数）、摘要缓存与增量摘要、工具调用结果的特殊处理、
  以及可配置的策略层级——骨架与本实验相同。

## 8. 总结

压缩策略的价值要用实验说话：本篇用同一段长对话、同一套测验量化出"summary
用 74% 的 token 保住 100% 的事实，window 省 25% 却全盘失忆"。项目 16 的
占比报告、17 的两层记忆、18 的压缩评估，合起来就是上下文工程的完整工具箱。
