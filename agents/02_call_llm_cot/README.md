# 02 · Prompt 结构设计：CoT + Few-shot 引导结构化输出

> 用一套分层的 System Prompt（系统提示词）——角色设定 + CoT 思维链 +
> Few-shot（少样本）示例 + 输出标签约定——让模型"先想后说"，稳定输出
> 可解析的 JSON（结构化数据格式）。四种模式实测：单次分析、Zero-Shot
> vs Few-Shot 格式遵循率对照、Self-Consistency 投票、三种角色同题实测。
> 读完你能写出一份让模型稳定输出结构化数据的提示词模板。

## Background

在没有结构化约定之前，让模型输出数据的最常见做法是直接加一句"请返回
JSON"。模型通常配合，但偶尔会在 JSON 前后添一句"好的，以下是您要的
内容"，或者临时加字段、换行带注释。程序侧的 `json.loads`（Python 标准
库的 JSON 解析函数）碰到这些字符就直接抛异常。

这件事在 Agent 场景是硬约束：Agent（在循环中自主调用模型并执行动作的
程序）的每个决策都来自模型输出，而程序的每个动作都要求输出可解析。
输出格式不稳，程序就无法可靠地往下走。

问题不在模型"不配合"，而在于调用方没有同时说清两件事：想的过程放在
哪、结果的格式长什么样。把这两件事写进一份分层的系统提示词，再用示例
钉死格式，就是本篇的方案。

它也是 ReAct（推理与行动交替的 Agent 提示格式，见 04 实验）的直系
祖先——ReAct 的 `Thought/Action/Answer` 就是同一套思路。

## What

System Prompt 结构化设计，指用一份分层的提示词（Prompt，发给模型的
文字输入）同时约束模型的推理过程与输出格式，使回复既可读、又可被程序
解析。四层结构：

| 层 | 作用 | 本项目的实现 |
| :--- | :--- | :--- |
| 角色（Identity） | 限定语气与专业域 | "你是一个专业的数据分析助手" |
| 任务 + 格式约定 | 说明做什么、输出长什么样 | 情感分析 + `<thinking>`/`<output>` 双标签 |
| CoT 指令 | 要求先推理再下结论 | "先在 `<thinking>` 中逐步分析" |
| Few-shot 示例 | 用 3 个样例钉死格式 | 正面/负面/中性各一条 |

CoT（Chain of Thought，思维链）指要求模型把推理步骤写出来再下结论。
它不是一个技巧而是一族（sentiment 判断用 Few-Shot 就够，高准确率场景
上 Self-Consistency，需要工具时进化成 ReAct）：

| 形态 | 一句话 | 适用 |
| :--- | :--- | :--- |
| Zero-Shot | 指令里只说"一步步想"，不给示例 | 简单问答 |
| Few-Shot | 带推理示例供模仿（本篇默认） | 复杂推理、格式钉死 |
| Self-Consistency | 同一问题多次采样、投票取多数 | 高准确率要求 |
| Program-Aided | 让模型写代码，执行后取结果 | 数学/逻辑精确计算 |
| ReAct | 推理与行动交替进行 | 需要外部信息的任务（见 04 实验） |
| Tree-of-Thoughts | 多路径探索 + 评估 + 回溯剪枝 | 复杂决策 |

心智模型：**可以把写这份 Prompt 想象成"用自然语言编程"——Prompt 是
编程，示例是类型声明，双标签是返回值的信封。** 但和真代码不同的是：
模型不保证完全遵守约定，解析侧永远要留兜底（见 How It Works 的两级
回退）。

## When to Use

核心判断：输出要给程序消费，就该约定格式；纯属给人看的聊天，不必上
模板。

典型场景：

- **给 Agent 或流水线喂模型输出**：后续代码要读取字段做判断，输出必须
  可解析；
- **接口不支持服务端格式约束**：本地模型或旧版接口没有 Function
  Calling（函数调用——由服务端强制模型按预定义函数的参数格式输出的
  机制）或 JSON mode（服务端保证只输出合法 JSON 的开关），只能靠提示词
  自救；
- **要控制回答的视角**：让同一个问题从不同专业视角作答，见 `roles`
  模式的三角色实测。

何时不用：接口支持 Function Calling 或 JSON mode 时优先用服务端保证，
比提示词约定更稳。

| 方案 | 差异 | 什么时候选它 |
| :--- | :--- | :--- |
| Prompt + 标签约定（本篇） | 纯提示词层实现，任何接口可用 | 无服务端约束的接口、本地模型 |
| Function Calling | 服务端强制 JSON Schema，连解析都省了 | 接口支持时的首选（见 09 实验） |
| JSON mode | 服务端保证合法 JSON，不保证字段 | 只要求"是 JSON"，字段自行校验 |

## Quick Start

前置条件与 01 实验相同：Ollama 已启动、已执行 `ollama pull
qwen3.8:latest`、Python 环境装有 `requests` 库。

```bash
cd agents/02_call_llm_cot
python call_llm_cot.py                    # 单次分析（默认，最快）
python call_llm_cot.py zero-vs-few        # 两种形态格式遵循率对照
python call_llm_cot.py self-consistency   # 多次采样 + 投票
python call_llm_cot.py roles              # 三种角色同题实测
python call_llm_cot.py all                # 依次跑全部四段
```

默认模式读入待分析文本（回车用默认"这个产品很好用，质量也很棒！"），
打印模型完整响应——你能亲眼看到 `<thinking>` 里的推理过程——然后美观
打印五字段结果（`category / sentiment / confidence / keywords /
summary`）。

`zero-vs-few` 各跑 3 轮并报告格式合规率；`self-consistency`
对一条正负混合的反馈采样 3 次投票；`roles` 让工程师/产品经理/安全审计
对同一反馈各自作答。诚实预期：对照与投票模式要多次调用本地模型，全部
跑完约 1-2 分钟。

## How It Works

本节回答三个问题：这份模板为什么能稳定出 JSON、投票为什么更稳、解析侧
怎么接住偶尔的不合规输出。

### 为什么稳定：每一层都在缩小输出空间

角色层限定语气与专业域。它不是玄学，是对采样分布（模型输出逐词按概率
挑选，角色设定改变这些概率）的条件约束：`roles` 模式把 System Prompt
换成工程师/产品经理/安全审计三种角色问同一个问题，回答侧重点立刻分化——
工程师谈实现、产品谈用户价值、审计谈风险。

格式层由 Few-shot 与双标签配合：模型对"照着例子输出"的服从度远高于
"按 JSON Schema 输出"，三个示例覆盖正/负/中性三类，等于告诉模型——
**输出就长这样，字段一个都不能少**；双标签则给解析器一个精准的锚点。

`zero-vs-few` 模式把两种形态放在同一把尺子下量（可解析 + 五字段齐全 +
取值合法），示例的价值会直接体现在合规率上。

### CoT：先想后说

`<thinking>` 圈住推理、`<output>` 圈住结论，推理过程可读、结论可解析，
两者兼得。可以把 `<thinking>` 想象成发给模型的草稿纸：把推理显式写出
来，后面的内容就能参考前面的分析（为什么这能提升准确率，见文末 Q1）。

但和草稿纸不同的是：草稿内容留在上下文里、会持续影响后续输出，因此只
把 `<output>` 的 JSON 交给程序，`<thinking>` 不进入下游。

### Self-Consistency：用投票换准确率

单次采样是一次随机抽签，混合情感（"物流慢但客服好"）这类输入容易在
正/负之间摇摆。Self-Consistency 的做法：把温度调高（0.7）采样多次，
对最终答案多数投票——单次的随机偏差被票数抵消。

代价是延迟和调用量线性翻倍，所以只用在准确率优先的场景。注意它可能
平票：平票时应提高采样数或降低温度重跑，而不是硬选一个。

### 解析的两级回退

```python
pattern_tag  = r"<output>\s*(\{.*?\})\s*</output>"   # 第一级: 标签内提取
pattern_json = r"\{[^{}]*\}"                          # 第二级: 全文第一个 {...}
```

正则表达式（用模式字符串在文本中定位内容的工具）分两级：第一级精准，
第二级兜底——模型偶尔忘写标签时仍能救回。第二级只匹配无嵌套的扁平
JSON，所以字段设计时要避免嵌套对象。

正则必须带 `re.S`（DOTALL，让 `.` 也能匹配换行符的标志），否则跨行
JSON 匹配失败。完整的自救链见文末 Q3。

## Pitfalls & Q&A

踩坑清单（每条 = 现象 + 原因 + 解法）：

- **解析出的 JSON 多字段、换行带注释**：`temperature` 偏高，模型在格式
  上"发挥"。解法：结构化任务把温度控制在 0-0.3。
- **`confidence` 很高但答案是错的**：`confidence` 是模型自估的置信度，
  **不是真实概率**。解法：只拿它做相对比较，不做绝对判断。
- **`keywords` 里混着标点**：模型按示例风格输出，不保证自行清洗。解法：
  下游解析后做一次标点清洗。
- **Self-Consistency 平票**：采样数太少或输入太模糊。解法：提高采样数
  或降低温度重跑。

**Q1: CoT 为什么能提升准确率？**

把中间推理显式化，相当于给模型草稿纸——后续 token 可以"参考"前面的
推理，降低一步到位的出错率；代价是输出变长、延迟变高。

**Q2: Few-shot 示例数量越多越好吗？**

不是。示例占上下文窗口（模型单次能读入的最大文本长度）且边际收益递减，
2-5 个覆盖典型 case 通常最优；示例的**格式一致性**远比数量重要。

**Q3: 模型输出的 JSON 解析失败有哪些自救手段？**

①正则提取标签/花括号；②重试并在消息里附上解析错误；③温度调 0；
④终极方案 Function Calling / JSON mode 由服务端保证格式。

**Q4: temperature=0.3 而不是 0，为什么？**

留一点随机性避免措辞僵化，同时足够低保证格式稳定；纯分类任务可以到 0
（温度对照实验见 01 实验）。
