# 21 · 向量化存储：从文本块到语义索引

> 把切分好的文本块逐一转成"数字坐标"存入专门的数据库，让检索按意思匹配
> 而不是按字面。读完你能搭起"建索引 + 语义查询"的完整闭环，并看懂检索
> 结果里距离数值的含义。

## Background

在资料库里找内容，最初靠关键词检索：程序按字面匹配，找"包含这些词的
文本"。文本量小时它又快又准，是数据库和编辑器的默认能力。

字面匹配的天花板很快出现：用户问"怎么切分文档"，资料里写的却是"递归
字符切分"——两句话一个共同的词都没有，就永远检索不到。同义改写、
上下位词（"评估"与"打分"）都撞在同一堵墙上：匹配依据是字面，不是意思。

出路的思路是把文本变成数字坐标，意思近的文本坐标也近，"找相关"变成
"找坐标附近的邻居"。手写的坐标比对能验证原理，但生产环境还需要数据
落盘不丢、按来源过滤、规模变大后依然查得快——这些工程能力催生了专门的
存储与检索工具，本篇采用其中最常用的轻量实现。

## What

**向量化存储是一种把文本转成向量、再按向量间距离检索的存储方案：写进去时
逐块 embedding，查的时候把问题也变成向量、取最相近的几条。** embedding
指把一段文本映射成一个固定长度的数字串（即向量），语义越接近的文本得到
的向量越接近。

它有两条路径：**索引路径**——20 实验产出的 chunks（即切好的文本块）逐块
embedding 后 upsert（按 id 存在则更新、不存在则插入的写入方式）进持久化
的 Chroma（一个开源的轻量向量数据库）集合。

**查询路径**——把用户问题也变成向量，在库中取 top-3（距离最小的前 3 条），
distance 越小越相关。

心智模型一句话：**embedding 把"语义"变成"几何"——找相关文本变成找
最近邻。**

可以把向量库想象成一座按内容主题排架的图书馆：意思相近的书摆在相邻的
书架上，"找同类"就是"走到附近的架子"。但和图书馆不同的是，架位由
embedding 模型自动学出，人看不懂坐标含义，"相邻"只保证模型眼里语义
相似，不保证事实正确或逻辑等价。

## When to Use

在检索需要"按意思找"的时候用：问答机器人的知识库召回（问法与答案用词
不同也能命中）；内容的相似推荐与查重（找语义重复的文档）；跨表述搜索
（用户说"怎么切分"，资料里写"递归字符切分"）。

不用的情况：要精确命中（订单号、报错码、人名），关键词匹配更快更准；
库很小（几十条文本，直接遍历计算相似度即可，见 17 实验的手写余弦版）；
离线且无 embedding 模型可用——每条文本都要一次 embedding 才能入库。

| | 关键词检索 | 向量检索 |
| :--- | :--- | :--- |
| 匹配依据 | 字面共现 | 语义邻近 |
| 同义改写 | 找不到 | 自然命中 |
| 成本 | 零 | 每条文本一次 embedding |
| 可解释性 | 直观 | 需要距离度量辅助 |

## Quick Start

前置条件：`pip install chromadb`；真实模式还需本地 Ollama
（localhost:11434，本地运行大模型的工具）并已拉取 `nomic-embed-text`；
`--demo` 模式离线、无需 Ollama。

```bash
cd agents/21_vector_store
python vector_store.py --demo   # 离线：伪向量走完 Chroma 全流程
python vector_store.py          # 真实：nomic-embed-text + 持久化 Chroma
```

真实模式先复用 20 实验的加载与切分（9 个 chunks），逐块 embedding 后
`upsert` 入库（幂等，重复跑不会重复），再跑 4 组查询。

实测预期：4 组查询的 top-1 全部语义正确——"文档应该怎么切分"命中切分
策略段（dist 300）、"为什么需要评估"命中评估手册开头（dist 205）、
"RAG 有哪些步骤"命中速查表。

诚实预期：真实模式首次运行需要为 9 个块逐一请求 embedding，比 demo 慢；
跑完后脚本目录下会出现持久化目录（demo 用 `chroma_db_demo/`，真实用
`chroma_db/`），删除目录即可完全重建。

## How It Works

建索引的入口是 `build_index`——加载、切分、embedding、入库四步连成一条线：

```python
def build_index(collection, docs_root=DOCS_DIR):
    """加载 -> 切分 -> 逐块 embedding -> upsert 入 Chroma"""
    docs = load_directory(docs_root)            # 复用项目 20
    chunks = split_documents(docs)
    for c in chunks:
        c["id"] = f"{c['source']}#{c['chunk_id']}"
    collection.upsert(
        ids=[c["id"] for c in chunks],
        embeddings=[embed_fn(c["text"]) for c in chunks],
        documents=[c["text"] for c in chunks],
        metadatas=[{"source": c["source"], "chunk_id": c["chunk_id"]} for c in chunks],
    )
```

关键点是 id 的构造：`文件名#块序号`，由内容位置唯一决定。ids 必须稳定，
否则重复建索引会产生重复条目——第二次写入无法识别"这条已经在库里"。

upsert 与持久化：`PersistentClient` 把数据落在 `chroma_db/` 目录，重启
不丢；`upsert` 按 id 幂等（同一输入重复执行，结果不变）写入，重复建索引
不产生重复条目。Quick Start 里"重复跑不会重复"的现象就来自这里。

**距离的含义**：Chroma 默认返回平方 L2 距离（两个向量对应分量之差的平方
再求和；数值几百属正常，因为 nomic 向量未归一化——向量长度没有被缩放到
固定范围）。重要的不是绝对值，而是**相对排序**：同一查询下 distance
越小越相关。

实测里切分段 dist 300、评估段 dist 205，都是与各自查询相比的排序第一名。
若换用 cosine 空间（space="cosine"），距离落在 0-2 之间更直观。

## Pitfalls & Q&A

踩坑清单（每条：现象 → 原因 → 解法）：

- **维度不匹配报错**。现象："expecting embedding with dimension of 32,
  got 768"。原因：集合的向量维度在第一次写入时定死，本篇 demo（32 维
  伪向量）与真实（768 维）用了不同持久化目录，混用即报错。解法：两模式
  不共用目录；排查先看库目录是否残留旧数据——`get_or_create_collection`
  拿到的可能是维度不符的已有集合，不匹配在 add 时才爆。
- **建索引太慢**。现象：块多时入库耗时长。原因：embedding 请求逐条发，
  网络往返占大头。解法：生产用 `/api/embed` 批量接口；chunk 数量大后
  再考虑 HNSW（一种近似最近邻索引结构）参数调优。
- **demo 结果乱序**。现象：demo 模式检索结果毫无语义。原因：伪向量——由
  内容 hash 算出的替代向量，只为验证管线——不携带语义。解法：正常现象，
  语义召回要看真实模式。

**Q1: 向量数据库解决什么问题？**

高维向量的存储与最近邻检索，即 What 节两条路径的工程化：支撑语义检索、
推荐与去重。

**Q2: 手写余弦版（17 实验）和 Chroma（本篇）的差距在哪？**

持久化、元数据过滤（按描述数据来源的附加字段筛选）、增量更新、规模化后
的近似最近邻索引（HNSW）——原理相同，工程能力不同。
