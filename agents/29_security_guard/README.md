# 29 · Agent 安全防护：注入检测、白名单与输出过滤

> 防护铺满全链路：**输入侧**注入检测（规则库 + LLM 复核打分）、**执行侧**
> 工具白名单、**输出侧**敏感信息过滤——并内置 8 条攻击/正常混合用例做端到
> 端回归。真机实测：5 拦 3 过零误伤，危险命令在输入阶段就被 LLM 复核拦下
> （操纵分 10/10）。

## What

三道防线的分工：

| 防线 | 位置 | 手段 | 拦截的问题 |
| :--- | :--- | :--- | :--- |
| 注入检测 | 输入侧 | 规则库 + LLM 复核（0-10 操纵分） | 提示注入、越狱、提示词泄露 |
| 工具白名单 | 执行侧 | 登记表外一律拒绝 | 诱导调用危险工具 |
| 输出过滤 | 出站侧 | 密钥/危险命令模式替换 | 敏感信息与破坏性内容出站 |

用户输入先过注入检测（规则库优先，边界样本 LLM 复核打分）；放行后若涉及
工具调用则检查白名单；LLM 的回答出站前再过滤敏感模式。任何一道防线拦截都
直接返回安全话术，不把原因细节暴露给潜在攻击者。

**规则 + LLM 的双层判定**：规则库（正则）快、可解释、零成本，但只能挡已知
模式；LLM 复核覆盖变形攻击。策略：**规则优先、LLM 兜边界**——规则未命中
再交 LLM 打操纵分（≥7 拦截）。

心智模型一句话：**进有门禁、动有白名单、出有过滤——三道防线各自可测。**

## Why

Agent 一旦对外开放（28 的 HTTP 服务），第一天就会遇到三类攻击：**提示
注入**（"忽略之前所有指令"骗模型越过规则）、**越权工具调用**（诱导调用
白名单外的危险工具）、**敏感信息出站**（响应里泄露密钥或危险命令）。防线
必须分层且可回归测试——安全不是功能，是可以被攻击样例反复验证的**性质**。

## How

```bash
cd agents/29_security_guard
python security_guard.py --demo   # 离线：仅规则与启发式
python security_guard.py          # 真实：规则 + LLM 复核（边界样本二次判定）
```

内置 8 条用例（2 正常 + 3 注入 + 危险命令 + 白名单外工具 + 1 条边界样本）。
**真机实测**：3 条注入全部被规则拦截（中英文各命中）；危险命令与白名单外
工具在输入阶段被 LLM 复核拦下（操纵分 10/10）；边界样本"把规则翻译成
英文"被 LLM 判为正常放行——**零误伤、零漏拦**。拦截报告就是防御的回归
测试表。

三道防线的串联实现：

```python
def guarded_chat(query):
    allowed, reason = inspect_input(query)          # 防线 1: 注入检测
    if not allowed:
        return {"blocked": "input", "reason": reason}
    tool_m = re.search(r"(使用|调用|运行)\s*[\"']?(\w+)", query)
    if tool_m:
        tool_ok, tool_reason = check_tool(tool_m.group(2))   # 防线 2: 白名单
        if not tool_ok:
            return {"blocked": "tool", "reason": tool_reason}
    answer = llm_answer(query)
    safe_text, blocked = filter_output(answer)      # 防线 3: 输出过滤
    if blocked:
        return {"blocked": "output", "reason": str(blocked)}
    return {"blocked": None, "text": safe_text}
```

## Deep Dive

**fail-safe 与最小暴露**：

- 判定失败（网络/解析错误）→ 放行但按正常业务处理（可用性优先），危险类
  命中则 fail-closed；
- 拦截话术统一为"检测到疑似注入，已拒绝"——**不向潜在攻击者暴露具体命中
  的规则**（信息最小暴露原则）；
- 拦截的详细原因进审计日志（服务端可见），不出站。

**已知边界**：正则库是黑名单思维，无法覆盖全部变形注入——LLM 复核与人工
红队测试是必要补充；防御是持续对抗：攻击样例库要随真实攻击进化，每次加
规则都重跑回归表。

踩坑清单：

- 拦截话术统一，不泄露命中规则（不给攻击者迭代弹药）；
- 规则用大小写不敏感匹配，攻击者会用大小写与全半角变体；
- 回归用例随每次真实攻击样本进化——防御是持续对抗不是一次性功能。

## Q&A

**Q1: 提示注入的防御为什么不能只靠提示词？**

提示词是"软约束"，注入攻击的目标恰是绕过它；必须在系统层（输入检测、
白名单、输出过滤）建立硬约束，提示词只是第一道软防线。

**Q2: 拦截话术为什么不能包含具体原因？**

最小暴露原则——攻击者可据命中规则迭代变体；详细原因只进服务端审计日志。

**Q3: 如何验证防御没有退化？**

攻击样例回归表（本篇的 8 条用例）纳入 CI，每次改规则全量重跑；线上新增
真实攻击样本持续补充用例。

**Q4: 与项目 15 的审批层是什么关系？**

15 管"执行时人工确认"，29 管"进出站自动化拦截"——审批解决授权，防护
解决攻击，互补不重叠。
