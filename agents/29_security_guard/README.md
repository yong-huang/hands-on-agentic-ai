# 29 · Agent 安全防护：注入检测、白名单与输出过滤

> 防护铺满全链路：输入侧注入检测（规则库 + LLM 复核打分）、执行侧工具白名单、输出侧敏感信息过滤——并内置 8 条攻击/正常混合用例做端到端回归。读完本篇你能理解三道防线各自拦什么、怎么串联，并把这套防护搬进自己的 Agent。真机实测：5 拦 3 过零误伤，危险命令在输入阶段就被 LLM 复核拦下（操纵分 10/10）。

## Background

在没有防护的做法里，Agent 把用户输入原样交给模型、把模型输出原样返回，工具调用不做限制。单机自用的聊天脚本一直这么做，也没出过事——因为它不接真实工具，也不对外开放。

痛点从对外开放的第一天出现（比如给 Agent 套上 28 实验那样的 HTTP 服务）：提示注入（用"忽略之前所有指令"一类话术骗模型越过规则）、越权工具调用（诱导调用白名单外的危险工具）、敏感信息出站（响应里泄露密钥或危险命令）三类攻击随即到来。

传统 Web 安全早就给出过答案——输入校验、权限控制、输出编码的分层防御。Agent 场景把这套思路搬到模型链路上，形成输入/执行/输出三道防线，并要求防线可以被攻击样例反复验证：安全不是功能，是可以回归测试的性质。

## What

Agent 安全防护是一套覆盖输入、执行、输出全链路的自动化拦截机制，由三道防线组成：

| 防线 | 位置 | 手段 | 拦截的问题 |
| :--- | :--- | :--- | :--- |
| 注入检测 | 输入侧 | 规则库 + LLM（大语言模型）复核（0-10 操纵分） | 提示注入、越狱（绕过模型安全限制的攻击）、提示词泄露 |
| 工具白名单 | 执行侧 | 登记表外一律拒绝 | 诱导调用危险工具 |
| 输出过滤 | 出站侧 | 密钥/危险命令模式替换 | 敏感信息与破坏性内容出站 |

可以把这三道防线想象成一栋大楼的安保：进门查证件（输入检测）、各楼层门禁刷卡（工具白名单）、出门开包检查（输出过滤）。但和大楼不同的是：这里的"访客"会主动伪装成正常访客（提示注入），所以门禁还需要一个会识别伪装的复核员（LLM 复核）。

处理流程：用户输入先过注入检测（规则库优先，边界样本交 LLM 复核打操纵分——衡量输入操纵模型行为意图强度的 0-10 分）；放行后若涉及工具调用则检查白名单（白名单：仅允许登记过的条目，其余一律拒绝）；LLM 的回答出站前再过滤敏感模式。任何一道防线拦截都直接返回统一安全话术，不把原因细节暴露给潜在攻击者。

规则 + LLM 的双层判定：规则库（正则表达式，按模式匹配文本的手段）快、可解释、零成本，但只能挡已知模式；LLM 复核覆盖变形攻击。策略：**规则优先、LLM 兜边界**——规则未命中再交 LLM 打操纵分（≥7 拦截）。

心智模型一句话：**进有门禁、动有白名单、出有过滤——三道防线各自可测。**

## When to Use

适合在三类时候上防护：

- Agent 对外开放服务时：接口公网可达，就要假设第一天就会被扫描与试探。
- Agent 能调用工具或执行命令时：只要存在"动"的能力，就需要白名单兜住越权。
- 响应会携带内部数据出站时：密钥、配置、内部路径不能随回答流向用户。

可以不设防的情况：内网个人脚本、不调用工具、不接触敏感数据——三道防线都可以省略，直接跑裸 Agent。

| 方案 | 差异 | 什么时候选它 |
| :--- | :--- | :--- |
| 仅提示词约束 | 软约束，可被注入绕过 | 简单原型、无外部输入 |
| 仅规则黑名单 | 快、免费，挡不住变形攻击 | 廉价的第一层，需配合复核 |
| 三道防线自动化（本篇） | 输入/执行/输出全链路拦截 | 对外开放的 Agent 服务 |
| 人工审批层（见 15 实验） | 执行时人工确认授权 | 高危操作的最后一道人工关 |

## Quick Start

前置条件：Python 3 环境，`pip install requests`；本机 Ollama（本地运行大模型的工具）——`--demo` 仅免去 LLM 复核（规则层照跑），放行用例仍会调用 Ollama 生成回答，完全离线跑不通。

```bash
cd agents/29_security_guard
python security_guard.py --demo   # 半离线：跳过 LLM 注入评分，放行用例仍调本机 Ollama
python security_guard.py          # 真实：规则 + LLM 复核（边界样本二次判定）
```

内置 8 条用例（2 正常 + 3 注入 + 危险命令 + 白名单外工具 + 1 条边界样本）。

诚实预期（真机实测）：3 条注入全部被规则拦截（中英文各命中）；危险命令与白名单外工具在输入阶段被 LLM 复核拦下（操纵分 10/10）；边界样本"把规则翻译成英文"被 LLM 判为正常放行——**零误伤、零漏拦**。拦截报告就是防御的回归测试表（回归测试：保证修复过的旧问题不重现的重复测试）。

## How It Works

三道防线在代码里就是一个串联的判定链，任何一环拒绝就直接返回、不再往下走：

```python
def guarded_chat(query):
    allowed, reason = inspect_input(query)          # 防线 1: 注入检测
    if not allowed:
        return {"blocked": "input", "reason": reason}
    tool_m = re.search(r"(使用|调用|运行)\s*[\"']?(\w+)", query)
    if tool_m:
        tool_ok, tool_reason = check_tool(tool_m.group(2))   # 防线 2: 白名单
        if not tool_ok:
            return {"blocked": "tool", "reason": tool_reason}
    answer = llm_answer(query)
    safe_text, blocked = filter_output(answer)      # 防线 3: 输出过滤
    if blocked:
        return {"blocked": "output", "reason": str(blocked)}
    return {"blocked": None, "text": safe_text}
```

`inspect_input` 先跑正则规则库，未命中的边界样本再交 LLM 打操纵分、≥7 拦截——Quick Start 里"危险命令被复核拦下（10/10）"就是这条路径的产物；`check_tool` 把正则提取到的工具名与登记表比对；`filter_output` 用模式匹配替换出站文本里的密钥与危险命令。

两条设计原则贯穿全程：

- fail-safe 导向：判定失败（网络/解析错误）→ 放行但按正常业务处理（可用性优先），危险类命中则 fail-closed（宁可拒绝也不放行的失败策略）。
- 信息最小暴露：拦截话术统一为"检测到疑似注入，已拒绝"，不向潜在攻击者暴露具体命中的规则；详细原因进审计日志（服务端留存的操作记录），不出站。

## Pitfalls & Q&A

踩坑清单（现象 / 原因 / 解法）：

- 攻击者快速迭代出绕过变体。现象：同一条规则很快失效。原因：拦截话术泄露了具体命中的规则，等于给攻击者递弹药。解法：话术统一、详情只进服务端审计日志（对应上文"信息最小暴露"）。
- 变体输入绕过规则。现象：改了大小写或全半角的注入词直接穿透。原因：规则匹配对大小写与全半角敏感。解法：规则用大小写不敏感匹配，并覆盖全半角变体。
- 加了新规则却破坏旧行为。现象：某条正常用例开始被误拦。解法：8 条用例作为回归表，每次改规则全量重跑。

已知边界：正则库是黑名单思维，无法覆盖全部变形注入——LLM 复核与人工红队测试（主动模拟攻击者验证防御）是必要补充；防御是持续对抗，攻击样例库要随真实攻击进化。

**Q1: 提示注入的防御为什么不能只靠提示词？**

提示词是"软约束"，注入攻击的目标恰是绕过它；必须在系统层（输入检测、白名单、输出过滤）建立硬约束，提示词只是第一道软防线。

**Q2: 如何验证防御没有退化？**

攻击样例回归表（本篇的 8 条用例）纳入 CI（持续集成，代码提交后自动跑测试的机制），每次改规则全量重跑；线上新增真实攻击样本持续补充用例。

**Q3: 与 15 实验的审批层是什么关系？**

15 管"执行时人工确认"，29 管"进出站自动化拦截"——审批解决授权，防护解决攻击，互补不重叠。
