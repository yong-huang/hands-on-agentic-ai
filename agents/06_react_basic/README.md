# 06 · ReAct 模式：Thought → Action → Observation 的推理循环

> 不依赖任何框架，用纯 `requests` + 正则（模式匹配）解析，手写一个
> ReAct（Reason + Act，推理与行动结合）循环：模型先说 Thought（下一步
> 打算），再说 Action（调哪个工具），本地执行后把 Observation（结果）
> 喂回去，直到模型给出最终答案。读完你能不借助框架实现一个最小可用的
> Agent 运行时。

## Background

只有推理能力时（CoT——Chain of Thought，思维链，让模型把推理步骤写
出来再作答），模型只能靠训练时记下的知识一口气答完。

这有两个撞墙的场景：知识停在训练截止日，问它今天的人口数据就只会编；
算术不可靠，238*17 这类计算可能给出似是而非的结果——而且错了也没有
任何环节能纠正，幻觉（模型一本正经编造错误内容的现象）混在长推理里
很难发现。

ReAct 的做法是把"想"和"做"交替起来：模型每步思考后可以决定调用一个
真实工具（计算器、搜索、数据库），把工具返回的真实结果喂回推理链再
继续想。

它是 Agent（在循环中自主调用模型并执行动作的程序）最核心的运行时模式
——LangChain、LangGraph（流行的 Agent 开发框架）内部运转的仍是这套
循环。手写一遍，框架对你才不是魔法。

## What

ReAct，指在模型的推理链里插入**行动**的模式：模型的每一步思考都可以
落地为一次真实的工具调用，观察结果后再继续想，直到给出最终答案。

主循环：LLM（Large Language Model，大语言模型）产出文本 → 正则（用模式字符串匹配文本的工具）解析出
Thought/Action/Answer → 是 Action 就执行工具，Observation（工具执行
结果）以 user（用户角色）消息回喂继续推理；是 Answer 就终止；

解析失败走错误回喂重试。

心智模型：**可以把 ReAct 想象成指挥一位只会说话的助手——他说"我要查
X"（Thought/Action），你替他查了念给他听（Observation），他接着想，
直到说"答案是 Y"（Answer）。**

但和真人助手不同的是：模型并不天然守规矩，全部协作靠一套文本格式约定
维持，一旦格式跑偏，就要靠解析器和重试机制兜底。

一句话概括实现本质：**ReAct = 用 prompt（发给模型的文字输入）约定一种
文本协议，再用一个 while 循环解析并执行它。**

## When to Use

核心判断：答案需要"查"或"算"才能保证可靠时，用 ReAct；纯凭参数内
知识就能答对的，用 CoT 更快。

典型场景：

- **需要实时或私有数据**：搜索、查数据库、读文件——模型参数里（即训练
  时记住的知识里）没有这些信息，必须行动获取；
- **需要精确计算**：算术交给计算器工具，结果可信，而不是让模型"心算"；
- **多步骤任务需要边做边看**：下一步做什么取决于上一步的结果，只能
  循环推进。

何时不用：单轮知识问答用 ReAct 是浪费——多次调用让延迟成倍增加；
流程完全固定的任务直接写代码编排即可，不必让模型决定每一步。

与 CoT 的对比：

| 维度 | CoT（见 03 实验） | ReAct（本篇） |
| :--- | :--- | :--- |
| 信息来源 | 模型参数内知识 | 参数知识 + 实时工具返回 |
| 输出 | 一次给全 | 每轮一段，循环多轮 |
| 准确性 | 算术/事实易幻觉 | 工具结果可信 |
| 延迟 | 单次调用 | 多次调用成倍增加 |

## Quick Start

前置条件：已安装 Ollama 并执行 `ollama pull qwen3.8:latest`、装有
`requests` 库；没有 Ollama 也可以用 `--demo` 离线模式跑通流程（内置
模拟回复，不需要 Ollama）。

```bash
cd agents/06_react_basic
python react.py                              # 默认问题：成都+深圳人口
python react.py --demo                       # 离线模式：内置回复，不需要 Ollama
```

脚本依次做四件事：

1. 注入 System Prompt（系统提示词，约定 Thought/Action/Answer 格式 +
   工具清单）；
2. 模型输出 `Thought: ... Action: Calculator(2126+1768)`；
3. 正则解析 → 查 `TOOLS` 注册表 → 本地执行 → 打印 `Observation: 3894`；
4. Observation 回喂，直到模型输出 `Answer: 成都和深圳的人口加起来是
   3894 万`。

预期输出：逐步打印 `>> Thought / >> Action / >> Observation`，最多
6 步。你在第二件事里看到的 `Calculator(2126+1768)`，就是模型根据
System Prompt 里拼进去的工具清单自己选的。

## How It Works

本节按"协议 → 循环 → 解析 → 执行"的顺序拆开这个最小 Agent。

### 文本协议：三种行前缀

System Prompt 约定三种行前缀——`Thought:`（推理）、`Action: 工具名
(入参)`（行动）、`Answer:`（终止）。解析器逐行扫描这三种前缀，把自由
文本变成可执行指令。**协议约定的可靠性完全取决于 prompt 工程与解析器
的容错。**

### 主循环与三个出口

| 出口 | 条件 | 行为 |
| :--- | :--- | :--- |
| 正常终止 | 解析到 `Answer:` | 返回答案 |
| 步数上限 | `step >= max_steps(6)` | 强制停止，如实报告未完成 |
| 解析失败 | 格式不符 | 错误回喂重试（消耗步数） |

ReAct 本质是有限状态机（在有限个状态间按规则流转的模型）：Think →
Act → Observe 循环，Answer 是唯一"正常"出口，`max_steps` 是防死循环
的强制上限。

### 解析器：和真实模型搏斗

`parse_react_output()` 要处理一地鸡毛：qwen3.8 会先吐 `<think>...</think>`
（要先剥掉）、把 `Thought` 写成 `Thinking Process`、冒号用全角、参数
带 `key=value` 或 JSON（结构化数据格式）。

生产经验：**解析器必须按"最常见变体清单"逐一兼容**；解析失败后的重试
通道（把错误回喂让模型自纠、多次失败如实终止）见文末 Q3。

### 工具注册表与安全计算器

`TOOLS` 是 `名字 → (函数, 描述)` 的字典（即工具注册表——名字到实现的
查找表）；描述会拼进 system prompt，模型据此选工具。

`tool_calculator` 用正则白名单（只允许列出的字符通过）
`^[\d\s+\-*/.()^]+$` 校验后才 `eval`（把字符串当代码执行的 Python
函数）——**LLM 输出永远不可信**，字符串直接进 `eval` 等于把 shell
（命令行解释器，可执行任意系统命令）交给模型。

工具执行与回喂的形态：

```python
def execute_tool(action, action_input):
    tool = TOOLS.get(action)
    if not tool:
        return f"Unknown tool: {action}. Available: {list(TOOLS)}"  # 错误也回喂
    return tool["fn"](action_input)

# Observation 回喂的形态（以 user 角色回到 messages）:
messages.append({"role": "user",
                 "content": f"Observation: {result}"})
```

你在 Quick Start 看到的 `Observation: 3894` 就是这条路：`execute_tool`
执行计算器，结果以 user 角色追加进 messages 再次发给模型（为什么用
user 角色，见文末 Q4）。连"工具不存在"的错误也回喂——模型看到错误
清单后会换一个工具名再试。

## Pitfalls & Q&A

踩坑清单（每条 = 现象 + 原因 + 解法）：

- **明明出了答案，最后却打印"未完成"**：现象是模型已给出 `Answer:`
  但输出里出现误导的步数告警。原因：解析出 Answer 后没有直接 return，
  流程落到了"已达最大步数"分支。解法：解析到 Answer 立即 return。
- **格式频繁跑偏**：现象是输出前缀忽对忽错。原因：温度偏高，格式稳定
  性下降。解法：格式任务用 `temperature=0.3` 这样的低温，留一点弹性
  处理追问即可。
- **多轮之后回答质量下降**：现象是后面的推理越来越差甚至报上下文超限。
  原因：工具结果原样拼接进 prompt，越滚越长。解法：超长结果先截断再
  回喂（见 13 实验）。

**Q1: ReAct 的核心思想是什么？**

用外部行动的结果修正推理，降低幻觉——推理决定做什么，真实结果纠正
推理本身。

**Q2: 手写 ReAct 需要哪几个组件？**

协议 system prompt、输出解析器、工具注册表、执行器、循环控制（终止
条件 + 步数上限）。

**Q3: 模型输出格式不合法怎么办？**

把解析错误作为消息回喂让模型自纠；多次失败则终止并如实报告；长期方案
是换 Function Calling（由服务端强制输出格式的机制，协议级保证）。

**Q4: 为什么工具执行结果要用 user 角色回喂？**

文本 ReAct 建立在"对话"之上，API 的可选角色只有 user/assistant；用
user 角色携带 Observation 前缀即可让模型"看到"执行结果。协议级的做法
是 `role: "tool"`（见 11 实验）。

**Q5: max_steps 应该设多大？**

与任务复杂度和预算相关；关键是必须有上限并如实报告"未完成"，而不是
静默截断。
