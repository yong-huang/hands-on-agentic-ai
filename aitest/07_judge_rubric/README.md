# 07 · LLM-as-Judge 校准：判分员上岗前，先对标准卷

> 开放式回答没有唯一标准答案，语义断言够不着——让 LLM 当判分员（judge）是常见出路，但 judge 自己也是模型，不校准就敢用等于没测。
> 本篇产出 `testbench/judges/rubric.py` + 20 条人工预标注校准集，实测相邻一致率与重复一致率双 20/20（验收线分别为 ≥16 与 ≥18）。
> 读完你能给 judge 建 rubric、算对齐与稳定性双指标，并知道"判分模型不可靠"的三种常见病因。

## Background

"这个回答质量打几分"在测试里无处不在：没有标准答案的场景（总结、建议、方案对比）、golden set 的兜底判分维度。最初的工具是语义相似度，但它回答不了"好多少"。

让 LLM 按评分标准（rubric，逐档定义分数含义的评分规则）打分是主流方案。但直接用会踩两个坑：判分不稳定（同一份回答两次打分不一样）和判分不对齐（模型心里的 3 分和人类的 3 分不是一个东西）。心理测量学对考官的解法一样适用：先发标准卷对分——考官与资深考官的分歧在允许范围内才上岗，隔天重判同一份卷分数应当复现。

本实验把这套"考官标定"变成自动化双指标：对齐（judge vs 人工标注）与稳定（judge vs 自己）。

## What

LLM-as-Judge 校准是一套"先对账再上岗"的流程：20 条人工预标注样本（4 道题 × 5 档质量）做标准卷，judge 逐条打 1-5 分，对账出对齐率；隔轮重判同一批，得出稳定率。

可以把校准想象成新考官入职：先判一批已经打过分的卷子（校准集），跟资深考官的分数比对（对齐），一周后重判同一批看记忆与手感是否一致（稳定）。但和人工考官不同的是：LLM 的"手感"由温度参数控制，temperature=0 下稳定率应当接近满分——它的风险不在漂移，而在系统性偏档。

| 指标 | 定义 | 本轮实测 | 验收线 |
|:--|:--|:--:|:--:|
| 相邻一致率 | \|judge − 人工\| ≤ 1 的比例 | 20/20 | ≥80% |
| 精确一致率 | judge =人工 的比例 | 14/20 | 报告用 |
| 重复一致率 | 两轮同分比例 | 20/20 | ≥90% |

验收线取相邻一致而非精确一致：5 档量表上差一档属于评分噪声（人类考官重判自己也有 10-20% 的档位漂移），要求逐分精确属于过度校准。

## When to Use

典型场景：

1. 项目 8 的 judge 维度：golden set 每条回答的 rubric 分，pass = 分数 ≥4。
2. 没有标准答案的评测：总结质量、建议可行性、方案对比偏好。
3. judge 换模型时：重跑校准，对齐不达标的新 judge 不许上岗。

何时不用：有标准答案的语义判定（lab 05 的 embedding 断言毫秒级且确定）；有事实源的真伪核对（lab 06 的三级核验更便宜）。

同类方案对比：

| 方案 | 差异 | 何时选它 |
|:--|:--|:--|
| 直接用一个 LLM 打分不校准 | 分数无法解释也无法信任 | 原型期的一次性参考 |
| 语义相似度 | 只能对比"像不像"，给不出质量分 | 有标准答案时优先 |
| 校准过的 rubric judge（本实验） | 分数可解释、误差有界 | 无标准答案的长期评测 |

## Quick Start

前置条件：本机 Ollama 与 `qwen3.8:latest`（判分模型）；离线单测不需要。

```bash
cd aitest
python3 -m pytest tests/test_judge_rubric.py -q     # 离线: 解析链路与对齐数学
cd 07_judge_rubric && python3 judge_rubric.py       # 真机: 40 次 judge 约 15 分钟
```

真机校准实测输出（qwen3.8，节选）：

```text
  [jr_001] 人工=5 judge=5 ✅ (正确完整，commit暂存区快照+SHA-1、push上传远程，要点齐全)
  [jr_015] 人工=2 judge=3 ✅ (大方向对但未解释7和5各代表什么权限，关键细节缺失)
  [jr_020] 人工=1 judge=1 ✅ (答非所问，且bash不是图形界面，核心错误)

对齐: 精确一致 14/20 · 相邻一致(|Δ|<=1) 20/20 (验收 ≥16)
稳定性: 重复评分一致 20/20 (验收 ≥18)
PASS
```

诚实预期：精确一致 70%——judge 在 3 分与 4 分的边界上比人类略宽松，差档全部发生在相邻档之间。整轮真机约 15 分钟：qwen3.8（17GB）每次判分 15-30 秒，40 次调用是校准的固定成本；判分 prompt 必须 `num_predict=800` 起步（原因见踩坑第 1 条）。

## How It Works

### rubric 进 prompt，分数出 JSON

`score_answer()` 把 RUBRIC（逐档定义"答非所问/有事实错误/含糊冗余/少要点/完整可用"）连同问题与回答发给 judge，要求只输出 JSON 分数与 30 字理由。

输出解析复用 lab 04 的结构化断言：剥围栏、schema 校验（score 枚举 1-5）、失败自动带错误重试一次——解析不出就返回 `score=None` 的"不可用评分"，宁可弃权不硬编。

对照 Quick Start 的 jr_015 行：judge 给 3 分并写出"未解释 7 和 5 各代表什么"——理由与 rubric 的档位定义直接对应，分数因此可解释。

### 双指标的算法

对齐：20 条样本逐条算 |judge − 人工|，相邻一致率 = 满足 ≤1 的比例。稳定性：同一批样本用相同参数再判一整轮，逐条比对两轮分差。两轮都用 temperature=0——lab 03 的画像已证明该配置字面一致率 1.0，所以稳定率失守只能是解析或采样故障，不是模型随机性。

### 校准集的分层设计

20 条 = 4 道运维题 × 5 档质量，每档 4 条。分层是校准集的命门：如果全是高分样本，judge 只要把什么都判 4-5 分就能通过对齐——分层逼它在每一档都做出区分。标注由人完成并写入 `judge_labeled.yaml`，与代码同库版本化，judge 换模型时对账基准不变。

## Pitfalls & Q&A

### 踩坑清单

1. **`num_predict=300` 让对齐率虚跌到 70%**。现象：首轮校准 6 条"不可用评分"，相邻一致 14/20。原因：qwen3.8 的思考段比 4b 长得多，300 token 常常思考未完正文已截，content 为空串，解析直接失败——错的全是解析不是判断。解法：判分预算提到 800，重跑后相邻一致 20/20。凡"judge 大面积不可用评分"，先查 token 预算再怀疑模型。

2. **判分 prompt 必须锁死输出格式**。现象：不加"只输出 JSON"时，模型会输出整段评语。解法：JSON 要求 + schema 枚举校验 + 失败重试，三层都在（复用 lab 04 管线，自己不重写）。

3. **校准集不分层会让对齐率虚高**。现象：早期手填样本时高分档占七成，judge 恒答 4 分也能过线。解法：每档强制等量（4×5），分布写进单测断言。

### 深入问答

**Q：精确一致只有 70%，这个 judge 能用吗？**

能，且要知道它偏在哪。14 条精确一致、6 条全部差一档（judge 把含糊的 3 分答得稍宽容），方向系统性而非随机——这种误差有界的判分器用于"≥4 分算通过"的门禁是安全的；若用于排序或精细分档，应扩校准集到 50 条并逐档复核边界定义。测量学的结论：误差有界且可解释的量具可用，随机漂移的量具不可用。

**Q：判分模型为什么用 qwen3.8 不用更快的 4b？**

5 档打分是细粒度语义任务，lab 06 的经验是二分类（SUPPORTED/UNSUPPORTED）4b 足够，但 5 档边界的判别需要更强的语言理解；3.8 在本校准集上达到相邻一致 100%。判分是低频高价值调用（20 条 × 2 轮），慢一点可接受——高频场景才需要换 4b 并重跑校准。

**Q：怎么判断该重校准了？**

三种触发：judge 模型或版本变更、rubric 文本修改、校准集更新。定期抽 5 条人工复核对账也是廉价保险——judge 的"漂移"通常不是自己漂，而是输入分布变了。
