# 20 · CI 门禁分级：变更路由与退出码

> 每次提交都跑 30 分钟全量门禁，CI 会被拖垮；永远只跑分钟级冒烟，SUT 代码变更又测不出来。本篇给门禁加一个路由器：按**变更文件**决定档位——只动数据集/弹药库（payloads 目录，存放注入/越狱等安全测试的攻击样本）走 smoke（分钟级小样本档），触碰 SUT（System Under Test，被测系统，本系列里指 harness/mh）或测试台（testbench，本系列逐步搭起来的测试代码库）代码走 full（全量档）；未知变更按 fail-safe（失效安全：拿不准时选更保守的一侧）走 full。
> 实测：自检 8/8 全绿——假 diff（手工构造的"这次提交改了哪些文件"清单）两态各路由到正确档位，退出码判定（崩溃/机制未过 → 1）逐条可断言；`make gate` 接真机整合。
> 读完你能给测试台装一个"该快就快、该严就严"的 CI 入口。

## Background

门禁进 CI 后马上遇到成本问题：全量档（18 线——本系列项目 18 的 runner，统一跑批入口——的 full）30 分钟起步，每次提交都跑，开发者等待时间无法忍受；于是团队退而求其次只跑 smoke，结果改了 SUT 代码却只过小样本，坏版本照样合并。

传统 CI 的解法是**按变更影响面路由**：改动只碰数据/配置（不碰代码）时，用快档验证管道；触碰代码时，必须全量。判断依据来自版本控制系统的变更文件列表——路由规则本身成为一份可测试的代码。

还有一条安全底线：**未知变更一律走全量**（fail-safe）。路由规则不可能枚举所有文件，新目录、重命名、删除都可能绕开白名单——默认从严是唯一安全的选择。

## What

门禁分级由三个部件构成：路由、档位执行、退出码判定。

| 部件 | 职责 | 本实验形态 |
|:--|:--|:--|
| 路由 | 变更文件列表 → 档位 | 数据/弹药 → smoke；SUT/测试台代码/未知 → full |
| 档位执行 | 调 18 线 runner（统一跑批入口） | smoke 分钟级 / full 全量 |
| 退出码 | 结果 → CI 判决 | 模块崩溃或机制类未过 → 1，否则 0 |

路由规则表：`aitest/datasets/`、`aitest/payloads/` 命中且未命中 full 规则 → smoke。

`harness/`、`qa/`、`agents/`、`langchain/`、`aitest/testbench/`、`aitest/tests/`、aitest 根下脚本与 Makefile → full；其余（含空变更）→ full。

可以把门禁分级想象成机场安检的分流：常旅客（低风险变更）走快速通道，随机旅客（代码变更）走完整流程。但和安检不同的是：**身份判别错了代价不对称**——把高风险放进快通道是漏检，把低风险送进全流程只是多等，所以规则设计天然偏严。

## When to Use

典型场景：

1. PR 流水线：一个 `make gate` 步骤完成"路由 → 跑批 → 退出码"。
2. 单人开发：提交前本地跑 `python3 -m testbench.gate run --dry-run` 先看会走哪档。
3. 规则演进：新增代码目录时把它加进 full 前缀；`selftest` 保证规则改动不破坏既有路由。

何时不用：CI 预算充足且容忍全量时长（直接跑 full 更省心）；变更类型单一的小仓库（路由收益低于维护规则的成本）。

同类方案对比：

| 方案 | 用时 | 风险 | 何时选它 |
|:--|:--|:--|:--|
| 永远 full | 30 分钟+/次 | 无（最严） | 小团队、低频合并 |
| 永远 smoke | 分钟级 | SUT 变更漏检 | 只改数据的高频迭代期 |
| 按变更路由（本实验） | 分钟级—30 分钟 | 路由规则本身的正确性需自检 | 大多数持续开发场景 |

## Quick Start

前置条件：pytest 与 selftest 全离线（系统 `python3`）；真机整合 `make gate` 会调用 runner（按路由档位实际跑批）。

```bash
cd aitest
python3 -m pytest tests/test_gate.py -q       # 离线 5 条：路由规则/退出码
cd 20_gate
python3 gate_lab.py all                       # pytest + selftest + dry-run 演示
cd .. && python3 -m testbench.gate run --dry-run          # 只演示路由, 不跑 runner
```

真机实测（节选）：

```text
=====> [pytest] 离线单测(路由规则/退出码判定)
  5 passed in 0.01s

=====> [selftest] 假 diff 两态: 数据->smoke, SUT/未知->full
  ✅ route(['aitest/datasets/tasks.yaml']) = smoke
  ✅ route(['harness/mh/loop.py']) = full
  ✅ route(['README.md']) = full
  ✅ route(空) = full
  ✅ decide: 全过=0, 双违规=1(2 条原因)

selftest: 8/8 通过

=====> [dry-run] 两条假 diff 的路由演示(不跑 runner)
变更文件(1): ['aitest/datasets/tasks.yaml']
路由档位: smoke
变更文件(1): ['harness/mh/loop.py']
路由档位: full
```

诚实预期：`selftest` 离线秒级，是路由规则的"合同测试"；`make gate` 的实际时长取决于路由档位（smoke 约 7 分钟、full 30 分钟起步）。`--dry-run` 只演示路由不跑批。退出码：0 = 可合并；1 = 模块崩溃或机制类检查未过（原因逐条打印）。

## How It Works

### 路由：白名单加速、黑名单强制、默认从严

`route(files)` 的判定顺序：任一文件命中 full 前缀 → 立刻 full（混合变更从严重者）；全部文件都命中 smoke 前缀 → smoke；否则 full。

空变更列表按 full 处理——拿不到变更信息时不敢赌。`_is_full` 额外把 aitest 根下的脚本与 Makefile 算作 full（测试台代码）。

### 退出码：只认机制与崩溃

`decide(report)` 遍历 18 线的模块结果：`status=="error"`（模块崩溃）或机制类模块 `passed is False`（安全/契约/轨迹没过）→ 退出码 1。

阈值类模块（评测、性能）的数字只打印不判死——阈值判断留给专门的 13/17 门禁或人工评审。这样 CI 的红色永远指向"确定的问题"，不因数字波动误报。

### selftest：用假 diff 锁住路由行为

`selftest` 构造六组假变更（数据文件、弹药、SUT 代码、测试台代码、未知文件、空列表）逐条断言路由结果，再对假报告验证退出码判定。路由规则是纯函数，因此合同测试完全离线、秒级——每次改规则先跑它。

## Pitfalls & Q&A

### 踩坑清单

1. **路由通配符的边界比想象中难写**。现象：最初实现里 `aitest/datasets/tasks.yaml` 被错误路由到 full（selftest 当场抓住）。原因：把"aitest 根下脚本"写成了过宽的前缀匹配（凡以 `aitest/` 开头的路径都算代码），数据文件被连带判成 full。解法：把"根目录脚本"改成显式判定（`aitest/` 下且只有一层路径且是文件），并在 selftest 里固定"数据文件 → smoke"这条用例——**路由规则的测试就是路由本身的保险**。
2. **混合变更从严重者**。现象：一次提交同时改数据和 SUT 代码，按"多数票"路由到了 smoke。原因：路由聚合策略写错。解法：只要任一文件触发 full 就 full（本实验实现），因为 SUT 变更的影响无法被数据侧的快档覆盖。
3. **退出码要可解释**。现象：CI 红了，但看日志不知道哪项没过。原因：只给退出码不给原因。解法：`decide` 返回逐条原因（模块名 + 崩溃/未过），`gate` 打印后再退出——红色必须有"为什么"。

### 深入问答

**Q：门禁分级和 13 的安全门、18 的 runner 是什么关系？**

三层套娃：13 的安全门是**专项门禁**（三维安全自有阈值）；18 的 runner 是**总收集器**（把七个模块收进一份结果）；20 的 gate 是**CI 总入口**（决定跑哪档、给出合并判决）。CI 配置里只需要一行 `make gate`，复杂度全部内聚在测试台里。

**Q：git diff 识别变更有什么边界？**

三个已知边界：**重命名**（视为删除+新增，通常更严——合理）；**删除文件**（同样从严）；**未跟踪文件**（`git diff` 看不到，路由可能漏）。

最后一条最隐蔽：本地新增的测试文件如果没 `git add`，`python3 -m testbench.gate run`（或 `make gate`）不知道它存在。CI 环境 checkout 后不存在这个问题，本地自测时记得先 add。

**Q：什么时候该往 smoke 白名单里加新目录？**

判断标准是"改这里的文件会不会影响被 SUT 执行的行为"：评测数据、弹药库、标注文件——不会，可以 smoke；任何会被 SUT import、执行、读取以改变行为的代码——不可以。拿不准就不加（默认 full 是安全侧）；加进去的每一条都由 selftest 锁定并留痕。
