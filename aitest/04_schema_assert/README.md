# 04 · 结构化输出断言：从任意 LLM 文本到可判定的 PASS/FAIL

> "让模型输出 JSON"是 Agent 测试的第一需求，也是最先碎掉的约定。
> 本篇产出断言库第一个模块 `testbench/asserts/schema.py`：提取 → 规则修复 → schema 校验 → LLM 重试兜底，四级管线。
> 读完你能把"输出符合结构"写成一条可复跑的断言，并知道 10 类常见坏输出里 9 类可以离线修复。

## Background

让 LLM 按结构回答，最初的做法是在 prompt 里写"只输出 JSON"，然后对回答直接 `json.loads`。

这种做法撑不过十次调用：回答包着 ```json 围栏、前面加一句"好的，结果是："、写到一半被截断、数字写成字符串——每一次解析失败都要人手工救，救完下次换个姿势又坏。

软件工程对这类问题的标准解法是校验层：数据进来先过 schema（结构声明，规定有哪些字段、什么类型、哪些必填）校验，不合法就拒绝。但对 LLM 输出只做"拒绝"太浪费——大部分坏输出离正确只差一次剥围栏或补一个括号。本实验把"提取、修复、校验"合成一条自动管线，坏到规则修不好的，才交给模型重写一次。

## What

结构化输出断言是一条把任意 LLM 文本变成判定结果的管线：输入是字符串，输出是带修复记录的 PASS/FAIL，全程可复跑。

可以把管线想象成机场安检：箱子（文本）先开箱（提取 JSON 对象），摆放规整（规则修复），再过 X 光（schema 校验），有疑问的开箱复查一次（LLM 重试）。但和安检不同的是：这里的"规整"有明确目标——每一步修复都记进 repairs 清单，断言不仅给结论，还给"我修过什么"的账单。

断言结果 `AssertResult` 的构成：

| 字段 | 含义 |
|:--|:--|
| `ok` | 是否通过 schema 校验 |
| `data` | 修复后的结构化数据（dict） |
| `repairs` | 每一步修复的可解释记录，如"剥 ```json 围栏"、"强转 confidence" |
| `error` | 失败时的校验错误清单 |

## When to Use

典型场景：

1. Agent 输出结构化结果的场景：工具调用参数、评分 JSON、分类标签，断言先过再消费。
2. 为项目 8 的全量评测打底：golden set 每条用例的输出都过这条管线，FAIL 率本身就是指标。
3. 提示词改版回归：改版后 FAIL 率上升，说明结构约定被改坏了，比语义劣化更先暴露。

何时不用：模型本来就输出自由文本的场景（去项目 5 用语义断言）；数据来自确定性代码（直接 `json.loads` 就够）。

同类方案对比：

| 方案 | 差异 | 何时选它 |
|:--|:--|:--|
| 裸 `json.loads` | 围栏/废话/截断全都解析失败 | 数据源是程序不是模型 |
| jsonschema 库校验 | 只判对错不修复，报错是英文路径 | 服务端API的入参校验 |
| 本实验管线 | 修复+校验+重试，报错中文可定位 | 消费 LLM 输出的测试台 |

## Quick Start

前置条件：Python 3.10+，无第三方依赖；`llm_live` 段需要本机 Ollama。

```bash
cd aitest
python3 -m testbench.asserts.schema        # 离线硬验收: 10 条坏输出 ≥9/10
cd 04_schema_assert && python3 schema_assert.py   # 全流程(含真机重试演示)
```

离线自检真实输出（节选）：

```text
selftest: 10 条坏输出, 走规则修复(无 LLM)
  [01] ✅ 围栏包裹: 修复=['剥 ```json 围栏', '剥前后废话']
  [05] ❌ 值内截断: error=$: 缺必填字段 'confidence'
  [08] ✅ 类型错: 数字写成字符串: 修复=['剥前后废话', "强转 confidence: '数字字符串'→number"]
规则修复: 9/10 (验收口径 ≥9)
```

真机 LLM 重试段输出：

```text
=====> [llm_live] 真机: 模型按 schema 回答 + 坏 JSON 走 LLM 修复重试
  [模型直答] ok=True 修复=['剥前后废话']
  [LLM 重试] ok=True 修复=['剥前后废话', 'LLM 修复重试']
  断言: 直答过 schema ✅ / 缺字段由 LLM 重试补齐 ✅
```

诚实预期：第 05 号坏输出（值内截断）修好后仍缺 `confidence` 字段——缺字段无法凭规则编造值，这正是 LLM 重试路径存在的意义；本离线自检按 9/10 计 PASS。

## How It Works

### 提取：先找到 JSON，再谈别的

`extract_json()` 做三件事：正则剥 ```json 围栏；找第一个 `{`；从那里做括号配平扫描（跟踪是否在字符串内、是否转义），配平到 0 就截出完整对象，扫到结尾没配平则判定截断并返回候选。

对照 Quick Start：01 号 case 靠"剥围栏"、02 号靠"剥废话"，输出里的修复记录就是这条扫描路径的日志。

### 规则修复：只做可解释的转换

`repair_rules()` 与类型强转按固定顺序执行：截断补全（补引号/补括号）→ 去尾逗号 → 单引号转双引号（值与键分开处理）→ 字面换行替换 → 按 schema 保守强转 → 剔除未声明字段。

每条规则命中都记进 `repairs`，任何一条都不猜测业务语义——"缺字段"就修不了，留给重试。

### 校验器与重试边界

`validate()` 手写 25 行：type、required、enum、嵌套 properties、additionalProperties，报错带字段路径（如 `$.confidence: 期望 number, 实际 str`）。

手写而非 jsonschema 的原因有二：报错要中文可读且一次报全；修复管线需要按 schema 逐字段尝试强转，自己拿着 schema 对象遍历最直接。

重试边界是一条硬规则：规则修不好时，把校验错误清单和原文喂回模型重写，只重试一次，重试稿再过不了校验就 FAIL。对照 Quick Start 的 LLM 重试输出——缺 `confidence` 的坏 JSON 被模型补全，repairs 里留下"LLM 修复重试"的记录，审计时能区分"原文就好"和"模型救回来的"。

## Pitfalls & Q&A

### 踩坑清单

1. **单引号 JSON 只转了值没转键**。现象：`{'a': 'x'}` 修复后仍是非法 JSON。原因：替换规则只匹配 `: '` 前缀的值，键在 `{` 或 `,` 后面。解法：键与值用两条正则分别处理（`[{,]\s*'key'` 与 `: 'value'`）。

2. **字符串内截断补括号没用**。现象：`{"answer": "Git 提交` 补了 `}` 仍解析失败。原因：字符串没闭合，先补的 `}` 落进了字符串里。解法：按引号配平判断"字符串开着"（奇数个未转义引号），先补 `"` 再补 `}`。

3. **修复顺序错了会把合法改坏**。现象：先转引号再去尾逗号时，某些组合产生双重修复冲突。解法：管线顺序固定为"结构补全 → 逗号 → 引号 → 换行 → 强转"，每条修复只增不删，selftest 的 10 条 case 就是回归网。

### 深入问答

**Q：为什么不直接用 jsonschema 库？**

两个原因。一是报错形态：标注与评审需要"第几个字段、期望什么、实际什么"的中文一句话，jsonschema 的报错是英文路径加指针，还要二次加工。

二是修复耦合：类型强转要拿着 schema 逐字段尝试，自己实现校验后 schema 对象本来就在手上。校验语义本身二者等价。

**Q：LLM 重试会不会把"应该 FAIL"的输出救成 PASS，造成漏报？**

会漏掉"模型不守规矩"这一事实，但断言的目的在此处是"拿到可用数据"。漏报有账可查——repairs 里的"LLM 修复重试"标记让两类 PASS 可区分。如果测试目标就是"结构遵循率"本身（项目 8 会统计），应禁用 chat_fn 让规则修复说了算，两种口径都支持。

**Q：为什么不修复"缺字段"？**

缺的是语义内容，规则无法编造：缺 `confidence` 时填 0.5 是在伪造模型判断。规则修复的边界是"形式对、内容不变"，凡是要发明信息的修复都属于重试或判 FAIL——这条边界让 repairs 清单里的每一条都可信。
