# 14 · 工具调用契约测试：mock 工具 + 调用序列断言

> Agent 的"工作成果"主要落在工具调用上：写了哪个文件、参数对不对、调用顺序对不对。只看最终回答测不出这些——一句"已完成"背后可能漏传参数、调错工具。
> 本篇给被测系统（SUT，System Under Test——本实验里就是被驱动着完成任务的 Agent）挂一组会记录每次调用的 mock 工具（模拟工具：用行为可控的假实现替代真实工具，并把每次调用记录下来），对调用日志做两类断言（参数必填×类型、调用序列是剧本的有序子序列——期望的调用按顺序出现即可，中间允许夹带白名单内的其他调用）；再用三个"工具描述被写坏"的变体自证测试有效：正常 SUT 全绿，错型/漏参/多调各被抓到。
> 读完你能把"模型的工具行为"变成可断言的契约。

## Background

工具类 Agent 的测试盲区很典型：断言最终回答"任务完成"，但完成过程不可查。模型可以在回答里说"笔记已写好"，实际调用却漏了 `body` 参数、或者把 `write_note` 换成了一个语义相近的别的工具——输出层面的文本断言全部通过，行为层面的错误全部漏掉。

工具调用出错的一个高发来源是**工具描述本身**：schema 和 description 是模型看到的"接口文档"，写错一个类型（number 写成 string）、漏一段说明（必填参数没提），模型的行为就会稳定偏航。

这类问题在改描述、换模型、加工具之后尤其常见，靠人工翻 trace（Agent 每次工具调用的执行记录）发现太慢。

测试工程里的解法是契约测试：约定"工具该怎么被调用"（参数形状 + 调用顺序），挂记录型 mock 工具收集实际调用，逐条对照断言。契约不关心回答文本——它只问"调用对不对"。

## What

工具契约由两部分断言组成，mock 工具表负责取材：

| 部件 | 职责 | 本实验形态 |
|:--|:--|:--|
| mock 工具表 | 提供工具实现并记录每次调用 | `{name, args}` 按调用顺序入日志 |
| 参数契约 | 必填键齐全 + 类型匹配 | `CONTRACT`：write_note/title+body，calc_sum/a+b 数字 |
| 序列契约 | 调用序列是期望剧本的有序子序列；白名单外= 多余调用 | 剧本 `[write_note, calc_sum]` |

可以把契约测试想象成"给工具调用装了行车记录仪 + 交规考卷"：记录仪（mock 日志）留下每个动作，考卷（断言）判定动作是否合规。但和交规不同的是：**违规判定不看结果悬念**——参数类型错了就是错了，不管回答多漂亮。

三个"写坏描述"的变体用于自证（阴性对照：故意注入缺陷的对照样本——测试能抓到它，才证明测试有效）：

| 变体 | 破坏方式 | 期望被抓的违规 |
|:--|:--|:--|
| `wrong_type` | calc_sum 参数声明成 string | `wrong_type`（传了 `"21"`） |
| `missing_param` | 抹掉 write_note 的 body | `missing_param` |
| `extra_call` | write_note 描述说成只读 + 放一个等价诱饵 `save_memo` | `extra_call` + `missing_call` |

## When to Use

典型场景：

1. 工具描述/schema 改动后：契约测试是描述变更的回归闸门。
2. 换模型（如 qwen3.8:latest 换成 qwen3:4b）：工具调用风格差异立刻可见。
3. 工具集扩张：新增工具是否抢了原有工具的调用（描述重叠）用序列断言发现。

何时不用：被测对象没有工具（纯文本任务，走 4-8 线断言）；只想验证端到端任务完成（15 线终态断言更直接）。

同类方案对比：

| 方案 | 关注点 | 何时选它 |
|:--|:--|:--|
| 人工翻 trace | 眼查调用 | 一次性排查 |
| 输出文本断言 | 回答内容 | 纯问答场景 |
| 契约断言（本实验） | 调用参数与顺序 | 工具型 Agent 的回归 |

## Quick Start

前置条件：离线段用系统 `python3`（自带 pytest；仓库 `.venv` 不含 pytest，不要在 .venv 里跑）即可。

真机四态需要 Ollama 与 `qwen3:4b`——先 `ollama serve` 并确认已 pull 模型；未探活时 `all` 只跑 pytest、真机段打印"诚实跳过"（退出码 0）。

```bash
cd aitest
python3 -m pytest tests/test_tool_contract.py -q   # 离线 11 条：断言/变体/录制
cd 14_tool_contract
python3 tool_contract.py all                       # pytest + 真机四态
```

真机实测（qwen3:4b，一轮四态约 1.5 分钟）：

```text
=====> [pytest] 离线单测(两类断言/变体构造/录制包装)
  11 passed in 0.01s

=====> [real] 真机四态(qwen3:4b)
  variant=normal: 调用序列=['write_note', 'calc_sum'] 违规=0
  variant=wrong_type: 调用序列=['write_note', 'calc_sum'] 违规=2
    - [wrong_type] 参数 a='21' 类型应为 (<class 'int'>, <class 'float'>)
    - [wrong_type] 参数 b='21' 类型应为 (<class 'int'>, <class 'float'>)
  variant=missing_param: 调用序列=['write_note', 'calc_sum', 'write_note'] 违规=1
    - [missing_param] 缺少必填参数 body
  variant=extra_call: 调用序列=['save_memo', 'calc_sum'] 违规=2
    - [missing_call] 剧本要求调用 write_note, 实际序列 ['save_memo', 'calc_sum']
    - [extra_call] 调用了剧本外的工具 save_memo

  四态: normal:0 违规 | wrong_type:2 违规 | missing_param:1 违规 | extra_call:2 违规
  落盘 -> .../results/tool_contract.json
```

诚实预期：`normal:0` 是"契约全绿"，三个变体各 ≥1 违规是"测试有效"的阴性对照——如果某个变体也全绿，说明契约没有覆盖它声称能抓的场景。

真机四态的模型行为可能随模型版本漂移（违规的**形态**可能变化，如 missing_param 下模型额外多调一次写笔记）；断言只锚定"至少抓到期望类别"，不锚定具体调用次数。

## How It Works

### mock 工具表：同一套 schema，两种用途

`build_tools(variant)` 把工具定义包成 mh（本系列的主被测 Agent 运行时，每轮真调 LLM）期望的结构（`desc/schema/fn`），`fn` 外面再套一层记录包装——真实实现照常执行，调用先入日志。

SUT 收到的 schema 与变体破坏后的描述完全一致，因此"模型行为偏航"可以被稳定归因到描述本身。

### 参数契约：必填齐全 + 类型匹配

`check_args` 遍历日志，对每个已知工具检查 `CONTRACT` 里的每个键：缺失记 `missing_param`，类型不符记 `wrong_type`（`isinstance` 判定，数字接受 int/float）。未知工具的参数不在这里判——它属于序列契约的"多余调用"。

### 序列契约：子序列语义与失败报告

`check_sequence` 检查剧本 `[write_note, calc_sum]` 是否为实际序列的有序子序列：**每项从上次匹配位置之后找最早出现**，找不到记 `missing_call` 且不推进光标。

光标语义是命门：失败时若推进光标，首个缺失会把后续项全部误报（单测 `test_sequence_missing_first` 固定该语义）。

白名单外的调用记 `extra_call`。

三个变体的实测轨迹印证了断言的覆盖面：string 声明的参数让模型传 `'21'`（wrong_type ×2）；被抹掉的 body 让模型漏参（missing_param）。

描述改写 + 等价诱饵让模型整体换道：save_memo 调用引发 missing_call + extra_call 双违规。

## Pitfalls & Q&A

### 踩坑清单

1. **序列断言的光标语义是命门**。现象：首个期望项缺失时，后续项被连锁误报缺失。原因：朴素的 `for want in expected: any(... for n in it)` 在失败时会把迭代器耗尽。解法：每项独立找"光标之后的最早匹配"，失败不动光标——单测固定这条语义（开发时实踩过）。
2. **工具描述就是 prompt，改描述=改行为**。现象：只动了 description 里的一个类型词，模型就开始传字符串。原因：模型按描述决定参数值与工具选择，描述错误会稳定传导为行为错误。解法：把描述当代码评审对象；契约测试作为描述改动的回归闸门。
3. **诱饵要配合任务措辞**。现象：`extra_call` 变体最初全绿——任务里点名了 `write_note` 且要求"不要调用其他工具"，模型严格照做。原因：模型会优先服从任务里的显式指令。解法：该变体换成"不点名写笔记工具"的任务（`TASK_EXTRA`），诱饵才有生效空间——契约测试的变体本身也要校准。

### 深入问答

**Q：契约测试和 15 线的端到端测试怎么分工？**

契约测**过程**（调用参数与顺序），e2e 测**终态**（文件写出了没、内容对不对）。两者抓的缺陷不同：参数错型可能不影响终态（模型折中算出结果），终态失败也可能调用序列完全合规（工具实现自己的 bug）。工具型 Agent 两个都要有。

**Q：mock 工具的"记录包装"会不会改变被测行为？**

包装只加了一次 `log.append`，对模型不可见（schema 与描述不变），对语义无影响。真正的失真风险在**工具实现**：mock 的 `write_note` 只返回字符串、不真写磁盘——本实验只测调用契约，文件真伪交给 15 线（真工具 + 终态断言）。

**Q：契约该断言到什么粒度？**

从"最贵的失误"开始：必填参数、类型、禁止工具、关键顺序。粒度越细维护成本越高——比如断言每个可选参数的默认值，描述一改就大批失败，收益很低。让契约跟着事故走：线上出过哪类调用错误，就往契约里加哪类断言。
