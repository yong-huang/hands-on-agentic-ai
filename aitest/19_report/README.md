# 19 · 评测报告生成器：HTML 五区块

> `results.json` 是给机器读的：字段完整、可校验，但人打开它得上下来回找数字。本篇加一个报告生成器：一条命令把 JSON 变成单文件 `report.html`——总览、评测、安全、行为、性能五个区块，纯内联 CSS、零前端依赖，浏览器直开。
> 实测：用 18 线真实产物生成 3.7KB 单文件，抽查 3 处数字与 JSON 完全一致；`verify()` 能检出被篡改的数字。
> 读完你能给任何测试台补上一张"人读得懂、数字不撒谎"的报告。

## Background

测试台的产物天然是给机器的：JSON 字段稳定、方便程序消费，但评审会议里没人愿意对着 JSON 找"安全那三个数是多少"。测试平台的标准答案是自动生成报告页——跑完即出，人直接看。

生成报告有两条常见路线：上前端框架（React/Vue/模板引擎），或**字符串模板**。前者对一个内部报告是重装备：要构建、要依赖、要防版本漂移；后者用 Python 拼 HTML 字符串、CSS 内联在 `<style>` 里，单文件浏览器直开、离线可看、可邮件可归档。

报告有个容易踩的坑：**数字来源必须唯一**。如果生成器顺手做了"格式化重算"（比如把 0.667 自己算成 66.7%），报告与 JSON 就有了两套口径，对账时永远说不清哪个对。正确做法是"搬运不重算"——展示层只做字符串呈现，数值一律取自 JSON 原值。

## What

报告生成器由三个部件构成：模板、区块映射、对账。

| 部件 | 职责 | 本实验形态 |
|:--|:--|:--|
| 模板 | Python 字符串拼单文件 HTML | 内联 CSS，零依赖 |
| 区块映射 | JSON 字段按域落进五个区块 | 总览/评测/安全/行为/性能 |
| 对账 | 抽查 HTML 数字与 JSON 一致 | `verify()` 取 3 处原值比对 |

五个区块的数据来源：总览=模块状态与耗时；评测=eval（评测模块）通过率与回归三态（改善/持平/劣化）；安全=三维安全指标（injection/jailbreak/fuzz）。

行为区块=契约违规数（工具调用契约测试中不合契约的调用次数）、e2e 成功率（端到端任务完成率）、轨迹自证分（预置轨迹的可区分性打分：快/慢/循环三条轨迹应拉出分差）；性能=P50/P95（延迟中位数/95 分位，单位秒）与 tokens（用量估算）。

可以把生成器想象成"体检报告装订机"：各科室的原始数据（JSON）已有，装订机只负责排版成册。但和装订机不同的是：**它对数据有"保真义务"**——装订后抽页对账，数字印错一页就得返工。

## When to Use

典型场景：

1. 评审与汇报：跑完 smoke（18 线的小样本冒烟档，分钟级）直接把 `report.html` 发给相关人。
2. 归档：results.json 是源、HTML 是快照，按日期存档即可回溯。
3. 回归对比的展示层：两天的报告并排看，劣化项红色一眼可见。

何时不用：只给自己看一个数字（直接读 JSON 更快）；需要交互式钻取（图表联动、筛选）——那是 BI 工具的领域，不是单文件报告的射程。

同类方案对比：

| 方案 | 依赖 | 何时选它 |
|:--|:--|:--|
| 直接读 JSON | 无 | 单人快速查看 |
| 字符串模板报告（本实验） | 零依赖 | 内部报告、归档、评审 |
| 前端框架 / BI 平台 | 构建链或服务 | 需要交互钻取与多人协作 |

## Quick Start

前置条件：pytest 用系统 `python3`；`real` 段读取 18 线产出的 `results/run_results.json`（若不存在会提示先跑 18），全程离线。

```bash
cd aitest
python3 -m pytest tests/test_report.py -q   # 离线 5 条：区块/抽查/篡改/高亮/CLI
cd 19_report
python3 report_lab.py all                   # pytest + 用真实产物出报告
```

真机实测（节选：报告生成基于 18 线的 smoke 产物）：

```text
=====> [pytest] 离线单测(五区块/抽查/篡改检出)
  5 passed in 0.01s

=====> [real] 用 18 线 results.json 生成报告并抽查
  ✅ 抽查 eval.overall_pass_rate
  ✅ 抽查 security.injection
  ✅ 抽查 e2e.success
  五区块 html -> .../results/report.html (3729 字节)
```

诚实预期：报告内容取决于 `results.json` 里有什么——如果 18 线是离线跑的，真机模块会显示为灰色 `skipped`（在 18 线结果里因离线跳过并写明原因），这是如实呈现而非缺陷。文件大小只有几 KB（无图表、纯排版）。

`verify` 是**抽查**（默认 3 处）而非逐字段 diff；要全量对账需要更严格的 contract 测试（见踩坑 3）。

## How It Works

### 模板：字符串拼接 + 状态染色

`build_html` 把每个模块的结果行拼成表格行，按 `status`/`passed` 染色：`error` 或 `passed=False` 红色、`skipped` 灰色、其余绿色。

五个区块用 `<section id="...">` 独立成块，样式集中在文件头部的 `<style>`——单文件、无外部请求。

### `_fmt`：只做呈现，不做计算

数字格式化只有一个 `_fmt` 函数：浮点去掉多余零（`0.50` → `0.5`；`0.667` 原样）、字典展开成 `k=v` 串。**没有任何算术**——报告不重新计算通过率或延迟，只搬运。这是"数值来源唯一"的实现保障。

### `verify`：抽查对账

`verify(html, report)` 从 JSON 里挑 3 个代表性数字（评测通过率、安全第一个维度 injection、e2e 成功数），检查它们的原值字符串出现在 HTML 里。单测里的篡改用例演示了它的作用：把 JSON 里的数字改掉、用旧 HTML 对账，立刻报不一致。

## Pitfalls & Q&A

### 踩坑清单

1. **报告不许重算数字**。现象：报告显示 66.7%、JSON 是 0.667，"到底以哪个为准"没人说得清。原因：展示层顺手算了百分比。解法：`_fmt` 只格式化不计算；格式化口径（小数、百分号）写进函数注释，全站统一。
2. **skipped 的颜色不能用绿**。现象：离线报告"满屏绿色"给人全通过的错觉。原因：只按 `passed` 染色，忽略了 `status`。解法：染色函数先看 `status`（error 红/skipped 灰），再看 `passed`；灰和绿在视觉上必须能区分。
3. **抽查 ≠ 全量对账**。现象：verify 全过，报告里另有一个数字与 JSON 不符。原因：抽样只查了 3 处。解法：抽查是日常快速检查；发布级报告用"逐字段 contract"：遍历 JSON 所有叶子值逐一断言在 HTML 出现（本项目未做，列为可扩展点）。

### 深入问答

**Q：为什么不用 Jinja2 模板引擎？**

边界收益比不划算：本报告的结构固定、循环只有"模块行"与"指标行"两种，Python f-string 拼接足够；引入模板引擎会增加依赖与转义约定。当报告开始需要多层嵌套与可配置布局时，再迁移不迟——先跑通"生成+对账"的闭环。

**Q：这个报告和 21 线的 FINAL_REPORT 是什么关系？**

定位不同：19 的报告是**机器产物的人类视图**（所有模块原样呈现，无观点）；21 的 FINAL_REPORT.md 是**人类写的叙事**（四维结论、总评级 A-F、修复建议清单）。19 给"数据是什么"，21 给"所以怎么样"。

**Q：报告要长期归档吗？**

归档源而不是快照：`results.json` 带时间戳入库，`report.html` 随时可重生成（同一 JSON 必得同一 HTML，因为没有随渲染变化的内容）。这样归档的是数据、可复现的是视图——与 06 线"检查点存档"同一哲学。
