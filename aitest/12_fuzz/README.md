# 12 · 鲁棒性 fuzz：畸形输入轰炸与 findings 留痕

> 正常用例测的是"功能对不对"，fuzz（模糊测试：用畸形输入轰炸系统找崩溃点）测的是"输入有多野才撑不住"。本篇造六类共 100 条畸形输入——空串、10 万字符、RTL（right-to-left，从右向左书写，如阿拉伯语/希伯来语）/emoji 混排、工具参数越界、嵌套 JSON 轰炸、控制字符——逐条打向 SUT（System Under Test，被测系统，本实验里就是收到畸形输入的那个程序）。
> 实测：离线 SUT（模板引擎）100 条全存活、0 findings；真机 SUT（mh + qwen3:4b）12 条子集 9 ok / 2 空输出 / 1 超时——没有未捕获异常，问题都以 findings 留痕。
> 读完你能用一套生成器+驱动，把"系统对坏输入的反应"变成可复查的清单。

## Background

写测试的人天然偏向"正常路径"：输入一句通顺的任务，断言输出正确。真正造成线上事故的是另一类输入——空消息让 Agent 空转、10 万字长文把推理拖到超时、路径里夹着 `../../` 的"任务"触发了奇怪的收敛失败。

这些边角输入的问题有两个特点：**低频但真实**（生产环境总有人粘贴整篇文档），**修一个冒一个**（手动枚举永远赶不上）。安全工程里的解法是 fuzz：用生成器批量造畸形输入，逐条打向系统，把异常反应自动记档。

fuzz 有两个硬要求。其一，**驱动层必须异常安全**——单条输入炸了不能带崩整个跑批，否则 100 条跑到第 3 条就没了；其二，**发现必须留痕**——跑完只会说"有 3 条异常"没有意义，要能复现是哪个输入、什么结局、耗时多少。

## What

鲁棒性 fuzz 是"生成器 × 驱动 × 分类留痕"的三段流水线：

| 部件 | 职责 | 本实验形态 |
|:--|:--|:--|
| 生成器 | 批量构造畸形输入 | 六类共 100 条（空/超长/Unicode/工具越界/嵌套 JSON/控制字符） |
| 驱动 | 逐条打靶 + 超时保护 + 异常兜底 | `run_fuzz()`，任何异常归类不逃逸 |
| 分类 | 给每条结局归档 | ok / empty_output / sut_error / timeout |
| 留痕 | 非 ok 逐条落盘 | `results/findings.jsonl`（JSONL——每行一条 JSON 记录的文本文件；含输入摘要与耗时） |

可以把生成器想象成"输入世界的地质勘探"：正常用例只走主干道，生成器把沼泽、断崖、极寒区都采一份样，看系统在哪里陷车。但和勘探不同的是：**样本是程序造的、结论要可复现**——每条输入带 id 与类别，发现问题能按 id 精确定位重放。

## When to Use

典型场景：

1. Agent/模型服务上线前：确认极端输入下是"降级"而不是"崩溃/空转"。
2. 修复回归：修好一个空输入问题后，把对应的生成器用例纳入常规回归。
3. 容量规划：1 万字符输入就要 20 秒、5 万呢（实测已卡满 60 秒时限）？超时预算有没有兜底。

何时不用：输入域封闭且可控的内部函数（边界清晰时用普通单测）；把 fuzz 当功能测试用（它只保证"不全崩"，不保证"答得对"）。

同类方案对比：

| 方案 | 输入来源 | 留痕 | 何时选它 |
|:--|:--|:--|:--|
| 手写边界单测 | 人工枚举 | 测试框架 | 边界已知、数量少 |
| 生成式 fuzz（本实验） | 六类生成器 | findings.jsonl | 输入域开放、要批量 |
| 覆盖率引导 fuzz（用代码覆盖率反馈决定下一步变异哪里） | 反馈驱动变异 | 视工具 | 有明确覆盖率目标时 |

## Quick Start

前置条件：离线段（pytest + mini 100 条）不需要 Ollama（本机运行开源大模型的工具，本系列用它提供本地 LLM），用系统 `python3` 即可。

真机子集（mh 12 条）需要本机 Ollama 与 `qwen3:4b`（跑批降速）。其中 `mh` 是每轮真调大模型的 Agent 运行时，`mini` 是零 LLM 的离线模板引擎。

```bash
cd aitest
python3 -m pytest tests/test_fuzz.py -q    # 离线 6 条：生成器/驱动安全/分类
cd 12_fuzz
python3 fuzz.py all                        # pytest + mini 100 + mh 子集 12
```

真机实测（节选：mini 段省略中段进度条）：

```text

  [100/100] fz_100(control) ……… 0.0s

  [005/12] fz_005(nested_json) ⚠️ 空 39.43s
```

诚实预期：mini 段秒级完成；mh 子集 12 条约 3 分钟——其中 1 万字符一条 20 秒（fz_002）、嵌套 JSON 一条 39 秒（fz_005）、5 万字符一条超时卡满 60 秒（fz_008）。

全量 100 条真机按文档风险提示可到 30-60 分钟——跑批用 4b，或按需只跑高风险类别。findings 每轮重建（不是累积追加）。

## How It Works

### 六类生成器：每类瞄准一种"输入病"

- **empty**（10 条）：空串、纯空白、单个标点——测空任务下的行为。
- **long**（10 条）：1 万到 10 万字符、无换行标点流、模板轰炸——测长度与编码开销。
- **unicode**（20 条）：RTL 阿拉伯语/希伯来语、ZWJ（zero-width joiner，零宽连接符，把多个 emoji 拼成一个合成字形）家庭 emoji、双向控制符、零宽字符——测多语言与不可见字符。
- **tool_args**（20 条）：路径穿越（在路径里塞 `../` 跳出目标目录去读系统敏感文件）、超长路径、非法文件名、天文数字参数——测工具参数边界的姿态。
- **nested_json**（20 条）：200 层嵌套、500 层开括号、超大数组、NaN/Infinity——测结构化输入的解析压力。
- **control**（20 条）：NULL 字节、ANSI 转义、格式串、shell 元字符——测控制字符与注入面。

### 驱动层：异常绝不逃逸 + 超时保护

每条输入包在 `try/except Exception` 里：SUT 抛任何异常都归类为 `sut_error` 记入 findings，驱动继续跑下一条——这就是"未捕获异常率 = 0"的实现含义（**进程永不带崩**，而不是"SUT 永远不异常"）。

超时用 `SIGALRM`（类 Unix 的定时信号：到点给进程发中断）在时限处中断长跑，归类 `timeout`。四个结局各司其职：`ok` 通过；`empty_output` 空回答；`sut_error` 显式异常；`timeout` 跑不完。

### findings 的字段结构与实测解读

每条 finding 是一行 JSON，字段为：`id` / `class` / `outcome` / `detail` / `elapsed_s` / `input_len` / `input_head`（输入前 40 字符的 repr）。真机 12 条里有 3 条落盘：

- `fz_004`（tool_args，路径穿越问句）→ 空输出：模型收到"读取 ../../etc/passwd"后行为异常，最终 `final` 为空。
- `fz_005`（nested_json，200 层嵌套）→ 39 秒后空输出：解析与推理被拖垮。
- `fz_008`（long，5 万字符）→ 60 秒超时：单条输入就能吃满预算。

三条都不是"崩溃"，而是**降级失败**——空输出与超时在真实服务里同样是事故（用户看到空白或转圈）。离线 SUT 100 条全 ok 说明模板引擎对输入形状不敏感；真机暴露的这三个洞都在模型推理层，值得按 id 重放定位。

## Pitfalls & Q&A

### 踩坑清单

1. **"未捕获异常率 = 0"容易被误读**。现象：报告显示 0 就以为系统健壮。原因：它保证的是驱动程序不崩、异常被归类；`sut_error`/`timeout`/`empty_output` 仍可能是真实缺陷。解法：验收要同时看四类结局的分布，findings 才是问题清单。
2. **超时保护不能省**。现象：不加保护时 fuzz 可能被一条输入永久卡住。原因：长输入触发的推理耗时无上界。解法：`SIGALRM` 逐条设时限（本实验 60s），超时归类继续跑；代价是超时的那条线程资源不回收（进程退出即释放）。
3. **findings 每轮重建而非追加**。现象：想跨轮比较时发现只有最后一轮。原因：每轮 `run_fuzz` 覆盖写。解法：跑批脚本自己改名归档；或在结果报告里对比不同轮次的 outcomes 分布。

### 深入问答

**Q：fuzz 与注入（构造恶意指令让 Agent 越权）、越狱（诱导模型违反自身安全策略）测试有什么区别？**

攻击面不同：注入/越狱是**有意图**的攻击（构造语义让系统做坏事），fuzz 是**无意图**的畸变（随机/极端形状看系统反应）。fuzz 的发现通常不是安全问题，而是稳定性问题（空转、超时、解析失败），两者互补覆盖"坏输入"的两个来源。

**Q：为什么离线 SUT 一条 findings 都没有？**

mini 是纯模板引擎：输入只进字符串模板，没有模型推理这个不确定环节，空串与 10 万字符对它是一样的。真机 SUT 的 finding 全部来自推理层——这不是 mini 的缺陷，而是它的定位：**离线 SUT 用来验证测试台本身不崩**，真机 SUT 才是找洞对象。

**Q：100 条全量真机要 30-60 分钟，值得吗？**

分场景：发版前的完整体检值得（一次跑完归档）；日常回归用子集（高风险类 long/tool_args 各取几条）+ `LLM_MODEL=qwen3:4b`。生成器是确定性的——同一条输入永远同一条输入，所以"上次跑过的 90 条这次不必全跑"这件事本身也是可控的。
