# 17 · 性能与成本门禁：P50/P95 与 token 预算

> 两个 Agent 成功率一样，一个每任务 19 秒、另一个 40 秒——用户体验和账单完全不同。本篇给任务集加一条性能门禁：多轮采样统计延迟分位数（P50/P95）与 token 估算，对照预算判分，超标标红、退出码 1。
> 实测（mh——本系列的主被测 Agent 运行时，每轮真调 LLM——+ qwen3:4b，3 任务 ×3 轮）：P50 19.41s / P95 19.69s / tokens≈4686 全部达标；把 P50 阈值压到 0.5s 立刻失败退出——两态都可脚本验证。
> 读完你能把"快不快、贵不贵"变成和成功率一样可门禁的指标。

## Background

成功率告诉你的信息止于"做成了"。做成花多久、烧多少 token，成功率一概不知——但用户能感知前者（等待），账单能感知后者。尤其当两个方案成功率接近时，延迟与成本就是决策的关键。

延迟不能只看单次：本机模型推理抖动大，一次跑出 25 秒、一次 15 秒都正常。统计口径要抗抖动——工程上标准做法是**分位数**（P50 表示中位体验，P95 表示尾部体验）加**多轮采样**（同一配置跑几轮，每轮的指标取中位再对照预算），单次数字只当参考。

token 计量在小规模自研测试台里有个现实约束：精确用量要从模型响应里读（langchain 线 `11_callbacks_trace` 用 `usage_metadata`——模型返回的用量字段，含 input/output tokens——做回调计量的做法），但在跑批封装里透传不便。

本实验用的是**估算口径**（喂入与回复的总字符 ÷ 4），够用于"预算量级断言"，但必须明确标注——估算不是账单。

## What

性能门禁由"采样 → 分位 → 预算判定"三步构成：

| 指标 | 采集方式 | 预算方向 | 默认阈值 |
|:--|:--|:--|:--|
| P50 延迟 | 每轮任务耗时的中位数，多轮取轮间中位 | 越低越好 | ≤ 60s |
| P95 延迟 | 每轮任务耗时的 P95（最近秩法：样本排序后取第 `round(0.95×(N−1))` 个位置的值，不插值），多轮取中位 | 越低越好 | ≤ 120s |
| tokens | 估算：总字符 ÷ 4，多轮取中位 | 越低越好 | ≤ 100000 |

可以把这条门禁想象成"高速收费站"：不看车是什么牌子（模型/方案），只看过站耗时与收费额，超了抬杆拦住。但和收费站不同的是：**这里是抽样测速**——单次通过速度不能定罪，多轮采样后的分位数才是判据（漏检与误判的平衡点在采样量与阈值上）。

## When to Use

典型场景：

1. 方案选型：两种提示词成功率打平，用 P50/token 选更快的那个。
2. 性能回归：模型或代码变更后延迟翻倍，门禁先于用户发现。
3. 预算控制：给跑批定 token 上限，防止一次跑批烧穿额度。

何时不用：单任务的微基准（调研性能用 `time` 更直接）；延迟不敏感的后台任务（只看成功率与轨迹即可）。

同类方案对比：

| 方案 | 粒度 | 何时选它 |
|:--|:--|:--|
| 单次 `time` | 一次运行 | 本地快速查看 |
| 出口报告（本实验） | 多轮分位 + 预算门禁 | CI、方案对比 |
| 专业 APM（Application Performance Monitoring，应用性能监控）/可观测平台 | 全链路指标 | 生产环境 |

## How It Works

### 分位数与"轮间取中位"

每轮的 P95 用最近秩法（nearest-rank）计算，P50 取标准中位数（偶数样本为中间两值平均）；三轮各得一组，再对 P50、P95、tokens 分别取**轮间中位**作为最终指标。

实测数据展示了这样做的理由：第一轮 P50 20.84s（含模型冷加载），后两轮 19.4s 左右——若拿单轮当结论，首轮会虚高 7%。中位数天然排除单轮离群值，是小样本抗抖动的低成本方案。

### token 估算的透明口径

`counting_chat_fn` 包装 mh 的聊天函数：每次调用前累计喂入消息的字符数，调用后加上回复字符数，除以 4 得估算。这个口径无法区分中英文 token 密度（中文一个汉字常占 1-2 token、英文一个词约 1 token），估算误差 ±30% 量级。

所以字段名是 `tokens_est`、报告里明说"估算"。要精确值走 langchain 线 11_callbacks_trace 的回调路径读 `usage_metadata`（本测试台的对应精确口径见下文 Ollama 的 `prompt_eval_count`/`eval_count`）。

### fail-closed 与退出码

`evaluate_budget` 对三个指标统一用"值 ≤ 预算"判定，`None` 一律失败（fail-closed，与 13 线安全门同语义）。任一超标 → `failed` 非空 → CLI 退出码 1、终端标红。`--strict` 只是把 P50 预算改成 0.5s 的演示开关，判定逻辑与生产路径完全一致。

## Pitfalls & Q&A

### 踩坑清单

1. **单轮指标会被冷启动污染**。现象：首轮 P50 比后两轮高 7%。原因：模型首次调用含加载。解法：多轮采样取中位（本实验 3 轮）；或跑前先预热一次模型（预热运行不计入采样）。
2. **token 估算别当精确值解释**。现象：估算与真实用量差 30% 以上。原因：字符 ÷ 4 对中英文/代码的 token 密度不敏感。解法：字段带 `_est` 后缀、文档标注口径；精确审计换 langchain 线 11_callbacks_trace 的回调方案。
3. **阈值过紧的门禁会被绕过**。现象：P50 阈值定 20s（贴近实测 19.4s），机器一忙就红，团队开始习惯性忽略。原因：门禁的"持续红灯"会摧毁其严肃性。解法：默认阈值留 3 倍余量（60s），把收紧作为迭代节奏而非一刀切；`--strict` 仅用于演示两态。

### 深入问答

**Q：P95 在小样本（3 任务）下有意义吗？**

意义有限，这是本实验的诚实局限：3 个样本的 P95 实际就是最大值。小样本下 P95 的作用是"暴露最慢任务"而不是统计意义上的尾延迟。任务集与轮次扩大（如 20 任务 ×5 轮）后 P95 才接近其本义——门禁的两个指标都随规模成熟，文档如实标注比假装严谨更重要。

**Q：性能门禁和 16 线的轨迹分有什么分工？**

数字互补：轨迹分解释"为什么慢/贵"（绕路、重复、循环），性能门禁给"到底多慢/多贵"（P50/P95/tokens）。低轨迹分通常伴随高成本，但两者并不等价——一条高效轨迹也可能每步都很慢（模型推理慢是另一类问题）。回归失败时先看性能门禁定位，再用轨迹分归因。

**Q：什么时候值得上精确 token 计量？**

三个信号：估算误差开始影响决策（方案 A 估 90k、方案 B 估 110k，真实值可能反转）；需要按 token 计费或配额；要做模型间成本对比报告。

此时把 langchain 线 11 的精确计量接进跑批封装（Ollama 原生响应顶层有 `prompt_eval_count`/`eval_count` 两个计数字段；mh 的 llm 层目前只返回 message 字典，需先把这两个字段透传出来），逐步替换估算口径。
