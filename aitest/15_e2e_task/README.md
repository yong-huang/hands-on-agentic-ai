# 15 · 端到端任务成功率：终态断言

> Agent 说"已完成"不算数——磁盘上的文件才算数。本篇把 10 个终态可判的任务（建文件、写 N 行、复制内容、统计行数……）跑两遍，判分只读沙箱（每个任务独立的临时工作目录）磁盘，不看中间轮次的任何文本。
> 实测：mh（本系列的主被测 Agent 运行时，每轮真调 LLM）在 qwen3:4b 上两遍均 10/10，最大波动 0 个任务；失败任务会自动留"最后回答 + trace（Agent 每次工具调用的执行记录）尾部"的终态证据。
> 读完你能把"Agent 到底干没干成"变成一个可复算的成功率数字。

## Background

Agent 测试最容易上当的地方：模型回答"任务已完成，文件已创建"，于是测试通过——但打开沙箱一看，文件根本不存在，或者行数不对。断言回答文本等于把模型的自我汇报当成了事实。

端到端测试的判断标准应该和用户一致：**用户看到的是磁盘结果**。文件在不在、内容对不对、行数够不够，这些才是任务的"终态"。Agent 的中间轮次可能有反复（写错又改、绕路再回来），终态断言天然容忍这些过程噪声——它只问最后一刻的状态。

另一个现实问题是不确定性：同一任务跑两遍，成功率可能不同。端到端测试因此不能追求"每遍 100% 复现"，而要一个**稳定性口径**——两遍差值在允许范围内（本实验取 ≤1 个任务）即认为被测系统行为稳定。

其中被测系统（SUT，System Under Test）在本实验里就是被驱动完成任务的 Agent；这个差值口径沿用 harness/eval 线的实测经验。

## What

端到端测试是"任务集 × 独立沙箱 × 终态判分"的组合，外加两遍跑批看稳定性：

| 部件 | 职责 | 本实验形态 |
|:--|:--|:--|
| 任务集 | 可判终态的自然语言任务 | `datasets/tasks.yaml` 10 条（借用 harness/eval 已验证任务） |
| 沙箱 | 每任务独立工作目录 | 终态断言只读这个目录 |
| 判分器 | 六类磁盘检查 | 文件存在 / 行数 / 含子串行数 / 含文本 / 两文件一致 / 多文件存在 |
| 稳定性 | 两遍成功率比较 | 差值 ≤1 个任务记为 stable |

可以把终态断言想象成"验收交房"：不问装修队中途返工几次，只拿钥匙开门看——墙砌了没、水电通了没。但和验房不同的是：**判分器是代码**，每类检查都有精确口径（"3 行"就是 `splitlines()` 后恰好 3 行），不留模糊空间。

## When to Use

典型场景：

1. Agent 能力回归：改 system prompt / 换模型后，同一任务集成功率是否掉。
2. 工具/沙箱变更验证：工具实现改了，终态是否符合预期。
3. 发版体检：15 的成功率 + 13 的安全三维 + 17 的性能预算，构成发版三维证据。

何时不用：任务的"完成"无法用终态定义（开放式写作、主观问答）——那属于 4-8 线的文本断言；要查过程质量（步数、绕路）用 16 线轨迹评测。

同类方案对比：

| 方案 | 判据 | 何时选它 |
|:--|:--|:--|
| 文本断言 | 回答内容 | 纯问答场景 |
| 终态断言（本实验） | 磁盘最终状态 | 有工具副作用的任务 |
| 轨迹评测（16 线） | 过程效率与形态 | 关注"怎么做的" |

## Quick Start

前置条件：离线段用系统 `python3`（自带 pytest；仓库 `.venv` 不含 pytest，不要在 .venv 里跑）。

真机两遍需要 Ollama 与 `qwen3:4b`——先 `ollama serve` 并确认已 pull 模型；未探活时 `all` 只跑 pytest、真机段打印"诚实跳过"（退出码 0）。

```bash
cd aitest
python3 -m pytest tests/test_e2e_task.py -q   # 离线 5 条：判分器/证据/稳定性口径
cd 15_e2e_task
python3 e2e_task.py all                       # pytest + 真机两遍（10 任务 ×2）
```

真机实测（节选：第二遍与此相同）：

```text
=====> [pytest] 离线单测(判分器/证据/稳定性)
  5 passed in 0.03s

=====> [real] 10 任务 × 2 遍真机(mh, qwen3:4b)

---- 第 1/2 遍 (10 任务) ----
  [01/10] t01 ✅ a.txt exists=True
  [02/10] t02 ✅ x/b.txt exists=True
  [03/10] t03 ✅ lines=3 期望=3
  ...
  [10/10] t10 ✅ 含 '4'=True

---- 第 2/2 遍 (10 任务) ----
  [01/10] t01 ✅ a.txt exists=True
  ...

  成功率: 10/10 / 10/10 | 最大波动 0 个任务 | stable=True
  落盘 -> .../results/e2e_tasks.json
```

诚实预期：两遍 20 个任务约 2-4 分钟（本机实测；qwen3.8:latest 会明显更慢）。10/10 不代表"SUT 对任意任务都行"——只代表**这 10 个任务在两遍内全部达标**；任务集本身要随实际业务扩充（这套任务借用 harness/eval 的成熟任务集）。

失败任务会在 `results/e2e_tasks.json` 的 `evidence` 字段留下最后回答与 trace 尾部。退出码：0 = 稳定、1 = 两遍差值 >1。

## How It Works

### 六类判分器：终态检查的表达力

任务集的 `check.kind` 覆盖六类磁盘断言：`file_exists`（文件存在）、`files_exist`（多文件）、`line_count`（行数精确值）。

其余三类是 `line_contains_count`（含某子串的行数）、`content_contains`（含文本）、`content_equal`（两文件一致）。判分器是纯函数——输入 checklist 与沙箱路径，输出 `(ok, detail)`，单测可以在临时目录里把六类全部打一遍。

任务设计的两条铁律：**终态指标必须无歧义**（"写 3 行"对应 `splitlines()` 恰好 3 行，不说"写几行内容"）；**任务之间无依赖**（每个任务独立沙箱、可单独重跑）。

后者是 harness/eval 线的实测教训：串行依赖的任务一旦中断，后续全部连环失败，定位成本极大。

### 独立沙箱与失败取证

`run_e2e` 对每个任务调 `run_sut` 时新建独立沙箱目录，判分前不会复用任何状态。判分失败时自动收集证据：`final`（模型最后说了什么）与 `trace_tail`（最后三条工具调用）——这两样足够人工复现"它以为完成了但磁盘没变"的现场。

实测 10/10 全过，证据字段为空；证据机制由离线单测固定（`test_run_once_failure_evidence` 用假驱动验证）。

### 稳定性口径：差值 ≤1 的来历

`max_diff = |run1.success - run2.success|`，≤1 记 stable。这个阈值不是拍脑袋：LLM 在同一任务上会有偶发失败（重试策略、措辞扰动），要求两遍完全相等会把大量正常波动判成"不稳定"；容许 1 个任务的滑动，又足以在真实劣化（成功率掉 ≥2）时报警。

阈值随任务集增长可以放宽到总任务的 ~10%，本实验 10 任务取 1 是等价的保守值。

## Pitfalls & Q&A

### 踩坑清单

1. **任务措辞的粒度决定判分口径**。现象：任务写"写几行内容"，判分器无法定义"几行"。原因：自然语言验收标准有模糊空间。解法：任务措辞与 check 字段成对设计——"写 3 行"配 `line_count: 3`；改任务必须同步改 check（tasks.yaml 里两者就在同一个条目里，强制原子修改）。
2. **不要用任务间依赖考验 Agent**。现象：给任务加"接着上一个任务继续"的语境，失败率暴涨且难以定位。原因：独立沙箱隔离下，依赖任务没有先前状态可依。解法：每条任务自包含；需要多步串联的验证用单条复杂任务（t10 就是"写 4 个文件再统计"的一体化任务）。
3. **成功率抖动不等于劣化**。现象：某次跑出 9/10，判定"退化"开始排查。原因：单遍抽样的正常波动。解法：看两遍差值口径（本实验）；要更稳的结论就加大 runs 与任务数——统计上的成本和置信度永远要一起谈。

### 深入问答

**Q：为什么直接借用 harness/eval 的任务集？**

那套任务在 harness 线经过全量实跑验证（"mh 能做且终态可判"已成立），复用它可以把注意力放在测试台工程（判分器、稳定性口径、证据），而不是重新调任务难度。跨线复用已验证资产是设计里明说的意图——本清单不重复造 harness 组件。

**Q：终态断言会不会太宽容？模型绕一大圈把事办了也满分。**

会——这正是分工：终态断言只保证"事办了"，不评价"怎么办的"。绕路、重复调用、高成本，交给 16 线（轨迹分）与 17 线（性能预算）来扣。测试维度分开，每条断言只对它关心的质量负责。

**Q：失败任务的证据够复现吗？**

`final + trace_tail` 给出"模型宣称什么 + 最后几步干了什么"，足以判断是工具没调用、调用失败、还是写错了地方。要完全复现需要把该任务的沙箱保留下来——目前沙箱随进程回收，长期留档可以把 `cwd` 拷到 results 目录（任务集变大后值得做）。
