# 21 · 🏁 终极四维体检：harness/mh 完整质量报告

> 散装的测试结果堆不出结论。最后一步把 18 线 runner 的七模块结果组装成**四维体检**：功能（golden set——预先人工标注标准答案与要点的小型评测题集）、安全（三维扫描——注入/越狱/模糊输入三类攻击）、性能（延迟与 token 预算）、回归（prompt diff——同一批任务在新旧两版提示词下的输出对比），给出总评级 A-F 与修复建议清单，产出 `FINAL_REPORT.md`。
> 实测 quick 档：同批数据评级 A（四维全过），报告含四区块 + 评级 + 建议 + 可复现性说明；全量口径 `make checkup` 一条命令，30 分钟量级。
> 读完你手里就有一个从"单点断言"到"总检报告"的完整测试平台。

## Background

前面二十个项目各自交付结论：断言库能判对错、安全门能拦风险、性能门禁能卡预算……但没有一个地方回答"harness/mh 现在到底行不行"。评审会上要的是总检结论：四维各是什么水平、整体给什么评级、下一步修什么。

总检报告有两种失败写法：**堆数字**（把七份 JSON 粘一起，等于没组装）和**乱加权**（把通过率/分位数/劣化数打折求和算"总分"，量纲不同没法相加）。工程上可信的写法是**维度制**：每维独立给结论（过/不过），失守维度数映射评级，建议按失守维度生成——等级只表达"几个维度出了问题"，不伪装成连续分数。

还有可复现性这一关：体检报告如果隔天重跑结论大变，就没法当决策依据。端到端类指标的波动用 15 线的既有口径收口（成功率两跑差 ≤1 个任务即视为可复现）；机制类结论（断言/门禁逻辑）本身就是确定性的。

## What

四维体检由"维度映射 + 评级 + 叙事"三件构成：

| 维度 | 数据来源 | 通过标准 |
|:--|:--|:--|
| 功能 | eval 各维通过率 | schema（结构断言通过率）≥0.8 且 semantic（语义相似通过率）≥0.5 且 judge（LLM 评审通过率）≥0.8（fact（事实性）维按 08 线口径仅作趋势观察） |
| 安全 | security 三维指标（injection 注入攻击成功率、jailbreak 越狱拒绝率、fuzz 模糊输入异常率） | 三维全达标（门禁 verdict=pass） |
| 性能 | perf P50（延迟中位数）/P95（95 分位延迟）/tokens（token 消耗估算） | 全项 ≤ 默认预算 |
| 回归 | regression 三态 | 劣化数为 0 |

评级规则简单可解释：失守 0 维 = A，1 维 = B，2 维 = C，3 维 = D，4 维 = F（不设 E 档）。行为三件套（契约/e2e/轨迹）作为附录列出，不计入评级。

可以把体检报告想象成汽车年检：制动、灯光、排放、底盘四项各判过/不过，最后给"几项未过"的结论与维修清单。但和年检不同的是：**它把历史口径写进标准**——功能维为何不判"总体通过率"，是因为本线 08 实验已确认 fact 维偏严（基线 0.2 是已知趋势而非故障），门槛必须贴合这条线的真实基线。

## When to Use

典型场景：

1. 阶段收口：一轮开发结束，跑一次体检留档（FINAL_REPORT.md 落盘；原始数据 results.json 由 18 线 runner 产出，一并归档）。
2. 发版前：`make checkup` 全量口径，评级进发布说明。
3. 回归对照：两次体检报告的评级与四维数字并排看，退步维度一目了然。

何时不用：日常提交（20 线门禁分级已覆盖，秒级到分钟级）；单维度深挖（直接跑对应模块，体检只负责总览）。

同类方案对比：

| 方案 | 结论形态 | 何时选它 |
|:--|:--|:--|
| 七份原始 JSON | 无结论 | 机读、下游程序消费 |
| HTML 报告（19 线） | 全量数据视图 | 人工核对细节 |
| 四维体检（本实验） | 评级 + 建议 | 评审、归档、决策 |

## How It Works

### summarize：纯函数做四维判定

`summarize(report)` 从 runner 报告里抽四个模块的数字，按上表标准逐维判定 `ok`，数失守个数映射评级，再按失守维度生成建议。纯函数设计让单测离线覆盖全部分支（含"四维全失 → F"），不需要真机。

### 功能维的门槛为什么不是"总体通过率"

这是设计里最容易被质疑的一点。首版实现用"总体通过率 ≥0.8"，结果本线数据永远失败——因为 08 线早已查明 fact 维口径极严（基线通过率 0.2，且明说"是趋势信号不是绝对幻觉率"）。

门槛若无视历史结论，体检报告天天红灯、很快失去信誉。现方案取三维硬门槛（schema/semantic/judge），把 fact 维留在趋势观察位——**评级标准也是测试资产，要随基线证据演进**。

### 评级、建议与可复现性

评级是"失守维数"的直接映射（0→A 至 4→F，无 E 档），不做加权——四维量纲不同，加权求和会造出"安全失守被性能优秀抵消"的假分数。修复建议按失守维度逐条生成（如安全失守 → 复核 13 线扫描器 detail）。报告末尾写明可复现性口径：机制类结论确定性，端到端成功率两跑差 ≤1 即视为可复现。

## Pitfalls & Q&A

### 踩坑清单

1. **门槛必须贴合本线历史口径**。现象：首版用"总体通过率 ≥0.8"，功能维永远判失守，体检长期误报（评级被无端压到 B）。原因：fact 维偏严（08 线基线 0.2）拖垮总体通过率。解法：改为三维硬门槛 + fact 趋势位；任何门槛调整都要在报告标准行里留痕（本报告直接印出判定标准）。
2. **quick 档的评级不是决策依据**。现象：quick 评级 A 让人以为"全线健康"。原因：样本量小（2 条评测、2 任务 e2e）。解法：报告头部印出档位与样本口径；文档明确决策用 full 档——防止"小样本绿灯"被误用是报告设计的责任。
3. **评级只给信号，建议才是行动项**。现象：团队把"从 B 升到 A"当目标，却不去修具体劣化。原因：等级太抽象。解法：建议清单逐条对应失守维度与下游模块定位信息（如"回归: 存在 2 个劣化项，按 09 线报告逐条复核"），行动永远落到具体报告页。

### 深入问答

**Q：四维体检和 20 线门禁是什么关系？**

互补：20 线的 gate 是**每次提交的选择性关卡**（按变更路由、分钟级反馈）；21 的体检是**阶段性全检**（固定全量口径、完整报告与评级）。CI 里 gate 负责日常，里程碑时 `make checkup` 出总检——一个管节奏，一个管结论。

**Q：为什么评级不设 E 档？**

字母等级的历史约定（学业、年检）里 E 常被省略；更重要的是本报告的语义是"0-4 个维度失守"，五个结论映射五个字母，不需要凑六档。少一档就少一处争议。

**Q：怎么验证"隔天重跑可复现"？**

三类指标三种验法：机制类（断言/门禁/评级逻辑）离线自证，天然确定；性能类按 17 线口径多轮取中位；端到端类按 15 线口径两跑差 ≤1。体检报告在"可复现性"节写明这些口径——复现验证是跑两次对比，不是相信一次数字。
