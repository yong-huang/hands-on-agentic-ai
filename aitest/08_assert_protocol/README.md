# 08 · ⛓️ 断言统一协议：golden set 首轮全量评测

> 前七个项目各造了一把尺子：结构断言、语义断言、幻觉检测、judge 打分。
> 本篇把它们收进一个协议——`evaluate_case()` 一条用例跑四维，`run_eval` 驱动 SUT 跑完全部 20 条，产出带数字的首轮基线 `results/baseline.json`。
> 读完你能看懂"分维通过率"怎么读、None 维为什么不算失败，以及基线在后续回归里的锚点角色。

## Background

断言库成型后的第一件事是"全量跑一遍"，最初的写法是一个大脚本把所有断言代码顺序调一遍。

这种写法在第二种断言加入后开始腐化：每个断言的入参形态不同（有的要 schema、有的要参考答案、有的要事实源）、结果字段名不同（ok/pass/score）、失败口径不同（有的抛异常有的返回 False）。聚合"这次整体过没过"要写一堆特判，新增断言维度的成本随维度数线性上涨。

软件集成的标准解法是统一协议：定义一个公共入口，入参是"用例 + 被测回答"，出参是固定形状的分维结果；每个断言维度是协议的一个实现。本实验把四把尺子插进同一个卡槽，首轮全量评测的产出 `baseline.json` 从此成为后续一切回归的对照锚点（项目 9-21 都读它）。

## What

统一断言协议是评测台的中枢接口：一条 golden 用例加一份 SUT 回答，返回 schema/semantic/factuality/judge 四维结果，每维自带 `pass` 布尔与证据，缺失的维度记 `None` 而不是 0 分。

可以把协议想象成体检报告的格式：身高体重血常规各科填各的栏（分维），没做的项目标"未检"（None）而不是填 0（None 不进分母），最后汇总页给出分科结论（聚合通过率）。但和体检不同的是：这里"适用范围"由用例类别决定——tool 类用例的 JSON 维天然不适用，协议必须诚实地留空而不是硬测。

四维的适用与判据：

| 维度 | 适用 | pass 判据 | 证据字段 |
|:--|:--|:--|:--|
| schema | 非 tool 类（JSON 变体二次驱动） | 过 lab 04 管线校验 | repairs / error |
| semantic | 全部 | 全部期望要点相似度 ≥0.60 | 逐点相似度 |
| factuality | 全部 | 无 unsupported claim | claims 计数 |
| judge | 全部 | rubric 分 ≥4 | 分数 + 理由 |

## When to Use

典型场景：

1. 提示词或模型改版前后各跑一次：两份 baseline.json 做 diff 就是项目 9 的回归报告。
2. 新断言维度上线：先在基线上跑出分布，确认该维度有区分度再纳入门禁。
3. 换 SUT 模型的横向对比：同一 golden set，不同 `--model` 各出一份基线。

何时不用：单条用例的调试（直接调 `evaluate_case` 更快）；还没建 golden set 时（先做 lab 02）。

同类方案对比：

| 方案 | 差异 | 何时选它 |
|:--|:--|:--|
| 大脚本顺序调断言 | 入参/结果/失败口径各自为政 | 只有单一维度时 |
| promptfoo 等托管平台 | 断言类型受平台限制 | 已绑定该生态 |
| 本实验统一协议 | 四维同形、None 语义明确、可加维度 | 断言库要持续生长 |

## Quick Start

前置条件：本机 Ollama 与 `qwen3:4b`（SUT 与 judge 模型）；离线管道自检不需要。

```bash
cd aitest
python3 -m pytest tests/test_run_eval.py -q                # 离线: 聚合与协议单测
cd 08_assert_protocol && python3 assert_protocol.py        # 离线层: mini SUT 管道自检
python3 assert_protocol.py real                            # 真机基线(约 6-10 分钟)
```

真机首轮基线（golden_v1 × mh，qwen3:4b）：

```text
各维通过率: {"schema": 1.0, "semantic": 0.4, "factuality": 0.2, "judge": 0.8}
总通过率: 0.1 -> results/baseline.json
```

分维读法（首轮实测，qwen3:4b，2026-10-09）：

| 维度 | 通过率 | 解读 |
|:--|:--:|:--|
| schema | 1.0 | JSON 化变体下 4b 全部守格式 |
| semantic | 0.4 | 期望要点全中的用例 8/20，措辞距离是最常见的失分点 |
| factuality | 0.2 | 口径最严的一维：期望要点当迷你事实源，回答的合理扩展也计 unsupported |
| judge | 0.8 | rubric ≥4 的回答 16/20，回答质量本身不差 |
| 总通过 | 0.1 | 全维都过的用例 2/20——被 factuality 维拉低，见下节 Q&A |

诚实预期：首轮基线不是"考试分数"而是"起点快照"——总通过率受 judge 阈值（≥4）、语义阈值（0.60）等可调参数影响，跨版本对比才有意义。

factuality 维 0.2 的口径偏严是设计现状：期望要点不是完整事实源，回答的正确扩展也会计 unsupported。它适合看趋势（这轮比上轮多了几条 unsupported），不适合当绝对质量分，解读方式见 Q&A。

## How It Works

### 双驱动：schema 维的采样方式

原生 query 的回答是自由文本，没有 JSON 可校验。schema 维的做法是二次驱动：对每条非 tool 用例，把 query 加上 JSON 输出指令再问一遍 SUT，用这份"JSON 化回答"过 lab 04 管线。它测的是"SUT 被要求结构化时守不守规矩"，与原生回答的质量互相独立——两次调用、两个问题，不算重复计费。

### evaluate_case：四维收口与 None 语义

`evaluate_case(case, answer, chat_fn, schema_answer)` 是唯一的断言入口。维度缺失记 `None` 的语义是"不适用"，聚合时分母里不出现——tool 类 6 条不计入 schema 通过率，judge 缺判分模型时整维为 None 而不是全员 0 分。这个设计让"加一个维度"不破坏历史口径：新维度上线前各案例该维全是 None，通过率曲线在启用点才开始记录。

### 聚合：分维通过率与总通过率

`_aggregate()` 按维算 `pass=True` 占比（None 不进分母），总通过率是"四维（或全部适用维）都 pass 的用例占比"——比四维通过率的均值更严格，一条用例只要有一维不过就不算过。对照 Quick Start 的基线表：semantic 维的通过率单独成列，改版后哪一维掉了一眼可见。

### 基线的锚点角色

`baseline.json` 记录元信息（数据集、SUT、模型、生成时间、是否离线）与逐用例结果。项目 9 的回归套件对两份基线做逐用例 diff，项目 21 的体检报告直接引用其中的分维数字。文件即协议：后续加维度只在 case 行里多一个键，旧的 diff 逻辑不需要改。

## Pitfalls & Q&A

### 踩坑清单

1. **tool 类用例硬测 schema 会全军覆没**。现象：首版把 schema 维跑在全部 20 条上，6 条 tool 用例全 FAIL。原因：tool 类的任务是"创建文件"而非"结构化作答"，原生回答就不是 JSON。解法：schema 维只对 JSON 变体的二次驱动采样，tool 类明确不适用（None）。

2. **None 当 0 分会让通过率虚低**。现象：把 judge 缺席（无判分模型）的用例算 FAIL。原因：None 语义是"未测"，不是"不及格"。解法：聚合时分母排除 None，报告里单列"适用数"。

3. **离线自检的数字冒充真机基线**。现象：`MOCK`/mini SUT 跑出的"通过率"看起来也是百分比。解法：离线运行的 `meta.offline=true` 写进结果文件，README 明示"数字是管道自检，不代表真实质量"。

### 深入问答

**Q：总通过率为什么不用四维均值的口径？**

均值会掩盖单点故障：一条用例 semantic 0 分但 judge 满分，均值口径下仍有贡献。全过口径（所有适用维都 pass 才算过）回答的是"多少条用例经得起全部检验"，与发布门禁的语义一致。两套数字都存了（`overall_pass_rate` 与分维 `rates`），读哪套取决于问题。

**Q：基线的绝对分数能对外报告吗？**

不建议。0.60 的语义阈值、≥4 的 judge 阈值都是本项目实测标定（lab 05/07），换标定换模型数字就变。对外可报告的是相对量：改版后哪维掉了几个百分点、哪条用例从过变不过——锚点比绝对值可靠。

**Q：factuality 维 0.2 这么低，是 SUT 真的在胡说吗？**

不是。该维把期望要点拼接文本当迷你事实源，而期望要点只覆盖"正确回答的最小内核"——回答里的合理展开（补充例子、换个说法强调）在迷你事实源里找不到依据，全部计 unsupported。所以它的正确读法是趋势信号：同一口径下，这轮 unsupported 计数比上轮暴涨才说明真出了幻觉。绝对幻觉率要用 lab 06 的完整事实源口径另测。

**Q：为什么 judge 维的 pass 线是 ≥4 不是 ≥3？**

rubric 定义里 3 分是"方向对但含糊冗余"，作为测试通过线太宽：含糊的回答放进回归里会让劣化信号被稀释。≥4 意味着"正确且清楚"起步，与"通过测试的质量观"对齐——门槛松紧可以调，但必须有意识地调并记录在案。
