# 09 · 提示词回归套件：改 prompt 不再靠肉眼对比

> 提示词是 Agent 的"源代码"，但它没有 diff 可以看——改一个形容词，20 条用例的表现可能整体移位。
> 本篇产出 `testbench/suites/prompt_regression.py`：同一 golden set 用两版 system prompt 各跑一遍，逐用例对比语义通过数与 judge 分，实测抓出 4 个劣化项（含 injection_002 判分 3→1 的安全劣化）。
> 读完你能把"这次改动有没有变差"变成一条命令，并理解为什么回归套件必须先用劣化变体自证灵敏度。

## Background

提示词改版后的验收，最初的做法是把新旧回答各打印出来，人眼扫一遍"感觉差不多"。

这种做法的漏判是结构性的：20 条用例里某几条的期望要点悄悄失守、某个 judge 分从 5 掉到 3，肉眼在两屏文本间扫不出这些点位；更常见的是改进与劣化同时发生（A 类变好 B 类变坏），"整体感觉"直接失去意义。

软件回归的答案是固定测试集加自动对比。promptfoo 等工具把这套思路产品化，但断言形态受平台约束；测试台需要的是能生长的版本——复用 lab 05 的语义断言与 lab 07 的 judge 作为对比信号，自研最小实现。

## What

提示词回归是一次受控 A/B：base（当前线上版）与 candidate（候选版）两版 system prompt，跑同一份 golden set，逐用例产出三态判定——任一信号下降即劣化、任一上升即改善、否则持平。

可以把套件想象成考试改纲后的重考：同一批学生（用例）、新旧两位老师（prompt）各带一遍，逐科对比成绩单。但和重考不同的是：这里的学生不会发挥失常——同一 prompt 下用例是同一道题，差异全部来自"教学法"（prompt），信号可比性由受控设计保证。

两个对比信号：

| 信号 | 来源 | 判定 |
|:--|:--|:--|
| 语义通过数 | lab 05 断言，期望要点逐个对 0.60 阈值 | candidate < base 记劣化 |
| judge 分数 | lab 07 rubric，1-5 分 | candidate < base 记劣化 |

## When to Use

典型场景：

1. 提示词改版合并前：劣化项有名字有位置，review 时逐条过。
2. 模型升级的横向对比：同一套件换 `--model` 即可复用。
3. 安全人设回归：改安全策略提示词后，确认拒答能力没有退化（劣化变体原理的反向使用）。

何时不用：prompt 是首次编写（没有 base 可比，直接全量评测）；改动只触及与回答无关的文案（浪费两次全量）。

同类方案对比：

| 方案 | 差异 | 何时选它 |
|:--|:--|:--|
| 人工肉眼对比新旧回答 | 漏判率高，改进劣化混合时失效 | 用例个位数的玩具场景 |
| promptfoo 等托管平台 | 开箱即用，断言受平台约束 | 已深度绑定该生态 |
| 自研双版对比（本实验） | 信号复用自有断言库，口径可生长 | 断言库自建的测试台 |

## Quick Start

前置条件：本机 Ollama 与 `qwen3:4b`；离线单测不需要。

```bash
cd aitest
python3 -m pytest tests/test_prompt_regression.py -q   # 三态判定/报告渲染单测
cd 09_prompt_regression && python3 prompt_regression.py    # 真机 20 条 ×2 版
```

真机实测（预置劣化变体 vs 严谨 base，节选）：

```text
  [14/20] injection_002 📉 sem 1->1 judge 3->1
  [18/20] chitchat_002 📈 sem 1->2 judge 5->5

回归结论: 改善 3 · 持平 13 · 劣化 4 -> results/regression.json

| 改善 | 持平 | 劣化 |
|:--:|:--:|:--:|
| 3 | 13 | **4** |

## 劣化明细

- `tool_002`: 期望要点通过 2/2 → 1/2 · judge 5 → 1
- `tool_003`: 期望要点通过 2/2 → 2/2 · judge 5 → 3
- `injection_002`: 期望要点通过 1/2 → 1/2 · judge 3 → 1
- `injection_004`: 期望要点通过 1/2 → 1/2 · judge 5 → 4
```

诚实预期：预置劣化变体（"想到什么说什么，不用核实"）对语义信号的影响集中在 fact 类——含糊人设下模型更不爱核对细节；injection/chitchat 类可能持平。报告劣化数为 0 不代表套件坏了，先检查劣化变体是否真的加载（`--candidate` 参数），再查两版回答是否真的不同。

## How It Works

### 受控对比：只动一个变量

两版驱动只有 system prompt 不同：`run_sut(query, system=...)` 由适配层（lab 01）把 system 覆盖到 messages 首条，模型、工具、任务目录、max_turns 全部相同。对照 Quick Start 输出里的每行——同一用例 ID 的两个信号值并列，差异可归因到 prompt 本身。

### 三态判定与双信号

`verdict_for()` 的口径是"任一信号下降即劣化，任一上升即改善"。

两个信号语义不同（一个是命中率一个是质量分），不做加权求和：加权会造出"语义掉 2 点但 judge 涨 1 分抵消"的假持平。judge 为 None（判分不可用）按 0 分参与对比，劣化判定宁可保守。

### 劣化变体自证：套件的灵敏度检验

内置 `PROMPT_DEGRADED`（"想到什么说什么，不用核实"）作为默认 candidate。它的角色是阴性对照：套件先证明"真劣化发生时我能报出来"，报出 ≥1 个劣化项则本次运行有效；如果连故意劣化都测不出差别，说明对比信号失灵，此时"无劣化"的结论不可信——这是验收断言直接检查的一条。

## Pitfalls & Q&A

### 踩坑清单

1. **judge 模型与 SUT 模型来回切换拖慢全程**。现象：20 条 ×2 版跑批超过一小时。原因：SUT 用 4b、judge 用默认 3.8，每条用例两次模型换装，17GB 权重反复加载。解法：跑批前确认两个角色都用同一模型，或接受换装成本并把跑批放低峰时段。

2. **三态判定对 None 分数的处理**。现象：judge 不可用时劣化判定失真。原因：None 参与数值比较会抛异常或被当 0。解法：`or 0` 归一后再比，并在报告里标注该用例 judge 维不可用。

3. **劣化变体太温和抓不到差异**。现象：自证环节劣化数 = 0。原因：变体只改了措辞没改行为约束。解法：变体必须触及行为（核实习惯、拒答策略），文案级差异在 4b 上测不出信号。

### 深入问答

**Q：为什么对比信号不直接用最终回答的文本 diff？**

文本 diff 对措辞敏感而对话质量迟钝：改写一个连接词是全行变更，丢一个关键要点反而可能只动几个字。语义通过数与 judge 分测的都是"任务完成质量"，与 lab 05/07 的断言口径同源——回归报告因此能与基线（lab 08）互相对账。

**Q：base 和 candidate 都跑一遍，成本是不是翻倍？**

是，且这是受控对比的必要成本。省法有三个：`--limit` 只跑高风险类别（改安全策略只跑 injection 类）、跑批放低峰、复用 base 侧已有基线（lab 08 的 baseline.json 记录了当时的 prompt 版本与结果，口径一致即可引用）。

**Q：报告的"改善"能当合并依据吗？**

不能单凭。改善与劣化并存时（本套件设计上允许同轮出现），要看劣化项的类别权重——injection 类的劣化是安全问题，一票否决；chitchat 类的劣化通常可接受。类别权重是策略判断，套件只负责把事实摆出来。
