# 06 · 幻觉检测器：把回答拆成原子句，逐条对照事实源

> 语义断言（lab 05）只能回答"说得像不像"，回答不了"说得对不对"。
> 本篇产出 `testbench/asserts/factuality.py`：claims 拆解 + 数字核对/覆盖率子串/LLM judge 三级核验，混淆矩阵验收（检出 10/10 · 误报 0/10）。
> 读完你能为"有事实源可对照"的场景写出幻觉率断言，并理解为什么子串快车道必须设覆盖率门槛。

## Background

检测 LLM 幻觉（回答里混入与事实不符的内容），最初的做法是人工通读回答、对照资料逐句核对。

这种方式无法进入测试流水线：一次评测几十条回答，人工核对慢且标准会漂移。

更麻烦的是幻觉很隐蔽——"每次 commit 生成一个 SHA-256 哈希"里，"commit 记录版本快照"是真的，错的只有"SHA-256"一个词，通读很容易放过。

事实核查领域的思路是分而治之：把回答拆成原子句（claim，一个可独立判定真伪的最小事实主张），逐条与事实源对照。多数主张能靠机械规则判定（照抄原文的、数字对不上的），拿不准的才交给模型判——这正是"规则优先、模型兜底"的成本结构。

## What

幻觉检测器的输入是"回答 + 事实源段落"，输出是逐条 claim 的判定清单：`supported`（有依据）/ `unsupported`（无依据=幻觉）/ `unknown`（无法判定），以及整体结论 `has_hallucination`。

可以把检测器想象成海关查验：行李（回答）先分箱（claims 拆分），申报与实物一致的直接放行（覆盖率子串），申报单上数字对不上的直接扣下（数字核对），剩下的开箱人工查验（LLM judge）。

但和海关不同的是：这里的"扣下"必须给出证据字段——每条判定都带 method（走的哪一级）和 verdict，混淆矩阵就是这么对账出来的。

三级核验的分工：

| 级别 | 判什么 | 判定 |
|:--|:--|:--|
| 数字核对 | claim 含数字，且数字全部不在事实源 | 直接 `unsupported`（硬信号） |
| 覆盖率子串 | claim 与事实源的最长公共片段覆盖 claim 大半（≥60% 且 ≥8 字） | 直接 `supported`（近似照抄） |
| LLM judge | 以上两级拿不准的 | 模型答 SUPPORTED/UNSUPPORTED |

## When to Use

典型场景：

1. 有事实源的消费场景：RAG 回答对照检索到的文档、运维助手回答对照手册——golden set 里 fact 类用例的事实性维度（项目 8）。
2. 回归监控：提示词改版后幻觉率上升是比语义相似度下降更刺眼的劣化信号。
3. 数据清洗：从模型生成的语料里筛掉与来源不符的样本。

何时不用：没有事实源的开放生成（创意写作无"对错"可言）；事实源本身不可信（对错由源决定，垃圾进垃圾出）。

同类方案对比：

| 方案 | 差异 | 何时选它 |
|:--|:--|:--|
| 人工通读核对 | 准但慢、标准漂移 | 仲裁争议样本 |
| 纯 LLM 判定 | 每条都问模型，慢且自身有方差（本项目实测 4b 裸判会翻车） | 一次性小批量 |
| 三级核验（本实验） | 机械规则先拦大头，judge 只管疑难 | 进流水线的长期方案 |

## Quick Start

前置条件：本机 Ollama 与 `qwen3:4b`（judge 用）；离线单测不需要。

```bash
cd aitest
python3 -m pytest tests/test_factuality.py -q     # 离线: 拆分/规则/解析 8 条单测
cd 06_factuality && python3 factuality.py         # 全流程: 真机 judge 约 2 分钟
```

      预测=幻觉  预测=忠实

## How It Works

### 拆分：原子化是判定的前提

`split_claims()` 按句号/问号/分号切分，过滤短于 6 字的寒暄残句。拆分粒度是第一道杠杆：太粗（整段一个 claim）会让真伪混合的句子无法判定，太细（子句全拆）会让代词失去指代对象。按句切分是"每个 claim 自含主谓"的最小粒度。

### 数字优先：最便宜的硬信号

带数字的 claim 不走子串通道，直接先做数字核对：数字全部不在事实源 → `unsupported`（如"SHA-256"对照只有"SHA-1"的 source）。

数字在场也要送 judge——数字对了语义仍可能颠倒（"404 表示服务器内部错误"）。顺序是刻意为之：数字改错时句子其余部分与 source 高度重合，子串通道会误放行，首版实测因此漏检 5 条。

### 覆盖率门槛：子串通道的安全阀

无数字的 claim 走子串快车道，但判定条件不是"有公共片段"而是"公共片段覆盖 claim 大半（≥60% 且 ≥8 字）"。

原因同样是实测教训："git push 用于把远程仓库的提交拉取到本地"与 source 有 10 字公共片段（"gitpush用于把"），但方向反了——主题词复用是幻觉的标配伪装，只有近似照抄才配直判 supported。

### judge 兜底与空响应防御

剩下的疑难 claim 交给 judge，提示词带判定规则与两个少样本示例（一个 UNSUPPORTED 一个 SUPPORTED）。防御点：qwen3 系是混合推理模型，`num_predict` 给小了思考段会吃掉全部输出预算，content 返回空串。

`_judge` 对空响应重试一次，仍为空则返回 `unknown`——不计入检出也不计入误报，诚实标注"无法判定"。

## Pitfalls & Q&A

### 踩坑清单

1. **子串快车道无覆盖率门槛时检出率只有 5/10**。现象：首版只要最长公共片段 ≥6 字就判 supported，"404/500 语义颠倒"、"push/pull 方向反"全部漏检。原因：幻觉句几乎总会复用正确的主题词，前缀重合不代表断言正确。解法：覆盖率 ≥60% 门槛 + 数字 claim 绕行。

2. **`num_predict=60` 让 judge 全体沉默**。现象：误报 8/10，逐条查发现 judge 响应是空串。原因：思考段吃掉 token 预算，正文一个字没生成；空串按解析规则落进"unsupported"分支，把忠实回答全判成幻觉。解法：judge 给足 300 token，`_judge` 空响应重试一次后仍空则返回 `unknown`。

3. **裸 judge 提示词对 4b 模型太弱**。现象：加了 token 后仍有边界样本判反。原因："资料是否支持？只答 SUPPORTED 或 UNSUPPORTED"没有给判定标准，模型按语感猜。解法：提示词写明"数字、方向、主体必须一致"并列两个少样本示例。

### 深入问答

**Q：为什么"unknown"不算误报也不算漏检？**

混淆矩阵的对账对象是"检测器的判定质量"，unknown 是"检测器弃权"——把它算进任何一格都会扭曲指标。生产含义是：弃权率高的样本域需要换更强模型或补充事实源，它本身是一个监控指标（本项目 20 样本实测 unknown=0）。

**Q：检出率和误报率冲突时保哪个？**

看下游动作。检测出的幻觉会阻断发布（高成本动作）→ 保误报率，宁可漏检不可冤枉；只用于人工复核排队（低成本动作）→ 保检出率。本项目验收口径（检出 ≥9 且误报 ≤1）对应"复核排队"场景；若用于门禁，应把阈值收紧到误报 0 再谈检出。

**Q：和语义断言（lab 05）什么关系？互补还是替代？**

互补，判的问题不同。语义断言对照"标准答案"回答"说得像不像"，相似度阈值之下照样可以整句是错的（像而错）；幻觉检测对照"事实源"回答"每个主张有没有依据"。事实源与标准答案重合时（golden set 的 fact 用例），两个断言都跑——语义断言卡措辞漂移，幻觉检测卡事实错误。
