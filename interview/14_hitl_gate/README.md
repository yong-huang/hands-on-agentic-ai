# 14 · Human-in-the-loop 审批门

> 覆盖面试题：HITL 的介入时机怎么设计？哪些操作必须人工确认？（必问）
> 10 个混合操作先过风险分级器：金额/删除/对外发送/敏感导出 → 强制审批；
> 纯查询/内部写 → 自动放行（零打扰）。审批三态：批准/拒绝/超时默认拒绝
> （fail-safe）。全部决策写审计日志（JSONL）。交互终端真输入；非交互
> 环境走脚本化用户决策并如实标注。

## 1. 运行与实测

```bash
MOCK=1 python hitl_gate.py    # 离线: 脚本化用户决策 (批准/拒绝/不应答)
python hitl_gate.py           # 终端下真实输入; 管道下 fail-safe 全拒
```

实测（2026-09-09）：

| 指标 | 结果 |
|:--|:--|
| 危险操作全部卡住审批 | ✓ 5/5（退款/转账/删除/群发/导出） |
| 安全操作零打扰 | ✓ 5 个（查询×3 + 内部写×2） |
| 批准/拒绝/超时拒绝 | 2 / 2 / 1 |
| 审计日志条数 | 10（每操作一条, JSONL 落盘） |

## 2. 分级规则（写入侧）

- 强制审批四类红线：**资金操作**（退款/转账>¥1000）、**删除类**、
  **对外发送**（邮件/短信/发布）、**敏感数据出域**（导出/下载）。
- 自动放行：纯查询、内部低风险写——红线用规则判定，不用模型猜。

## 3. 深入要点

- 介入时机：不可逆、出域、涉资金的操作必须人批；查询类打扰即体验灾难。
- fail-safe 原则：审批超时/通道不可用 = 默认拒绝——宁可不做，不可做错。
- 审计日志（谁/何时/批了什么/为什么）是生产 HITL 底线：事后可追责，
  而不是"模型说它问过"。
